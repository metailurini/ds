# v0.1.0 Spec — Lexer, Parser, AST, and Diagnostics

## Status

Implemented. The scoped frontend code exists and the `v0.1.0` test plan is covered by executable tests.

## Goal

Build the first frontend for `ds`.

This version should read `.ds` files, tokenize them, parse them into an AST, report useful syntax errors, and expose debug commands for tokens and AST output.

`v0.1.0` is intentionally frontend-only. It does not execute scripts and does not emit Bash.

## Motivation

A language project needs a reliable frontend before runtime work begins.

Starting with lexer, parser, AST, and diagnostics gives the project:

- a concrete syntax foundation;
- early debug tooling;
- a way to test source handling;
- a stable base for Bash emission in `v0.2.0`;
- a stable base for the bytecode VM in `v0.3.0`.

This version also proves the command-mode parsing rule: normal programming constructs use language syntax, while ordinary command lines remain shell-like.

This version also introduces the `docs/language.ds` syntax catalog. The catalog is not executed or emitted in `v0.1.0`; it exists so the project can track the whole planned language syntax in one place while milestone specs define the implementable subset.

## Non-goals

This version does not include:

- bytecode VM;
- script execution;
- Bash emission;
- imports;
- functions;
- loops;
- arrays;
- maps;
- CLI argument blocks;
- command result capture;
- redirection syntax;
- formatter;
- test runner;
- standard library.

`docs/language.ds` may contain planned future syntax, but that future syntax is not considered supported by `v0.1.0` unless it is explicitly listed in this spec.

If any of these become tempting during implementation, record them as deferred items.

## User-facing commands

`v0.1.0` should support these commands:

```sh
ds tokens <file.ds>
ds ast <file.ds>
ds check <file.ds>
```

### `ds tokens <file.ds>`

Print tokens in a stable debug format.

The output does not need to be beautiful, but it should be stable enough for golden tests.

Example conceptual output:

```txt
1:1   LET        "let"
1:5   IDENT      "name"
1:10  EQUAL      "="
1:12  STRING     "Danh"
1:18  NEWLINE    "\n"
```

### `ds ast <file.ds>`

Print a readable AST.

Example conceptual output:

```txt
Script
  LetStmt name
    String "Danh"
  IfStmt
    Condition
      BinaryExpr ==
        Ident name
        String "Danh"
    Then
      CmdStmt
        Word "echo"
        String "hello"
```

### `ds check <file.ds>`

Validate syntax.

Expected behavior:

- exits `0` when parsing succeeds;
- exits non-zero when parsing fails;
- prints diagnostics for invalid syntax.

## Supported source features

The supported `v0.1.0` source subset is intentionally much smaller than the full syntax catalog in `docs/language.ds`.

Implementation should not attempt to parse every example in `docs/language.ds` as valid runnable input during `v0.1.0`. Parser tests should use focused fixtures for the supported subset.

### Comments

Line comments start with `#`.

```ds
# this is a comment
let name = "Danh" # trailing comment
```

Comments are ignored by the parser but should preserve line structure for diagnostics.

### Newlines

Newlines separate statements.

```ds
let name = "Danh"
echo "hello"
```

Blank lines are allowed.

### Variables

Basic `let` statements are supported:

```ds
let name = "Danh"
let count = 3
let ok = true
```

Only declaration is required in `v0.1.0`.

Mutation is deferred.

Deferred examples:

```ds
count += 1
name = "Other"
```

### Literals

Supported literals:

```ds
"string"
123
true
false
```

String escapes are intentionally minimal in `v0.1.0`.

The lexer accepts only these escape sequences:

Recommended initial escapes:

```txt
\n
\t
\"
\\
```

Any other escape sequence is rejected with a diagnostic at the escape location.

Unterminated strings and trailing escapes must also produce clear diagnostics.

### Identifiers

Identifiers should support simple ASCII names first:

```txt
name
target
build_count
```

Suggested initial rule:

```txt
[A-Za-z_][A-Za-z0-9_]*
```

Unicode identifiers are not required in `v0.1.0`.

### If statements

Supported form:

```ds
if condition {
  echo "yes"
}
```

With `else`:

```ds
if name == "Danh" {
  echo "yes"
} else {
  echo "no"
}
```

Nested `if` statements should parse.

No `else if` sugar is required yet. Users can write nested `if` inside `else` for now.

### Command statements

A statement that does not start with language syntax is parsed as a command statement.

Examples:

```ds
git status
npm install
echo "hello"
docker compose up
```

Command statements should preserve words in the AST.

In `v0.1.0`, commands are parsed but not executed.

### Expressions

Supported expression forms:

```ds
name
"Danh"
123
true
false
!ok
name == "Danh"
count > 3
count >= 3
count < 10
count <= 10
name != "Other"
```

Minimum binary operators:

```txt
==
!=
>
>=
<
<=
```

Optional arithmetic operators may be parsed if simple:

```txt
+
-
*
/
```

But arithmetic behavior does not need to be implemented until runtime versions.

### Blocks

Blocks use braces:

```ds
if ok {
  echo "ok"
}
```

A missing closing brace must produce a useful diagnostic.

## Command-mode parsing rule

A line is parsed as a language statement when it starts with language syntax such as:

```txt
let
if
else
```

Otherwise, it is parsed as a command statement.

Examples:

```ds
let branch = "main"
git checkout $branch
```

The first line is a language statement. The second line is a command statement.

Command variables using `$branch` should be tokenized and represented, but behavior is not implemented until later versions.

## Diagnostics requirements

Diagnostics should include:

- filename;
- line;
- column;
- severity;
- short message;
- source snippet where practical;
- caret/span marker where practical.

Example:

```txt
examples/bad.ds:3:12 error: expected expression after `=`

  let name =
           ^
```

`v0.1.0` diagnostics do not need advanced recovery, but the parser should not crash on invalid input.

## AST requirements

The AST should include enough information for:

- debug printing;
- future HIR lowering;
- future Bash emission;
- diagnostics;
- future formatting.

Every AST node should preserve a source span if practical.

Minimum AST node categories:

```txt
Script
LetStmt
IfStmt
BlockStmt
CmdStmt
IdentExpr
StringExpr
IntExpr
BoolExpr
UnaryExpr
BinaryExpr
```

## Internal implementation expectations

This is not a code-level requirement, but implementation should generally follow:

```txt
source -> lexer -> tokens -> parser -> AST -> diagnostics
```

Recommended early C modules:

```txt
source
lexer
parser
ast
ast_print
diag
cli
```

The exact file structure can be decided during implementation.

## Examples

### Valid example

```ds
# examples/basic.ds
let name = "Danh"
let ok = true

if name == "Danh" {
  echo "hello"
} else {
  echo "who are you?"
}
```

Expected:

```sh
ds check examples/basic.ds
```

exits `0`.

### Invalid example

```ds
let name =
```

Expected:

```sh
ds check examples/bad.ds
```

exits non-zero and prints a useful diagnostic.

## Acceptance criteria

`v0.1.0` is complete when:

- `ds tokens <file.ds>` prints token output.
- `ds ast <file.ds>` prints readable AST output.
- `ds check <file.ds>` exits `0` for valid syntax.
- `ds check <file.ds>` exits non-zero for invalid syntax.
- Lexer handles comments, strings, integers, identifiers, keywords, braces, and operators.
- Parser handles `let`, `if`, `else`, blocks, command statements, and basic expressions.
- Diagnostics include filename, line, column, and useful message.
- Empty files and comment-only files parse successfully.
- Golden tests exist for lexer/parser/AST/diagnostics.
- `docs/language.ds` exists under `docs/` as a non-runnable syntax catalog.
- `docs/language.ds` clearly marks future syntax as planned, candidate, deferred, or rejected rather than implying it is already implemented.
- No runtime execution is accidentally introduced.
- No Bash emission is accidentally introduced.

### Technical debt

- The current parser/AST implementation uses simple heap allocation and direct structs. This is acceptable for `v0.1.0`; later runtime work should introduce the planned `src/core` ownership primitives.
- Command words are reconstructed from contiguous lexer tokens. This is intentionally enough for frontend debug output in `v0.1.0`, but the command parser should be revisited before command execution in `v0.3.0`.
