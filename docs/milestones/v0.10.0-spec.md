# v0.10.0 Spec — Arrays, Maps, and Loops

## Status

Implemented without tests.

## Goal

Add the first user-facing collection values and iteration constructs while
preserving the project rule that every supported feature must run in the VM and
emit to standalone Bash.

This milestone should make practical shell automation less repetitive by
supporting lists of services, simple string-keyed configuration maps, and loops
over those values without pulling in a broad standard library or advanced type
system.

The feature is complete only when equivalent behavior works through:

```sh
ds ./script.ds [script args...]
ds run ./script.ds [script args...]
ds emit bash ./script.ds -o ./script.sh
bash ./script.sh [script args...]
```

## Motivation

The language now supports reusable functions, imports, script arguments,
conditionals, command-result capture, readable redirection, and VM/Bash parity
for the current conservative subset. Real scripts still need a way to process
multiple services, files, ports, or command names without copy/paste.

`v0.10.0` introduces the smallest useful collection and loop model:

```ds
let services = ["api", "web", "worker"]

for service in services {
  docker compose restart $service
}
```

The design should stay boring and shell-emittable. Arrays and maps are concrete
runtime values, loops are synchronous control-flow constructs, and Bash emission
may use Bash arrays and Bash 4 associative arrays where maps are used.

## Non-goals

This version does not include:

- nested destructuring;
- generic types;
- user-defined collection types;
- ordered map guarantees;
- advanced collection methods such as `filter`, `map`, `reduce`, or `sort`;
- ranges unless explicitly needed for a minimal `while` test helper;
- `break` or `continue` unless deliberately scoped and tested in both VM and
  Bash emission;
- loop labels;
- pipelines;
- globbing helpers;
- `lines("file.txt")` iteration;
- file/path/cmd standard-library helpers;
- JSON/TOML parsing;
- nested arrays or nested maps unless the implementation can support and emit
  them safely without widening the type model;
- arrays or maps as function return values, because `v0.9.0` has no return-value
  model;
- making emitted Bash depend on `ds` or the C runtime.

If an item above becomes tempting during implementation, record it as deferred
unless the spec is deliberately amended before implementation continues.

## Supported syntax

### Array literals

Add array literals with comma-separated expressions:

```ds
let services = ["api", "web", "worker"]
let nums = [1, 2, 3]
let flags = [true, false]
let empty = []
```

Supported element expressions in `v0.10.0`:

- string literals;
- integer literals;
- boolean literals;
- `null` if the existing runtime value model supports it consistently;
- identifiers;
- simple expressions already supported by the current expression pipeline;
- command-result field access;
- function call expressions only if return values are explicitly added, which
  this milestone does not plan to do.

Array literals may be assigned to `let` bindings and may be passed to functions
only if the implementation supports parameter binding for collection values in
both VM and Bash emission. Otherwise, passing arrays to functions must be
rejected with a clear diagnostic and recorded as deferred.

### Array indexing

Add zero-based indexing:

```ds
let services = ["api", "web"]
let first = services[0]
echo "first={first}"
```

Index expressions must evaluate to integers. Negative indexes are rejected in
both VM and emitted Bash. Out-of-range indexes are runtime errors with source
context in VM mode and a clear emitted Bash failure helper in Bash mode.

Indexed values may be used anywhere an existing scalar expression can be used,
including interpolation, command arguments through a binding, comparisons, and
conditions.

### Array mutation

Support one minimal append operation:

```ds
services.push("cron")
```

`push` appends one value to an array variable and mutates that array. It is a
statement-oriented operation in this milestone. It does not return a value.

Rejected in `v0.10.0` unless explicitly amended:

- `pop`, `insert`, `remove`, `clear`, or slicing;
- assigning through an index such as `services[0] = "api2"`;
- chaining such as `services.push("x").push("y")`;
- pushing to a non-array value;
- pushing to a literal such as `["a"].push("b")`.

### Map literals

Add string-keyed map literals:

```ds
let ports = {
  api: 3000,
  web: 5173,
  worker: 9000
}

let labels = {
  "api-service": "api",
  "web-service": "web"
}
```

Supported keys:

- identifier-style keys, lowered as string keys;
- quoted string keys.

Supported values follow the same conservative expression subset as array
elements.

Duplicate map keys are semantic errors when duplicates can be detected at
compile time. If duplicate detection for computed keys is not supported because
computed keys are out of scope, the diagnostic should say computed keys are not
supported rather than silently accepting ambiguous behavior.

Empty maps require an explicit design because `{}` already means a block in the
language. This milestone should either:

- reject empty map literals with a diagnostic and record typed empty maps as
  deferred; or
- introduce a deliberate syntax for empty maps and document Bash emission.

Do not silently make `{}` mean both block and empty map without an unambiguous
parse rule.

### Map access

Support field and bracket access:

```ds
let api_port = ports.api
let web_port = ports["web"]
```

Field access works only for identifier-style keys. Bracket access works for
string expressions if Bash emission remains safe. If dynamic string-key access
is too broad for this version, bracket access should be limited to string
literals and identifiers known to be strings.

Missing keys are runtime errors in both VM and emitted Bash. They must not
silently expand to an empty string.

### `for item in array` loops

Add array iteration:

```ds
for service in services {
  echo "service={service}"
  docker compose restart $service
}
```

The loop variable is local to the loop body. It must not leak after the loop.
Each iteration binds the next array element to the loop variable.

Nested loops are allowed only if block scoping and Bash emission can preserve
loop variables without collisions. If nested loops are not implemented, reject
them explicitly with a diagnostic instead of miscompiling them.

### `for key, value in map` loops

Support map iteration only if VM and Bash emission can agree on deterministic or
documented ordering:

```ds
for name, port in ports {
  echo "{name}:{port}"
}
```

Because Bash associative array ordering is not a stable product contract, this
milestone must choose one of these approaches:

1. support map iteration with explicitly unspecified order and prohibit tests
   from depending on ordering; or
2. implement deterministic key ordering in both VM and Bash emission; or
3. defer map iteration and support only direct map access in `v0.10.0`.

The implementation should prefer option 1 only if docs and tests make the order
contract obvious. Do not accidentally promise map insertion order.

Loop key and value variables are local to the loop body and must not leak.

### `while condition` loops

Add `while` loops using the existing condition expression semantics:

```ds
let i = 0

while i < 3 {
  echo "{i}"
  i += 1
}
```

This requires the implementation to support enough reassignment/update syntax to
make `while` loops useful. If reassignment or `+=` is not currently implemented
despite being cataloged, the milestone may choose one conservative path:

- implement simple reassignment and `+=`/`-=` for integers in both VM and Bash;
- support `while` only for conditions that become false through already
  supported statements; or
- defer `while` to a follow-up version and document the deferral.

Infinite loops are a user responsibility. The VM should not add an arbitrary
iteration limit unless it is a debug/test-only guard.

## Semantics

### Value model

Arrays and maps become user-facing `DsValue` kinds.

Requirements:

- arrays preserve insertion order;
- arrays can contain the supported scalar values and, if implemented, collection
  values;
- maps use string keys;
- maps reject unsupported key types;
- collection values have clear ownership and copying rules;
- VM values and Bash-emitted values must behave equivalently for all supported
  operations.

If collection values are assigned to another variable, the implementation must
choose and document either value-copy or reference-like mutation behavior. Prefer
the simpler model that can be made identical in VM and Bash emission. Tests must
lock the chosen behavior.

### Type consistency

The project still does not have a full type checker. This milestone should keep
runtime and lowering checks conservative:

- indexing requires an array value and integer index;
- map field access requires a map value and existing key;
- array iteration requires an array value;
- map iteration requires a map value if supported;
- `push` requires a mutable array variable;
- `while` conditions use the current condition truthiness/comparison model.

Diagnostics should clearly say what was expected and what was found where the
runtime can know the actual kind.

### Scoping

Loop bodies use the existing block-scope model.

Requirements:

- loop variables are introduced by the loop and scoped to the loop body;
- loop variables may not duplicate another loop variable in the same loop head;
- loop variables should not overwrite outer bindings unless the existing
  shadowing rules explicitly allow it;
- `let` bindings inside loop bodies do not leak;
- function-local loops preserve function scoping rules from `v0.9.0`;
- imported files follow the existing import composition rules.

### Commands inside loops

Existing command behavior applies unchanged inside loops:

- plain commands are fail-fast;
- captured `run` commands are non-fatal and inspectable;
- redirection applies only to plain command statements;
- unsupported pipelines remain rejected.

Loop execution order must match between VM and emitted Bash for arrays and
`while` loops. Map loop output ordering follows the chosen map-order contract.

## Bash emission requirements

Generated Bash remains standalone and must not call back into `ds`.

Requirements:

- generated Bash uses a strict-mode header consistent with prior versions;
- array emission uses Bash indexed arrays;
- map emission may require Bash 4+ associative arrays;
- scripts that use maps should emit a Bash-version guard if associative arrays
  are used;
- generated variable names avoid collisions between top-level bindings,
  function locals, loop variables, arrays, maps, and temporaries;
- array element interpolation and command argument passing quote safely;
- map field/bracket access fails clearly when a key is missing;
- out-of-range array access fails clearly;
- generated Bash remains `bash -n` valid for every supported fixture.

If a script does not use maps, Bash emission should not unnecessarily require
Bash 4 associative arrays.

## CLI and debug commands

The existing commands must understand the new syntax:

```sh
ds tokens file.ds
ds ast file.ds
ds check file.ds
ds bytecode file.ds
ds run file.ds
ds file.ds
ds emit bash file.ds -o file.sh
```

Debug output must remain deterministic and pointer-free. It should display
array literals, map literals, indexing, field access, `for`, and `while` nodes
clearly enough for golden tests.

## Examples and docs

Add or update examples only when implementation reaches this milestone.
Candidate examples:

```txt
examples/collections.ds
examples/loops.ds
```

`docs/language.ds` already lists arrays, maps, and loops as `v0.10.0`. Update it
only if this spec deliberately narrows syntax, defers a cataloged form, or makes
a syntax decision such as the empty-map rule or map-iteration ordering.

## Acceptance criteria

- Parser accepts the supported array, map, indexing, `push`, `for`, and `while`
  syntax.
- Parser rejects malformed collection and loop syntax with source-located
  diagnostics.
- Semantic/lowering checks reject unsupported operations, duplicate map keys,
  invalid loop heads, unknown variables, invalid index types, invalid `push`
  targets, and unsupported empty-map syntax if deferred.
- VM executes supported arrays, maps, indexes, loops, and `push` operations.
- Bash emitter emits standalone Bash for the same supported behavior.
- VM and emitted Bash agree on stdout, stderr where relevant, and exit status
  for all parity fixtures.
- Generated Bash passes `bash -n`.
- Command behavior inside loops remains consistent with previous versions.
- Imports and functions work with supported collection and loop usage according
  to the existing composition and scope rules.
- Docs/examples are updated only to reflect implemented behavior.
- Deferred items and technical debt are recorded before the milestone is closed.

## Deferred items

Expected deferrals unless explicitly pulled into this spec:

- deterministic ordered maps;
- nested collections;
- collection equality;
- collection interpolation beyond scalar element access;
- collection methods beyond `array.push(value)`;
- index assignment;
- slices;
- `break` and `continue`;
- ranges;
- glob and line iteration;
- typed empty collection literals;
- arrays/maps in function return values;
- collection type annotations;
- Bash emission optimizations for large collections.

## Completion review

Implementation pass complete without tests.

Implemented:

- array literals, including empty arrays;
- array indexing with runtime out-of-range checks in the VM and Bash strict-mode failures in emitted scripts;
- `array.push(value)` for mutable array variables;
- string-keyed map literals with identifier and quoted-string keys;
- duplicate static map-key diagnostics;
- map field and bracket access;
- `for item in array` loops with per-iteration loop-variable scope;
- arrays, maps, indexing, `push`, and array loops in VM execution, bytecode debug output, and standalone Bash emission;
- functions/imports continue to compose through the existing lowered-program path.

Deferred during implementation:

- empty map literals, because `{}` remains ambiguous with blocks without typed empty collection syntax;
- map iteration, because the milestone intentionally avoids promising map ordering;
- `while`, because useful `while` loops require reassignment/update syntax that is not implemented yet;
- nested collections;
- passing whole collections directly as command arguments;
- map field command arguments such as `echo ports.api`; bind to a scalar first;
- collection return values, index assignment, slices, ranges, `break`, and `continue`.

Tests remain to be added from `docs/milestones/v0.10.0-test-plan.md`.
