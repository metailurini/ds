# v0.11.0 Spec — Shell-Oriented Standard Library

## Status

Implemented without tests.

## Goal

Add the first boring, shell-oriented standard-library helpers that make common
scripts shorter and safer than equivalent Bash while preserving the project rule
that every supported feature must run in the VM and emit to standalone Bash.

This milestone focuses on practical filesystem, path, command-discovery,
environment, globbing, and line-iteration helpers. It should integrate with the
existing expression, function, import, collection, loop, command-result, and
Bash-emission architecture without introducing a package system or broad
standard-library surface.

The feature is complete only when equivalent behavior works through:

```sh
ds ./script.ds [script args...]
ds run ./script.ds [script args...]
ds emit bash ./script.ds -o ./script.sh
bash ./script.sh [script args...]
```

Generated Bash must remain standalone and must not require `ds` or the C runtime
at execution time.

## Motivation

`ds` already has the language shape needed for useful automation: arguments,
imports, functions, command results, redirection, collections, and loops. Real
shell scripts still repeatedly need to ask basic questions and perform common
operations:

- does this file or directory exist?
- where is this command?
- join and inspect paths safely;
- read and write small text files;
- list files matching a pattern;
- iterate over a file line by line;
- read or update the environment for child commands.

Bash can do all of this, but its syntax is inconsistent and easy to misuse. This
milestone introduces a small, explicit standard library that keeps scripts
readable while still mapping naturally to Bash helpers.

```ds
cmd.require("git")

if file.exists("package.json") {
  npm install
}

for line in lines("input.txt") {
  echo $line
}
```

## Non-goals

This version does not include:

- networking helpers;
- JSON, TOML, YAML, dotenv, or config parsing;
- process management beyond existing command execution and `cmd.exists` /
  `cmd.require`;
- temporary files or directories;
- recursive remove/copy/move helpers;
- chmod/chown/stat metadata beyond the explicitly listed predicates;
- path normalization with cross-platform Windows semantics;
- symlink policy beyond the predicate behavior defined here;
- binary file APIs;
- streaming file handles;
- async IO;
- user-defined modules or packages;
- mocks or a testing framework for standard-library calls;
- broad string APIs;
- regex helpers;
- command pipelines;
- changing existing plain-command fail-fast or captured-`run` behavior.

If implementation work reveals a helper is too broad to emit safely to Bash, the
helper should be deferred rather than implemented VM-only.

## Supported syntax and APIs

Standard-library calls are normal call expressions/statements using namespace
objects or builtin functions. Namespace member heads are recognized by the
language:

```txt
file
dir
path
cmd
env
```

Builtin iterable functions are also recognized where call expressions are
accepted:

```txt
glob
glob!
lines
```

Calls must use the exact supported names and arity. Unknown stdlib members are
semantic errors. Bare variable names such as `file` may still be used as ordinary
loop variables, but `file.exists(...)` always resolves to the stdlib namespace
member rather than to a user-defined field call in this milestone.

### `file` helpers

Supported predicates:

```ds
file.exists(path)
file.is_file(path)
```

Behavior:

- `path` must be a string expression.
- `file.exists(path)` returns `true` when the path exists.
- `file.is_file(path)` returns `true` only for regular files.
- Missing paths return `false`; they are not runtime errors.
- Permission errors that prevent checking should produce a runtime error with
  source context rather than silently returning a misleading value.

Supported text operations:

```ds
let text = file.read(path)
file.write(path, text)
file.append(path, text)
```

Behavior:

- all arguments must be strings;
- `file.read` returns the full text contents of a file;
- `file.write` overwrites or creates the target file;
- `file.append` appends or creates the target file;
- text is treated as bytes/string data without encoding transformation;
- embedded NUL bytes are not supported in this milestone and should produce a
  clear runtime error if detected;
- write and append create the file but do not create missing parent directories;
- read/write/append failures are runtime errors with source context;
- write and append are statement-oriented in this milestone and do not return a
  useful value.

Rejected in `v0.11.0`:

```ds
file.delete(path)
file.copy(from, to)
file.move(from, to)
file.size(path)
file.read_bytes(path)
file.write_bytes(path, data)
```

### `dir` helpers

Supported predicate:

```ds
dir.exists(path)
```

Behavior:

- `path` must be a string expression;
- returns `true` only when the path exists and is a directory;
- missing paths return `false`;
- permission errors should produce a runtime error when the runtime cannot make
  a reliable determination.

Rejected in `v0.11.0`:

```ds
dir.create(path)
dir.remove(path)
dir.list(path)
```

Directory creation/listing/removal should wait until the project has a broader
filesystem mutation policy.

### `path` helpers

Supported helpers:

```ds
path.cwd()
path.join(part1, part2, ...)
path.basename(path)
path.dirname(path)
path.ext(path)
```

Behavior:

- `path.cwd()` returns the current working directory as a string;
- `path.join` accepts one or more string arguments and joins them with `/` while
  avoiding duplicate separators at join boundaries;
- `path.basename` returns the final path component;
- `path.dirname` returns the parent path using simple POSIX-style rules;
- `path.ext` returns the extension including the leading dot, or an empty string
  when there is no extension;
- all path helpers use POSIX-style semantics because generated Bash targets
  Bash-compatible systems;
- helpers do not normalize `..`, resolve symlinks, expand `~`, or absolutize
  paths unless already provided in the input.

Edge behavior to define and test:

- `path.join("src", "main.ds")` -> `src/main.ds`;
- `path.join("src/", "main.ds")` -> `src/main.ds`;
- `path.join("/tmp", "ds")` -> `/tmp/ds`;
- `path.basename("/tmp/ds/file.txt")` -> `file.txt`;
- `path.dirname("file.txt")` -> `.`;
- `path.ext("archive.tar.gz")` -> `.gz`;
- `path.ext("README")` -> empty string;
- hidden files such as `.env` should not be treated as having extension `env`
  unless the implementation deliberately documents that behavior.

### `cmd` helpers

Supported helpers:

```ds
cmd.exists(name)
cmd.require(name)
```

Behavior:

- `name` must be a string expression;
- `cmd.exists(name)` returns `true` when `name` can be found on `PATH` as an
  executable command;
- `cmd.require(name)` fails the script with a clear message when the command is
  missing;
- `cmd.require(name)` is statement-oriented and does not return a useful value;
- command names containing path separators are allowed only if VM and Bash can
  apply consistent executable checks; otherwise reject them with a clear
  diagnostic and record path-based command checks as deferred.

`cmd.require` failure should use the same broad runtime-diagnostic style as
other runtime failures and should include the missing command name.

### `env` helpers and namespace access

The syntax catalog already reserves direct environment assignment:

```ds
env.NODE_ENV = "production"
env.PATH += "./node_modules/.bin"
```

For `v0.11.0`, support the smallest reliable environment model:

```ds
let home = env.get("HOME")
let target = env.get("TARGET", "staging")
env.set("NODE_ENV", "production")
env.unset("DEBUG")
```

Behavior:

- environment names must be strings and must match a conservative portable
  pattern: `[A-Za-z_][A-Za-z0-9_]*`;
- `env.get(name)` returns the environment value when set, otherwise `null`;
- `env.get(name, default)` returns the default string when unset;
- `env.set(name, value)` sets the environment for the current `ds` process and
  child commands run after the call;
- emitted Bash uses `export name=value` so later commands see the value;
- `env.unset(name)` removes the variable for later commands;
- direct `env.NAME` assignment syntax remains cataloged but can be deferred if
  the parser/lowering work is too broad for this milestone;
- environment changes are process-local and must not mutate the parent shell.

If direct `env.NAME` syntax is implemented in this milestone, it must behave the
same as `env.set`/`env.get` and must have VM/Bash parity tests. Otherwise it
must produce a clear diagnostic and be recorded as deferred.

### `glob` and `glob!`

Supported helpers:

```ds
for file in glob("*.txt") {
  echo $file
}

for file in glob!("*.ds") {
  echo $file
}
```

Behavior:

- pattern arguments must be strings;
- `glob(pattern)` returns an array of matching path strings;
- unmatched `glob(pattern)` returns an empty array;
- `glob!(pattern)` returns matches or fails when the pattern has no matches;
- returned paths are sorted lexicographically to keep VM/Bash parity stable;
- patterns use Bash/POSIX shell-style globbing, including `*`, `?`, and bracket
  classes where both backends can match consistently;
- recursive `**` is supported only if both VM and emitted Bash can agree on
  behavior; otherwise it must be rejected or documented as deferred;
- glob expansion does not run through the shell in VM mode, so patterns are data
  and must not execute code.

`glob` results integrate with the `v0.10.0` array loop model.

### `lines`

Supported helper:

```ds
for line in lines("input.txt") {
  echo $line
}
```

Behavior:

- `lines(path)` returns an array-like iterable of strings, one per line;
- line terminators are not included in each line value;
- an empty file produces zero iterations;
- the final line is returned even when the file does not end with a trailing
  newline;
- missing files, directories, and unreadable files are runtime errors;
- embedded NUL bytes are rejected;
- very large files may be read eagerly in this milestone if documented, but the
  implementation should preserve output parity and avoid crashing on reasonable
  test fixtures.

`lines` is intended primarily for `for` loops. Assigning `let xs = lines(path)`
may be supported if it naturally produces an array value in both backends; if not,
that use must be rejected clearly.

## Semantic and lowering rules

- Standard-library namespace member calls and builtin iterable calls are
  recognized during semantic/lowering analysis.
- Unknown helpers are semantic errors, not command statements.
- Wrong arity is a semantic error.
- Wrong argument type is a semantic error when statically known and a runtime
  error when only known at runtime.
- Statement-only helpers such as `file.write`, `file.append`, `cmd.require`,
  `env.set`, and `env.unset` must not be used as value expressions unless the
  implementation defines a deliberate `null` result and tests it in both
  backends.
- Helper calls must lower to HIR nodes or call metadata consumed by both the VM
  and Bash emitter.
- Runtime errors must include source context where the current diagnostic system
  can provide it.
- The implementation must not add VM-only helpers.

## VM behavior

VM mode may call C runtime helpers for filesystem, path, environment, command
lookup, globbing, and line-reading behavior.

Requirements:

- use `stat`/equivalent checks for file and directory predicates;
- use safe C file APIs for read/write/append with checked errors;
- use `getcwd` for `path.cwd`;
- use deterministic string operations for path helpers;
- use `getenv`, `setenv`, and `unsetenv` or portable equivalents for `env`;
- use PATH search behavior compatible with emitted Bash for `cmd.exists`;
- produce sorted glob results;
- preserve existing plain-command and captured-`run` behavior after environment
  mutations;
- avoid leaking heap-owned strings, arrays, maps, or runtime values.

## Bash emission requirements

Generated Bash remains standalone and must not call back into `ds`.

Requirements:

- emit helper functions only when needed by the script;
- preserve the existing strict-mode header strategy;
- generated Bash passes `bash -n` for every supported fixture;
- helper names use reserved internal prefixes to avoid collisions with user
  functions and variables;
- quote all user-provided paths, command names, environment values, glob results,
  and line values safely;
- use Bash tests such as `[[ -e ... ]]`, `[[ -f ... ]]`, and `[[ -d ... ]]` for
  predicates;
- use Bash builtins or small helpers for path manipulation;
- use `command -v -- "$name"` or an equivalent safe check for `cmd.exists`;
- use `export`/`unset` for environment mutation;
- use Bash globbing carefully without allowing unmatched patterns to become
  literal accidental results;
- sort glob results for parity with VM mode;
- implement `lines(path)` with a loop that preserves the final unterminated line;
- fail clearly from generated Bash on missing required commands, missing files,
  read/write failures, unreadable line files, and required-glob misses.

If a helper requires Bash features newer than the current generated Bash baseline,
the emitter must either add an explicit guard or defer the helper.

## CLI and debug commands

The existing commands must understand standard-library calls:

```sh
ds tokens file.ds
ds ast file.ds
ds check file.ds
ds bytecode file.ds
ds run file.ds
ds file.ds
ds emit bash file.ds -o file.sh
```

`tokens` should not need special behavior beyond recognizing existing call and
namespace syntax. `ast`, `check`, and `bytecode` output must remain deterministic
and pointer-free.

## Acceptance criteria

- `file.exists`, `file.is_file`, `dir.exists`, `file.read`, `file.write`, and
  `file.append` work in VM mode and emitted Bash.
- `path.cwd`, `path.join`, `path.basename`, `path.dirname`, and `path.ext` work
  in VM mode and emitted Bash.
- `cmd.exists` and `cmd.require` work in VM mode and emitted Bash.
- `env.get`, `env.set`, and `env.unset` work in VM mode and emitted Bash, and
  later commands observe mutations.
- `glob` and `glob!` produce deterministic sorted arrays or iterables in VM mode
  and emitted Bash.
- `lines(path)` iterates with the same line values in VM mode and emitted Bash,
  including final unterminated lines.
- All helpers lower through the shared pipeline rather than backend-specific
  parsing.
- Unsupported helper names, wrong arity, unsupported argument types, and deferred
  forms produce clear diagnostics.
- Runtime errors include useful source context where supported by the current
  diagnostic system.
- Generated Bash is standalone and passes `bash -n`.
- VM and emitted Bash agree on stdout, stderr where relevant, file side effects,
  environment effects for child commands, and exit status for parity fixtures.
- Existing behavior from previous milestones remains unchanged.
- Deferred items and technical debt are recorded before the milestone is closed.

## Deferred items

Expected deferrals unless explicitly pulled into this spec:

- direct `env.NAME` syntax if parser/lowering support is too broad;
- recursive `**` globbing if parity is not straightforward;
- binary file reads/writes;
- directory creation/listing/removal;
- file copy/move/delete;
- file metadata helpers beyond the scoped predicates;
- temporary files/directories;
- path normalization, realpath, symlink resolution, and `~` expansion;
- command checks that take path-like names if parity is unclear;
- streaming `lines` implementation;
- standard-library mocking helpers;
- stdlib docs beyond examples and syntax catalog updates.

## Completion review

Implementation is complete for the scoped `v0.11.0` standard-library pass, but
the dedicated `v0.11.0` test suite has not been added yet.

Implemented:

- namespace helper calls for `file`, `dir`, `path`, `cmd`, and `env`;
- builtin iterable calls for `glob`, `glob!`, and `lines`;
- VM behavior for the scoped helpers;
- standalone Bash helper emission for the scoped helpers;
- helper calls inside functions, imports, conditions, and array loops through the
  shared lowered representation;
- deterministic sorted glob results;
- eager `lines(path)` arrays/iterables that preserve final unterminated lines;
- Bash/VM fail-fast parity for unmatched `glob!` and unreadable `lines` inputs;
- explicit rejection for recursive `**` glob patterns;
- clear diagnostics for unknown helpers, wrong arity, static non-string
  arguments, statement-only helper misuse, invalid static environment names,
  direct `env.NAME` access, and stale emitted Bash cleanup through the
  existing emit path.

Deliberately deferred:

- direct `env.NAME` access/assignment;
- recursive `**` glob parity beyond explicit rejection;
- binary file APIs and embedded-NUL support;
- directory creation/listing/removal;
- file copy/move/delete and additional metadata helpers;
- streaming `lines` internals;
- stdlib mocks/testing framework.

The next test pass should follow `v0.11.0-test-plan.md` strictly and may expose
additional diagnostic or parity fixes.
