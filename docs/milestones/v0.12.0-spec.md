# v0.12.0 Spec — Cleanup: Standard Library and Type Consistency

## Status

Complete. The behavior-preserving cleanup and dedicated `v0.12.0` regression
suite are implemented. The version adds no user-facing syntax or stdlib helpers;
it closes the scoped standard-library metadata, VM/Bash helper-boundary, and
hashmap absorption cleanup work.

## Goal

Repay the technical debt introduced while adding functions, collections, loops,
and the first shell-oriented standard library in `v0.9.0` through `v0.11.0`.

This is a cleanup milestone. It should not expand the user-facing language
surface. The goal is to make the standard-library implementation, type/arity
rules, VM behavior, Bash emission, docs, tests, and map/hashmap runtime boundary
easier to read, maintain, and extend before the roadmap moves on to debugging
and tracing in `v0.13.0`.

The central product rules remain unchanged:

```txt
every supported feature runs in the VM
every supported feature emits standalone Bash
VM behavior and emitted Bash behavior stay equivalent
unsupported or deferred forms fail clearly
```

## Motivation

`v0.11.0` deliberately chose a small but useful standard-library surface:

```txt
file.exists     file.is_file     file.read     file.write     file.append
dir.exists
path.cwd        path.join        path.basename path.dirname   path.ext
cmd.exists      cmd.require
env.get         env.set          env.unset
glob            glob!            lines
```

The implementation is useful, but the helper metadata and behavior are now
spread across several places:

- `src/lower.c` knows helper names, namespaces, arity, return kinds,
  statement-only rules, string-argument checks, recursive-glob rejection,
  invalid env-name checks, collection/type restrictions, and diagnostics.
- `src/vm.c` contains bytecode compilation, bytecode printing, VM execution,
  script-arg binding, process execution, command-result helpers, runtime scopes,
  collection operations, and the C stdlib helper implementations.
- `src/bash_emit.c` contains expression emission, statement emission, helper
  dependency detection, collection helpers, command helpers, stdlib helper
  bodies, and generated-script guards.
- `include/ds.h` exposes most internal declarations in a single wide header.
- `libs/hashmap/` is still a staged library subtree even though runtime maps now
  depend on it through `DsMap`. The architecture docs already say this should be
  absorbed behind the project-owned runtime/core boundary instead of remaining a
  separately staged implementation detail.
- The `v0.10.0` and `v0.11.0` test suites are strong, but they contain repeated
  fixture patterns and hand-written matrices that will become harder to extend
  when debugging/tracing features arrive.

A cleanup pass here should make the next wave safer by making the current rules
obvious and centralized.

## Non-goals

This version does not include:

- new standard-library helpers;
- changing supported helper names only for preference;
- direct `env.NAME` access or assignment;
- recursive `**` globbing;
- binary file APIs;
- directory mutation/listing APIs;
- pipelines, background jobs, or broader shell operators;
- return values from functions;
- collection function arguments;
- map iteration, ordered-map guarantees, `while`, ranges, slices, or index
  assignment;
- the `v0.13.0` debug/tracing commands;
- the `v0.14.0` test runner;
- the `v0.15.0` formatter/checker.

Behavior changes are allowed only when they fix inconsistency, tighten an
already documented rejection, or improve diagnostics without expanding scope.
Any renamed or changed API must be explicitly justified in the completion
review.

## Starting point review

The current implementation after `v0.11.0` has good feature coverage, but the
following refactor opportunities should be reviewed during this cleanup pass:

1. **Builtin metadata is duplicated.** Helper names, namespaces, arities,
   return/value kinds, statement-only rules, and argument constraints are encoded
   separately in lowering, VM execution, bytecode printing, Bash helper naming,
   Bash helper dependency detection, and docs.
2. **`src/vm.c` is doing too much.** It mixes bytecode construction/debug output,
   VM runtime execution, process handling, script-arg binding, stdlib runtime
   implementation, and collection operations in one large file.
3. **`src/bash_emit.c` is doing too much.** It mixes Bash quoting/expression
   rendering, statement rendering, helper dependency analysis, helper body text,
   collection support, stdlib support, and artifact output behavior.
4. **Type rules are still represented by a small internal `SymKind`.** That has
   been sufficient so far, but stdlib helpers, arrays, maps, command results,
   statement-only helpers, and Bash-assignable expression restrictions now need a
   clearer shared type/value contract.
5. **Diagnostics for unsupported or backend-limited forms are scattered.** Some
   checks live in parser code, some in lowering, some in VM runtime helpers, and
   some in emitted Bash helpers. The split is valid, but the contract should be
   documented and kept consistent.
6. **Generated Bash helpers are emitted as large string literals.** This works
   but makes helper review, dependency tracking, and shellcheck-style auditing
   harder.
7. **The single public internal header is becoming crowded.** Splitting is not
   mandatory, but the cleanup should decide whether a small internal-header split
   is low-risk now or should remain deferred.
8. **The staged hashmap should be absorbed.** `libs/hashmap/` is currently linked
   into the project and wrapped by `DsMap` in `src/runtime.c`, but keeping it as
   an external-looking subtree makes ownership, headers, build rules, and future
   runtime refactors less obvious. The cleanup should move the implementation
   into the project core/runtime area, keep the public `DsMap` abstraction, and
   remove direct `hashmap`/`hm_*` knowledge from frontend, VM, Bash emitter, and
   public headers.
9. **Test suites have repeated edge-case scaffolding.** The shared test library
   is useful, but v0.10/v0.11 fixture creation, VM/Bash parity calls, environment
   setup, fake PATH construction, and side-effect checks could be made easier to
   reuse.

## Required cleanup work

### 1. Centralize standard-library metadata

Introduce a single internal source of truth for supported standard-library
helpers.

The exact C shape is flexible, but it should cover at least:

- user-facing helper name, including namespace members such as `file.exists`;
- namespace classification (`file`, `dir`, `path`, `cmd`, `env`, or bare
  iterable helper);
- minimum and maximum arity;
- result kind: bool, int, string, array, map, command result, or statement-only;
- whether the helper is statement-only;
- whether all arguments must be strings in `v0.12.0`;
- whether static argument validation is needed, such as env-name or recursive
  glob rejection;
- Bash helper name and Bash-helper dependency flags, if the helper emits one;
- whether the helper can appear as a `for` iterable.

Requirements:

- Lowering, builtin-name collision checks, bytecode debug output, VM stdlib
  dispatch, Bash helper-name emission, and Bash dependency detection should use
  the shared metadata wherever practical.
- Unknown helpers and wrong arity diagnostics should be produced through shared
  helper lookup/formatting code.
- The metadata must not make generated Bash depend on `ds` or the C runtime.
- If full centralization is too large for one milestone, centralize lowering and
  Bash/VM lookup first, then document the remaining duplicated pieces.

### 2. Standardize type and value-kind rules

Review and clarify the internal type/kind model used during lowering.

Requirements:

- Keep the user-facing type surface unchanged.
- Document the supported value kinds used by lowering/runtime today:
  `null`, `bool`, `int`, `string`, `command-result`, `array`, `map`,
  `function`, and unknown/error.
- Ensure stdlib helper return kinds, script-arg types, collection element limits,
  command-argument limits, interpolation limits, and if-condition behavior are
  consistent with that model.
- Keep statement-only helpers from being used as values.
- Keep value-returning helpers from being used as statements unless explicitly
  documented.
- Preserve the existing conservative rule that expressions which cannot yet be
  emitted into Bash assignments are rejected for collection literals.

### 3. Tighten builtin and user-name collision behavior

Review all names that can be called or referenced:

- user functions;
- stdlib helpers;
- namespace member helpers;
- variables named `file`, `dir`, `path`, `cmd`, or `env`;
- loop variables;
- script args/options/flags.

Requirements:

- Existing supported behavior remains: bare variables such as `file` may exist,
  while `file.exists(...)` resolves to the stdlib helper.
- User functions must not redefine builtin callable names such as `glob`,
  `glob!`, `lines`, `file.exists`, or `cmd.require`.
- Duplicate top-level names should report once with a clear source location.
- Diagnostics should distinguish ordinary duplicate variables from builtin-name
  collisions.

### 4. Refactor VM stdlib/runtime boundaries

Reduce the maintenance burden in `src/vm.c` without changing behavior.

Good candidate extractions:

- bytecode compile/debug helpers;
- process execution helpers;
- stdlib runtime helper dispatch;
- path/file/env/cmd/glob/lines utility helpers;
- collection runtime helpers.

Requirements:

- Behavior must remain covered through public CLI commands, not private unit-only
  assumptions.
- Ownership rules for returned strings/arrays/maps must stay explicit.
- Runtime diagnostics must keep source spans where currently available.
- VM/Bash parity must not regress.
- If files are split, update the Makefile and docs accordingly.

### 5. Absorb the staged hashmap into the project runtime/core boundary

Move the owned hashmap implementation out of the temporary `libs/hashmap/`
staging shape and make it an internal implementation detail of `DsMap`.

The exact destination is flexible, but the end state should be clear and boring:

- the implementation lives under project-owned source/include layout such as
  `src/core/`, `src/runtime/`, or a similarly named internal area;
- production code includes an internal project header rather than
  `libs/hashmap/hashmap.h`;
- `Makefile`, `compile_flags.txt`, editor docs, and any direct unit-test compile
  lines are updated to the new paths;
- `libs/hashmap/` is deleted if it no longer has a role, or its remaining role is
  explicitly documented as temporary debt;
- `DsMap` remains the only map abstraction visible to parser, lowerer, VM,
  Bash emitter, and user-facing docs;
- map behavior remains unchanged: string keys, explicit missing-key failures,
  duplicate static key diagnostics, no map iteration, no ordered-map promise, and
  Bash associative-array behavior only in emitted Bash where maps require it;
- the absorbed code retains its license notice and attribution in an appropriate
  internal source/header comment or repository documentation;
- hashmap-specific test scripts, fuzz scripts, or benchmarks are either moved
  under a project-owned test/dev location or explicitly removed from release
  scope with a note in the completion review.

Requirements:

- `DsMap` ownership rules must remain explicit for keys and values.
- Existing map runtime tests must keep passing without relying on the old
  `libs/hashmap` path.
- No production file outside the map implementation should call `hm_*` functions
  or include the raw hashmap header.
- The cleanup must not change hash semantics in a way that exposes ordering as a
  user-visible contract.
- Any deliberate deviation from full absorption must be recorded in this
  milestone's completion review with the remaining follow-up work.

### 6. Refactor Bash helper emission boundaries

Reduce the maintenance burden in `src/bash_emit.c` without changing generated
behavior except for intentionally improved diagnostics/comments.

Good candidate extractions:

- helper dependency analysis;
- helper-body emission;
- stdlib helper-name mapping;
- expression emission helpers;
- collection helper emission.

Requirements:

- Helper functions still use the reserved `__ds_` prefix.
- Helpers are still emitted only when needed.
- Bash 4+ guard behavior remains targeted: map/associative-array features require
  it; array-only scripts do not get unnecessary guards.
- Emitted scripts remain standalone.
- Failed emission still removes stale output artifacts.

### 7. Improve diagnostics consistency without expanding scope

Audit and, where practical, standardize diagnostics for:

- unknown stdlib namespace members;
- wrong helper arity;
- statement-only helper used as a value;
- value-returning helper used as a statement;
- non-string helper arguments;
- invalid static and dynamic env names;
- recursive `**` glob patterns;
- embedded NUL text inputs;
- missing files for `file.read` and `lines`;
- missing required glob matches;
- directories passed to command-existence checks;
- builtin-name collisions;
- unsupported direct `env.NAME` access;
- unsupported direct collection access in command arguments.

The goal is boring consistency, not prettier messages for their own sake.

### 8. Test infrastructure cleanup

Review the test infrastructure for repeated helper patterns introduced by
`v0.10.0` and `v0.11.0`.

Requirements:

- Keep per-version suites readable.
- Move reusable VM/Bash parity and side-effect helpers into shared test helpers
  only when doing so reduces duplication.
- Avoid making test failures harder to debug.
- Preserve existing check counts only where useful; do not rely on check counts
  as the main correctness signal.
- Keep ASAN/UBSAN targets working with the normalized Makefile version list.

### 9. Documentation consistency pass

Update docs only to describe real behavior and cleanup results:

- `docs/architecture.md` should describe the stdlib metadata/dispatch path if it
  changes.
- `docs/runtime.md` should describe actual value kinds, ownership, and stdlib
  runtime boundaries if clarified.
- `docs/architecture.md`, `docs/runtime.md`, `docs/editor.md`, and build notes
  should no longer describe `libs/hashmap/` as the live production integration
  once the hashmap is absorbed.
- `docs/language.ds` should not gain new syntax, but may clarify current
  supported/deferred stdlib/type behavior.
- `README.md` should keep current status and important files accurate.
- This milestone spec’s completion review should list completed refactors,
  behavior-preserving changes, tests, and remaining debt.

## Acceptance criteria

`v0.12.0` is complete when:

- no new user-facing syntax or stdlib helper was added;
- VM behavior and emitted Bash behavior remain equivalent for the supported
  `v0.1.0` through `v0.11.0` language surface;
- stdlib helper metadata is centralized or the remaining duplication is clearly
  documented with a reason;
- type/value-kind rules are documented and used consistently during lowering;
- builtin/user-name collision behavior is clear and tested;
- the staged hashmap has been absorbed into the project-owned runtime/core
  boundary, or the remaining staged pieces are explicitly justified;
- VM/Bash helper boundaries are easier to read or the completion review explains
  why a larger split was deferred;
- diagnostics listed above are covered by regression tests or explicitly
  deferred;
- docs accurately describe the cleaned architecture;
- all prior version suites pass;
- the dedicated `v0.12.0` cleanup/regression suite passes;
- ASAN/UBSAN targets pass where available or any environment-specific limitation
  is recorded honestly;
- the completion review is filled in.

## Completion review

This section records the completed implementation and test pass.

### Implementation summary

Implemented the scoped cleanup without adding user-facing syntax or new stdlib
helpers. The standard-library helper table in `src/ds_stdlib.c` is now the shared
metadata source for helper names, Bash helper names, arity, return kind,
statement-only status, iterable status, string-argument requirements, and static
validation flags. Lowering, VM stdlib dispatch, bytecode debug output, and Bash
emission consume that metadata where practical.

Absorbed the staged hashmap into the project-owned runtime boundary under
`src/runtime/hashmap.c`, `src/runtime/hashmap.h`, and
`src/runtime/hashmap.LICENSE`. Production code builds through `src/runtime.c`'s
`DsMap` bridge rather than `libs/hashmap`.

Split VM stdlib runtime behavior into `src/vm_stdlib.c` behind the VM-private
`ds_vm_stdlib_call()` entrypoint in `src/vm_internal.h`. Split emitted Bash
helper bodies into `src/bash_helpers.c`/`src/bash_helpers.h`, leaving
`src/bash_emit.c` responsible for dependency analysis and rendering decisions.

### Behavior changes

No intentional user-facing behavior changes. Existing helper names, arities,
deferred forms, map semantics, Bash helper names, fail-fast runtime behavior,
and VM/Bash parity contracts are preserved.

### Refactors completed

- Centralized stdlib helper metadata in `src/ds_stdlib.c`.
- Routed stdlib lowering and VM dispatch through shared helper lookup.
- Routed Bash stdlib helper-name emission through shared metadata.
- Moved raw hashmap implementation into `src/runtime/` and kept raw `hm_*`
  usage contained inside the absorbed implementation plus `src/runtime.c`'s
  `DsMap` bridge.
- Added `src/vm_internal.h` as the VM-private boundary for bytecode/interpreter
  structs shared across VM implementation files.
- Moved VM file/path/env/cmd/glob/lines helper execution into
  `src/vm_stdlib.c`.
- Moved emitted Bash helper body text into `src/bash_helpers.c` so helper bodies
  can be reviewed separately from expression and statement emission.
- Updated architecture/runtime/README docs to describe the absorbed hashmap,
  value-kind contract, stdlib metadata, and new helper boundaries.

### Tests added or changed

Added the dedicated `tests/v0_12/run.sh` cleanup suite and wired `0-12` into the
normalized Makefile version list. The suite covers static stdlib metadata and
build-boundary checks, hashmap absorption checks, VM/Bash parity for stdlib,
imports, functions, namespace-like variables, maps, glob/lines behavior, and
side-effect files, plus representative diagnostics and runtime failure parity.

### Deferred cleanup / debt

- Post-v0.15 cleanup split the VM into focused `src/vm_*.c` components for
  bytecode construction, dumping, script-arg binding, scopes/function calls,
  process execution, stdlib runtime, and test execution. `src/vm.c` now focuses
  on the main interpreter loop and public VM entrypoints.
- Post-v0.15 cleanup also split Bash emission into focused `src/bash_*.c`
  components for dependency analysis, expression rendering, command rendering,
  statement/function rendering, shared quoting/interpolation utilities, helper
  body strings, and the public artifact-writing entrypoint.
- Lowering still uses a local `SymKind` model mapped from shared stdlib return
  metadata. This keeps the change low-risk; a future checker module may promote
  this into a shared semantic value-kind type.
- Diagnostics are routed through shared stdlib lookup/validation where practical
  and are now covered by the representative v0.12 diagnostics matrix. A future
  checker module can still reduce duplication between parser, lowering,
  runtime, and emitted Bash diagnostics.
