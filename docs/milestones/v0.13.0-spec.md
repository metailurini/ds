# v0.13.0 Spec — Debugging and Tracing

## Status

Planned. This milestone spec and companion test plan define the next roadmap
version after the completed `v0.12.0` cleanup pass.

## Goal

Make `ds` easier to debug both while developing the language implementation and
while using `ds` for real shell automation.

This version introduces stable debug surfaces for the current compiler/runtime
pipeline and practical tracing for command/runtime execution. It should help a
user answer these questions without reading C code or generated Bash internals:

```txt
What did ds parse and lower?
What bytecode will the VM execute?
Which command is about to run?
Where did a runtime failure come from in my .ds file?
What source line did this emitted Bash failure correspond to?
```

The central product rules still apply:

```txt
every supported source-language feature runs in the VM
every supported source-language feature emits standalone Bash
VM behavior and emitted Bash behavior stay equivalent
unsupported or deferred forms fail clearly
```

Most `v0.13.0` work is tooling around already-supported source features rather
than new source syntax. Debug commands and VM instruction tracing are allowed to
be VM/compiler-only developer tooling, but command tracing and emitted-script
failure context must respect the standalone Bash requirement.

## Motivation

By `v0.12.0`, the language has enough moving parts that debugging behavior by
only reading AST dumps or final Bash is no longer pleasant:

- imports compose multiple files before lowering;
- script args bind user input before execution;
- functions, arrays, maps, loops, command results, and stdlib helpers lower into
  shared backend structures;
- VM execution and Bash emission intentionally share behavior but have different
  internal representations;
- emitted Bash is standalone, so runtime failures in Bash need useful context
  without calling back into `ds`;
- bytecode dumps exist, but they should be more useful as a debugging tool;
- runtime diagnostics should keep source spans through more failing paths.

The next feature wave starts with better visibility before adding a user test
runner and formatter. This avoids building new tools on top of opaque internals.

## Non-goals

This version does not include:

- interactive debugger;
- breakpoints;
- step-through UI;
- watch expressions;
- REPL;
- time-travel debugging;
- source maps as a separate file format;
- natural-language explain mode;
- profiler or timing measurements;
- coverage reporting;
- test runner features from `v0.14.0`;
- formatter/checker features from `v0.15.0`;
- new source-language syntax;
- new standard-library helpers;
- broad CLI flag redesign unrelated to debug/tracing;
- changing normal script stdout/stderr except when tracing is explicitly enabled;
- making generated Bash depend on `ds` or the C runtime.

If implementation work uncovers a diagnostic or trace improvement that requires
a source-language behavior change, defer it unless the completion review amends
this spec deliberately.

## Supported command surface

Add these user-facing debug commands and flags:

```sh
ds hir <file.ds>
ds bytecode <file.ds>
ds run --trace-cmd <file.ds> [args...]
ds run --trace-vm <file.ds> [args...]
ds run --trace-cmd --trace-vm <file.ds> [args...]
```

Existing commands must keep working:

```sh
ds <file.ds> [args...]
ds run <file.ds> [args...]
ds tokens <file.ds>
ds ast <file.ds>
ds check <file.ds>
ds bytecode <file.ds>
ds emit bash <file.ds> -o <file.sh>
```

### CLI parsing rules

- `ds hir <file.ds>` loads imports, composes the program, lowers it, and prints
  the lowered representation.
- `ds bytecode <file.ds>` remains available and should print improved bytecode
  output for the same lowered program.
- Trace flags are initially scoped to `ds run`, matching the roadmap. Direct
  execution with `ds <file.ds>` may remain unflagged in this version.
- Trace flags appear after `run` and before `<file.ds>`.
- Script args after `<file.ds>` must be passed to the script unchanged, including
  args that happen to look like trace flags.
- Unknown `ds run --trace-*` flags should produce a clear usage error.
- `ds run --trace-cmd` and `ds run --trace-vm` may be combined; output ordering
  must be deterministic.

## HIR debug output

`ds hir <file.ds>` prints the lowered program representation after parsing,
import composition, and semantic lowering.

Requirements:

- Output must be deterministic for the same input.
- Output must include enough structure to inspect:
  - script declarations and their types/defaults;
  - imported/composed top-level statement order;
  - function signatures, default parameters, and function bodies;
  - `let`, assignment, command, call, `if`, block, `for`, and `push`
    statements;
  - literals, identifiers, field access, indexing, arrays, maps, calls, run
    expressions, unary expressions, binary expressions, and interpolated strings;
  - stdlib helper calls with their user-facing names;
  - command words and redirections;
  - source spans or source labels where practical.
- Output must not expose raw pointer addresses or allocation-order-dependent
  values.
- Output must be stable enough for golden tests, but the format may remain
  explicitly internal/debug rather than a public serialization format.
- Invalid programs should fail with the existing diagnostic style and should not
  print partial misleading HIR unless deliberately documented.

Suggested output shape is indentation-based and human-readable:

```txt
Program
  Script
    Arg app: string
    Option target: string = "staging"
  Function deploy(target = "staging")
    Block
      Command echo "deploying {target}"
  Let result = Run npm test
  If Field result.failed
    Block
      Call fail("tests failed")
```

The exact labels may differ, but the completion review must document the chosen
format if it materially differs from this shape.

## Bytecode debug output improvements

`ds bytecode <file.ds>` already exists. `v0.13.0` should make it more useful
without changing VM behavior.

Requirements:

- Keep the command name and basic purpose stable.
- Print script-argument metadata if present.
- Print function metadata and function entry ranges if functions are present.
- Print constants in a readable, escaped form.
- Print instructions with stable indices.
- Print operands with useful names where possible instead of only opaque numbers.
- Include source-span or source-line markers for instructions where the compiler
  currently has span information.
- Include stdlib helper names for stdlib call instructions.
- Preserve deterministic output suitable for golden tests.
- Do not change normal `ds run` behavior while improving dumps.

## Command tracing

`ds run --trace-cmd <file.ds> [args...]` traces command execution while running
the VM.

Requirements:

- Trace output goes to stderr.
- Normal script stdout remains unchanged.
- Trace lines appear before the command they describe is executed.
- Trace lines include a stable prefix, recommended:

  ```txt
  trace: cmd <file>:<line>:<column>: <rendered command>
  ```

- Trace output must cover:
  - plain command statements;
  - captured `run` expressions;
  - commands inside functions;
  - commands inside `if`/`else` blocks;
  - commands inside array and stdlib iterable loops;
  - commands from imported files with the imported file's source path when that
    span is available;
  - command statements with redirection, showing the user-facing command shape
    and target path when practical.
- Trace output should render variable-expanded command arguments as the VM is
  about to execute them, because that is what the shell command sees.
- Secret redaction is not part of `v0.13.0`; documentation should avoid claiming
  traces are safe for secrets.
- Command tracing must not make a failing captured `run` expression fatal.
- Plain command fail-fast behavior must remain unchanged.

### Emitted Bash command tracing

Generated Bash remains standalone. To preserve parity for command tracing without
requiring `ds`, emitted scripts that contain commands should include a small
trace helper when needed or cheap enough to include.

Requirements:

- Emitted Bash must continue to run normally with no trace noise by default.
- Setting `DS_TRACE_CMD=1` when running the emitted script should enable command
  trace lines to stderr for command statements and captured commands where
  practical:

  ```sh
  DS_TRACE_CMD=1 bash script.sh [args...]
  ```

- Trace line prefixes should match the VM command trace prefix as closely as
  practical.
- Source file/line information in emitted Bash traces may come from generated
  source markers or embedded comments; it must not require loading the original
  `.ds` file at Bash runtime.
- If a small subset cannot be traced in Bash without making generated code
  confusing or unsafe, document the limitation in the completion review and add a
  regression test for the chosen behavior.

## VM instruction tracing

`ds run --trace-vm <file.ds> [args...]` traces VM instruction execution.

Requirements:

- Trace output goes to stderr.
- Normal script stdout remains unchanged.
- Each trace line has a stable prefix, recommended:

  ```txt
  trace: vm ip=<n> op=<OP> ...
  ```

- Trace output should include:
  - instruction pointer/index;
  - opcode name;
  - relevant operands in a readable form;
  - source span/line where available;
  - function frame transitions where practical.
- Trace output must be deterministic for the same input except for command output
  produced by the user's script.
- The trace should not dump unbounded large string contents by default. Use a
  readable clipped representation if needed.
- `--trace-vm` is developer tooling for the VM path and does not require a Bash
  equivalent.
- `--trace-vm` must not change VM semantics, exit status, or script stdout.

## Runtime diagnostics with source spans

Improve runtime errors so failing paths point back to user source wherever the
implementation already has enough span information.

Requirements:

- Runtime diagnostics should use the same filename/line/column/snippet/caret
  style as parser and lowering diagnostics.
- Improvements should cover representative failures from current language
  features:
  - missing required CLI args;
  - invalid integer args/options;
  - plain command not found or non-zero exit;
  - `cmd.require` failure;
  - `file.read` missing file;
  - `file.write`/`file.append` write failure;
  - `glob!` no matches;
  - `lines` missing file;
  - invalid runtime field/index access if it can still occur after lowering;
  - failed import load diagnostics should keep the import site span.
- Diagnostics should include source from imported files when the failing span
  belongs to an imported file and the source is still available.
- Do not replace useful C/runtime error details such as `strerror(errno)`; add
  source context around them.

## Emitted Bash source markers and failure helpers

Improve generated Bash debugging without breaking standalone execution.

Requirements:

- Keep generated Bash standalone and runnable with ordinary Bash.
- Preserve or improve source comments around emitted statements.
- Add a small failure-reporting helper for generated Bash command failures when
  needed.
- Failing emitted Bash command statements should report a useful source marker to
  stderr before exiting, matching VM fail-fast behavior as closely as practical.
- Captured `run` failures must remain non-fatal and should not call the failure
  helper.
- The failure helper should use the reserved `__ds_` prefix and avoid collisions
  with user symbols.
- Helper emission should remain dependency-based where practical; do not dump a
  large unrelated debug runtime into every emitted script.
- Generated Bash must still pass `bash -n`.

## Diagnostic visual consistency

Review user-facing diagnostics across parser, lowerer, VM runtime, Bash emitter,
and emitted Bash failure helpers.

Requirements:

- Keep parser and semantic diagnostic wording stable unless there is a clear
  consistency improvement.
- Make newly added diagnostics use the same general style:

  ```txt
  path/to/file.ds:line:column error: message

    source line
        ^^^

  help: optional actionable hint
  ```

- Avoid duplicate diagnostics for the same root cause.
- CLI usage errors may remain simpler than source diagnostics, but trace flag
  mistakes should clearly say which flag/position is invalid.
- Diagnostics should not claim unsupported future features are supported.

## Documentation updates

Update docs only where they become outdated or where users need to discover the
new debug surfaces.

Expected updates:

- `README.md` project status and command list;
- `docs/architecture.md` compiler pipeline/debug surface notes;
- `docs/runtime.md` trace/diagnostic runtime notes if new helper boundaries are
  added;
- `docs/language.ds` only if needed to record that `v0.13.0` adds no source
  syntax and only debug commands/trace flags;
- examples only if a small debugging example helps manual smoke testing.

## Acceptance criteria

`v0.13.0` is complete when:

1. `ds hir <file.ds>` exists and prints deterministic lowered-program debug
   output for the currently supported language surface.
2. `ds bytecode <file.ds>` has improved readable metadata/instruction output
   without regressing existing bytecode dump behavior.
3. `ds run --trace-cmd <file.ds>` traces VM command execution to stderr without
   changing stdout, exit status, or fail-fast/captured-command semantics.
4. `DS_TRACE_CMD=1 bash emitted.sh` provides standalone emitted Bash command
   trace behavior for the supported command forms, or any deliberate limitation
   is documented and tested.
5. `ds run --trace-vm <file.ds>` traces VM instruction execution to stderr
   without changing program semantics.
6. Runtime failures added or touched by this milestone include useful source
   spans where available.
7. Emitted Bash failures for plain command statements include useful source
   context while captured `run` remains non-fatal.
8. Parser/semantic/runtime/Bash-emitter diagnostics remain visually consistent.
9. The dedicated `v0.13.0` test suite implements the companion test plan.
10. Existing `v0.1.0` through `v0.12.0` behavior remains compatible.
11. Docs/examples are updated where the new commands or trace behavior make the
    old docs incomplete.
12. The completion review below is filled in with implementation notes,
    validation results, and any deferred debugging debt.
