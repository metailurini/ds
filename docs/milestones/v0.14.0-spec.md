# v0.14.0 Spec — Test Runner

## Status

Planned. This milestone spec and companion test plan define the next roadmap
version after `v0.13.0` debugging and tracing.

## Goal

Add a small built-in test runner so `ds` users can test scripts without pulling
in an external framework for simple automation checks.

This version introduces test declarations and assertions as project-local test
metadata, not as normal production script behavior. A script should be able to
contain tests near the code they exercise, while normal execution and normal
Bash emission remain production-only unless the user explicitly invokes the test
runner.

The product rules still apply:

```txt
every supported source-language behavior has VM behavior
every supported production behavior emits standalone Bash
normal emitted Bash must not require ds at runtime
VM and Bash behavior stay equivalent for code executed by tests
unsupported or deferred forms fail clearly
```

For this milestone, `test` blocks are a test-runner surface. They are parsed,
checked, and executable through `ds test`; they are ignored by normal `ds run`
and normal `ds emit bash` output. The expressions and statements inside each
`test` block must use the same supported language subset as normal code so the
runner tests real behavior rather than a separate mini-language.

## Motivation

By `v0.13.0`, `ds` has enough language surface that users need a first-class way
to lock down small scripts:

- script argument defaults and validation;
- imports;
- functions;
- arrays, maps, and loops;
- command-result capture;
- redirection;
- shell-oriented standard-library helpers;
- tracing and diagnostics.

Relying only on shell scripts around `ds` is too heavy for simple checks. A tiny
native test runner keeps tests readable and gives the project a future place for
fixtures, mocks, and coverage without adding those larger features now.

## Non-goals

This version does not include:

- mocking or stubbing framework;
- snapshot testing;
- property-based testing;
- parallel test execution;
- coverage reporting;
- watch mode;
- test filtering by glob/regex unless explicitly added in a later milestone;
- nested `test` blocks;
- `before_each`, `after_each`, suites, or describe-style grouping;
- assertion messages beyond a simple optional string if implementation chooses
  to include it;
- diff rendering for failed strings or collections;
- testing private VM internals from ds code;
- persistent test cache;
- package/workspace discovery beyond a single file or explicit directory walk;
- formatter behavior from `v0.15.0`;
- new collection, string, or path APIs just to make tests nicer.

Do not add new stdlib helpers in this milestone unless the spec is deliberately
amended. If a desirable helper appears during implementation, record it as
future test-runner ergonomics debt.

## Supported syntax

### Test blocks

Add a top-level `test` declaration:

```ds
test "target defaults to staging" {
  assert "staging" == "staging"
}
```

Rules:

- `test` is a keyword only in declaration position.
- Test names are string literals.
- Test blocks are top-level declarations, like functions and imports.
- Test names should be reported exactly as written after normal string literal
  escaping is processed.
- Empty test names are rejected to avoid unclear reports.
- Duplicate test names in the same composed program are rejected.
- Test blocks may contain normal supported statements plus `assert` statements.
- Test blocks may declare local variables and call top-level functions.
- Test block local variables must not leak to other tests or production code.
- Tests should run in source order after import composition rules are applied.
- Tests in imported files are supported only through the rules in this spec.
- Nested test blocks are rejected.
- Test blocks inside functions, loops, `if`, or other test blocks are rejected.

### Assertions

Add an `assert` statement for simple boolean checks:

```ds
assert app == "api"
assert result.ok
```

Rules:

- `assert` is only valid inside a `test` block in `v0.14.0`.
- The assertion expression must be accepted anywhere an `if` condition is
  accepted today.
- Passing assertions produce no per-assertion output by default.
- A failing assertion fails the current test and reports the assertion source
  span.
- After a failed assertion, the runner may stop executing that test immediately;
  this fail-fast-within-test behavior must be documented in the completion
  review.
- A runtime error inside a test also fails that test and reports the runtime
  diagnostic with the test name attached.
- Assertion expressions must not introduce a new truthiness model. Reuse the
  language's current condition semantics.
- Optional message syntax, such as `assert expr, "message"`, is deferred unless
  explicitly added by an amended spec.

## CLI behavior

Add the command:

```sh
ds test [path]
```

Initial behavior:

- With a file path, run tests declared by that file and its imported files.
- With no path, run tests for the current directory only if a simple discovery
  rule is implemented and documented. Otherwise, print usage and require an
  explicit file. The implementation must choose one behavior and record it in
  the completion review.
- If a directory path is accepted, discovery must be deterministic and should
  be conservative, such as finding `*.ds` files under that directory in lexical
  order while ignoring hidden directories. Directory discovery may be deferred.
- `ds test path/to/file.ds` must not run normal top-level production statements
  outside tests except definitions/import composition needed to make tests
  executable.
- `ds test` must return exit code `0` only when all selected tests pass.
- It must return non-zero when parsing/lowering fails, no selected tests are
  found, at least one test fails, a runtime error occurs in a test, or CLI usage
  is invalid.
- It must print a clear summary with total, passed, and failed counts.
- It should print each test name with pass/fail status in deterministic order.
- Output should be stable enough for CLI tests. Avoid durations by default, or
  hide them behind a later opt-in flag.

Suggested output shape:

```txt
ok   target defaults to staging
fail rejects missing package

2 tests, 1 passed, 1 failed
```

The exact markers may differ, but the test plan must assert the implemented
shape consistently.

### Optional backend flag

To preserve the Bash-emission principle without turning normal emitted scripts
into test harnesses, the implementation may add one of these forms in
`v0.14.0` if it remains small:

```sh
ds test --backend vm file.ds
ds test --backend bash file.ds
ds test --backend both file.ds
```

If implemented:

- `vm` runs tests through the direct runner.
- `bash` generates a temporary standalone Bash test harness and runs it without
  depending on `ds` at harness runtime.
- `both` runs both backends and reports mismatches or backend-specific failures.

If not implemented in `v0.14.0`, the completion review must explicitly record
Bash test-harness execution as deferred debt, and normal Bash emission behavior
for test blocks must still be tested.

## Parser and AST behavior

Parser requirements:

- Recognize top-level `test "name" { ... }` declarations.
- Preserve the source span for the `test` keyword, test name, body, and each
  assertion.
- Represent `assert` statements distinctly from expression statements and
  command statements.
- Reject missing test names, non-string test names, missing bodies, and malformed
  assertions with existing diagnostic style.
- Reject `test` declarations in non-top-level positions.
- Reject `assert` outside test blocks.
- Keep existing function, import, script block, and command parsing behavior
  unchanged.

AST/HIR debug output from `v0.13.0` should include test blocks and assertions if
those debug commands are run on a file that contains tests. This is a debug
surface update, not a new user-facing language feature beyond the test runner.

## Semantic and lowering behavior

Semantic requirements:

- A composed program may contain production top-level statements, function
  definitions, script declarations, imports, and test declarations.
- Test blocks are not normal top-level statements during `ds run` or direct
  execution.
- `ds test` should build a test plan from the composed program without executing
  production top-level statements outside tests.
- Test bodies may call functions declared in the root file or imported files.
- Function definitions must remain shared between production execution and test
  execution.
- Script argument declarations are allowed in a file that also contains tests,
  but `ds test file.ds` must not require script args unless a test explicitly
  executes code that needs them. If the implementation cannot safely model this,
  reject script blocks plus tests with a clear diagnostic and record the deferral.
- Duplicate test names after import composition are errors.
- Import cycles, missing imports, duplicate functions, stdlib/user function name
  collisions, and existing semantic errors must fail before tests run.
- The runner must isolate each test's local scope from every other test.
- Side effects in the filesystem, environment, and external commands are not
  automatically isolated in `v0.14.0`; tests should document that users must use
  temp paths and explicit cleanup for side effects.

## VM test-runner behavior

The VM runner must support executing test bodies using the same runtime behavior
as normal script bodies for currently supported statements and expressions:

- `let`, assignment, and scalar expressions;
- `if`/`else`;
- command statements;
- captured `run` expressions;
- functions and default parameters;
- arrays, maps, indexing, field access, `push`, and array/stdlib iteration;
- stdlib helpers from `v0.11.0`;
- failure helpers `fail` and `exit` as runtime failures/exits within tests;
- imports and imported functions.

Failure rules:

- Failed assertions fail the current test.
- Direct command failures inside tests fail the current test using existing
  fail-fast semantics.
- Captured `run` failures do not fail unless asserted or handled as failures by
  user code.
- `fail "message"` inside a test fails that test with the message.
- `exit 0` inside a test should either pass/stop that test or be rejected inside
  tests; choose one behavior and document it.
- `exit nonzero` inside a test fails the test.
- A test failure should not prevent later tests from running unless a fatal
  compiler/load error occurred before execution.

## Bash emission behavior

Normal production Bash emission remains:

```sh
ds emit bash file.ds -o file.sh
```

Requirements:

- Normal emitted Bash must not execute test blocks.
- Normal emitted Bash must not contain test runner output or require test-only
  runtime state.
- If a source file contains only tests and no production statements, normal Bash
  emission should still emit a valid standalone script that performs no test
  work, or it should reject with a clear "no production statements" diagnostic;
  choose one behavior and document it.
- Test declarations and assertions must not corrupt generated Bash for the
  production program around them.
- Source markers in emitted Bash may mention that a test declaration was skipped
  only if that does not create confusing runtime output.
- Generated Bash must continue to pass `bash -n` for programs containing test
  blocks.

If the optional Bash test backend is implemented, its generated harness must be
standalone and may include assertion/report helpers. It must not call `ds` at
runtime.

## Import behavior

Initial import rules:

- Root-file tests are always selected by `ds test root.ds`.
- Tests in imported files are selected by default only if that is documented and
  deterministic. The preferred rule is: run all tests in the composed import
  graph in the same order the files are composed, then root tests at the points
  determined by the program order.
- If imported-file test execution is deferred, imported test blocks must still be
  parsed/checked and ignored with a documented warning or deterministic behavior.
- Duplicate test names across root and imported files are errors.
- Imported helper functions must be callable from root tests.
- Import cycles and missing imports use existing diagnostics.

## Diagnostics

Diagnostics must follow the existing style:

- filename;
- line;
- column;
- clear message;
- source line and caret where available.

Required diagnostic cases:

- malformed `test` declaration;
- empty test name;
- duplicate test name;
- nested test block;
- `assert` outside a test;
- assertion with missing expression;
- assertion expression that cannot be lowered;
- runtime assertion failure with source span;
- runtime error inside a named test;
- no tests found;
- unsupported CLI usage.

Test failure reports should include both the test name and the failing assertion
location. Keep user-facing messages simple and stable.

## Examples

Add or update examples only if they improve user understanding without becoming
a maintenance burden. Suggested example:

```ds
fn default_target(target = "staging") {
  echo "target={target}"
}

test "string equality" {
  let target = "staging"
  assert target == "staging"
}

test "captured command succeeds" {
  let result = run echo "ok"
  assert result.ok
  assert result.stdout == "ok\n"
}
```

Do not update `docs/language.ds` unless the final syntax differs from the
already cataloged `test`/`assert` direction.

## Acceptance criteria

The milestone is complete when:

- `test "name" { ... }` parses as a top-level declaration.
- `assert expr` works inside tests and is rejected outside tests.
- `ds test file.ds` runs selected tests in deterministic order.
- Passing tests exit `0` with a clear summary.
- Failing assertions exit non-zero, identify the test, and show the failing
  source span.
- Runtime failures inside tests fail that test without hiding later test results.
- Normal `ds file.ds` and `ds run file.ds` ignore test blocks.
- Normal `ds emit bash file.ds -o file.sh` does not execute test blocks and
  still produces standalone Bash for production statements.
- Imports and function calls work in tests according to the documented rules.
- Existing v0.1.0-v0.13.0 behavior remains unchanged.
- The dedicated `v0.14.0` test suite implements this test plan or records any
  amended/deferred items.
- Documentation and examples are updated only where behavior changed.
- The completion review below is filled in.
