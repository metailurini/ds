# v0.15.0 Spec — Formatter and Checker

## Status

Implemented. Dedicated tests are intentionally pending until the companion
`v0.15.0` test pass. The current implementation adds the formatter/checker CLI
surface and scoped warning behavior without changing VM, test-runner, or
standalone Bash runtime semantics.

## Goal

Add a deterministic source formatter and a small, reliable checker-warning layer
for real `ds` projects.

This version should make existing scripts easier to read and maintain without
changing their behavior. The formatter is a tooling feature over the already
supported source language. It must not become a syntax expansion milestone, and
it must not silently rewrite unsupported future syntax into something that looks
supported.

The product rules still apply:

```txt
every supported source-language behavior keeps VM behavior
every supported production behavior keeps standalone Bash emission behavior
formatting must not change runtime behavior
checker warnings must be reliable enough to trust
unsupported or deferred forms fail clearly
```

## Motivation

By `v0.14.0`, the language contains enough surface area that manual formatting
will drift:

- imports, script blocks, functions, tests, and top-level statements;
- conditionals, loops, nested blocks, arrays, maps, and function calls;
- command statements, captured commands, redirections, and stdlib calls;
- debug/test/normal execution paths.

A first formatter makes project files stable for review and future examples. A
small checker-warning layer catches obvious mistakes without pretending to be a
full type checker or linter.

## Non-goals

This version does not include:

- configurable style;
- formatter plugins;
- editor/LSP integration beyond documenting command behavior if useful;
- formatting only a selected source range;
- automatic semantic fixes;
- full data-flow analysis;
- full type inference;
- warning categories configurable by config file;
- warnings that require executing user code;
- changing Bash emission formatting;
- changing VM or Bash runtime semantics;
- adding new syntax to make formatting easier;
- auto-formatting generated Bash output;
- package/workspace formatting commands beyond explicit file paths unless the
  spec is deliberately amended.

If an attractive warning or formatting rewrite is not obviously reliable, defer
it rather than adding a noisy tool.

## Supported CLI

Add the commands:

```sh
ds fmt file.ds
ds fmt --check file.ds
ds check file.ds
```

### `ds fmt file.ds`

Initial behavior:

- Parse and validate the file using the existing frontend pipeline.
- Print formatted source to stdout by default.
- Exit `0` when formatting succeeds.
- Exit non-zero when the file cannot be loaded, parsed, or formatted.
- Do not modify the input file in place in `v0.15.0` unless an explicit `-w` or
  `--write` flag is added by amended spec and fully tested.
- Preserve user code behavior after parse → format → parse.
- Preserve semantically meaningful string contents exactly.
- Preserve comments where they are attached to existing supported syntax.
- Normalize whitespace, indentation, braces, and simple expression spacing.
- Emit a trailing newline.
- Produce deterministic output: formatting already formatted output must produce
  byte-identical output.

### `ds fmt --check file.ds`

Initial behavior:

- Do not print the formatted file on success.
- Exit `0` if the source is already formatted exactly as `ds fmt` would output.
- Exit non-zero if the source differs from formatter output.
- Print a short stable message identifying the file as needing formatting.
- Exit non-zero with normal diagnostics if parsing/loading fails.
- Do not modify the input file.

### Optional `--write`

`ds fmt --write file.ds` or `ds fmt -w file.ds` may be implemented only if it
stays small and safe.

If implemented:

- Write formatted source back to the same file atomically enough for normal local
  use.
- Preserve file permissions where practical.
- Refuse to write when parsing/formatting fails.
- Print a short stable message or no output on success.
- Keep `--check --write` invalid.

If not implemented, the completion review must explicitly record in-place
formatting as deferred.

## Formatting style

The first style is intentionally fixed and boring.

Required rules:

- two-space indentation;
- opening brace on the same line as the construct;
- closing brace on its own line;
- one blank line between top-level declarations or statement groups where this
  improves readability;
- no trailing whitespace;
- exactly one trailing newline at EOF;
- spaces around binary operators;
- no spaces immediately inside parentheses, brackets, or braces used for calls,
  indexes, array literals, or map literals;
- one space after commas;
- one space after colons in type annotations and map entries;
- command statements preserve command word order and argument text while
  normalizing leading indentation;
- redirection tokens remain separated enough to be readable;
- comments remain comments and should not migrate across unrelated statements.

Suggested examples:

```ds
fn greet(name = "world") {
  echo "hello {name}"
}

if target == "production" {
  npm test
} else {
  echo "skip"
}
```

```ds
script {
  arg app: string
  option target: string = "staging"
  flag force: bool = false
}
```

```ds
let xs = ["api", "web"]
let ports = { api: 3000, web: 5173 }
```

Formatter output should prefer readability over preserving the user's original
line breaks for small constructs. However, the first implementation may keep a
simple one-node-per-line strategy for complex expressions as long as it is
stable and documented.

## Comments and trivia

The formatter must preserve comments for supported syntax.

Minimum required behavior:

- leading file comments remain at the top;
- comments before top-level declarations stay before those declarations;
- comments before statements stay before those statements;
- inline trailing comments are preserved where the parser/trivia model can
  represent them reliably;
- comments inside blocks keep block-relative indentation;
- comments do not disappear during `fmt`.

If the existing lexer/parser cannot preserve every comment shape safely, the
implementation must choose one of these approaches and record it in the
completion review:

1. improve trivia preservation enough for the required cases; or
2. reject formatting files with unsupported comment placement using a clear
   diagnostic instead of dropping comments.

Dropping comments silently is not acceptable.

## AST/HIR and parser interaction

The formatter should reuse the existing frontend pipeline rather than building a
separate parser.

Requirements:

- Formatting malformed source reports existing-style diagnostics.
- Formatting must not require successful lowering when pure syntax is enough,
  except where lowering is intentionally reused for semantic safety.
- `fmt` should understand all syntax supported through `v0.14.0`, including
  test blocks and assertions.
- `fmt` must not make unsupported syntax appear accepted.
- `tokens`, `ast`, `hir`, `bytecode`, `run`, `test`, and `emit bash` behavior
  must remain unchanged except for help text listing the new command.

## Behavior preservation

For every supported script that formats successfully:

- `ds check original.ds` and `ds check formatted.ds` must both succeed or both
  fail for the same semantic reason.
- `ds run original.ds` and `ds run formatted.ds` should produce equivalent
  stdout, stderr, and exit status when the script has deterministic behavior.
- `ds emit bash original.ds` and `ds emit bash formatted.ds` should produce Bash
  scripts with equivalent runtime behavior, even if generated Bash text differs
  due to source comments/markers.
- `ds test original.ds` and `ds test formatted.ds` should report equivalent test
  outcomes.

The formatter must preserve string literals, interpolation, command arguments,
redirection targets, import paths, and test names exactly in meaning.

## Checker warnings

Improve `ds check` with a conservative warning layer.

Warnings are not errors by default in `v0.15.0` unless the implementation adds an
explicit opt-in flag. `ds check` should still exit `0` when only warnings are
present.

Required warning candidates, only when reliable:

- unused local variables introduced by `let` in a scope;
- unused function parameters;
- unreachable statements after `exit` or `fail` in the same block;
- duplicate or shadowing declarations that are legal but suspicious, if the
  implementation can identify them accurately;
- impossible script declarations, such as duplicate arg/option/flag names, if
  not already hard errors.

Reliability rule:

- It is better to implement fewer warnings than to produce noisy or misleading
  warnings.
- A warning must include filename, line, column, message, source line, and caret
  where available.
- A warning must not fire for variables consumed by interpolation, command `$var`
  arguments, function calls, map/array access, test assertions, or stdlib calls.
- A warning must respect lexical scope, function scope, test scope, and import
  composition rules.

If a candidate cannot be implemented reliably, defer it explicitly in the
completion review and test only the warnings that are implemented.

### Optional warning flags

The implementation may add:

```sh
ds check --warnings-as-errors file.ds
ds check --no-warnings file.ds
```

Only add these if the CLI behavior remains small and fully tested. If omitted,
record them as deferred.

## Bash-emission requirements

`v0.15.0` must preserve the Bash-emission contract.

Requirements:

- The formatter itself does not emit Bash.
- Formatting a source file must not remove or alter constructs needed by
  standalone Bash emission.
- `ds emit bash formatted.ds -o out.sh` must still produce standalone Bash for
  every supported production feature.
- Test blocks remain ignored by normal Bash emission according to `v0.14.0`.
- Source markers in emitted Bash may point to formatted line numbers when Bash is
  emitted from formatted source; that is acceptable.
- No generated Bash should depend on `ds` because of formatting/checking.

## Diagnostics

Diagnostics and warnings must follow existing style:

- filename;
- line;
- column;
- clear message;
- source line and caret where available.

Required diagnostic cases:

- missing input path;
- unknown `fmt` flag;
- invalid flag combinations, such as `--check --write` if `--write` exists;
- unreadable file;
- parse error while formatting;
- unsupported comment/trivia placement if the formatter cannot preserve it;
- formatter internal unsupported-node error, with a clear feature name;
- `fmt --check` detects unformatted source;
- checker warnings with stable wording.

## Examples and docs

Update docs/examples only where useful:

- README command list should mention `ds fmt file.ds` and `ds fmt --check` once
  implemented.
- `docs/language.ds` already records the fixed style direction; update it only
  if final style differs.
- Add a small formatter example only if it improves clarity.
- Do not turn examples into large golden fixtures.

## Acceptance criteria

The milestone is complete when:

- `ds fmt file.ds` formats supported source to stdout deterministically.
- `ds fmt --check file.ds` exits `0` for formatted input and non-zero for input
  that would change.
- Formatter output is idempotent.
- Formatter preserves comments according to the final documented rule and never
  silently drops comments.
- Formatter supports all syntax implemented through `v0.14.0` or clearly rejects
  unsupported shapes without changing files.
- Formatting preserves VM, Bash, and test-runner behavior for representative
  deterministic scripts.
- `ds check` emits only reliable warnings that respect scope and real usages.
- Warning-only `ds check` behavior is documented and tested.
- Existing `v0.1.0`-`v0.14.0` behavior remains unchanged.
- The dedicated `v0.15.0` test suite implements this test plan or records any
  amended/deferred items.
- Documentation and examples are updated only where behavior changed.
- The completion review below is filled in.

## Deferred items

Potential follow-up work:

- in-place `fmt --write` if not included;
- recursive directory/workspace formatting;
- configurable style;
- range formatting;
- editor/LSP formatting integration;
- richer lints and warning categories;
- warning suppression comments;
- `--warnings-as-errors` and `--no-warnings` if not included;
- formatter diff output;
- preserving every possible trivia shape if the first implementation supports a
  conservative subset;
- formatting generated Bash;
- performance tuning for very large files.

## Completion review

Completed for the implementation-only pass:

- Implementation summary: added `src/format.c` for AST-based source formatting,
  added `src/checker.c` for conservative warning diagnostics, wired both into
  the normal build, and routed the CLI through the existing source/parse/lower
  pipeline.
- Final CLI behavior: `ds fmt <file.ds>` prints formatted source to stdout;
  `ds fmt --check <file.ds>` exits `0` when input is byte-identical to formatter
  output and non-zero with `<path>: needs formatting` otherwise; `ds check
  <file.ds>` keeps hard-error behavior and may print warning-only diagnostics.
- Formatter style completed: two-space block indentation, same-line opening
  braces, own-line closing braces, spaces around binary operators, normalized
  call/array/map comma spacing, normalized script/function/test/loop/if blocks,
  normalized redirection spacing, and deterministic trailing-newline behavior for
  non-empty formatted output.
- Comment/trivia behavior completed: the current lexer discards comments, so the
  formatter rejects files containing comments with a source-span diagnostic
  instead of silently dropping them. Comment-preserving trivia support is
  deferred.
- Checker warnings completed: warning-only unused local variable and unused
  function parameter diagnostics with filename, line, column, source line, and
  caret. Warnings recognize uses in expressions, interpolation, `$name` command
  arguments, function/helper arguments, map/array access, assertions, and nested
  blocks. Script declarations are tracked for use but are not warned as unused.
- VM behavior preservation: no VM runtime semantics were changed.
- Bash emission behavior preservation: no Bash emission semantics were changed;
  formatting/checking add no generated Bash dependency on `ds`.
- Test-runner behavior preservation: normal `ds test` behavior is unchanged;
  formatter support includes test blocks and assertions in source output.
- Diagnostics completed: missing input, unknown fmt flags, parse/load failures,
  unsupported comments, format-check differences, and checker warnings report
  stable user-facing messages.
- Tests added: none yet; this pass intentionally implements code only. The
  dedicated `tests/v0_15/run.sh` suite remains pending for the test pass.
- Validation run: `make clean all`, `make check`, `make test-v0-12`,
  `make test-v0-13`, and `make test-v0-14` passed in targeted runs.
- Docs/examples updated: `README.md`, `docs/language.ds`, and this milestone
  completion review were updated.
- Deferred items confirmed: in-place `fmt --write`/`-w`, formatter diff output,
  comment-preserving trivia, recursive/workspace formatting, configurable style,
  warning controls, unreachable/shadowing warnings, and the dedicated v0.15 test
  suite.
