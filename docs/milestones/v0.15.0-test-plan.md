# v0.15.0 Test Plan — Formatter and Checker

## Status

Implemented. The dedicated `tests/v0_15/run.sh` suite covers the implemented
formatter/checker surface and records deferred comment-preservation behavior via
explicit unsupported-comment diagnostics.

## Scope under test

This plan covers only the `v0.15.0` formatter and checker milestone:

- `ds fmt file.ds` formatting to stdout;
- `ds fmt --check file.ds` status-only checking;
- optional `ds fmt --write` / `-w` only if implemented;
- formatting for all syntax supported through `v0.14.0`;
- comment preservation or explicit unsupported-comment diagnostics;
- formatter idempotence;
- behavior preservation across VM execution, Bash emission, and `ds test`;
- reliable `ds check` warnings that the implementation chooses to support;
- CLI diagnostics and regression coverage.

Out of scope as supported behavior:

- configurable style;
- formatter plugins;
- workspace formatting unless the spec is amended;
- range formatting;
- warning suppression comments;
- full type checking;
- semantic auto-fixes;
- editor/LSP integration.

Unsupported future items should still receive negative tests when the parser,
formatter, or checker could accidentally accept them.

## Required test target

Add a dedicated suite:

```txt
tests/v0_15/run.sh
```

Update Makefile wiring so these work:

```sh
make test-v0-15
make test
make asan
make ubsan
```

The suite should primarily test public CLI behavior. Static source checks are
allowed for build wiring, help text, idempotence harnesses, and ensuring no
formatter-specific runtime dependency leaks into emitted Bash.

## Test conventions

- Create all temporary `.ds` files, formatted outputs, emitted Bash files, fake
  commands, and side effects under the suite temp directory.
- Compare stdout, stderr, and exit status separately.
- Normalize absolute temp paths before comparing diagnostics.
- Avoid assertions on wall-clock timing.
- Keep each fixture focused on one formatting or warning rule.
- For behavior-preservation tests, run original and formatted copies in isolated
  temp directories so file side effects do not interfere.
- For `fmt --check`, assert both status and output/stderr shape.
- For warnings, assert stable message fragments and caret location, but avoid
  overfitting to unrelated note ordering.

## Formatter golden tests

### Basic declarations and spacing

Input:

```ds
let   name="Danh"
let count=1+2*3
if count>3{echo "big"}else{echo "small"}
```

Expected formatted shape:

```ds
let name = "Danh"
let count = 1 + 2 * 3

if count > 3 {
  echo "big"
} else {
  echo "small"
}
```

Assertions:

- stdout exactly matches the expected formatter output;
- stderr is empty or contains only documented warnings if warnings are emitted by
  `fmt`;
- exit status is `0`;
- output ends with exactly one newline;
- no trailing whitespace exists.

### Script block formatting

Input includes uneven indentation and spacing:

```ds
script{arg app:string
option target:string="staging"
flag force:bool=false}
```

Assertions:

- declarations are indented two spaces inside `script`;
- colons and defaults use the final documented spacing;
- formatting is idempotent;
- `ds check` succeeds on formatted output.

### Function and call formatting

Fixtures:

```ds
fn greet( name="world",title="" ){echo "hello {name}"}
greet("Danh","Mr")
```

Assertions:

- function header spacing is normalized;
- body indentation is two spaces;
- call argument comma spacing is normalized;
- default values are preserved;
- function-call semantics remain unchanged after formatting.

### Imports, tests, and assertions

Fixtures include:

```ds
import   "./lib.ds"

test   "works"{assert true}
```

Assertions:

- import path string meaning is preserved;
- test block and `assert` are formatted according to block rules;
- `ds test` passes for original and formatted source;
- normal `ds run` still ignores tests after formatting.

### Arrays and maps

Fixtures:

```ds
let xs=["api","web"]
let ports={api:3000,web:5173}
let first=xs[0]
let port=ports.api
```

Assertions:

- array and map literal spacing is normalized;
- index/member access remains compact and valid;
- formatted source runs with the same VM output;
- formatted source emits Bash with equivalent output.

### Loops and nested blocks

Fixtures:

```ds
for service in services{if service=="api"{echo "api"}else{echo "other"}}
```

Assertions:

- nested indentation increments by two spaces per block;
- `} else {` shape is stable;
- blank lines do not appear inside tight nested blocks unless documented;
- VM/Bash behavior matches after formatting.

### Command statements and redirection

Fixtures:

```ds
echo   "hello"
npm run build&>"build.log"
let result=run sh -c "printf ok"
```

Assertions:

- command word/argument order is preserved;
- command argument string contents are preserved exactly;
- redirection token and target are formatted according to final style;
- captured command formatting does not turn command text into expression text;
- original/formatted behavior matches for deterministic fake commands.

### Standard-library calls

Fixtures use implemented helpers:

```ds
let cwd=path.cwd()
let exists=file.exists("package.json")
cmd.require("sh")
```

Assertions:

- dotted stdlib call formatting remains valid;
- helper names are not rewritten;
- check/run/emit behavior remains unchanged after formatting.

## Idempotence tests

For every golden formatter fixture:

1. Run `./ds fmt input.ds > once.ds`.
2. Run `./ds fmt once.ds > twice.ds`.
3. Assert `cmp once.ds twice.ds` succeeds.
4. Run `./ds check twice.ds`.

Add one larger mixed fixture containing imports, script args, functions, arrays,
maps, loops, tests, comments, stdlib calls, captured commands, and redirections.
Assert idempotence on the mixed fixture as well.

- test assertion comments remain inside the test block;

## Behavior preservation tests

### VM behavior

For representative deterministic fixtures:

- basic variables/expressions;
- script args/options/flags;
- imports;
- functions and defaults;
- arrays/maps/loops;
- command capture;
- redirection;
- stdlib helpers;
- tests/assertions.

Procedure:

1. Run original with `./ds run original.ds` or direct execution.
2. Format to `formatted.ds`.
3. Run formatted with the same arguments/environment.
4. Assert stdout, stderr, and exit status match after normalizing temp paths.

### Bash emission behavior

Procedure:

1. Emit Bash from original source.
2. Format source.
3. Emit Bash from formatted source.
4. Run both Bash scripts with the same arguments/environment.
5. Assert runtime stdout, stderr, exit status, and side effects match.
6. Assert generated Bash remains standalone and does not invoke `ds` for
   formatter/checker behavior.

### Test-runner behavior

Procedure:

1. Run `./ds test original.ds`.
2. Format source.
3. Run `./ds test formatted.ds`.
4. Assert pass/fail counts and named test outcomes match.
5. Include at least one failing assertion fixture and verify the formatted source
   reports the correct formatted source line/span.

## Checker warning tests

Only assert warnings that are implemented in `v0.15.0`. For each implemented
warning, include positive and negative cases.

### Unused local variable warning

Positive fixtures:

```ds
let unused = "x"
echo "done"
```

```ds
fn f() {
  let inner = 1
  echo "f"
}
```

Assertions:

- `ds check` exits `0` when only warnings are present;
- warning includes filename, line, column, source line, and caret;
- warning names the unused binding;
- warning ordering is deterministic.

Negative fixtures must not warn when variable is used by:

```ds
echo "{name}"
echo $name
let b = a + 1
if ok { echo "yes" }
assert ok
let item = xs[0]
let value = ports.api
file.write(path, content)
```

### Unused function parameter warning

Positive fixture:

```ds
fn greet(name, unused = "x") {
  echo "hello {name}"
}
```

Negative fixtures:

- parameter used in interpolation;
- parameter passed to a command with `$param`;
- parameter used in a defaulted function call path;
- parameter used inside a nested block or loop.

### Unreachable statement warning

Positive fixtures:

```ds
fail "stop"
echo "unreachable"
```

```ds
exit 1
echo "unreachable"
```

Negative fixtures:

```ds
if cond {
  fail "stop"
}
echo "reachable"
```

Assertions:

- same-block statements after unconditional `fail`/`exit` warn;
- statements after conditional exits do not warn unless the implementation proves
  both branches terminate;
- warning points at the first unreachable statement.

### Shadowing or duplicate-declaration warnings

If implemented, cover:

- local variable shadowing a script arg;
- local variable shadowing an outer block variable;
- function parameter shadowing a top-level binding;
- legal reassignment not warning as shadowing;
- already-hard-error duplicates remaining errors, not warnings.

If deferred, include a completion-review note and do not add failing tests that
require it.

### Warning controls

If `--warnings-as-errors` is implemented:

- warning-only source exits non-zero;
- output still says warning or promoted warning according to final wording;
- clean source exits `0`.

If `--no-warnings` is implemented:

- warning-only source exits `0` with no warning output;
- hard errors still print diagnostics and exit non-zero.

If these flags are not implemented, assert they are rejected as unsupported or
unknown flags and record the deferral.

## Acceptance checklist

Before completing `v0.15.0`, verify:

- formatter CLI behavior matches the final spec;
- `fmt` output is deterministic and idempotent;
- `fmt --check` status behavior is correct;
- optional write mode is either fully tested or explicitly deferred;
- comments are preserved or unsupported placements are diagnosed, never silently
  dropped;
- supported syntax through `v0.14.0` formats or receives an explicit documented
  formatter diagnostic;
- formatting preserves VM behavior, Bash behavior, and test-runner behavior;
- checker warnings are reliable and scoped correctly;
- warning-only `ds check` exit behavior is tested;
- old features still pass their existing suites;
- docs/examples are updated only where needed;
- the v0.15.0 completion review is filled in with implemented/deferred warning
  details.
