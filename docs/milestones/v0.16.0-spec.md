# v0.16.0 Spec — Cleanup: Pre-Beta Hardening

## Status

Planned. This is the next unwritten milestone after `v0.15.0`.

`v0.16.0` is a cleanup/debt-repayment version in the roadmap wave. It must not
add major user-facing syntax. Its job is to make the implemented language through
`v0.15.0` easier to trust, easier to explain, and easier to maintain before the
next feature wave starts with control-flow completion.

## Goal

Pause feature work and harden the current implementation into a boring,
consistent baseline for broader experimentation.

The implementation now includes a meaningful shell-native language slice:

- frontend tokens/AST/checking;
- standalone Bash emission;
- VM execution;
- script args/options/flags;
- local imports;
- command result capture and readable redirection;
- functions;
- arrays, maps, and array loops;
- shell-oriented standard-library helpers;
- debug/tracing options;
- VM-backed test blocks;
- formatter and conservative checker warnings.

This cleanup must verify that those pieces still behave as one language, not as
separate VM/Bash/tooling paths that happen to share syntax.

The central product rules remain unchanged:

```txt
every supported production feature runs in the VM
every supported production feature emits standalone Bash
VM behavior and emitted Bash behavior stay equivalent
test-only constructs stay test-only
formatting/checking never change runtime meaning
unsupported or deferred forms fail clearly
```

## Motivation

The previous milestones deliberately favored small feature slices and frequent
cleanup. That has kept the project moving, but several broad consistency checks
are now due:

1. **Formatter ergonomics are intentionally incomplete.** `v0.15.0` rejects files
   containing comments because the lexer/parser pipeline does not retain trivia
   safely. Comments are part of the language catalog, examples, and real scripts,
   so the project should either add retained trivia/comment attachment or make
   the deferral/status unmistakable before users rely on formatting.
2. **The CLI entrypoint still owns many responsibilities.** `src/main.c` handles
   usage, source loading, import composition, path normalization, direct script
   dispatch, test dispatch, formatting flags, checking flags, and command
   routing. The code is not huge, but it is now the crossroad for every public
   command.
3. **Tooling paths need a shared contract.** `tokens` and `ast` intentionally see
   only the root file, while `check`, `hir`, `bytecode`, `run`, `test`, `fmt`,
   and `emit bash` use composed/lowered programs where appropriate. This should
   be documented and regression-tested so future import work does not drift.
4. **Examples have become the public tour of the language.** Every example should
   run in VM mode, emit standalone Bash when it contains production code, format
   where comments/trivia rules allow, and remain aligned with docs.
5. **The current warnings must remain conservative.** Warning behavior added in
   `v0.15.0` should not become noisy or scope-confused as the next feature wave
   adds more control flow.
6. **Runtime ownership deserves a focused audit.** The project uses owned strings,
   copied `DsValue`s, arrays, maps, subprocess capture buffers, temporary files,
   script-arg values, and import-loaded source buffers. A cleanup pass should run
   sanitizer-backed regression suites and fix obvious ownership leaks or
   double-free risks discovered inside existing scope.
7. **Docs need a single status view.** The README, architecture/runtime docs,
   roadmap, language catalog, examples, and milestone completion notes contain
   the truth, but users need one current status document that clearly separates
   stable, experimental, test-only, and deferred areas.

## Non-goals

This version does not include:

- new production syntax;
- `while`, `break`, `continue`, or `case` from the `v0.17.0` control-flow wave;
- function return values;
- string methods;
- regex/membership operators;
- map iteration, index assignment, ranges, slices, nested collections, or
  collection values passed directly to functions/commands;
- new standard-library helpers;
- direct `env.NAME` access or assignment;
- recursive `**` glob support;
- configurable formatter style;
- formatter plugins, range formatting, or workspace formatting;
- warning suppression comments or a linter plugin system;
- editor/LSP integration beyond updating docs if behavior changes;
- backend expansion to zsh/fish;
- native compilation.

Small behavior changes are allowed only when they remove inconsistency, improve
an existing diagnostic, fix an existing bug, or clarify an already documented
rejection. Any such change must be explicitly recorded in the completion review.

## Starting point review

The current codebase after `v0.15.0` already reflects earlier cleanup work:

- parser implementation is split by grammar area;
- lowerer, VM, and Bash emitter responsibilities are split into focused modules;
- standard-library metadata is centralized in `src/stdlib.c`;
- the absorbed hashmap implementation lives under `src/runtime/` and remains
  hidden behind `DsMap`;
- `include/ds.h` is a compatibility umbrella while internal code generally uses
  focused headers;
- formatter and checker live behind backend/tooling entrypoints.

The main remaining cleanup opportunities visible from the current docs and code
are:

- retained trivia/comment handling for formatter input;
- clearer CLI/import composition boundaries outside `src/main.c`;
- a current status document for supported/deferred/test-only language areas;
- example and docs synchronization;
- warning and formatter regression hardening;
- sanitizer-backed runtime ownership checks;
- static checks that prevent raw hashmap, generated-Bash, or formatter/runtime
  dependencies from leaking across boundaries.

## Required cleanup work

### 1. Write a current status document

Add `docs/status.md` or an equivalent clearly named document.

It must summarize the project state after `v0.15.0` and before the next feature
wave:

- supported production syntax and commands;
- supported VM behavior;
- supported standalone Bash emission behavior;
- supported test-only syntax and how normal execution treats it;
- supported formatter/checker behavior;
- known formatter limitations, especially comment/trivia handling;
- deferred language features from `docs/language.ds` that users are likely to
  ask about;
- known backend limitations where VM and Bash parity depends on conservative
  restrictions;
- current examples and how to run them;
- the next-wave direction from the roadmap.

The status document should be user-readable, not a raw milestone dump. It should
link conceptually to README/roadmap/language docs without replacing them.

### 2. Reconcile docs, examples, and the language catalog

Review at least:

- `README.md`;
- `docs/product-principles.md`;
- `docs/architecture.md`;
- `docs/runtime.md`;
- `docs/roadmap.md`;
- `docs/version-workflow.md`;
- `docs/language.ds`;
- `docs/editor.md` if include/build paths change;
- all `examples/*.ds`.

Requirements:

- no doc should imply unsupported syntax is implemented;
- no example should rely on behavior outside the current implemented scope;
- command lists should include current public commands exactly once where they
  are intended to be complete;
- docs should state which commands use root-file views and which commands use
  composed import-aware programs;
- docs should state that emitted Bash remains standalone and must not call `ds`;
- deferred items from earlier versions should remain deferred unless this spec
  explicitly chooses to fix a cleanup-only bug.

### 3. Harden formatter trivia/comment behavior

Choose one deliberate path and document it in the completion review.

Preferred path:

- retain line comments in the lexer/parser or an adjacent trivia structure;
- attach comments to nearby top-level declarations, statements, block entries,
  or end-of-file positions conservatively;
- update `ds fmt` to preserve supported comment positions instead of rejecting
  every file with a comment.

Minimum acceptable path if retained trivia is too large:

- keep the explicit unsupported-comment diagnostic;
- improve docs/status/test coverage so users understand the limitation;
- ensure examples and formatter tests never suggest comments are silently
  dropped or supported beyond reality.

If comment preservation is implemented, it must preserve behavior and meaning:

- file header comments remain at the top;
- comments before declarations stay before those declarations;
- comments before statements stay inside the same block;
- comments around `else`, loops, tests, and imports do not move across logical
  boundaries;
- inline trailing comments are either preserved correctly or rejected with a
  clear diagnostic;
- formatting remains deterministic and idempotent.

Silent comment dropping is forbidden.

### 4. Clean CLI and import composition boundaries where low-risk

Review `src/main.c` and extract stable internal helpers only where it reduces
coupling without creating noisy churn.

Good candidate boundaries:

- import composition/loading into a focused internal module;
- CLI path normalization and source loading helpers;
- command-specific flag parsing for `fmt` and `check`;
- shared command dispatch helpers for composed/lowered commands.

Requirements:

- public CLI behavior remains unchanged except for intentionally improved usage
  text or diagnostics;
- root-file debug commands remain root-file views unless deliberately documented
  otherwise;
- composed commands keep import resolution, load-once behavior, import-cycle
  diagnostics, and source spans;
- `ds test` continues to use VM-backed test execution and normal commands still
  ignore test blocks;
- any new source files are wired into `Makefile` and sanitizer builds.

If extraction is deferred, the completion review must state why `main.c` remains
acceptable for now.

### 5. Verify VM/Bash/tooling parity for every supported feature

Build a regression matrix covering features through `v0.15.0`.

For each production feature that can be deterministic, verify:

- `ds check` succeeds or fails for the same documented reason;
- `ds run` / direct execution behavior is correct;
- `ds emit bash` produces standalone Bash;
- emitted Bash behavior matches VM behavior;
- formatting the source, when supported, preserves behavior;
- formatting unsupported-comment files fails clearly rather than producing
  misleading output.

For test-only features:

- `ds test` executes tests and reports outcomes;
- `ds run`, direct execution, and normal Bash emission ignore test blocks;
- failing assertions and test-only `fail` / `exit` behavior remain scoped to the
  active test.

### 6. Audit runtime ownership and diagnostics under sanitizers

Run sanitizer-backed tests where practical and fix bugs exposed inside the
current milestone scope.

Focus areas:

- `DsValue` copy/free behavior for strings, arrays, maps, command results, and
  default arguments;
- array/map literals and `push`;
- function calls and default parameter values;
- script-arg binding and help/error paths;
- command capture stdout/stderr/status buffers and temporary files;
- stdlib helpers that allocate strings or arrays (`file.read`, `path.*`,
  `glob`, `glob!`, `lines`, `env.get`);
- import-loaded source buffers and composed AST/HIR cleanup;
- formatter output buffers and in-place write paths;
- checker warning traversal state.

Do not add broad performance work. Fix obvious avoidable O(n²) or repeated
parsing/loading problems only if they are local and low-risk.

### 7. Preserve internal boundaries

Add static or regression checks for boundaries that earlier cleanup versions
established:

- production code outside `src/runtime/hashmap.*` and the `DsMap` bridge must not
  include raw hashmap internals or call raw `hm_*` APIs;
- emitted Bash helper text must not depend on `ds` or on the C runtime;
- formatter/checker code must not execute user commands while formatting or
  checking;
- test-only AST/HIR nodes must not leak into normal production execution;
- internal code should prefer focused headers over the compatibility umbrella
  where practical;
- generated outputs, temporary files, and tests must stay under suite temp
  directories.

### 8. Update next-wave readiness notes

Update `docs/status.md`, `docs/roadmap.md`, or the completion review with a short
readiness section for `v0.17.0`.

It should identify what is now safe to build on and what should remain deferred
when implementing control flow:

- existing loop model and array iteration behavior;
- reassignment and compound assignment constraints;
- scope behavior for blocks/functions/tests;
- Bash-emission implications for loop control;
- diagnostics and test coverage that must be preserved.

## Bash-emission requirements

No cleanup may weaken the Bash-emission contract.

Requirements:

- every supported production feature still emits standalone Bash;
- generated Bash must not call `ds`;
- generated Bash must not require project source files at runtime;
- emitted Bash remains syntax-valid with `bash -n`;
- VM/Bash parity tests cover representative successful and failing cases;
- formatter/checker/test-runner cleanup does not introduce any generated Bash
  dependency;
- test blocks remain ignored by normal Bash emission according to `v0.14.0`.

## Diagnostics requirements

Diagnostics must keep the existing user-facing style:

- filename;
- line;
- column;
- clear message;
- source line and caret where available;
- optional help text when it materially improves actionability.

Required diagnostic review areas:

- missing/unreadable files;
- import cycles and missing imports;
- unsupported comments/trivia if not implemented;
- malformed source during `fmt`, `check`, `test`, `run`, and `emit bash`;
- unsupported deferred syntax from `docs/language.ds`;
- warning-only `ds check`, `--warnings-as-errors`, and `--no-warnings`;
- runtime errors from stdlib helpers and command capture;
- write failures from `fmt --write`.

## Acceptance criteria

The milestone is complete when:

- the next unwritten version is documented as `v0.16.0`;
- `docs/status.md` or equivalent exists and accurately summarizes current
  supported, experimental, test-only, and deferred areas;
- docs/examples are reconciled with implemented behavior;
- formatter comment/trivia behavior is either improved or explicitly retained as
  an unsupported diagnostic with stronger tests/docs;
- CLI/import composition boundaries are cleaned where low-risk or explicitly
  deferred with rationale;
- every supported production feature has representative VM/Bash parity coverage;
- test-only behavior remains test-only;
- formatter/checker behavior remains deterministic and non-executing;
- runtime ownership checks pass under normal and sanitizer-backed runs where
  practical;
- static boundary checks protect hashmap, Bash, formatter/checker, and test-only
  boundaries;
- existing `v0.1.0`-`v0.15.0` suites continue to pass or any environment timeout
  is reported honestly;
- no major new language feature is introduced;
- completion review records implemented cleanup, deferred cleanup, validation
  commands, and next-wave readiness notes.

## Deferred items

Likely follow-up work after `v0.16.0`:

- control-flow completion in `v0.17.0`;
- function return values;
- string helpers;
- regex/membership operators;
- richer type checking;
- configurable formatter style;
- warning categories and warning suppression comments;
- editor/LSP integration;
- workspace formatting;
- larger performance work;
- package/module system beyond local imports.

## Completion review

Completed in the implementation pass.

- Implementation summary: added the current support/status document, reconciled
  the high-level docs with the implemented command surface, moved CLI
  source/import composition and lowering setup behind `src/cli_program.c` /
  `src/cli_program.h`, kept `src/main.c` focused on public command dispatch and
  flag parsing, and updated the CLI usage banner to `ds v0.16.0`.
- Docs/status updates: `docs/status.md` now records supported production
  syntax, VM behavior, standalone Bash behavior, test-only syntax, formatter and
  checker behavior, known limitations, examples, deferred language features,
  backend boundaries, and the `v0.17.0` control-flow direction. README,
  architecture, runtime, and changelog entries point at or summarize that
  status.
- Formatter comment/trivia decision: comment-preserving formatting remains
  deferred. This is the explicit minimum acceptable path for `v0.16.0` because
  the current lexer/parser pipeline discards trivia and a correct solution needs
  a dedicated comment attachment model. `ds fmt`, `ds fmt --check`, and
  `ds fmt --write` reject comment-bearing files with a source-located diagnostic
  and do not rewrite them; normal parsing/checking/running/emission still accept
  comments.
- CLI/import boundary cleanup: completed for the stable low-risk boundary.
  `DsCliProgram` owns source loading, root-file parse, import-aware composition,
  lowering, import cycle/load-once diagnostics, and cleanup of loaded units.
  `tokens` and `ast` remain root-file debug views; `check`, `hir`, `bytecode`,
  `run`, direct execution, `test`, and `emit bash` use the composed program;
  `fmt` remains root-file-only.
- VM/Bash parity validation: representative production examples were checked in
  VM and Bash modes: `basic`, `args`, `import-main`, `command-result`,
  `functions`, `collections`, `stdlib`, `vm`, and `redirection`. For each, the
  source checked successfully, emitted Bash passed `bash -n`, and VM/emitted
  Bash stdout, stderr, and status matched with the documented arguments. The
  intentionally invalid `examples/bad.ds` still fails with a source diagnostic.
- Runtime ownership/sanitizer validation: normal `make clean all` passed.
  AddressSanitizer and UndefinedBehaviorSanitizer builds passed focused smoke
  coverage for collection/map copying, command-result buffers, stdlib/runtime
  execution, checking, and VM-backed tests. AddressSanitizer was run with leak
  detection disabled to match the existing project sanitizer target policy in
  this environment.
- Static boundary validation: grep-based boundary checks found no raw hashmap
  includes or `hm_*` calls outside `src/runtime/hashmap.*` and the `DsMap` bridge
  in `src/runtime.c`; `include/ds.h` does not expose raw hashmap types; live
  build/editor paths do not reference `libs/hashmap`; representative generated
  Bash contains only source comments/helper names with `ds` text and no runtime
  invocation of the project binary; `ds check` and `ds fmt` were verified not to
  execute a fixture command with file-system side effects.
- Behavior changes, if any: the CLI usage banner now reports `ds v0.16.0`
  instead of the stale `ds v0.6.0`. No syntax or runtime feature was added.
- Deferred items: comment-preserving formatting, workspace/range formatting,
  warning suppressions/categories, control-flow completion, function return
  values, string helpers, regex/membership operators, map iteration, nested
  collections, direct environment field syntax, recursive glob support, editor
  integration, and alternate backends remain deferred.
- Notes for `v0.17.0`: control-flow work can build on the existing composed
  program boundary, block/function/test scoping, array-loop lowering model, and
  VM/Bash parity harness. `while`, `break`, `continue`, and `case` should keep
  test-only behavior isolated, reject unsupported loop-control placements with
  source diagnostics, and preserve standalone Bash emission without introducing
  a runtime dependency.
