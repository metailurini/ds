# v0.18.0 Spec — Pipelines

## Status

Implementation complete; test-plan implementation is still pending. This is the
first implementation pass after `v0.17.0`.

`v0.18.0` is the feature-expansion pass after control-flow completion. Its job
is to add shell-native pipelines to both plain command statements and captured
`run` expressions while preserving the project rule that every supported feature
runs in the VM and emits standalone Bash.

## Goal

Add pipeline syntax for command chains:

```ds
cat access.log | grep "ERROR" | sort | uniq

let errors = run cat access.log | grep "ERROR"
if errors.failed {
  echo errors.stderr
}
```

Pipelines must behave consistently in direct VM execution and emitted Bash:

```txt
plain command pipelines fail-fast like plain commands
captured run pipelines return a command-result value
pipeline exit status follows Bash pipefail-style semantics
redirections remain explicit and readable
unsupported pipeline forms fail before partial execution/emission
generated Bash remains standalone and never calls ds
```

## Motivation

`ds` is a shell-native language. By `v0.17.0`, scripts can use conditionals,
arguments, imports, command results, redirection, functions, arrays/maps,
stdlib helpers, tests, formatting, cleanup-hardened CLI boundaries, and core
control flow. The largest remaining shell-native gap is pipeline support.

Without pipelines, common automation tasks still need temporary files or nested
commands. This milestone makes idioms like filtering logs, extracting fields,
and checking command chains possible without falling back to Bash syntax.

`v0.7.0` deliberately rejected `|` so the command model and redirection syntax
could stabilize first. `v0.18.0` now revisits that deferral with a narrowly
scoped implementation.

## Non-goals

This version does not include:

- pipeline expressions outside command syntax;
- pipeline-as-value or reusable pipeline declarations;
- async/background pipelines;
- named pipes/FIFOs;
- process substitution such as `<(...)` or `>(...)`;
- here-documents or here-strings;
- shell grouping/subshell syntax such as `(cmd | cmd)`;
- logical shell operators `&&` and `||`;
- command substitution syntax;
- redirection on intermediate pipeline stages, unless explicitly listed below;
- tee-like built-in fan-out helpers;
- streaming stdlib APIs beyond ordinary process pipes;
- custom pipeline status objects beyond the existing command-result fields;
- Windows shell support;
- changing the command word/interpolation language beyond what pipelines need;
- changing the `|>` / `|>>` redirection operators introduced in `v0.7.0`.

If a tempting shell feature requires expanding beyond a simple linear pipeline,
defer it. This milestone should not become a general shell grammar rewrite.

## Syntax

### Plain command pipelines

Supported:

```ds
cat access.log | grep "ERROR"
cat access.log | grep "ERROR" | sort | uniq
```

A plain pipeline is still a command statement. It is not an expression and does
not produce a `command-result` value.

Rules:

- each stage is a command word sequence using the existing command-word rules;
- at least two stages are required when `|` appears;
- each stage must contain at least one command word;
- leading, trailing, and repeated pipes are syntax errors;
- newline ends the pipeline statement unless future continuation syntax is
  explicitly added;
- command interpolation inside stage words follows existing command behavior;
- plain pipeline non-zero status is fatal in normal run/direct execution, just
  like existing plain command failure.

### Captured `run` pipelines

Supported:

```ds
let result = run cat access.log | grep "ERROR" | sort
```

A captured pipeline returns the existing command-result value shape:

```txt
stdout: string
stderr: string
code: int
ok: bool
failed: bool
```

Rules:

- non-zero captured pipeline status is not fatal by itself;
- `result.code` is the pipeline status defined below;
- `result.stdout` is stdout from the final stage;
- `result.stderr` contains stderr from all stages in process order as observed by
  the runtime/Bash backend;
- `result.ok` is `true` when the pipeline status is zero;
- `result.failed` is the inverse of `ok`.

### Redirection with pipelines

Supported in `v0.18.0`:

```ds
cat access.log | grep "ERROR" |> "errors.txt"
cat access.log | grep "ERROR" |>> "errors.txt"
cat access.log | grep "ERROR" !> "errors.err"
cat access.log | grep "ERROR" &> "errors.all"
```

Rules:

- redirection suffixes apply to the whole pipeline, not to individual stages;
- the existing suffix redirection syntax and target restrictions remain in
  force;
- captured `run` pipelines still reject redirection, matching existing captured
  command behavior;
- redirection before the final stage, or multiple redirection suffixes, is
  rejected;
- `|>` and `|>>` remain stdout redirection operators, not pipelines.

Examples that must be rejected:

```ds
cat a |> "out" | grep x       # redirection cannot appear mid-pipeline
let r = run cat a | grep x |> "out"  # captured run redirection remains deferred
cat a |                       # missing stage
| grep x                      # missing stage
cat a || grep x               # logical OR is not a pipeline
```

## Pipeline exit status semantics

`ds` uses Bash `pipefail`-style pipeline status:

- if every stage exits `0`, the pipeline status is `0`;
- if one or more stages fail, the pipeline status is the status of the
  rightmost failing stage;
- for plain pipelines, non-zero pipeline status is fatal and becomes the script
  exit status unless an existing surrounding construct intentionally captures or
  branches on it;
- for captured `run` pipelines, non-zero pipeline status is stored in
  `command-result.code` and does not stop the script.

Rationale: emitted Bash already uses strict mode with `set -euo pipefail`, and
`pipefail` avoids the surprising Bash default where `false | true` succeeds.
The VM must emulate this rule rather than returning only the last stage status.

## VM behavior

The VM must execute pipelines without invoking a shell just to interpret `|`.
Each stage should use the existing process execution path where practical, but
with explicit pipe wiring between child processes.

Requirements:

- create pipes between adjacent stages;
- connect stage stdin/stdout through file descriptors;
- collect stdout from the final stage for captured `run` pipelines;
- collect stderr from all stages for captured `run` pipelines;
- apply whole-pipeline redirection suffixes for plain command pipelines;
- wait for every child process;
- compute pipefail-style status from all child statuses;
- close all unused file descriptors in parent and child paths;
- report fork/pipe/dup/exec/wait failures with existing diagnostic style;
- preserve existing command tracing behavior where practical:
  - trace each expanded stage command;
  - trace the pipeline status for plain command failure;
  - do not change stdout/stderr/status when tracing is disabled.

Implementation may initially be sequential only in setup/wait orchestration, but
process stages themselves must run concurrently enough to avoid deadlock on
large streams. Do not implement a pipeline by reading one entire stage into
memory and then feeding the next stage.

## Bash emission behavior

Generated Bash must emit a normal Bash pipeline for supported pipeline syntax:

```bash
cat access.log | grep 'ERROR' | sort | uniq
```

Requirements:

- output must pass `bash -n`;
- emitted scripts must not call `ds`;
- plain pipelines should rely on the generated `set -euo pipefail` header for
  fail-fast pipefail behavior;
- captured `run` pipelines must capture stdout, stderr, and pipefail status in a
  way that matches the VM command-result contract;
- quoting/interpolation of individual stage words must reuse existing Bash
  command-word rules;
- whole-pipeline redirection suffixes must be rendered after the complete
  pipeline;
- source markers and trace helpers should still identify useful source spans;
- helper functions may be embedded only if they are standalone Bash and use the
  existing reserved `__ds_` prefix.

If Bash capture requires an embedded helper to preserve pipefail status and both
stdout/stderr, the helper must be selected only when needed and tested to ensure
it is embedded in emitted Bash, not loaded from `ds`.

## Parser, AST, and HIR requirements

The current command model stores one `DsCommand` as a word vector plus an
optional redirection. `v0.18.0` should promote command representation to a small
pipeline-aware model without exposing Bash implementation details through the
frontend.

Required representation changes:

- represent a command stage as the existing command-word sequence;
- represent a pipeline as one or more stages plus an optional whole-pipeline
  redirection;
- keep the single-stage case cheap and compatible with existing code;
- update clone/free/printer paths for the new structure;
- update AST and HIR statement/expression nodes that currently store commands;
- ensure imports, functions, test blocks, formatter, checker, bytecode dump,
  VM, Bash dependency scans, and free paths traverse every stage.

Parser requirements:

- parse `|` as a pipeline separator only inside command syntax and captured
  `run` syntax;
- keep `|>` and `|>>` as redirection tokens, not `|` plus `>`;
- do not allow `|` as an expression operator;
- do not regress `case` alternative parsing from `v0.17.0`;
- produce clear diagnostics for leading/trailing/repeated pipes;
- produce clear diagnostics for logical operators or unsupported adjacent shell
  syntax.

## Lowering and validation requirements

Lowering must validate pipeline shape before VM execution or Bash emission:

- no empty stages;
- no redirection inside captured `run` pipelines;
- no mid-pipeline redirection;
- each stage command word must pass existing command-word validation;
- interpolation expressions inside all stages must be valid and lowered;
- diagnostic spans should point to the invalid pipe/operator/stage when
  possible;
- recovered errors must not produce partially executable HIR.

## Formatter and checker behavior

`ds check` must accept supported pipelines and reject unsupported forms without
executing commands.

`ds fmt` must format pipelines deterministically while preserving the existing
comment-safety rule:

```ds
cat access.log | grep "ERROR" | sort
let result = run cat access.log | grep "ERROR"
```

Minimum formatting requirements:

- keep simple pipelines on one line;
- normalize spaces around `|`;
- normalize spaces before whole-pipeline redirection suffixes;
- format captured `run` pipelines consistently with command pipelines;
- keep rejecting comment-bearing files until comment-preserving formatting is
  implemented.

Multi-line pipeline formatting can remain deferred unless the implementation
adds explicit continuation syntax. The formatter should not invent unsupported
line-continuation behavior.

## Diagnostics

Diagnostics should be stable enough for tests to assert fragments. Required
cases include:

- missing command before `|`;
- missing command after `|`;
- repeated `||` / logical OR unsupported;
- `&&` unsupported;
- redirection before a later pipeline stage;
- captured `run` redirection remains unsupported;
- pipeline used in an expression position;
- command stage with invalid interpolation;
- failure to create OS pipes/fork/wait where practical to surface.

Old diagnostic text saying `pipelines are not supported in v0.7.0` must be
removed or limited to tests for older snapshots. Current `v0.18.0` diagnostics
should describe the specific invalid pipeline shape instead.

## Examples

Add or update at least one production example, such as
`examples/pipeline.ds`, covering:

```ds
script {
  arg log: string
}

let errors = run cat $log | grep "ERROR" | sort
if errors.ok {

```

fixture commands rather than depending on host-specific logs.

## Acceptance criteria

`v0.18.0` is complete only when:

- plain command pipelines parse, check, run in VM mode, and emit standalone Bash;
- captured `run` pipelines parse, check, run in VM mode, and emit standalone
  Bash;
- VM and emitted Bash agree on stdout, stderr, exit status, side effects, and
  command-result fields for deterministic fixtures;
- pipefail-style status is implemented and tested in both backends;
- existing redirection suffixes apply to whole plain pipelines and remain
  rejected for captured `run` pipelines;
- parser/lowerer diagnostics reject malformed or out-of-scope pipeline syntax
  before partial execution;
- `case` alternatives from `v0.17.0` still work and are not confused with
  command pipelines;
- command tracing behavior remains observational;
- generated Bash contains no dependency on `ds`;
- formatter/checker support the new syntax without executing commands;
- docs, examples, and status files match the implemented behavior;
- the test plan in `docs/milestones/v0.18.0-test-plan.md` is implemented or
  explicitly amended;
- the completion review below is filled in.

## Deferred items

Carry these forward unless deliberately re-scoped later:

- logical command operators `&&` and `||`;
- pipeline grouping/subshells;
- background/async pipelines;
- process substitution;
- here-documents/here-strings;
- per-stage redirection;
- pipeline expressions outside command and captured `run` syntax;
- structured pipeline status arrays;
- multi-line pipeline continuation syntax;
- Windows shell backend semantics.

## Implementation review

Implementation is complete for the scoped feature surface; tests must still be
added from `v0.18.0-test-plan.md` in the next pass.

- Implementation summary: command ownership was promoted to a stage-aware
  `DsCommand` model shared by AST, HIR, formatter, checker, bytecode, VM, and
  Bash emission. Plain command pipelines and captured `run` pipelines now parse,
  lower, execute, and emit Bash.
- VM behavior confirmed: the VM expands each stage, creates OS pipes, forks all
  stages, closes unused file descriptors, waits for all children, and computes
  rightmost-failing-stage pipefail status.
- Whole-pipeline redirection confirmed: stdout redirection targets final-stage
  stdout, stderr redirection applies to every stage, and combined redirection
  captures final-stage stdout plus every stage stderr in both VM and emitted
  Bash.
- Bash emission behavior confirmed: plain pipelines emit as standalone Bash
  pipelines under `set -euo pipefail`; captured pipelines now emit structured
  staged argv directly into a capture block, avoiding `eval` while preserving
  standalone Bash behavior.
- Pipefail/capture semantics confirmed: captured pipelines expose final-stage
  stdout, observed stage stderr, `code`, `ok`, and `failed`.
- Formatter/checker behavior confirmed: `ds fmt` normalizes spaces around `|`
  for simple one-line pipelines and `ds check` accepts supported pipelines
  without executing commands.
- Docs/examples updated: README, status, language, runtime, architecture,
  changelog, and `examples/pipeline.ds` were updated.
- Deferred items carried forward: logical `&&`/`||`, grouping/subshells,
  background pipelines, process substitution, here-documents/here-strings,
  per-stage redirection, pipeline expressions outside command syntax, structured
  per-stage status arrays, multiline pipeline continuation syntax, and Windows
  shell semantics.
- Known debt for `v0.19.0` / `v0.20.0`: the next pass must implement the
  comprehensive v0.18 test suite. Captured pipeline Bash emission has already
  been tightened away from `eval` by emitting structured staged pipelines inside
  capture blocks.
