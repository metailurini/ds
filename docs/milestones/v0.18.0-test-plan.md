# v0.18.0 Test Plan — Pipelines

## Status

Implemented in `tests/v0_18/run.sh`.

## Purpose

Verify that `v0.18.0` adds shell-native pipelines without weakening the VM/Bash
parity contract or pulling in broader shell grammar.

The core signal:

```txt
plain and captured pipelines parse and lower
VM and emitted Bash execute pipelines with pipefail semantics
captured run pipelines expose the existing command-result fields
redirection applies only to whole plain pipelines
unsupported shell-adjacent syntax remains rejected
```

## Scope under test

Covered:

- plain command pipelines with two or more stages;
- captured `run` pipelines with two or more stages;
- pipeline status using pipefail-style rightmost-failing-stage rules;
- stdout/stderr behavior for plain and captured pipelines;
- whole-pipeline redirection suffixes for plain pipelines;
- parser, AST, HIR, bytecode, VM, Bash, formatter, checker, imports, functions,
  script blocks, test blocks, and tracing behavior for pipelines;
- docs/status/example consistency;
- regression coverage for `case` alternatives from `v0.17.0`;
- negative coverage for unsupported adjacent shell syntax.

Not covered as supported behavior:

- `&&` and `||` logical operators;
- background pipelines;
- process substitution;
- here-documents/here-strings;
- grouping/subshells;
- per-stage redirection;
- captured `run` redirection;
- pipeline expressions outside command syntax;
- multiline continuation syntax;
- Windows shell behavior.

## Test entrypoint

Add a new executable suite:

```sh
tests/v0_18/run.sh
```

and wire it into the Makefile:

```sh
make test-v0-18
make test
make asan
make ubsan
```

The suite should primarily test public CLI behavior. Static checks are allowed
for Makefile/docs/source-boundary contracts that are not directly observable
through CLI output.

## Test conventions

- Create all temporary `.ds` files, input files, generated Bash files, fake
  commands, stdout/stderr captures, and side-effect files under the suite temp
  directory.
- Use fake commands where host command differences could make output unstable.
- Compare stdout, stderr, and exit status separately.
- Normalize temp paths in diagnostics before comparing.
- Run `bash -n` before executing emitted Bash.
- Execute emitted Bash without `ds` in `PATH` unless a fixture intentionally
  tests a user command named `ds`.
- For VM/Bash parity, run VM and emitted Bash from isolated temp directories so
  side effects cannot leak between backends.
- Avoid wall-clock timing and large data volume assertions.
- Prefer stable diagnostic fragments over exact full diagnostic prose unless the
  exact wording is central to the feature.

## Static and build wiring tests

### Makefile target wiring

Assertions:

- `TEST_VERSIONS` contains `0-18` exactly once and after `0-17`;
- `make test-v0-18` invokes `tests/v0_18/run.sh`;
- aggregate `make test` includes the new suite;
- `make asan` and `make ubsan` include the new suite or aggregate target that
  includes it;
- every new source file is included in normal, ASAN, and UBSAN builds;
- `make clean all` succeeds.

### Source-boundary checks

Assertions:

- command pipeline representation lives behind the project command/HIR/runtime
  boundaries and does not expose Bash-specific state to frontend callers;
- clone/free paths visit every pipeline stage;
- AST printer, HIR printer, bytecode dumper, formatter, checker, VM compiler,
  Bash dependency scanner, and Bash statement/expression emitters explicitly
  handle pipeline-aware command structures;
- every switch over statement/expression/command kinds handles new pipeline data
  explicitly or uses a shared command traversal helper;
- generated Bash for representative fixtures contains no `ds` runtime
  dependency;
- no new source path reintroduces stale `libs/hashmap` references or raw hashmap
  exposure.

## Documentation and examples tests

### Milestone/status docs

Assertions:

- `docs/milestones/v0.18.0-spec.md` and this test plan exist;
- `docs/status.md` moves pipelines out of the deferred list after
  implementation;
- `README.md` project status mentions `v0.18.0` only after implementation/tests
  complete;
- `docs/language.ds` marks pipelines as implemented in `v0.18.0`;
- docs still list logical operators, process substitution, per-stage
  redirection, async/background pipelines, heredocs, and regex/string methods as
  deferred or out of scope where applicable;
- no current docs claim plain or captured pipelines are unsupported after
  implementation, except historical milestone text.

### Examples

For every `examples/*.ds` file:

- `./ds check <example>` succeeds unless intentionally invalid;
- intentionally invalid examples keep stable diagnostic fragments;
- production examples run in VM mode with documented args;
- production examples emit Bash, pass `bash -n`, and match VM behavior where
  deterministic;
- test examples run with `./ds test` when they contain tests;
- normal run and emitted Bash ignore test blocks.

If `examples/pipeline.ds` is added, assert it covers:

- a plain pipeline;
- a captured `run` pipeline;
- command-result field access from a captured pipeline;
- pipefail behavior that is documented rather than surprising;
- VM/Bash parity using deterministic temp files or fake commands.

## Lexer/parser/token tests

### Token coverage

Fixture:

```ds
cat input.txt | grep "ERROR" | sort
let result = run cat input.txt | grep "ERROR"
cat input.txt |> "copy.txt"
```

Assertions:

- `tokens` emits a distinct/stable token for command pipeline `|` if the lexer
  exposes token names;
- `|>` and `|>>` remain redirection tokens and are not tokenized as pipeline
  plus greater-than;
- `case` alternatives from `v0.17.0` still tokenize/parse correctly;
- unsupported `||` and `&&` are diagnosed rather than silently split into pipes
  or command words.

### Parser acceptance

Fixtures/assertions:

- two-stage plain pipeline checks successfully;
- three-stage plain pipeline checks successfully;
- two-stage captured `run` pipeline checks successfully;
- three-stage captured `run` pipeline checks successfully;
- command interpolation inside stages checks successfully;
- pipelines inside `if`, `while`, `for`, functions, imports, script blocks, and
  test blocks parse successfully where the surrounding construct is supported;
- whole-pipeline redirection suffix checks successfully for plain pipelines.

### Parser rejection

Fixtures/assertions:

- `| grep x` fails with missing command before pipe;
- `echo x |` fails with missing command after pipe;
- `echo x || grep x` fails with logical OR unsupported or missing stage in a
  clear way;
- `echo x && grep x` fails with logical AND unsupported;
- `echo x | | grep x` fails with missing command between pipes;
- `let x = echo a | grep a` fails because pipeline is not an expression;
- `if run echo a | grep a { ... }` fails unless the language already supports
  command-result truthiness in conditions with clear semantics;
- `let r = run echo a |> "out.txt"` still fails because captured redirection is
  out of scope;
- `echo a |> "out.txt" | grep a` fails because redirection cannot be mid-
  pipeline.

## AST, HIR, and bytecode tests

### AST coverage

Assertions:

- `ast` prints a deterministic pipeline structure for plain command pipelines;
- `ast` prints a deterministic pipeline structure for captured `run` pipelines;
- each stage appears in source order;
- whole-pipeline redirection appears once and after the stages;
- output contains no pointer addresses or nondeterministic temp IDs.

### HIR coverage

Assertions:

- `hir` contains pipeline-aware command data for plain pipelines;
- `hir` contains pipeline-aware command data for captured `run` pipelines;
- imported pipeline statements appear in composed order;
- pipeline statements in test blocks are visible in test-aware paths and ignored
  by normal run/emission according to existing rules;
- malformed pipelines never produce executable HIR.

### Bytecode coverage

Assertions:

- `bytecode` for a plain pipeline includes a pipeline command instruction or an
  equivalent command instruction that visibly contains multiple stages;
- `bytecode` for captured `run` pipeline assigns a command-result value;
- stage order is deterministic;
- redirection metadata is attached to the whole pipeline, not intermediate
  stages.

## VM behavior tests

### Plain pipeline success

Fixture:

```ds
printf "b\na\n" | sort
```

Assertions:

- direct execution and `ds run` succeed;
- stdout is sorted exactly;
- stderr is empty;
- emitted Bash matches VM output/status.

Use fake commands if relying on system `printf`/`sort` behavior is unstable in
the test environment.

### Plain pipeline failure and pipefail

Fixtures/assertions:

- `false | true` exits non-zero in VM and Bash;
- `true | false | true` exits with the rightmost failing stage status rather
  than zero;
- when a fake middle stage exits `7` and a later stage exits `0`, the pipeline
  status is `7`;
- when multiple stages fail, the status is the rightmost failing status;
- plain pipeline failure stops later statements in normal execution.

### Captured pipeline success

Fixture:

```ds
let result = run printf "b\na\n" | sort
echo "ok={result.ok}"
echo "code={result.code}"
echo result.stdout
```

Assertions:

- script exit status is zero;
- `ok=true`, `failed=false`, and `code=0`;
- stdout contains final-stage stdout only;
- VM and Bash output/status match.

### Captured pipeline failure

Fixtures/assertions:

- `let result = run false | true` does not stop script execution;
- result status follows pipefail and is non-zero;
- `result.failed` is true and `result.ok` is false;
- stdout from later successful stages is captured according to actual pipeline
  behavior, but status still reflects failure;
- VM and Bash agree on stdout/stderr/status fields for deterministic fake
  stages.

### Stderr capture

Fixtures/assertions:

- a fake first stage writing stderr and stdout pipes stdout to the second stage;
- captured result stderr includes stderr from the first stage;
- a fake later stage writing stderr is included too;
- VM and Bash stderr ordering is asserted only where deterministic; otherwise
  assert inclusion of expected fragments.

### Large-stream smoke

Fixture/assertion:

- pass enough lines through a two-stage pipeline to prove the VM implementation
  does not deadlock by buffering an entire stage before starting the next stage;
- keep data volume modest so the test remains fast.

## Bash emission tests

### Plain pipeline rendering

Assertions:

- generated Bash includes the expected `cmd | cmd` structure;
- generated Bash passes `bash -n`;
- generated Bash has no call to `ds`;
- `set -euo pipefail` remains present;
- generated Bash output/status matches VM for deterministic fixtures.

### Captured pipeline rendering

Assertions:

- generated Bash captures stdout, stderr, and pipefail status correctly;
- helper functions are embedded only when needed and use the `__ds_` prefix;
- helper code is standalone Bash;
- captured success/failure fixtures match VM command-result fields.

### Redirection rendering

Fixtures/assertions:

- `echo hello | cat |> "out.txt"` writes stdout to the target file;
- `echo hello | cat |>> "out.txt"` appends;
- fake stderr pipeline with `!>` writes stderr to the target file;
- fake mixed-output pipeline with `&>` writes both streams to the target file;
- VM and Bash side-effect files match exactly.

## Formatter and checker tests

### Checker non-execution

Fixture:

```ds
missing_command_that_should_not_run | also_missing
```

Assertions:

- `ds check` succeeds if syntax is valid even though commands do not exist;
- no side-effect files are created;
- unsupported malformed pipelines fail during check before execution.

### Formatter support

Fixtures/assertions:

- `echo a|grep a` formats to `echo a | grep a` or equivalent canonical spacing;
- `let r=run echo a|grep a` formats with canonical assignment/run/pipeline
  spacing;
- whole-pipeline redirection spacing is normalized;
- formatted output re-checks successfully;
- formatting remains idempotent;
- comment-bearing files with pipelines are still rejected with the existing
  comment-preservation diagnostic.

## Import/function/script/test integration tests

### Imports

Assertions:

- imported file containing a pipeline is composed and executed in VM mode;
- emitted Bash contains imported pipeline behavior in composed order;
- duplicate imports with pipelines obey existing import rules;
- diagnostics from malformed imported pipelines point at the imported file.

### Functions

Assertions:

- a function body can contain a plain pipeline;
- a function body can capture a pipeline with `run`;
- calling the function in VM and Bash produces matching output/status;
- malformed pipelines inside functions fail at check time before any function is
  called.

### Script args

Assertions:

- script args can be interpolated into pipeline stage command words;
- VM and Bash behavior match for deterministic arg values;
- generated Bash help/arg parsing behavior is unchanged.

### Test blocks

Assertions:

- `ds test` can execute a test block containing a successful pipeline;
- failing plain pipeline inside a test block fails that test without crashing the
  runner;
- captured failing pipeline inside a test can assert/print result fields and
  continue;
- normal `ds run` and emitted Bash ignore test blocks as before.

## Case/regression tests

`v0.17.0` uses `|` inside `case` arms for alternatives. Pipelines must not break
that grammar.

Fixtures/assertions:

```ds
let lang = "sh"
case lang {
  "bash" | "sh" { echo "shell" }
  _ { echo "other" }
}
```

- `check`, `run`, `emit bash`, and emitted Bash still succeed;
- AST/HIR distinguish case alternatives from command pipelines;
- malformed case alternatives still get case diagnostics, not pipeline
  diagnostics.

## Diagnostics edge cases

Assertions should check stable fragments for:

- missing stage before pipe;
- missing stage after pipe;
- repeated pipes;
- unsupported `||`;
- unsupported `&&`;
- captured `run` redirection;
- mid-pipeline redirection;
- pipeline in expression position;
- invalid interpolation inside a stage;
- command failure trace source markers for a plain pipeline.

## Sanitizer and resource tests

Under ASAN/UBSAN builds, run a focused subset that includes:

- successful plain pipeline;
- successful captured pipeline;
- captured failing pipeline;
- whole-pipeline redirection;
- malformed pipeline diagnostics;
- import/function/test integration fixture.

Assertions:

- no sanitizer reports;
- no obvious file descriptor leaks in repeated small pipeline loops where the
  test environment can observe them;
- repeated captured pipelines free command-result strings/stderr buffers.

## Manual smoke tests

After automated tests pass, manually run or script these smoke checks:

```sh
make clean all
make check
make test-v0-18
make test
make asan
make ubsan

./ds check examples/pipeline.ds
./ds run examples/pipeline.ds <fixture args>
./ds emit bash examples/pipeline.ds -o /tmp/pipeline.sh
bash -n /tmp/pipeline.sh
bash /tmp/pipeline.sh <fixture args>
```

Also inspect one emitted Bash file to confirm:

- it is readable;
- it contains no dependency on `ds`;
- helper functions, if any, use the `__ds_` prefix;
- pipefail behavior is visible or otherwise explained by the strict-mode header.

## Completion checklist

Before closing `v0.18.0`:

- all acceptance criteria in the spec are satisfied;
- this test plan is implemented or deliberately amended;
- VM/Bash parity passes for deterministic pipeline fixtures;
- docs/status/examples match implemented behavior;
- `docs/milestones/v0.18.0-spec.md` completion review is filled in;
- deferred shell features are recorded for later versions;
- known technical debt is recorded for `v0.19.0` or `v0.20.0`.
