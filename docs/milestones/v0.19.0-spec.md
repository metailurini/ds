# v0.19.0 Spec — String Library and Formatted Output

## Status

Implementation complete; tests are intentionally deferred to the follow-up test-plan pass.

`v0.19.0` continues the second post-cleanup feature wave. Its job is to make
ordinary text processing pleasant enough for shell scripts without adding a
separate formatting command, a full regex engine, or a new numeric model.

## Goal

Add practical string operations and interpolation formatting that work the same
way in direct VM execution and in emitted standalone Bash:

```ds
let raw = "  Hello, ds  "
let name = raw.trim().lower().replace("hello", "hi")

if name.contains("ds") {
  echo "contains ds"
}

let parts = "api,web,worker".split(",")
for part in parts {
  echo "service={part:upper}"
}

let port = 5432
echo "port={port:05d}"
echo "name={name:<12}done"

let body = """
line one
line two
"""
echo "{body}"
```

The project rules still apply:

```txt
every supported string operation runs in the VM
every supported string operation emits standalone Bash
VM and emitted Bash behavior match for stdout, stderr, exit status, and side effects
unsupported/deferred string and formatting forms fail clearly before partial execution/emission
generated Bash must not call ds
```

## Motivation

By `v0.18.0`, `ds` has the core shell execution surface: imports, script args,
functions, arrays/maps, array loops, standard-library helpers, command capture,
redirection, tracing, tests, formatting/checking, control flow, and pipelines.
The next common scripting need is text manipulation:

- trim command output before using it in messages or comparisons;
- normalize case for options and environment values;
- test string prefixes/suffixes/substrings;
- replace small literal fragments;
- split delimited command output into arrays for existing `for` loops;
- align or pad output without dropping into Bash `printf`;
- write multi-line messages/config fragments without awkward `\n` chains.

This milestone keeps the feature set deliberately boring and shell-portable. It
should make everyday scripts easier without turning `ds` into Python, adding a
regex engine, or making `echo` a hidden `printf` wrapper.

## Non-goals

This version does not include:

- regex-based string methods or regex literals;
- locale-aware case conversion;
- Unicode grapheme/normalization semantics beyond byte-oriented UTF-8 text
  preservation;
- binary strings or strings containing embedded NUL bytes;
- arbitrary Python/Rust/printf format strings;
- a standalone `printf`, `fmt`, or `format` built-in;
- string interpolation of arbitrary expressions beyond the syntax explicitly
  listed below;
- shell parameter expansion syntax exposed to users;
- heredocs, here-strings, or command-input redirection;
- raw strings;
- escape-sequence redesign beyond what is necessary for triple-quoted strings;
- floating-point arithmetic or a general float value type;
- decimal numeric literals unless they already exist before this milestone;
- arithmetic operators from `v0.21.0`;
- function return values from `v0.21.0`;
- maps or arrays converted implicitly to command arguments;
- streaming split/lines semantics beyond the existing `lines` helper;
- formatter comment/trivia preservation from the `v0.16.0` deferral.

If a formatting or string helper needs a broader type system, regex, locale, or
floating-point semantics, defer it rather than approximating behavior that cannot
be emitted to Bash reliably.

## Syntax and user-facing behavior

### String method calls

`v0.19.0` adds expression-level methods on string values:

```ds
let s = "  Hello, World!  "

let trimmed = s.trim()
let upper = s.upper()
let lower = s.lower()
let replaced = s.replace("World", "ds")
let has_world = s.contains("World")
let parts = s.split(", ")
let starts = s.starts_with("  Hello")
let ends = s.ends_with("!  ")
```

Supported methods:

| Method | Result | Notes |
| --- | --- | --- |
| `value.trim()` | string | Remove leading and trailing ASCII whitespace. |
| `value.upper()` | string | ASCII uppercase transform. |
| `value.lower()` | string | ASCII lowercase transform. |
| `value.replace(from, to)` | string | Literal global replacement. |
| `value.contains(sub)` | bool | Literal substring test. |
| `value.split(sep)` | array<string> | Literal separator split. |
| `value.starts_with(pre)` | bool | Literal prefix test. |
| `value.ends_with(suf)` | bool | Literal suffix test. |

Method receivers may be:

- string literals;
- string variables;
- string-valued field accesses such as `result.stdout` and `result.stderr`;
- string-valued method chains;
- parenthesized string expressions where the parser already supports them.

Examples:

```ds
let result = run git branch --show-current
let branch = result.stdout.trim()

if branch.starts_with("release/") {
  echo "release branch"
}
```

### Method arity and type rules

Required arity:

```txt
trim()             0 args
upper()            0 args
lower()            0 args
replace(from, to)  2 args
contains(sub)      1 arg
split(sep)         1 arg
starts_with(pre)   1 arg
ends_with(suf)     1 arg
```

Rules:

- method names are exact and case-sensitive;
- arguments must be string values or values that the current language already
  treats as strings in expression contexts;
- `split` with an empty separator is rejected in `v0.19.0`;
- `replace` with an empty `from` string is rejected in `v0.19.0`;
- methods on arrays, maps, command-result objects, booleans, null, or integers
  are rejected unless the receiver is first converted through an explicitly
  supported string path;
- `contains`, `starts_with`, and `ends_with` are booleans and may be used in
  `if`, `while`, `case` arm expressions only where booleans are already allowed;
- `split` returns an array of strings and may be used with existing array
  indexing and `for item in parts` loops.

### Chaining

String methods may chain when each method returns a string:

```ds
let normalized = raw.trim().lower().replace(" ", "-")
```

Boolean-returning methods and `split` end the chain unless a later milestone
adds methods for booleans or arrays:

```ds
raw.trim().contains("x")      # supported
raw.contains("x").trim()      # rejected
raw.split(",").trim()         # rejected
```

### Interpolation format specifiers

`v0.19.0` extends string interpolation from `{name}` / `{name.field}` to a small
portable formatting subset:

```ds
let port = 5432
let label = "api"
let ok = true

echo "{port:05d}"
echo "{label:<10}done"
echo "{label:>10}"
echo "{label:^10}"
echo "{ok}"
echo "{label:upper}"
echo "{label:lower}"
echo "{label:trim}"
```

Supported specifier groups:

| Specifier | Meaning |
| --- | --- |
| `:upper` | ASCII uppercase string transform. |
| `:lower` | ASCII lowercase string transform. |
| `:trim` | ASCII leading/trailing trim. |
| `:<N` | Left-align string in width `N`. |
| `:>N` | Right-align string in width `N`. |
| `:^N` | Center-align string in width `N`. |
| `:0Nd` | Zero-pad signed integer to width `N`. |
| `:Nd` | Space-pad signed integer to width `N`. |
| `:.Pf` | Fixed decimal rendering for integer values as `value.00...` with precision `P`. |
| `:N.Pf` | Width plus fixed decimal precision for integer values. |

Because the language does not yet have a stable float value type, `f` formatting
in this milestone is intentionally narrow: it formats existing integer values as
fixed decimals with the requested precision. Decimal literals and floating-point
arithmetic remain deferred until the numeric model is deliberately expanded.

Rules:

- formatting applies only inside interpolated strings;
- the interpolation target remains a variable or field access, matching the
  current interpolation model;
- named transforms apply to string values;
- integer format specifiers apply to integer values;
- applying a string transform to an integer or an integer format to a string is
  rejected before execution/emission;
- applying a string transform or numeric format to an unknown-kind value, such
  as an untyped function parameter, is rejected before execution/emission so the
  VM cannot runtime-check one behavior while Bash coerces the shell string into
  another;
- negative integer padding follows the sign-aware form (`-003` for width 4);
- unsupported specifiers are rejected with a diagnostic that names the bad
  specifier and the supported subset;
- width and precision must be small positive decimal numbers within a documented
  implementation limit; start with `1..1024` unless implementation evidence
  supports a wider bound;
- width smaller than the rendered value does not truncate.

### Multi-line string literals

`v0.19.0` adds triple-quoted string literals:

```ds
let body = """
line one
line two
"""
```

Rules:

- triple-quoted literals preserve internal newlines exactly;
- interpolation is supported inside triple-quoted strings using the same syntax
  and format specifiers as normal strings;
- the opening delimiter is `"""` and the closing delimiter is the next `"""`;
- no heredoc marker syntax is added;
- embedded NUL bytes are rejected consistently with the existing text-file
  helper policy;
- escaping rules should match normal strings where practical, but do not add a
  new raw-string mode in this milestone;
- formatter output must preserve the multi-line body without changing text
  content.

The implementation must document the exact newline rule chosen. Preferred rule:
all bytes between the opening delimiter and closing delimiter are the literal
content. Do not secretly strip indentation unless the spec and tests are amended
before implementation.

## Parser and AST requirements

The parser must represent string methods and interpolation formatting without
leaking Bash-specific implementation details into the frontend.

Required frontend work:

- parse method calls on expression receivers, not only bare function calls;
- distinguish field access (`result.stdout`) from method calls (`s.trim()`);
- parse method chains left-to-right;
- parse string literals that may span multiple lines for triple quotes;
- retain enough string token/source information for formatter and diagnostics;
- extend interpolation validation to understand optional `:specifier` suffixes;
- keep existing command-mode `$name` argument syntax separate from normal
  expression and interpolation syntax;
- AST printer/debug output must expose enough information to diagnose method
  chains and triple-quoted strings.

Do not parse `name:specifier` as a type annotation inside strings. The colon has
meaning only inside interpolation braces.

## Lowering and semantic requirements

Lowering must validate string operations before VM execution or Bash emission:

- receiver kind and method name;
- method arity;
- method argument value categories;
- unsupported empty separator/replacement source rules;
- return type of each method for use by later expression contexts;
- interpolation variable/field existence;
- interpolation format specifier validity;
- format type compatibility;
- triple-quoted string text validity;
- unsupported method calls on command-result objects except field access first.

If the current type model is too shallow to prove compatibility statically in
all cases, the implementation may generate runtime checks, but unsupported forms
must still fail consistently in VM and emitted Bash with clear diagnostics or
runtime errors.

## VM behavior

The VM must implement string methods using project-owned runtime logic:

- no shelling out to `tr`, `sed`, `awk`, `cut`, `printf`, or similar tools for
  VM behavior;
- preserve existing `DsValue` ownership rules;
- allocate returned strings and arrays through existing runtime helpers;
- avoid leaking temporary values during chained method evaluation;
- handle empty strings, separators at boundaries, repeated separators, and
  no-match replacement cases;
- return booleans for predicate methods;
- return arrays from `split` compatible with existing array loops and indexing;
- format interpolation in VM mode with the same behavior as emitted Bash;
- report memory allocation failures through the existing diagnostic style where
  practical.

`split` result rules:

```txt
"a,b".split(",")       -> ["a", "b"]
"a,".split(",")        -> ["a", ""]
",a".split(",")        -> ["", "a"]
"a,,b".split(",")      -> ["a", "", "b"]
"abc".split(",")       -> ["abc"]
"".split(",")          -> [""]
```

## Bash emission behavior

Generated Bash must remain standalone and must not call `ds`.

Bash emission may use generated helper functions for string operations and
formatting. Requirements:

- helpers must be emitted only when needed;
- helper names must use the existing generated helper naming convention;
- helpers must avoid non-portable dependencies where practical;
- if Bash built-ins such as parameter expansion or `printf` are used inside the
  generated script, behavior must match the VM for supported ASCII cases;
- generated scripts must pass `bash -n`;
- emitted Bash must preserve stdout/stderr/status behavior;
- emitted Bash must not invoke project source files or runtime artifacts;
- helper emission must compose correctly with imports, functions, scripts, test
  blocks, pipelines, command-result capture, and existing stdlib helpers.

Using Bash `printf` inside generated Bash is allowed as an implementation
detail for formatting because the user-facing language still exposes formatting
only through interpolation. Adding a user-facing `printf` command or function is
not allowed.

## Formatter and checker behavior

### Checker

`ds check` must accept supported string methods, format specifiers, and
triple-quoted strings without executing commands or mutating files.

It must reject unsupported forms such as:

```ds
let x = "a".regex_replace("a", "b")
let x = "a".split("")
let x = 123.trim()
echo "{name:unknown}"
echo "{label:05d}"
```

### Formatter

`ds fmt` must format new syntax deterministically while preserving the existing
comment rejection behavior from `v0.16.0`.

Rules:

- method chains use no extra space before `.` or `(`;
- method arguments use normal expression-list formatting;
- interpolation text is preserved exactly except for surrounding source string
  literal normalization already performed by the formatter;
- triple-quoted string bodies are preserved exactly;
- formatting must be idempotent;
- formatter must not execute commands, read imports beyond current root-file
  formatting policy, or mutate files in `--check` mode.

## Import, function, script, pipeline, and test integration

String features must work in:

- imported files and root files;
- function bodies;
- script argument defaults and script-derived variables where already allowed;
- `if`, `while`, `case`, and loop bodies;
- command arguments through interpolation and `$name` variables;
- captured `run` result processing;
- plain command pipelines and captured run pipelines from `v0.18.0`;
- `test` blocks and `assert` expressions.

Imported helper emission must stay deduplicated. A string helper used in an
imported file and a root file should appear once in emitted Bash.

## Diagnostics

Diagnostics should be specific enough to guide the user:

- unknown string method: mention the method and supported methods;
- wrong arity: mention expected and actual argument counts;
- bad receiver: mention that the method requires a string receiver;
- `split("")`: mention that empty separators are deferred/unsupported;
- `replace("", to)`: mention that empty replacement sources are unsupported;
- bad interpolation specifier: mention the specifier and the supported subset;
- incompatible format type: mention the value/category and specifier;
- unterminated triple-quoted string: point at the opening delimiter;
- NUL in string literal: reject consistently with text helper policy.

Do not silently treat unsupported syntax as command words, Bash fragments, or
raw text.

## Acceptance criteria

`v0.19.0` is complete when:

- supported string methods parse, lower, run in VM mode, and emit standalone
  Bash;
- supported interpolation specifiers parse, validate, run in VM mode, and emit
  standalone Bash;
- triple-quoted strings parse, run, format, and emit Bash with preserved content;
- VM and emitted Bash behavior match for deterministic fixtures;
- `split` results work with existing array loops and indexing;
- unsupported string methods, bad arity, bad receivers, unsupported format
  specifiers, and malformed triple-quoted strings fail clearly;
- `ds check` accepts/rejects all scoped forms without executing user commands;
- `ds fmt` is deterministic and idempotent for new syntax;
- generated Bash contains no `ds` runtime dependency;
- imports, functions, scripts, pipelines, and tests compose with the new string
  features;
- docs and examples reflect the implemented syntax;
- the `v0.19.0` test plan is implemented or deliberately amended;
- completion review below is filled in.

## Deferred items and technical debt

Carry these forward unless the spec is deliberately amended:

- regex methods and regex literals;
- locale/Unicode-aware case conversion;
- raw strings;
- heredocs/here-strings;
- a general float value type and decimal numeric literals;
- full printf/Python/Rust format grammar;
- collection formatting/pretty-printing;
- formatter comment preservation;
- binary string/file APIs;
- streaming string operations for very large command output.

## Completion review

- Implementation summary: Added method-call parsing for expression receivers, string helper lowering through the shared helper-call path, VM string helpers, standalone Bash helper emission, formatted interpolation, and triple-quoted literals.
- VM/Bash parity notes: Supported string helpers and interpolation specifiers run in the VM and emit standalone Bash. `split` returns arrays that compose with existing `for` loops and indexing. Generated Bash may use Bash built-ins and `printf` internally, but does not call `ds`.
- Formatter/checker notes: `ds check` validates string helper receiver/arity, empty `split` separators, empty `replace` sources, scoped interpolation specifiers, `1..1024` width/precision bounds, and known value-kind compatibility before execution/emission. Unknown-kind string helpers or formatted interpolation are rejected to preserve VM/Bash parity until typed function parameters or hidden runtime type tags are introduced. The existing formatter can preserve triple-quoted literal token text and keeps the v0.16.0 comment rejection behavior.
- Docs/examples updates: Added `examples/strings.ds` and updated README, status, language, runtime, architecture, and changelog docs.
- Test plan execution summary: Not executed in this implementation-only pass; `docs/milestones/v0.19.0-test-plan.md` remains the source of truth for the next test pass.
- Deferred items: No additional in-scope feature was intentionally deferred beyond the items already listed in this spec.
- Known technical debt: String methods currently share the stdlib helper-call representation internally (`string.trim` etc.), and Bash interpolation width/format emission relies on `printf` inside generated Bash. Unknown-kind string operations are conservatively rejected instead of runtime-checked in emitted Bash because Bash command arguments erase value kinds. This is acceptable for v0.19.0 but should be covered heavily by the v0.19 test suite.
- Follow-up notes for `v0.20.0` cleanup: Consider a first-class HIR node for method calls if more receiver-based APIs are added, and reconsider hidden type-tag propagation for user-function parameters if the language should support formatted string operations directly on untyped parameters before full typed functions.
