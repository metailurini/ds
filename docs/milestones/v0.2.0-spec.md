# v0.2.0 Spec — Basic Bash Emitter

## Status

Implementation complete. Tests have not been added yet.

## Goal

Add the first Bash emission backend.

This version should convert the `v0.1.0` language subset into standalone Bash.

`v0.2.0` proves one of the most important project principles early: every supported feature should be able to emit to Bash.

## Motivation

Bash emission is not an optional export feature. It is part of the identity of `ds`.

By implementing the Bash emitter before the VM, the project confirms that the language syntax is Bash-emittable by construction.

This milestone also creates an early backend that can be used for behavior smoke tests before the bytecode VM exists.

This version should keep `docs/language.ds` aligned with any syntax decisions made while implementing Bash emission. Bash emission may reveal syntax that is readable in `ds` but difficult to emit safely; those decisions should be reflected in the syntax catalog.

## Non-goals

This version does not include:

- bytecode VM;
- direct script execution through VM;
- imports;
- functions;
- loops;
- arrays;
- maps;
- CLI argument blocks;
- command result capture;
- advanced redirection syntax;
- standard library;
- formatter;
- generated Bash optimization.

The emitter should support only the `v0.1.0` language subset.

## User-facing command

Add:

```sh
ds emit bash <file.ds> -o <file.sh>
```

Suggested behavior:

- parse and validate input file;
- emit Bash to output path;
- exit `0` on success;
- exit non-zero on parse/emission error;
- fail clearly if output path is missing.

Optional shorthand can be delayed.

## Supported input subset

The Bash emitter should support:

- comments where useful as source comments;
- `let` variables;
- string literals;
- integer literals;
- boolean literals;
- basic string interpolation;
- `if` statements;
- `if` / `else` statements;
- command statements.

Unsupported syntax should fail clearly.

## Generated Bash requirements

Generated Bash must:

- be standalone;
- start with a Bash shebang;
- use a strict header;
- emit safe variable names;
- quote string values safely;
- emit command statements as shell commands;
- emit `if` statements using Bash condition syntax;
- include source comments where useful;
- be accepted by `bash -n`.

Suggested header:

```bash
#!/usr/bin/env bash
set -euo pipefail
```

Generated Bash should not require `ds` at runtime.

Generated Bash also must not require the C runtime substrate used internally by the `ds` tool. The Bash emitter may use internal C helpers such as `DsString` while generating output, but the produced `.sh` file must contain only Bash code and embedded Bash helper functions.

`docs/language.ds` remains a catalog only and is not expected to emit fully to Bash until the whole language surface becomes real over later versions.

This distinction is important:

- the `ds` tool may use C runtime primitives while parsing and emitting;
- emitted Bash must remain independent and standalone;
- runtime-backed language features added later must define Bash behavior before they are considered complete.

## Variable emission

Input:

```ds
let name = "Danh"
let count = 3
let ok = true
```

Possible output:

```bash
__ds_name="Danh"
__ds_count=3
__ds_ok=true
```

Internal variable names should be prefixed to avoid collisions.

Suggested prefix:

```txt
__ds_
```

## String interpolation

Input:

```ds
let name = "Danh"
echo "Hello {name}"
```

Possible output:

```bash
__ds_name="Danh"
echo "Hello ${__ds_name}"
```

Interpolation behavior should be simple in `v0.2.0`:

- `{name}` references a known variable;
- unknown interpolation names should produce an emission or semantic error;
- complex expressions inside interpolation are deferred.

Deferred:

```ds
"Hello {name.upper()}"
"Sum: {a + b}"
```

## If emission

Input:

```ds
if name == "Danh" {
  echo "yes"
} else {
  echo "no"
}
```

Possible output:

```bash
if [[ "$__ds_name" == "Danh" ]]; then
  echo "yes"
else
  echo "no"
fi
```

Supported condition operators:

```txt
==
!=
>
>=
<
<=
```

Numeric-vs-string comparison rules are conservative in this version.

Current limitation: the Bash emitter uses Bash `[[ ... ]]` comparison syntax directly and does not perform type-aware numeric dispatch yet. For example, `<`, `<=`, `>`, and `>=` are emitted as Bash conditional operators rather than selecting arithmetic comparison from tracked `ds` operand types. Type-aware comparison semantics are deferred until the runtime/VM work can define typed behavior consistently.

## Boolean emission

Input:

```ds
let ok = true

if ok {
  echo "ok"
}
```

Possible output:

```bash
__ds_ok=true

if [[ "$__ds_ok" == true ]]; then
  echo "ok"
fi
```

This behavior should be consistent and tested.

## Command statement emission

Input:

```ds
npm install
echo "hello"
```

Output:

```bash
npm install
echo "hello"
```

Because generated Bash uses `set -e`, failed commands should normally stop the script.

Advanced command failure diagnostics are deferred to later versions.

## Source comments

Generated Bash should preserve source location comments where useful.

Example:

```bash
# ds: examples/basic.ds:3
if [[ "$__ds_name" == "Danh" ]]; then
  echo "hello"
fi
```

This is useful for debugging generated scripts.

Exact format can evolve, but it should be stable enough for tests once chosen.

## Safety expectations

The emitter should avoid obvious unsafe output.

Requirements:

- quote string literals safely;
- escape embedded quotes where necessary;
- avoid unprefixed internal variables;
- avoid generating invalid Bash identifiers;
- fail clearly if a `ds` identifier cannot be mapped safely;
- avoid accidental command execution during emission.

## Examples

### Example 1

Input:

```ds
let name = "Danh"

echo "Hello {name}"
```

Output shape:

```bash
#!/usr/bin/env bash
set -euo pipefail

__ds_name="Danh"

echo "Hello ${__ds_name}"
```

### Example 2

Input:

```ds
let target = "production"

if target == "production" {
  npm test
} else {
  echo "Skipping tests"
}
```

Output shape:

```bash
#!/usr/bin/env bash
set -euo pipefail

__ds_target="production"

if [[ "$__ds_target" == "production" ]]; then
  npm test
else
  echo "Skipping tests"
fi
```

## Acceptance criteria

`v0.2.0` is complete when:

- `ds emit bash <file.ds> -o <file.sh>` works for the `v0.1.0` subset.
- Generated Bash starts with a shebang.
- Generated Bash uses `set -euo pipefail`.
- Generated Bash is accepted by `bash -n`.
- Generated Bash runs for basic examples.
- `let` statements emit safe Bash variables.
- String interpolation emits Bash variable interpolation.
- `if` and `if/else` emit valid Bash.
- Command statements emit in order.
- Unsupported syntax fails with a clear diagnostic.
- Bash emission golden tests exist.
- Basic behavior tests for generated Bash exist.
- `docs/language.ds` is updated if Bash emission changes accepted syntax direction.

## Deferred items

Deferred to later versions:

- VM execution: `v0.3.0`.
- Advanced runtime error helpers.
- CLI args block.
- Imports and bundling.
- Functions.
- Loops.
- Arrays/maps.
- Redirection syntax.
- Command result capture.
- Bash helper minimization.
