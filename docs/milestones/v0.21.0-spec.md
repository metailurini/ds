# v0.21.0 Spec — Function Values and Arithmetic

## Status

Not started. This document defines the next feature-foundation milestone after
`v0.20.0` stabilized Wave 2.

`v0.21.0` begins Wave 3 by adding the first user-defined value-result model:
functions can return values, function calls can appear in expressions, and the
expression grammar gains the arithmetic operators needed by normal scripting
logic.

## Goal

Make user-defined functions useful as value-producing helpers while keeping the
language small, shell-native, and equivalent in both supported backends.

After this milestone, these examples are in scope:

```ds
fn normalize(name = " api ") {
  return name.trim().upper()
}

let label = normalize()
echo "service={label}"

fn double(n = 2) {
  return n * 2
}

let result = double(21)
echo "result={result}"
```

The core product rules remain unchanged:

```txt
every supported production feature runs in the VM
every supported production feature emits standalone Bash
generated Bash is standalone and must not call ds
VM and emitted Bash behavior match for stdout, stderr, exit status, and side effects
unsupported or deferred forms fail clearly before partial execution/emission
```

## Motivation

The current function implementation is intentionally procedure-like: functions
can group statements and take positional parameters, but callers cannot capture a
result. That limits reuse and encourages scripts to duplicate expressions.

At the same time, the expression language still lacks arithmetic beyond `+` and
`-`. Real automation scripts need multiplication, division, modulo, powers, and
compound updates for counters, sizes, retries, ports, timestamps, and backoff
calculations.

These two areas should land together because they both require a clearer
value-result model:

1. `return expr` must stop the current function body and transport a typed
   `DsValue` back to the caller.
2. `let x = fn()` requires function-call expressions and return-kind tracking in
   the lowerer, VM, and Bash emitter.
3. Arithmetic needs stricter integer semantics so VM and standalone Bash do not
   diverge under edge cases such as division by zero, precedence, and compound
   assignment.
4. Recursion becomes useful only once functions return values, so the milestone
   should define a conservative recursion story instead of accidentally relying
   on procedure-call behavior.

## Non-goals

This version does not include:

- typed function parameters;
- typed function return annotations;
- anonymous functions, closures, lambdas, or higher-order functions;
- multiple return values or tuple destructuring;
- implicit returns from the last expression in a function body;
- early return from top-level code, tests, `script` blocks, or imported files
  outside a function;
- `return` without an expression;
- returning arrays, maps, functions, or command-result values unless the current
  implementation can prove full VM/Bash parity without expanding collection
  passing semantics;
- passing arrays, maps, or command results through function parameters;
- floating-point arithmetic;
- string repetition with `*` or string concatenation beyond the already-supported
  `+` behavior;
- bitwise operators, shifts, increment/decrement operators, unary plus, or
  logical command chaining;
- ranges, slices, membership `in`, regex literals, or regex matching;
- signal handling, background jobs, async execution, or process-control work;
- optimizer work, tail-call optimization, or unbounded recursion guarantees;
- formatter comment/trivia preservation beyond the existing formatter contract;
- backend expansion beyond standalone Bash.

Small supporting changes are allowed only when needed to implement the scoped
return/arithmetic behavior safely, remove a direct VM/Bash parity gap, or improve
a diagnostic made confusing by the new syntax.

## Required feature work

### 1. `return expr` statements

Add `return expr` as a statement that is valid only inside function bodies.

Required behavior:

- parse and format `return expr`;
- reject `return` outside functions with a clear diagnostic;
- reject `return` without an expression in this milestone;
- reject unreachable statements after an unconditional `return` only if the
  existing checker has a simple, reliable way to do so; otherwise document that
  unreachable-code warnings are deferred;
- when executed, stop the current function immediately and return the evaluated
  value to the caller;
- preserve correct behavior through nested blocks, `if`/`else`, `while`, `for`,
  and `case` inside functions;
- make `break`/`continue` still apply only to loops and not to return control;
- keep imported function returns equivalent to local function returns.

Supported return value kinds for `v0.21.0`:

```txt
bool
int
string
null only if an expression already produces null with full VM/Bash parity
```

The milestone should prefer rejecting collection/command-result/function returns
until the project has a deliberate value-passing design for those kinds.

### 2. Function-call expressions

Allow calls to user-defined functions in expression positions.

Required examples:

```ds
let value = double(21)
echo "value={double(3)}"
if is_prod(target) {
  echo "production"
}
case normalize(app) {
  "API" { echo api }
  _ { echo other }
}
```

Required behavior:

- keep statement-style calls supported for procedures and for callers that ignore
  a return value;
- allow expression calls only for user-defined functions that can return a value
  on all reachable paths covered by the checker;
- provide a clear diagnostic when a value is required from a procedure that never
  returns;
- evaluate arguments left-to-right once;
- preserve existing default-argument behavior;
- keep recursion detection/depth behavior explicit and equivalent enough for VM
  and Bash;
- ensure function calls inside interpolation, command words, conditions, `case`
  selectors, arithmetic expressions, and return expressions either work or fail
  with a targeted unsupported-feature diagnostic.

### 3. Return-kind inference and validation

The lowerer must track the value kind returned by each function.

Rules:

- all explicit return paths in one function must agree on a supported return
  kind;
- functions with conditional returns should either prove all control paths return
  or be rejected when used as expression values;
- a function called only as a statement may omit returns or ignore its result;
- mixed return kinds are rejected with a diagnostic that points to the conflicting
  returns where possible;
- recursive functions may use declared or inferred fixed return kinds only when
  the implementation can avoid circular inference; otherwise recursive return
  inference may require a conservative restriction and a documented diagnostic;
- defaulted parameters keep the v0.20 static kind behavior;
- required untyped parameters remain unknown unless a call site/default gives the
  implementation a safe local kind; typed parameters remain out of scope.

### 4. Arithmetic operators

Add integer arithmetic operators:

```txt
*    multiplication
/    integer division, truncating toward zero
%    integer remainder
**   integer exponentiation
```

Add compound assignment:

```txt
*=   multiply and assign
/=   divide and assign
%=   remainder and assign
```

Operator precedence, from highest to lowest among existing/scoped operators:

```txt
parentheses
unary ! and unary - where currently supported
**                         right-associative
* / %                      left-associative
+ -                        left-associative
comparisons/equality
&&
||
```

Required behavior:

- arithmetic operands must be integers;
- division or modulo by zero fails clearly in VM mode and emitted Bash mode;
- integer operations use the project signed 64-bit integer contract where
  feasible;
- overflow behavior must be deliberately chosen and documented before completion:
  either detect and diagnose overflow consistently, or document matching VM/Bash
  wrap behavior if that is the chosen pre-1.0 compromise;
- exponentiation must reject negative exponents and should reject values that
  exceed the chosen integer contract;
- arithmetic expressions can appear in `let`, reassignment, conditions,
  interpolation, function return expressions, function arguments, script option
  defaults only if defaults already support expressions, and command words where
  interpolation is already supported;
- compound assignment is valid only on assignable integer variables and fields
  already valid for reassignment in prior milestones;
- collection index assignment remains out of scope.

### 5. VM behavior

VM execution must support:

- return-value propagation through function calls;
- early return through nested function blocks without leaking loop/control state;
- recursive calls with a documented depth/error behavior;
- function-call expressions inside larger expressions;
- checked integer arithmetic and compound assignment;
- deterministic diagnostics for runtime arithmetic failures such as division by
  zero;
- no accidental stdout/stderr changes beyond script behavior.

### 6. Standalone Bash behavior

Bash emission must support the same scoped features without calling `ds`.

Requirements:

- generated Bash functions return values through a deterministic internal
  mechanism, not through process stdout when that would collide with user command
  output;
- statement-style calls preserve normal command output from function bodies;
- expression-style calls capture only the function return value and do not swallow
  intentional user stdout unless the language explicitly rejects stdout-producing
  value functions;
- return type sidecars, helper variables, and temporary names use the reserved
  `__ds_` prefix;
- nested calls and recursive calls do not corrupt caller temporaries;
- arithmetic errors set a failing status and clear diagnostic, matching VM as
  closely as Bash allows;
- Bash 4+ guards are emitted whenever the chosen implementation relies on Bash 4+
  features;
- helper emission remains deterministic, deduplicated, dependency-class driven,
  and standalone.

If expression-style function calls cannot safely coexist with arbitrary command
stdout inside the called function body, the milestone should choose and document
one conservative rule, such as rejecting value-used functions that contain plain
command statements before their `return`.

### 7. Diagnostics and checker behavior

Diagnostics should be clear for:

- `return` outside a function;
- bare `return` without an expression;
- unsupported return kind;
- mixed return kinds;
- missing return on a path used as a value;
- calling a procedure in expression position;
- recursive return inference that cannot be resolved;
- arithmetic on non-integers;
- division/modulo by zero when statically knowable;
- negative exponent when statically knowable;
- compound assignment to an immutable/unknown/non-int target;
- use of new operators in unsupported syntactic contexts;
- Bash emission rejection for any form the VM can parse but the Bash backend
  cannot safely emit.

Diagnostics should include source spans and preserve the existing project style.

### 8. Formatter, docs, and examples

Update only where behavior changes:

- formatter support for `return expr`, arithmetic precedence, and compound
  assignment;
- `docs/language.ds` status comments for return values and arithmetic;
- `docs/status.md` support matrix after implementation and after tests;
- `docs/runtime.md` for return-value and arithmetic contracts;
- `docs/architecture.md` if the shared HIR/VM/Bash boundary changes;
- `README.md` examples only if they can be honest about supported behavior;
- `CHANGELOG.md` planned/completed entry;
- at least one example focused on value-returning functions and arithmetic, or
  update `examples/functions.ds` if that is clearer.

## Acceptance criteria

`v0.21.0` is complete only when:

- `return expr` parses, checks, formats, runs in VM mode, and emits to standalone
  Bash for supported scalar values;
- function-call expressions work in `let`, interpolation, conditions, `case`,
  arguments, and return expressions where scoped by this spec;
- procedure-style calls remain compatible with older scripts;
- `*`, `/`, `%`, `**`, `*=`, `/=`, and `%=` run in VM mode and emitted Bash with
  documented integer semantics;
- all unsupported/deferred forms fail before partial or misleading execution;
- generated Bash passes `bash -n`, is deterministic, and contains no call to
  `ds`;
- new docs and examples do not claim typed params, closures, arrays/maps returns,
  floats, or higher-order functions are supported;
- the dedicated `v0.21.0` test suite and all previous version suites pass, or any
  unrelated timeout/host limitation is documented honestly in the completion
  review.

## Out-of-scope list for implementers

Do not pull these into implementation while working on `v0.21.0`:

- typed parameters or return annotations;
- closures, anonymous functions, or functions as values;
- arrays/maps/command-result returns;
- passing collections through function parameters;
- implicit returns;
- floats;
- bitwise arithmetic;
- ranges, regex, or membership;
- signal handling;
- broad formatter redesign;
- per-helper Bash emission if the existing dependency-class helper model remains
  sufficient and documented.
