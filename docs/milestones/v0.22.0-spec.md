# v0.22.0 Spec — Process Control and Signal Handling

## Status

Implementation complete for the scoped production changes. The dedicated
automated test suite is intentionally pending because this pass was requested as
implementation-only. This document defines the Wave 3 expansion milestone after
`v0.21.0` function values and arithmetic.

`v0.22.0` adds the first deliberate process-cleanup and signal-awareness model.
The goal is not to expose every Bash `trap` detail, but to give scripts a small,
portable cleanup surface that behaves the same in VM mode and emitted standalone
Bash.

## Goal

Make ds scripts able to register cleanup work for normal exit and for the common
termination signals used by automation scripts.

After this milestone, these examples are in scope:

```ds
let tmp = temp.dir()

defer {
  remove tmp, recursive: true
}

defer on: "INT" {
  echo "interrupted"
  remove tmp, recursive: true
  exit 130
}

echo "working in {tmp}"
```

The lower-level `trap` form is also in scope as an explicit escape hatch for
scripts that need signal-specific behavior that is not nicely modeled by
`defer`:

```ds
trap "TERM" {
  echo "terminated"
  exit 143
}
```

The core product rules remain unchanged:

```txt
every supported production feature runs in the VM
every supported production feature emits standalone Bash
generated Bash is standalone and must not call ds
VM and emitted Bash behavior match for stdout, stderr, exit status, and side effects
unsupported or deferred forms fail clearly before partial execution/emission
```

## Motivation

Real scripts create temporary files, start child processes, update state, and may
be interrupted by Ctrl-C or process supervisors. Without cleanup handlers,
callers must duplicate cleanup code in every branch or accept stale files and
partial side effects.

Bash users typically reach for `trap`, but raw traps are easy to misuse:

- handler order is implicit;
- signal names and numeric exit statuses are easy to confuse;
- `EXIT`, `INT`, and `TERM` interact differently;
- nested or imported cleanup registration can be hard to reason about;
- generated Bash must avoid relying on the ds runtime.

`v0.22.0` should provide a boring ds-level model that covers common automation
needs while preserving a clearly named low-level escape hatch.

## Non-goals

This version does not include:

- background jobs, job control, coprocesses, async execution, or wait groups;
- process groups, terminal-control APIs, or forwarding signals to process trees;
- POSIX `sh` emission;
- Windows PowerShell or cmd.exe emission;
- arbitrary host signal lists;
- custom signal numbers in the public syntax;
- multiple signal names on one `defer on:` or `trap` statement;
- handler priority annotations;
- disabling or removing a previously registered handler;
- `try`/`catch`/`finally`, exceptions, panic/recover, or structured error values;
- command timeouts, retries, process cancellation tokens, or subprocess handles;
- returning values from cleanup handlers;
- continuing normal execution after an `INT`/`TERM` handler unless the spec below
  explicitly allows it;
- changing direct-command fail-fast semantics except where cleanup execution on
  exit requires an implementation hook;
- changing `run` command-result capture semantics;
- adding new standard-library filesystem helpers unless a tiny helper is needed
  only for deterministic tests.

Small supporting changes are allowed only when needed to implement scoped cleanup
and signal behavior safely, remove a direct VM/Bash parity gap, or improve a
diagnostic made confusing by the new syntax.

## Required feature work

### 1. EXIT-style `defer` blocks

Add production support for plain cleanup blocks:

```ds
defer {
  echo "cleanup"
}
```

Required behavior:

- parse and format `defer { ... }`;
- register the block when execution reaches the statement;
- run registered cleanup blocks when the current script exits normally, exits via
  `exit`, exits via `fail`, or aborts because a direct command statement fails;
- run cleanup blocks in last-in, first-out order;
- allow multiple `defer` blocks in one file and across imports;
- preserve import execution order: imported top-level defers are registered when
  that imported code is executed in the composed program;
- execute cleanup at most once;
- run cleanup after top-level `test` execution only when the test runner executes
  the source as a script; test-block-local behavior is covered below;
- reject `defer` outside executable statement positions where normal statements
  are already rejected;
- support the same statement subset inside cleanup blocks as normal blocks,
  except for restrictions listed below.

Handler restrictions:

- `break` and `continue` are valid only inside loops that are lexically inside
  the handler;
- `return` is valid only when lexically inside a function nested in the handler,
  not from the handler itself;
- a handler may call functions, run commands, and use scoped variables visible at
  the registration point if the implementation can preserve that behavior in
  Bash; otherwise reject the capture with a targeted diagnostic rather than
  silently changing scope behavior;
- collection mutation inside cleanup follows the same support rules as normal
  code.

### 2. Signal-specific `defer on:` blocks

Add signal-specific cleanup blocks for a conservative signal set:

```ds
defer on: "INT" {
  echo "interrupted"
  exit 130
}

defer on: "TERM" {
  echo "terminated"
  exit 143
}
```

Required behavior:

- parse and format `defer on: "INT" { ... }` and `defer on: "TERM" { ... }`;
- accept signal names case-sensitively as string literals for `INT`, `TERM`, and
  `EXIT`;
- treat `defer { ... }` as equivalent to `defer on: "EXIT" { ... }` for handler
  registration and ordering;
- reject unsupported signal names such as `HUP`, `QUIT`, `KILL`, `STOP`, empty
  strings, numeric strings, and interpolated or nonliteral signal expressions in
  this milestone;
- register handlers only when execution reaches the statement;
- run handlers for the matching signal in last-in, first-out order;
- on `INT`, default final exit status is `130` when no handler exits explicitly;
- on `TERM`, default final exit status is `143` when no handler exits explicitly;
- on normal exit, run `EXIT` handlers only;
- when an `INT` or `TERM` handler finishes without `exit`, the script should stop
  and exit with the signal's default status after running any remaining matching
  handlers and then `EXIT` handlers;
- if a signal handler calls `exit N`, preserve `N` as the final status while
  still running remaining applicable cleanup that is safe to run once;
- avoid double-running the same `EXIT` cleanup if a signal handler exits.

### 3. Lower-level `trap` blocks

Add a deliberate low-level form:

```ds
trap "INT" {
  echo "interrupted"
  exit 130
}
```

Required behavior:

- parse and format `trap "INT" { ... }`;
- support the same initial signal set as signal-specific defer: `EXIT`, `INT`,
  and `TERM`;
- use string-literal signal names only;
- reject dynamic signals and unsupported names with clear diagnostics;
- execute `trap` handlers for their signal in registration order or replacement
  order as chosen by the implementation, but the choice must be documented and
  tested;
- prefer replacement semantics for repeated `trap "SIGNAL" { ... }`, matching
  the common expectation that `trap` sets the low-level signal action;
- keep `defer on:` as the recommended stackable cleanup model;
- ensure `trap` does not accidentally disable or skip registered `defer` cleanup;
- emit standalone Bash traps without calling `ds`.

Recommended final model:

```txt
defer on: SIGNAL  stackable LIFO cleanup for SIGNAL
trap SIGNAL       one low-level handler per SIGNAL; later trap replaces earlier trap
on signal         run trap handler first, then matching defers, then EXIT defers
```

If implementation proves that a different order is safer for VM/Bash parity, the
implementation may choose it, but the spec completion review must record the
final order and the test plan must be amended accordingly.

### 4. Handler failure and exit semantics

Define failure behavior before implementation so VM and Bash do not drift.

Required behavior:

- cleanup handlers run even when the triggering status is non-zero;
- the original status is preserved if all handlers succeed and no handler calls
  `exit`;
- if a handler calls `exit N`, `N` becomes the final status after remaining safe
  cleanup runs;
- if a handler command fails under normal direct-command fail-fast behavior and
  the handler does not catch/inspect it with `run`, the handler failure becomes
  the final status unless a later handler explicitly exits;
- if multiple handlers fail, the last failing handler status may become the final
  status, but the chosen rule must be documented and tested;
- handler execution must not recurse infinitely if a handler itself exits or
  fails;
- diagnostics emitted from handlers should still include source locations.

### 5. VM behavior

The VM must implement signal/cleanup behavior without relying on generated Bash.

Required VM work:

- represent defer/trap registration in lowered/HIR or bytecode form;
- maintain handler stacks per execution context and per signal;
- maintain a cleanup-running guard to prevent recursive handler execution;
- run top-level cleanup on normal VM completion, `exit`, `fail`, direct command
  failure, and supported signal delivery;
- handle `INT` and `TERM` in a deterministic way suitable for tests;
- expose enough internal structure in `hir`/`bytecode` debug output to make
  cleanup lowering inspectable;
- preserve existing test runner isolation: a failing test or cleanup in one test
  must not leak registered handlers into a later test.

Signal delivery in tests may be implemented by actually sending OS signals to a
running `ds` process, by a deterministic test helper, or by a small internal test
mode if needed. The final behavior must still be real OS-signal-aware for normal
execution.

### 6. Bash emission behavior

Generated Bash must be standalone and equivalent.

Required Bash work:

- emit a Bash trap dispatcher for `EXIT`, `INT`, and `TERM` only when handlers are
  present;
- store stackable defer handlers safely in generated Bash without eval-ing user
  code assembled from strings;
- preserve LIFO order for `defer` handlers;
- implement `trap` replacement semantics if the recommended model is chosen;
- avoid double-running `EXIT` cleanup after `INT`/`TERM` handlers or explicit
  `exit` from a handler;
- preserve exit statuses according to the VM rules;
- quote and namespace all generated helper/function names safely;
- keep emitted Bash compatible with the project's existing Bash baseline and
  emit a guard if a new Bash version feature is required;
- ensure `bash -n` succeeds for emitted scripts;
- ensure generated scripts do not call `ds`.

### 7. Formatter and checker behavior

Required behavior:

- `ds fmt` formats `defer`, `defer on:`, and `trap` blocks with normal two-space
  indentation and one blank line between top-level declarations where applicable;
- `ds fmt --check` rejects unformatted signal handlers consistently;
- `ds check` validates signal literals, handler placement, and unsupported
  handler control flow without executing handlers;
- diagnostics should name the bad signal and list supported signals when useful;
- diagnostics should distinguish `defer on:` from `trap` so users know which form
  was rejected.

### 8. Imports, functions, scripts, and tests

Required behavior:

- imported top-level handlers register in the composed execution order;
- a handler in an imported file reports diagnostics with the imported file's
  source location;
- functions may contain `defer`/`defer on:`/`trap` only if the implementation can
  define whether registration is function-scoped or process-scoped with Bash
  parity;
- recommended v0.22 rule: handlers declared inside functions register when the
  function call reaches the statement and remain active for the process/script
  until fired, matching Bash's process-level traps; if that is too surprising,
  reject function-local handlers and defer local cleanup scopes;
- script argument parsing must happen before handlers that appear after the
  `script { ... }` block, preserving current script-contract behavior;
- test blocks must isolate handler registrations between tests.

## Supported syntax

```ds
defer {
  echo "cleanup"
}

defer on: "EXIT" {
  echo "leaving"
}

defer on: "INT" {
  echo "interrupted"
  exit 130
}

defer on: "TERM" {
  echo "terminated"
  exit 143
}

trap "INT" {
  echo "custom INT handler"
  exit 130
}
```

Only string-literal signals are supported in this milestone.

## Unsupported syntax examples

```ds
let sig = "INT"
defer on: sig { echo no }

trap "KILL" { echo impossible }

trap 2 { echo numeric }

trap "INT", "TERM" { echo multiple }

undefer "INT"
```

Each unsupported example must fail clearly before VM execution or Bash emission.

## Diagnostics

Diagnostics should cover at least:

- malformed `defer on:` syntax;
- malformed `trap` syntax;
- unsupported signal names;
- dynamic signal expressions;
- numeric signals;
- empty signal names;
- unsupported control flow from handlers;
- unsupported handler placement if function-local handlers are deferred;
- handler statements that are otherwise invalid under existing language rules;
- Bash emission rejection if a handler captures a value that cannot be emitted
  safely.

Diagnostic text does not need to match this spec exactly, but it must include the
feature name and the reason.

## Acceptance criteria

`v0.22.0` is complete only when:

- `defer { ... }` works in VM and emitted standalone Bash;
- `defer on: "EXIT"`, `defer on: "INT"`, and `defer on: "TERM"` work in VM and
  emitted standalone Bash;
- `trap "EXIT"`, `trap "INT"`, and `trap "TERM"` work according to the final
  documented replacement/order model;
- cleanup ordering is deterministic and tested;
- final exit-status behavior is deterministic and tested;
- handlers run for normal exit, explicit `exit`, explicit `fail`, direct-command
  failure, and supported signal delivery;
- handlers do not double-run;
- imports, functions, script args, and test blocks either work with the supported
  handler subset or reject unsupported forms clearly;
- `ds fmt`, `ds fmt --check`, `ds check`, `ds hir`, `ds bytecode`, VM run, and
  Bash emission remain consistent with the milestone's syntax;
- generated Bash passes `bash -n`, is standalone, and does not call `ds`;
- the version test plan is implemented and wired into aggregate test targets;
- docs and examples are updated if the implementation changes them;
- completion review records the final handler order, final-status rule, and any
  deferred process-control work.

## Deferred items

Expected deferrals unless deliberately pulled into this spec:

- background jobs and job control;
- process groups and child-process signal forwarding;
- async execution, coprocesses, and `wait` primitives;
- arbitrary or platform-specific signals beyond `EXIT`, `INT`, and `TERM`;
- signal numbers in public syntax;
- multiple signals per handler;
- removing handlers or handler handles;
- handler priority annotations;
- scoped RAII-style function-local cleanup if process-level handler registration
  is chosen;
- robust cleanup for abrupt VM termination such as `SIGKILL`;
- full `try`/`finally` or exception handling;
- command timeout/cancellation APIs;
- advanced test harness signal simulation beyond what is necessary for stable
  coverage.

## Completion review

- Final handler order: matching replacement `trap` first, matching `defer`
  handlers in LIFO registration order second, then EXIT cleanup for INT/TERM.
- Final exit-status rule: normal completion preserves status 0; explicit `exit`,
  `fail`, direct command failure, and handled INT/TERM preserve their triggering
  status unless handler code explicitly exits with a different status.
- Function-local handler rule: handlers are process-level registrations and may
  be registered from code that executes inside functions; there is no lexical
  RAII-style function cleanup scope in this milestone.
- Supported signal set: `EXIT`, `INT`, and `TERM` string literals only.
- VM implementation notes: the VM stores handler bytecode targets, uses
  replacement semantics for traps, runs defers in reverse registration order,
  and installs lightweight INT/TERM signal hooks that dispatch when the VM
  regains control between bytecode instructions.
- Bash emission notes: emitted Bash is standalone, defines cleanup arrays and
  trap variables, emits handler bodies as shell functions, and installs EXIT,
  INT, and TERM traps without calling `ds`.
- Docs/examples updated: README, status, runtime, language catalog, changelog,
  and this completion review were updated; no new examples were required.
- Tests added: none in this implementation-only pass.
- Deferred items: dedicated v0.22 automated tests and deeper process-control
  behavior listed below remain for later scoped work.
