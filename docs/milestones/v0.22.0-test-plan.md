# v0.22.0 Test Plan — Process Control and Signal Handling

## Status

Not started. This plan should be implemented after the `v0.22.0` feature work is
complete enough to run focused fixtures. The dedicated suite should be
`tests/v0_22/run.sh` and should be wired into the normal aggregate targets.

## Purpose

Prove that cleanup and signal handling form one coherent language surface across
parser, checker, formatter, VM execution, standalone Bash emission, imports,
functions, test blocks, diagnostics, and generated-script behavior.

The suite must preserve the main product rules:

```txt
VM mode and emitted Bash agree for supported features
generated Bash is standalone and never calls ds
unsupported/deferred forms fail clearly before partial execution/emission
older scripts without handlers keep working
```

## Test entrypoint

Add:

```sh
tests/v0_22/run.sh
```

Wire it consistently with previous suites:

```sh
make test-v0-22
make test
make test-asan
make test-ubsan
```

If OS-signal tests are too slow or flaky under sanitizer builds, provide focused
non-signal sanitizer subruns plus a small documented signal smoke subset in the
completion review.

## Test conventions

Follow existing version-suite conventions:

- `set -euo pipefail`;
- deterministic private temp directories;
- helper functions for writing fixtures, running VM mode, emitting Bash, running
  emitted Bash, comparing stdout/stderr/status, and asserting diagnostics;
- no network access;
- no timing-sensitive tests beyond minimal signal-delivery smoke tests;
- quote all temp paths;
- use only stable shell commands;
- normalize path-specific stderr only where exact paths are intentionally
  unstable;
- assert `bash -n` for every emitted Bash fixture;
- assert generated Bash does not contain a call to `ds`;
- avoid leaving background processes or temp files behind after test failure.

For VM/Bash parity tests:

1. Write `input.ds`.
2. Run `./ds input.ds`; capture stdout, stderr, and status.
3. Run `./ds emit bash input.ds -o out.sh`; assert success.
4. Run `bash -n out.sh`.
5. Assert `out.sh` does not call `ds`.
6. Run `bash out.sh`; capture stdout, stderr, and status.
7. Compare stdout, stderr, status, and declared side-effect files.

### Lexer/parser/AST/HIR/bytecode shape

Fixtures:

```ds
defer {
  echo cleanup
}
```

```ds
defer on: "INT" {
  echo interrupted
}
```

```ds
trap "TERM" {
  echo terminated
}
```

Coverage:

- token output includes the expected keywords/punctuation/string literals;
- AST output distinguishes plain `defer`, signal-specific `defer`, and `trap`;
- HIR output preserves handler signal and statement order;
- bytecode/debug output shows registration and handler body structure, or an
  equivalent stable representation chosen by the implementation;
- malformed syntax reports source-located diagnostics.

### Formatter coverage

Formatted input:

```ds
defer{echo cleanup}

defer on:"INT"{echo interrupted}

trap "TERM"{echo terminated}
```

Expected formatting:

```ds
defer {
  echo cleanup
}

defer on: "INT" {
  echo interrupted
}

trap "TERM" {
  echo terminated
}
```

Also cover:

- nested `if`, `for`, `while`, and `case` inside handlers;
- handler blocks inside functions if supported, or diagnostic if deferred;
- `ds fmt --check` failing on unformatted handlers and passing after formatting;
- formatter rejection of comments remains unchanged until comment preservation is
  deliberately implemented.

### Plain EXIT defer parity

Fixture:

```ds
echo start

defer {
  echo cleanup
}

echo end
```

Expected stdout:

```txt
start
end
cleanup
```

Assert VM/Bash parity and status `0`.

### LIFO ordering

Fixture:

```ds
defer { echo first }
defer { echo second }
defer { echo third }
echo body
```

Expected stdout:

```txt
body
third
second
first
```

Run in VM and Bash.

### `defer on: "EXIT"` equivalence

Fixture:

```ds
defer { echo plain }
defer on: "EXIT" { echo explicit }
echo body
```

Expected stdout should reflect the documented LIFO order. If both are the same
stack, expected output is:

```txt
body
explicit
plain
```

### Explicit `exit` triggers cleanup

Fixture:

```ds
defer { echo cleanup }
echo before
exit 7
echo after
```

Expected:

- stdout contains `before` then `cleanup`;
- stdout does not contain `after`;
- status is `7` for VM and Bash.

### `fail` triggers cleanup

Fixture:

```ds
defer { echo cleanup }
echo before
fail "boom"
echo after
```

Expected:

- stdout contains `before` then `cleanup`;
- stderr contains `boom`;
- stdout does not contain `after`;
- VM/Bash status match and are non-zero.

### Direct command failure triggers cleanup

Fixture:

```ds
defer { echo cleanup }
echo before
__definitely_missing_ds_command_v0_22__
echo after
```

Expected:

- stdout contains `before` then `cleanup`;
- stdout does not contain `after`;
- stderr reports command failure;
- status is `127` or the documented direct-command failure status for both
  backends.

### Captured command failure does not trigger early cleanup

Fixture:

```ds
defer { echo cleanup }
let result = run __definitely_missing_ds_command_v0_22__
echo "failed={result.failed}"
```

Expected:

- script continues after captured failure;
- cleanup runs only at normal exit;
- VM/Bash output and status match.

### Cleanup side effects

Fixture writes/removes temp files under the test temp directory:

```ds
let marker = ".../marker.txt"
write marker, "body"

defer {
  remove marker
}

echo file.exists(marker)
```

Expected:

- stdout before exit shows the file exists;
- after VM/Bash execution, the marker is removed;
- no leftover files remain.

Use only currently supported file helpers. If `write` is not available, use
plain commands with temp paths that are safe under the suite directory.

Expected:

### Handler `exit` final status

Fixture:

```ds
defer { exit 9 }
echo body
```

Expected:

- stdout contains `body`;
- final status is `9`;

### Handler `exit` still permits remaining cleanup when documented

Fixture:

```ds
defer { echo first }
defer { exit 8 }
defer { echo third }
echo body
```

Expected output and status must match the final documented rule. If remaining
safe cleanup runs after `exit`, expected stdout is:

```txt
body
third
first
```

with status `8`. If `exit` stops remaining handlers, document and assert that
instead. VM and Bash must match.

### Signal-specific INT smoke

Use a helper that starts VM and Bash scripts, waits for a ready marker, sends
`INT`, and waits for termination.

Fixture:

```ds
defer on: "INT" {
  echo interrupted
}

defer {
  echo exit-cleanup
}

echo ready
sleep 10
```

Expected after sending INT:

- stdout contains `ready`, `interrupted`, and `exit-cleanup` in documented order;
- final status is `130` unless the handler exits explicitly;
- no process remains running;
- VM and Bash agree.

### Signal-specific TERM smoke

Fixture:

```ds
defer on: "TERM" {
  echo terminated
}

defer {
  echo exit-cleanup
}

echo ready
sleep 10
```

Expected after sending TERM:

- stdout contains `ready`, `terminated`, and `exit-cleanup` in documented order;
- final status is `143` unless the handler exits explicitly;
- VM and Bash agree.

### Signal handler explicit status

Fixture:

```ds
defer on: "INT" {
  echo interrupted
  exit 77
}

echo ready
sleep 10
```

Expected after INT:

- stdout contains `ready` and `interrupted`;
- final status is `77`;
- no double cleanup.

### `trap` replacement semantics

Fixture:

```ds
trap "INT" {
  echo first
}

trap "INT" {
  echo second
}

echo ready
sleep 10
```

Expected after INT if replacement semantics are chosen:

- stdout contains `ready` and `second`;
- stdout does not contain `first`;
- status follows the documented INT default or explicit handler status;
- VM and Bash agree.

If implementation chooses stacking semantics instead, amend the spec and assert
that final behavior explicitly.

### `trap` plus `defer on:` ordering

Fixture:

```ds
trap "INT" {
  echo trap
}

defer on: "INT" {
  echo defer-int
}

defer {
  echo defer-exit
}

echo ready
sleep 10
```

Expected after INT must match the documented order. Recommended expected stdout:

```txt
ready
trap
defer-int
defer-exit
```

### Normal exit should not run INT/TERM handlers


### Functions

```ds

  defer { echo from-function }

```

Expected according to process-level registration:

```txt

```

If function-local handlers are deferred, the same fixture should produce a clear

Also test that function calls from handlers work:

```ds

  echo "cleanup={label}"

defer { cleanup("ok") }

```

### Script args

```ds
  arg name: string
```

Run VM and emitted Bash with an argument such as `api`. Expected cleanup sees the

### Test blocks isolation

Fixture:

```ds
test "one" {
  defer { echo one-cleanup }
  assert true
}

test "two" {
  assert true
}
```

Expected:

- the test runner does not leak the first test's handler into the second test;
- output shape follows existing test-runner conventions;
- failures inside cleanup are attributed to the correct test if test-local defer
  is supported.

If `defer` inside test blocks is deferred, assert a clear diagnostic and record
that deferral in the spec completion review.

### Conditions, loops, and case inside handlers

Fixture:

```ds
let xs = ["a", "b"]
let i = 0

defer {
  while i < len(xs) {
    case xs[i] {
      "a" { echo A }
      "b" { echo B }
      _ { echo other }
    }
    i += 1
  }
}

echo body
```

Expected VM/Bash parity:

```txt
body
A
B
```

### Interaction with v0.21 returns/arithmetic

After v0.21 is implemented, include:

```ds
fn code() {
  return 40 + 2
}

defer {
  echo "code={code()}"
}

echo body
```

Expected stdout:

```txt
body
code=42
```

If v0.22 is implemented before v0.21, this test should be postponed until the
v0.21 functionality exists and the completion review should say why.

### Bash emission internals

For emitted Bash fixtures, assert:

- `bash -n` passes;
- no `ds` invocation appears;
- helper names are namespaced with `__ds_` or the existing convention;
- traps are emitted only when handlers exist;
- scripts without handlers do not gain unnecessary trap dispatcher code;
- generated trap code uses functions or arrays safely and does not eval user
  source assembled from strings.

### Unsupported signal diagnostics

Invalid fixtures:

```ds
defer on: "" { echo bad }
```

```ds
defer on: "HUP" { echo bad }
```

```ds
defer on: "KILL" { echo bad }
```

```ds
trap "STOP" { echo bad }
```

Expected diagnostics:

- mention unsupported signal;
- include the signal name where possible;
- mention supported signals `EXIT`, `INT`, and `TERM`.

### Dynamic signal diagnostics

Invalid fixtures:

```ds
let sig = "INT"
defer on: sig { echo bad }
```

```ds
let sig = "TERM"
trap sig { echo bad }
```

Expected diagnostics:

- mention that signal names must be string literals;
- no VM execution or Bash output.

### Numeric signal diagnostics

Invalid fixtures:

```ds
defer on: 2 { echo bad }
```

```ds
trap 15 { echo bad }
```

Expected diagnostics:

- mention signal names must be string literals;
- reject before execution/emission.

### Malformed syntax diagnostics

Invalid fixtures:

```ds
defer on "INT" { echo bad }
```

```ds
defer on: "INT"
```

```ds
trap "INT"
```

```ds
trap { echo bad }
```

Expected diagnostics should mention expected `:` or block/string as appropriate.

### Unsupported deferred process-control forms

Invalid fixtures should remain rejected clearly:

```ds
sleep 1 &
```

```ds

```

```ds

```

```ds
trap "INT", "TERM" { echo bad }
```

```ds
undefer "INT"
```

Expected diagnostics mention unsupported/deferred background jobs, wait/coprocess,
multiple signals, or unknown statement syntax.
