# v0.23.0 Spec — Regex, Ranges, and Membership

## Status

Implementation and the dedicated `tests/v0_23/run.sh` test-plan pass are
complete. This document defines the Wave 3 integration/usability milestone after
`v0.21.0` function values/arithmetic and `v0.22.0` process control.

`v0.23.0` addresses the highest-priority deferred expression and iteration
features that remain before the pre-1.0 hardening pass: exact membership checks,
integer ranges, and a conservative regex matching surface.

## Goal

Make common script filtering and iteration patterns readable without falling back
to ad-hoc shell commands or fragile string comparisons.

After this milestone, these examples are in scope:

```ds
let app = "api"
let known = app in ["api", "web", "worker"]

if "deploy failed" matches /failed/ {
  echo "deployment failed"
}

for n in 1..3 {
  echo "n={n}"
}
```

The core product rules remain unchanged:

```txt
every supported production feature runs in the VM
every supported production feature emits standalone Bash
generated Bash is standalone and must not call ds
VM and emitted Bash behavior match for stdout, stderr, exit status, and side effects
unsupported or deferred forms fail clearly before partial execution/emission
```

## Motivation

By the end of `v0.22.0`, ds has practical functions, arithmetic, cleanup, control
flow, pipelines, collections, string methods, and formatted output. Real scripts
still need three small but important usability features:

1. Membership checks, so callers can write `app in allowed` instead of manual
   `case` ladders or loop flags.
2. Integer ranges, so loops over counts, retries, ports, and bounded sequences do
   not require hand-written counter arrays.
3. Regex matching, so text filters can stay inside ds conditions when spawning
   `grep` would be awkward or would lose VM/Bash parity around values.

These features belong together because they all extend the expression/iteration
surface without introducing a larger type system. They also create one final
feature-integration pass before `v0.24.0` freezes the pre-1.0 language shape.

## Non-goals

This version does not include:

- heredoc command stdin syntax or here-strings;
- regex replacement, regex splitting, global match arrays, captures as values, or
  named capture groups;
- full PCRE, Perl, Python, Rust, or JavaScript regex compatibility;
- runtime-constructed regex patterns;
- regex literals in command mode;
- regex flags beyond the small set explicitly listed below;
- range values as first-class arrays;
- open-ended ranges, half-open ranges, stepped ranges, reverse ranges, slices, or
  character/string ranges;
- membership over maps, command results, regexes, ranges, or arbitrary objects;
- set/dictionary literals or collection comprehensions;
- pattern matching or destructuring in `case`;
- new arithmetic operators beyond those scoped to `v0.21.0`;
- typed function parameters, generics, or iterable protocols;
- backend expansion beyond standalone Bash.

Small supporting changes are allowed only when needed to implement scoped regex,
range, and membership behavior safely, remove a direct VM/Bash parity gap, or
improve a diagnostic made confusing by the new syntax.

## Required feature work

### 1. Membership operator: `in`

Add `in` as an expression operator for membership tests.

Required syntax:

```ds
let known = app in ["api", "web"]

if target in allowed_targets {
  echo "known target"
}

if 2 in [1, 2, 3] {
  echo "two"
}
```

Required behavior:

- parse `in` as an infix operator lower than comparison/equality and higher than
  `&&` / `||`;
- return a boolean value;
- evaluate the left operand once, then evaluate the right operand once;
- support membership in arrays whose element kinds are supported scalar kinds:
  `string`, `int`, and `bool`;
- support array literals and variables as the right operand;
- support array results from existing string/stdlib helpers only when the
  element kind is known and scalar, such as `"a,b".split(",")` and `lines(path)`;
- use exact ds value equality, not Bash glob matching or substring matching;
- preserve type-sensitive equality: string `"2"` is not int `2`, bool `true` is
  not string `"true"`;
- support use in `let`, `if`, `while`, `case` selectors, assertions,
  interpolation, function returns, and function arguments where boolean
  expressions are already supported;
- reject right operands that are not supported arrays with a clear diagnostic;
- reject maps, command results, ranges, regexes, and unknown/heterogeneous arrays
  until a broader iterable/value model exists.

Bash emission requirements:

- emitted Bash must not call `ds`;
- generated membership checks must preserve exact kind-aware equality;
- string elements must be quoted safely and must not become Bash patterns;
- array membership must work for empty arrays;
- helper emission may be dependency-class based if consistent with existing Bash
  helper policy, but scripts using `in` must emit any required helpers and Bash 4
  guard only when needed.

### 2. Integer ranges: `start..end`

Add inclusive integer range syntax as a loop source.

Required syntax:

```ds
for n in 1..3 {
  echo "n={n}"
}

let start = 2
let end = 4
for n in start..end {
  echo "n={n}"
}
```

Required behavior:

- parse `expr .. expr` only in `for item in ...` loop-source position in this
  milestone;
- evaluate the start expression once before the loop;
- evaluate the end expression once before the loop;
- require both bounds to be integers;
- iterate inclusively from start to end when `start <= end`;
- when `start > end`, run zero iterations rather than implicitly counting down;
- bind the loop variable as an `int` in the VM, lowerer, and Bash type sidecars;
- preserve `break` and `continue` behavior;
- support ranges inside functions, imports, tests, and cleanup handlers where
  loops are already supported;
- support bounds that are literals, variables, arithmetic expressions, and
  supported scalar-returning function-call expressions;
- reject range syntax outside `for` loop sources in this milestone, including
  `let xs = 1..3`, `1..3 in xs`, command words, interpolation, and function
  returns;
- reject open-ended, half-open, stepped, reverse-counting, and non-integer ranges
  with targeted diagnostics.

Bash emission requirements:

- emitted Bash must use arithmetic loop constructs or helpers that preserve the
  inclusive/empty semantics exactly;
- generated Bash must not rely on brace expansion with runtime variables;
- bounds must be evaluated once, not on every iteration;
- generated loop variables must carry the `int` kind sidecar so `case`,
  interpolation formatting, arithmetic, and `in` behave as in the VM.

### 3. Regex literals and `matches`

Add a conservative regex match expression.

Required syntax:

```ds
if "deploy failed" matches /failed/ {
  echo "failed"
}

let ok = branch matches /^release\/[0-9]+$/
```

Required behavior:

- parse regex literals delimited by `/.../` only as the right operand of
  `matches` in this milestone;
- add `matches` as an infix expression operator returning bool;
- require the left operand to be a string;
- require the right operand to be a regex literal;
- use search semantics: the pattern may match anywhere unless anchored with `^`
  or `$`;
- support a conservative Extended Regular Expression subset that both the VM
  implementation and Bash `[[ string =~ regex ]]` can support consistently;
- preserve the pattern text exactly enough that escaping has the same meaning in
  VM and emitted Bash for the supported subset;
- reject unsupported constructs before execution/emission;
- support `matches` in conditions, `let`, assertions, function returns,
  interpolation, and boolean combinations where normal bool expressions work.

Supported regex subset for `v0.23.0`:

```txt
literal characters except unescaped `/` and newline
escaped literal slash `\/`
escaped backslash `\\`
anchors `^` and `$`
any character `.`
character classes such as `[abc]`, `[^abc]`, `[a-z]`
groups `( ... )`
alternation `|`
quantifiers `*`, `+`, `?`, `{m}`, `{m,n}`
```

Allowed optional flags:

```txt
i   case-insensitive matching
```

Required flag syntax:

```ds
if name matches /api/i {
  echo "api-ish"
}
```

Unsupported in `v0.23.0`:

```txt
lookaround
backreferences
named captures
inline flags such as (?i)
non-capturing groups syntax that is not shared with POSIX ERE
lazy quantifiers
Unicode character classes such as \p{L}
word-boundary shortcuts such as \b if VM/Bash parity is not exact
runtime regex strings such as s matches pattern
multi-line regex literals
```

Bash emission requirements:

- emitted Bash must not call `ds`;
- regex patterns must be emitted in a way that preserves Bash regex semantics and
  avoids accidental shell globbing or word splitting;
- `/.../i` may use a local `nocasematch` guard or equivalent helper, and must
  restore the caller's shell option state after the match;
- scripts that do not use case-insensitive regex must not unnecessarily change
  shell options;
- unsupported regex constructs must fail during checking/lowering/emission, not
  produce a script with divergent behavior.

### 4. Operator precedence and interactions

Precedence, from highest to lowest among relevant operators:

```txt
parentheses
method calls, field/index access, function calls
unary ! and unary - where supported
**
* / %
+ -
comparisons/equality/matches/in
&&
||
```

`matches` and `in` are comparison-level operators. They should not chain without
parentheses unless the parser already has a clear rule for comparison chaining.
Prefer rejecting ambiguous chains such as:

```ds
a in xs == true
s matches /x/ == true
```

with a diagnostic that asks for parentheses.

Interactions that must work:

```ds
if (app in allowed) && (branch matches /^release\//) {
  echo ok
}

for n in start + 1..end - 1 {
  echo "{n:03d}"
}

case app in allowed {
  true { echo known }
  false { echo unknown }
}
```

### 5. Diagnostics

Diagnostics should be clear for:

- unsupported regex syntax;
- unterminated regex literals;
- invalid regex flags;
- regex newline contents;
- `matches` with non-string left operand;
- `matches` with nonliteral right operand;
- `in` with non-array right operand;
- `in` over unsupported element kinds or unknown/heterogeneous arrays;
- type-sensitive membership surprises only where a static diagnostic is reliable;
- `..` outside `for` loop-source position;
- non-integer range bounds;
- malformed ranges such as `1...3`, `1..`, or `..3`;
- Bash emission rejection for any parsed form that cannot be safely emitted;
- formatter/checker handling of new syntax.

Diagnostics should include source spans and preserve the existing project style.

## Acceptance criteria

`v0.23.0` is complete only when:

- `in` parses, checks, formats, runs in VM mode, and emits to standalone Bash for
  supported scalar arrays;
- integer range loop sources parse, check, format, run in VM mode, and emit to
  standalone Bash with inclusive and empty-range semantics;
- `matches` parses, checks, formats, runs in VM mode, and emits to standalone
  Bash for the documented regex subset and `/i` flag;
- VM and Bash agree for stdout, stderr, exit status, and side effects across all
  scoped features;
- unsupported/deferred forms fail before partial or misleading execution;
- generated Bash passes `bash -n`, is deterministic, and contains no call to
  `ds`;
- new docs/examples do not claim heredocs, regex captures, runtime regex
  patterns, range values, map membership, reverse ranges, or stepped ranges are
  supported;
- the dedicated `v0.23.0` test suite and all previous version suites pass, or any
  unrelated timeout/host limitation is documented honestly in the completion
  review.

## Out-of-scope list for implementers

Do not pull these into implementation while working on `v0.23.0`:

- heredoc or here-string syntax;
- regex capture values, regex replace/split APIs, runtime regex strings, or full
  PCRE compatibility;
- ranges as values, stepped/reverse/half-open ranges, slices, or string ranges;
- membership over maps, ranges, regexes, command results, or unknown iterables;
- typed function parameters or generics;
- pattern matching beyond exact `case` from `v0.17.0`;
- broad formatter redesign or comment preservation;
- backend expansion beyond Bash.

### Technical debt

- The regex subset intentionally excludes PCRE-only escapes/features such as
  `\d`, `\w`, lazy quantifiers, lookaround, backreferences, and inline flags so
  the VM and Bash can share a portable POSIX ERE surface.
- Bash helper/version-guard behavior follows the existing dependency policy:
  helper code and Bash 4 guards are emitted only for scripts that need the
  corresponding collection/helper behavior.
- Membership remains conservative when the right-hand array element kind is not
  statically known as scalar; unsupported or heterogeneous arrays are rejected
  rather than compared with string coercions.
