# v0.24.0 Spec — Cleanup: Pre-1.0 Hardening

## Status

Implementation and dedicated test-plan pass are complete. This milestone
completed the scoped hardening work without adding production syntax, added the
`tests/v0_24/run.sh` regression suite, and wired it into the aggregate version
test list.

`v0.24.0` is the final cleanup and hardening pass before the project decides
whether the implemented language surface is ready to be declared `1.0.0`. It
must not add new production syntax. Its job is to make the existing language
boring, consistent, documented, and safe enough that the next step can be a
stable-release checklist instead of another feature wave.

This milestone follows the roadmap entry for `v0.24.0 — Cleanup: Pre-1.0
Hardening` and starts from the completed scoped implementation through
`v0.23.0`: exact scalar-array membership, inclusive integer range loop sources,
and conservative regex matching, plus all earlier VM, Bash, cleanup, process,
stdlib, formatter, checker, and test-runner work.

## Goal

Freeze and validate the pre-1.0 supported surface as one coherent scripting
language.

By the end of this milestone, the project should have:

- a documented stable/experimental/deferred support matrix;
- a complete `1.0.0` release checklist;
- regression/parity coverage that exercises the whole supported language, not
  only isolated version slices;
- generated Bash audits proving standalone behavior and helper hygiene;
- examples that accurately demonstrate supported behavior;
- sanitizer-backed confidence in memory ownership for the current C
  implementation;
- clear diagnostics for every unsupported or deferred construct encountered by
  the hardening pass.

The core product rules remain unchanged:

```txt
every supported production feature runs in the VM
every supported production feature emits standalone Bash
generated Bash is standalone and must not call ds
VM and emitted Bash behavior match for stdout, stderr, exit status, and side effects
unsupported or deferred forms fail clearly before partial execution/emission
cleanup work fixes inconsistency without expanding the language surface
```

## Motivation

The language has reached the final roadmap milestone before `1.0.0`. Earlier
versions deliberately shipped small vertical slices: frontend parsing, Bash
emission, VM execution, args, imports, command results, functions, collections,
stdlib helpers, tracing, tests, formatter/checker, control flow, pipelines,
strings, function values/arithmetic, process cleanup/signals, and finally regex,
ranges, and membership.

That incremental approach kept risk low, but it also creates several pre-stable
risks:

1. **The real contract is cross-feature composition.** Users will combine args,
   imports, functions, loops, command results, pipelines, strings, cleanup
   handlers, arithmetic, membership, ranges, and regex in one script. The final
   hardening pass must test those combinations directly.
2. **Docs must stop sounding provisional where behavior is stable.** The README,
   status document, runtime docs, language catalog, examples, and milestone
   notes need one consistent story about what is supported, experimental,
   deferred, rejected, or test-only.
3. **Generated Bash is a first-class deliverable.** Every supported feature must
   keep emitting standalone Bash with deterministic helper inclusion, correct
   quoting, correct Bash-version guards, and no accidental dependency on `ds`.
4. **Diagnostics matter before stability.** Unsupported syntax should fail with
   targeted messages instead of parser fall-through, misleading type errors, or
   backend-only failures.
5. **The C implementation needs one broad ownership pass.** The project now
   exercises owned strings, arrays, maps, regex values, command capture buffers,
   imports, cleanup handlers, generated Bash helpers, and test harness state.
   Obvious leaks, double frees, use-after-frees, and ownership ambiguities should
   be fixed before declaring a stable release.
6. **The release boundary must be explicit.** `1.0.0` should mean the existing
   supported surface is safe to depend on, not that every possible shell feature
   has landed.

## Non-goals

This version does not include:

- new production syntax;
- new expression operators, literals, statement forms, or command forms;
- heredocs, here-strings, command substitution, process substitution, shell
  logical command operators, background jobs, async/wait primitives, or public
  job-control APIs;
- richer signal metadata, handler context values, function-local RAII cleanup,
  or broad process-tree management beyond the supported foreground direct
  command and simple pipeline subset;
- regex captures as values, regex replacement/splitting, runtime regex strings,
  glob/regex `case` patterns, or full PCRE compatibility;
- first-class range values, stepped/reverse/half-open ranges, slices, or range
  membership;
- nested collections, map iteration, index assignment, destructuring, set
  literals, or collection comprehensions;
- collection/command-result function returns, typed return annotations, typed
  required parameters, generics, or recursion semantics beyond the current
  documented behavior;
- direct `env.NAME` assignment/access unless it is already implemented before
  this milestone begins;
- formatter configuration, formatter plugins, warning suppression comments,
  workspace formatting, retained comment/trivia preservation unless narrowly
  accepted as a bug fix for the current formatter contract;
- editor/LSP implementation work;
- backend expansion to zsh, fish, POSIX sh, or native compilation;
- a compatibility-breaking redesign unless a current supported behavior is
  demonstrably confusing or unsafe enough that it must be corrected before
  stability.

Small behavior changes are allowed only when they fix a bug, remove VM/Bash
parity drift, improve an existing misleading diagnostic, remove an unsafe
implementation detail, or clarify the current documented support contract. Every
such change must be recorded in the completion review and reflected in docs and
tests.

### 2. `1.0.0` release checklist

Add a clear `1.0.0` checklist in the most appropriate documentation location
(`docs/status.md`, `docs/roadmap.md`, a new `docs/release-checklist.md`, or a
combination if justified).

The checklist must cover:

### 3. Documentation and examples reconciliation

Review and reconcile:

- README command list, goals, examples, and important-file list;
- architecture boundaries;
- runtime semantics;
- roadmap scope and later-wave notes;
- language syntax catalog status markers;
- editor/build notes;
- current status document;
- milestone docs;
- all examples.

Requirements:

- no doc should claim unsupported syntax is implemented;
- no doc should call implemented supported syntax merely planned;
- docs must distinguish production, test-only, unsupported, rejected, deferred,
  and out-of-scope behavior;
- examples should be valid and representative, except intentionally invalid
  examples such as `examples/bad.ds`;
- examples that cannot be formatted because of documented formatter trivia limits
  must be treated consistently;
- every supported feature family should have at least one example or documented
  reason why it is omitted from examples;
- generated Bash must remain described as standalone.

### 4. Cross-version regression and parity audit

Run and harden all version suites as one regression pass:

- parser/token/AST checks;
- checker diagnostics and warnings;
- formatter checks;
- HIR/bytecode debug views;
- VM execution;
- standalone Bash emission;
- emitted Bash syntax validation with `bash -n`;
- emitted Bash runtime behavior;
- examples;
- test-runner behavior;
- deterministic process cleanup and signal harnesses.

Add coverage only for current supported behavior or clear rejection of current
unsupported/deferred behavior. Do not add new language features to make tests
pass.

### 5. Generated Bash hardening

Audit generated Bash across the complete supported surface.

Requirements:

- emitted Bash must never invoke `ds`;
- helper names must stay inside the reserved `__ds_` namespace;
- helper emission must be deterministic and deduplicated;
- Bash-version guards must appear whenever emitted syntax or helpers require
  Bash 4+ behavior;
- quoting must preserve ds string values, command arguments, regex literals,
  array elements, map keys, file paths, and interpolation results;
- sidecar type metadata must remain consistent for arrays, string helpers,
  function arguments/defaults, range loop variables, arithmetic results,
  membership results, regex results, and command-result fields;
- emitted scripts using imports, functions, tests, cleanup handlers, pipelines,
  regex, ranges, and membership must pass `bash -n`;
- unsupported features must fail during check/lowering/emission instead of
  generating partially invalid Bash.

### 6. VM/runtime and ownership hardening

Review ownership and lifetime behavior for:

- source buffers and imported units;
- tokens, AST, HIR, bytecode, diagnostics, and formatter output;
- `DsValue` strings, arrays, maps, command-result objects, regex payloads, and
  scalar return transport;
- standard-library helper return values;
- command capture stdout/stderr buffers;
- temporary files and process-session signal harness artifacts;
- cleanup/trap handler registration and execution;
- test-block isolation;
- Bash emission buffers and helper dependency state;
- error paths and early returns.

Run sanitizer-backed tests and fix in-scope memory bugs. If a sanitizer failure
exposes a feature bug, fix it in scope when it affects supported behavior; if it
exposes out-of-scope behavior, add or improve the diagnostic/rejection path.

### 7. Diagnostics and unsupported-feature audit

Audit diagnostics for common unsupported/deferred areas, including:

- malformed syntax near implemented constructs;
- invalid `script` declarations and CLI argument values;
- import cycles and missing imports;
- command-result misuse;
- redirection and pipeline misuse;
- function return/value-call misuse;
- arithmetic overflow/division/modulo errors;
- unsupported collection operations;
- invalid stdlib receiver/argument kinds;
- formatter comment/trivia limitations;
- invalid checker flags/warning modes;
- cleanup/signal unsupported forms;
- regex/range/membership rejected forms;
- test-only syntax outside `ds test` if applicable.

Diagnostics should name the unsupported construct, avoid backend-only surprises,
and prefer a short supported alternative when one exists.

## Acceptance criteria

`v0.24.0` is complete only when:

- no new production syntax has been added;
- `docs/status.md` accurately describes the implemented support matrix through
  `v0.23.0` plus any hardening fixes made in this milestone;
- the `1.0.0` release checklist exists and is specific enough to execute;
- every non-intentionally-invalid example is checked, run, emitted to Bash, and
  compared where deterministic;
- all dedicated version suites and aggregate tests pass;
- sanitizer-backed aggregate tests pass or any remaining issue is documented as
  outside supported behavior with a clear rejection path;
- generated Bash is standalone, syntax-valid, helper-clean, and deterministic
  for the supported surface;
- VM/Bash parity is proven for broad cross-feature scripts;
- unsupported/deferred forms discovered during the audit fail clearly;
- docs, examples, status, runtime notes, and language catalog agree;
- completion review records deferred work and technical debt without hiding
  unfinished in-scope work.

## Deferred beyond v0.24.0

These remain deliberately outside this cleanup milestone unless the roadmap is
amended:

- richer module systems and named imports;
- shell completion generation;
- JSON/TOML/dotenv support;
- richer path APIs;
- REPL and interactive debugger;
- explain mode;
- editor/LSP implementation;
- zsh/fish/POSIX-sh/native backends;
- advanced shell syntax and process-control features listed in non-goals;
- larger type-system work such as typed required parameters, generic iterables,
  collection returns, and stable recursion semantics.
