# v0.25.0 Spec — Portable Function Value Return ABI

## Status

Completed. This milestone is the first post-`v0.24.0` pre-`1.0.0` feature
foundation milestone. It follows the roadmap entry for `v0.25.0 — Portable
Function Value Return ABI` and must be implemented before collection-returning
functions, command-result returns, and direct function-call interpolation in
command words.

`v0.25.0` deliberately adds little or no new user-facing syntax. Its purpose is
to make the existing scalar function-return surface portable, explicit, and safe
enough for richer returned values in later milestones.

## Goal

Define and implement a shared function value-return contract for the VM and
emitted Bash.

By the end of this milestone:

- scalar function returns keep their existing user-facing behavior;
- emitted Bash uses a DS-owned typed return payload path for value-returning
  functions instead of relying on ad-hoc stdout capture;
- the VM continues to use real typed runtime values internally;
- VM and emitted Bash agree on returned `string`, `int`, `bool`, and `null`
  values where those values are already legal today;
- ordinary stdout from value-returning functions is rejected or clearly
  diagnosed before it can corrupt the return payload;
- effect/output-oriented functions remain valid when they are not used as value
  expressions;
- docs explain the distinction between output-oriented functions and
  value-returning functions.

The core product rules remain unchanged:

```txt
every supported production feature runs in the VM
every supported production feature emits standalone Bash
generated Bash is standalone and must not call ds
VM and emitted Bash behavior match for stdout, stderr, exit status, and side effects
unsupported or deferred forms fail clearly before partial execution/emission
```

## Motivation

Current scalar function returns are useful, but future roadmap work needs a more
precise contract. Bash functions cannot return rich values directly; they can
only return a small integer status. Everything else must travel through stdout,
variables, files, or a serialization protocol.

If DS later allows this:

```ds
fn names() {
  return ["api", "web"]
}

let apps = names()
```

or this:

```ds
fn search() {
  return run grep "ERROR" "app.log"
}
```

then emitted Bash needs a deterministic way to move typed values from the callee
to the caller. A plain command substitution is not enough because normal stdout
from the function becomes indistinguishable from the returned value.

This milestone solves that foundation first, while the return values are still
scalars. It is intentionally smaller than `v0.26.0`; the collection and
command-result features should be built on top of the protocol established here,
not implemented at the same time.

## Non-goals

This version does not include:

- user-facing collection function returns;
- function returns of arrays, maps, command results, ranges, regexes, or nested
  values;
- command-result object return semantics;
- typed return annotations;
- typed required parameters;
- recursive function semantics beyond the currently documented behavior;
- direct function-call interpolation in command words;
- collection values passed directly to commands;
- command substitution syntax;
- binary-safe string/command-output payloads;
- public serialization APIs;
- user-facing access to the internal value-return payload format;
- changes to the syntax of normal `return expr` statements unless required for
  diagnostics;
- broad refactoring of unrelated function semantics, imports, command execution,
  or cleanup/signal behavior.

Small supporting changes are allowed only when needed to make existing scalar
function returns safe and portable across the VM and emitted Bash.

## Required feature work

### 1. Classify function bodies by value-output behavior

Add or tighten the semantic model that distinguishes:

- **value-returning functions** — functions whose result is used as a value or
  whose body contains a supported `return expr` path;
- **output/effect functions** — functions used for commands, side effects, or
  human-facing stdout without producing a DS value.

Required behavior:

- preserve existing valid scalar value-returning functions;
- preserve existing valid statement-style/effect functions;
- classify functions consistently when used from imports, tests, cleanup
  handlers, loops, conditionals, and other functions;
- continue to enforce existing same-kind/all-path validation for scalar function
  values;
- reject ambiguous uses where a function both needs to return a DS value and
  writes ordinary stdout as part of its body;
- keep diagnostics focused on the source statement that creates the conflict.

The checker may remain conservative. If it cannot prove a function is safe to
use as a value, it should reject the value use with a clear diagnostic instead
of allowing backend-specific behavior.

### 2. Reserve stdout for value payloads in emitted Bash

For value-returning functions, emitted Bash must treat function stdout as an
internal return-value channel.

Required behavior:

- generated Bash functions that return DS values must emit only the encoded DS
  return payload to stdout on successful value-return paths;
- normal user-visible stdout from such functions must be rejected unless the
  statement is redirected away from stdout, for example to stderr or a file;
- debug/tracing output added by generated Bash must not contaminate the return
  payload;
- command failures inside value-returning functions must preserve the existing
  status/error behavior and must not produce partial decoded values;
- functions used only for effects may still write stdout normally.

Examples:

```ds
fn label(name = "api") {
  return "svc-{name}"
}

let value = label("web")
echo "{value}"
```

must remain valid.

```ds
fn bad(name = "api") {
  echo "debug"
  return name
}

let value = bad("web")
```

must be rejected or diagnosed because `echo "debug"` writes ordinary stdout in a
value-returning function.

```ds
fn ok(name = "api") {
  echo "debug" !> "/tmp/ds-debug.log"
  return name
}
```

may be accepted if the implementation can prove the output is redirected away
from stdout using already-supported redirection syntax. If this proof is not
ready, the implementation may conservatively reject command statements inside
value-returning functions and document that narrower rule.

### 3. Add a private typed return payload representation for Bash

Introduce a DS-owned internal representation for emitted Bash value returns. The
exact format is private implementation detail, but it must satisfy these
requirements:

- represent scalar `string`, `int`, `bool`, and `null` values where those are
  legal function return values today;
- preserve empty strings, whitespace, quotes, backslashes, tabs, and newlines in
  returned strings;
- distinguish values by DS kind so string `"2"`, int `2`, bool `true`, and null
  do not collapse into the same payload;
- be deterministic across hosts that satisfy the documented Bash requirement;
- avoid depending on `ds`, the C runtime, `jq`, Python, Perl, or non-standard
  tools at emitted-script runtime;
- be safe under generated Bash strict mode;
- leave room for flat arrays, flat maps, and command-result objects in
  `v0.26.0` without exposing that future encoding as supported user behavior in
  this milestone.

The implementation should prefer boring, parseable encodings such as typed
length-prefixed records or an equivalent Bash-parsable scheme. Plain
newline-separated output is not acceptable because DS strings may contain
newlines.

### 4. Decode value returns at Bash call sites

When emitted Bash calls a value-returning function from an expression position,
the generated caller must:

- capture the function payload;
- capture the function status;
- fail before using the value if the function status indicates failure;
- decode the payload into the expected scalar kind;
- preserve the existing type sidecar behavior used by Bash expression emission;
- reject malformed internal payloads with a generated-script diagnostic that is
  useful during DS development;
- avoid leaking temporary files, variables, or helper state into user-visible
  command behavior.

Supported expression contexts must include the current scalar function-call
surface, such as:

- `let value = f()`;
- `if f() { ... }` when the function returns `bool`;
- `return f()` from another scalar value-returning function;
- scalar interpolation after binding a returned scalar to a variable;
- `case`, `in`, arithmetic, regex, and other existing expression positions
  where scalar-returning function calls are already valid.

This milestone should not expand where function calls are allowed. It should
make existing allowed scalar call positions use the safer protocol.

### 5. Keep VM values direct but aligned

The VM does not need to serialize and deserialize values internally. It should
continue passing `DsValue` values through the runtime function-call mechanism.

However, the VM implementation and tests must align with the Bash protocol:

- same source programs succeed or fail in VM and Bash modes;
- same returned DS value kind and content are observed by callers;
- same diagnostics are produced where possible for stdout-in-value-function
  conflicts;
- command side effects and output remain aligned for effect functions;
- failure paths do not produce usable return values in either backend.

### 6. Diagnostics and docs

Add or update diagnostics for:

- ordinary stdout-producing statements inside value-returning functions;
- command pipelines in value-returning functions when stdout safety cannot be
  proven;
- functions whose return kind cannot be inferred safely;
- functions that mix incompatible scalar return kinds;
- value uses of functions that are effect/output-only;
- backend emission failures caused by unsupported value-return constructs.

Diagnostics should mention the safer alternatives where appropriate:

- bind command output through supported `run` capture if scalar data is needed;
- redirect debug output to stderr or a file;
- split output-oriented and value-returning behavior into separate functions;
- wait for `v0.26.0` for collection and command-result returns.

Update docs only where they would otherwise be misleading:

- `docs/status.md` should distinguish value-returning functions from
  output/effect functions if needed;
- `docs/runtime.md` may describe the value-return ABI at a high level;
- `docs/language.ds` should not claim collection or command-result returns are
  supported by this milestone;
- examples may be adjusted if they rely on behavior that this milestone now
  rightly rejects.

## Bash emission requirements

Generated Bash for this milestone must:

- remain standalone and never call the `ds` binary;
- include value-return helpers only when a script uses value-returning functions;
- use the reserved `__ds_` helper namespace consistently;
- avoid duplicate helper emission;
- preserve strict-mode behavior;
- preserve exact scalar values, including tricky strings;
- keep user stdout separate from internal value payload stdout;
- propagate function failure before decoding or using a value;
- preserve VM/Bash parity for stdout, stderr, exit status, and filesystem side
  effects.

## Examples

Valid scalar value function:

```ds
fn suffix(name = "api") {
  if name == "api" {
    return "service"
  }
  return "worker"
}

let kind = suffix("api")
echo "kind={kind}"
```

Valid effect/output function:

```ds
fn show(name = "api") {
  echo "deploying {name}"
}

show("api")
```

Invalid mixed stdout and value return:

```ds
fn label(name = "api") {
  echo "building label"
  return "svc-{name}"
}

let value = label("web")
```

Valid nested scalar forwarding:

```ds
fn base() {
  return "api"
}

fn decorated() {
  return base()
}

let value = decorated()
echo "{value}"
```

## Acceptance criteria

`v0.25.0` is complete when:

- scalar function returns use the new Bash value-return protocol in emitted
  Bash;
- VM scalar return behavior remains aligned with emitted Bash;
- returned strings preserve empty values, whitespace, shell metacharacters, and
  newlines;
- returned ints, bools, and nulls keep their DS kinds in supported expression
  positions;
- value-returning functions cannot accidentally write ordinary stdout into the
  Bash return payload;
- effect/output functions continue to work when not used as values;
- value use of output-only functions is rejected with a clear diagnostic;
- unsupported collection and command-result returns remain rejected or deferred
  with clear diagnostics;
- generated Bash is standalone, helper emission is deterministic, and scripts
  pass `bash -n`;
- the dedicated `v0.25.0` test plan is implemented;
- docs/examples are updated if the implementation changes the documented support
  boundary;
- the completion review below is filled in.

## Deferred items

Deferred to `v0.26.0`:

- flat array function returns;
- flat map/object function returns;
- command-result object function returns;
- decoding returned structured values at Bash call sites.

Deferred to `v0.27.0`:

- direct function-call interpolation in command words;
- direct `env.NAME` read/assignment syntax.

Deferred beyond this milestone:

- nested collections;
- arrays of maps or maps containing arrays;
- binary-safe command-output value returns;
- public serialization APIs;
- typed return annotations and typed required parameters;
- recursive functions unless a later milestone explicitly admits them.

## Completion review

- Implementation summary: scalar user-function returns now use the private
  typed Bash value-return ABI. VM execution continues to pass real typed values
  directly. Bash-emitted value calls capture the internal return type/value,
  validate the expected scalar kind, and use assignment-by-reference in direct
  binding/assignment/forward-return positions so returned strings keep trailing
  newlines.
- Test summary: `tests/v0_25/run.sh` implements the milestone test plan across
  scalar preservation, kind preservation, nested/imported/test-block returns,
  output/effect function boundaries, deferred return kinds, existing scalar
  diagnostics, helper emission, debug views, formatter/checker behavior, args,
  regex/range/membership, cleanup, and standalone emitted Bash smoke coverage.
- VM/Bash parity notes: valid scalar return cases compare VM and emitted Bash
  stdout, stderr, status, and selected side effects. The suite includes empty,
  whitespace, metacharacter, quote/backslash, and newline strings; integer zero,
  negative, and large integer returns; bool true/false; arithmetic, membership,
  range, regex, import, args, cleanup, and nested return contexts.
- Bash helper/ABI notes: emitted Bash uses the reserved `__ds_return_type` and
  `__ds_return_value` payload variables plus `__ds_call_value_capture`,
  `__ds_call_value_into`, and `__ds_call_value`. Helper emission is
  dependency-based and appears once per emitted script that needs scalar
  value-returning functions. Scripts with no value-returning functions do not
  emit these helpers. The assignment helper avoids local-name collisions with
  destination variables such as `target`.
- Diagnostics added or changed: value uses of output-only functions are
  rejected; functions that mix ordinary command statements with value returns
  are conservatively rejected with a v0.25 diagnostic; collection, map, and
  command-result returns are explicitly deferred to v0.26.0; existing same-kind
  and all-path scalar diagnostics remain active.
- Docs/examples updated: `docs/runtime.md` and `docs/status.md` describe the
  private typed scalar return ABI and the output/effect function distinction.
- Deferred items confirmed: flat array, flat map/object, and command-result
  function returns remain deferred to v0.26.0. Direct function-call
  interpolation in command words and direct `env.NAME` access remain deferred to
  v0.27.0. `return null` remains unsupported because `null` is not a current
  DS value literal.
- Technical debt: redirected stdout and `fail`/plain command statements inside
  value-returning functions are still conservatively rejected rather than proven
  safe. The private Bash ABI is scalar-only and not binary-safe; structured
  values and command-output payloads are intentionally left for later
  milestones.
