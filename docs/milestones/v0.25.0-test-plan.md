# v0.25.0 Test Plan — Portable Function Value Return ABI

## Purpose

This test plan verifies the `v0.25.0` foundation work for scalar value-returning
functions. The milestone is successful only if existing scalar return behavior is
preserved while emitted Bash moves to a private typed value-return protocol that
cannot be corrupted by ordinary function stdout.

The plan intentionally does not test collection or command-result function
returns as supported behavior. Those belong to `v0.26.0`. In this version, tests
should prove that those forms remain rejected or clearly deferred.

## Test suite location

Add a dedicated suite:

```sh
tests/v0_25/run.sh
```

Wire it into the aggregate test runner used by `make test` if the project has a
central version-suite list.

The suite should create temporary `.ds` inputs and emitted Bash outputs under a
test temp directory, run both backends where applicable, compare stdout/stderr
/status, and delete temporary files on success and failure.

## Commands every parity case should exercise

For valid production scripts, each relevant case should run:

```sh
./ds check input.ds
./ds run input.ds [args...]
./ds emit bash input.ds -o out.sh
bash -n out.sh
bash out.sh [args...]
```

Then compare VM and emitted Bash:

- stdout;
- stderr;
- exit status;
- filesystem side effects, when the case creates files.

For diagnostics-only cases, run at least:

```sh
./ds check input.ds
./ds emit bash input.ds -o out.sh
```

when emission is expected to reject the same unsupported form. The test should
assert non-zero status and a stable diagnostic substring, not an entire brittle
multi-line diagnostic unless existing version tests already require full golden
output.

## 1. Scalar return preservation

### 1.1 String return

Input:

```ds
fn name() {
  return "api"
}

let value = name()
echo "value={value}"
```

Expected stdout:

```txt
value=api
```

Assertions:

- VM and Bash match;
- emitted Bash passes `bash -n`;
- generated Bash contains the value-return helper/protocol only once if helper
  scanning is textual and testable;
- generated Bash does not call `ds`.

### 1.2 Empty string return

Input:

```ds
fn empty() {
  return ""
}

let value = empty()
echo "before[{value}]after"
```

Expected stdout:

```txt
before[]after
```

Edge assertion: empty payload content must not be confused with missing payload.

### 1.3 Whitespace string return

Return strings containing:

- leading spaces;
- trailing spaces;
- tabs if the syntax supports them;
- multiple internal spaces.

Example:

```ds
fn padded() {
  return "  api  "
}

let value = padded()
echo "[{value}]"
```

Expected stdout:

```txt
[  api  ]
```

### 1.4 Shell metacharacter string return

Return a string that would be dangerous if unquoted or treated as Bash syntax:

```ds
fn weird() {
  return "a b; rm -rf nope; $(echo bad) * ? [x]"
}

let value = weird()
echo "{value}"
```

Expected stdout must print the literal returned string. The emitted Bash must not
execute `echo bad`, expand `*`, or interpret semicolons as commands.

### 1.5 Newline string return

Use a supported multi-line string form or escape form from the current language
surface.

Example, if triple-quoted strings are supported:

```ds
fn block() {
  return """one
two"""
}

let value = block()
echo "{value}"
```

Expected stdout must preserve the newline exactly according to the language's
existing multi-line string rules. This is the key test that prevents naive
newline-separated Bash payloads.

### 1.6 Integer return

Input:

```ds
fn answer() {
  return 42
}

let value = answer()
echo "n={value}"
```

Expected stdout:

```txt
n=42
```

Also test returned ints in arithmetic:

```ds
fn two() {
  return 2
}

let value = two() * 5
echo "{value}"
```

Expected stdout:

```txt
10
```

### 1.7 Boolean return

Input:

```ds
fn enabled() {
  return true
}

if enabled() {
  echo "yes"
} else {
  echo "no"
}
```

Expected stdout:

```txt
yes
```

Also test `false` with the `else` path.

### 1.8 Null return, if supported by current function returns

If `return null` is currently legal for value-returning functions, test it in the
narrowest existing supported expression context.

If `return null` is not currently legal, add a diagnostic test proving it remains
rejected and update the spec completion notes accordingly.

## 2. Return kind preservation

### 2.1 String and int do not collapse

Input:

```ds
fn as_string() {
  return "2"
}

fn as_int() {
  return 2
}

let s = as_string()
let n = as_int()

if s == "2" {
  echo "string-ok"
}

if n == 2 {
  echo "int-ok"
}
```

Expected stdout:

```txt
string-ok
int-ok
```

Add a negative or behavior test, if the current type system supports it, proving
`as_string()` is not accepted where an int is required.

### 2.2 Bool and string do not collapse

Input:

```ds
fn as_bool() {
  return true
}

fn as_string() {
  return "true"
}

if as_bool() {
  echo "bool-ok"
}

let value = as_string()
echo "string={value}"
```

Expected stdout:

```txt
bool-ok
string=true
```

### 2.3 Returned values retain sidecar kind in Bash

Use returned values in existing kind-sensitive features:

```ds
fn app() {
  return "api"
}

fn port() {
  return 8080
}

fn ok() {
  return true
}

let known = app() in ["api", "web"]
let port_ok = port() in [8080, 9090]
let bool_ok = ok() in [true]

if known && port_ok && bool_ok {
  echo "all-ok"
}
```

Expected stdout:

```txt
all-ok
```

Assertions:

- VM and Bash preserve kind-aware membership;
- returned string `"8080"` must not satisfy integer membership unless explicitly
  converted by a supported language feature.

## 3. Function return composition

### 3.1 Return a scalar call from another function

Input:

```ds
fn base() {
  return "api"
}

fn wrapper() {
  return base()
}

let value = wrapper()
echo "{value}"
```

Expected stdout:

```txt
api
```

### 3.2 Conditional all-path returns

Input:

```ds
fn classify(name = "api") {
  if name == "api" {
    return "service"
  }
  return "worker"
}

let a = classify("api")
let b = classify("job")
echo "{a}"
echo "{b}"
```

Expected stdout:

```txt
service
worker
```

### 3.3 Loops and early returns

Use existing supported loop syntax:

```ds
fn first_match() {
  for name in ["web", "api", "job"] {
    if name == "api" {
      return name
    }
  }
  return "missing"
}

let value = first_match()
echo "{value}"
```

Expected stdout:

```txt
api
```

### 3.4 Imports and scalar returns

Create two files.

`lib.ds`:

```ds
fn service_name() {
  return "api"
}
```

`main.ds`:

```ds
import "./lib.ds"

let value = service_name()
echo "service={value}"
```

Expected stdout:

```txt
service=api
```

Assertions:

- import-aware `check`, `run`, `emit bash`, and emitted Bash all work;
- helper emission remains deterministic when the returning function comes from an
  import.

### 3.5 Test blocks and scalar returns

If test blocks can call functions, add:

```ds
fn value() {
  return 3
}

test "scalar return" {
  assert value() == 3
}
```

Run:

```sh
./ds test input.ds
```

Expected: test passes, and normal `run`/`emit bash` behavior around test blocks
remains unchanged according to existing rules.

## 4. Output/effect function behavior

### 4.1 Statement-style output function remains valid

Input:

```ds
fn show(name = "api") {
  echo "deploying {name}"
}

show("web")
```

Expected stdout:

```txt
deploying web
```

Assertions:

- VM and Bash match;
- no value-return payload text appears in user stdout;
- the function can still be used as a statement.

### 4.2 Output function cannot be used as a value

Input:

```ds
fn show(name = "api") {
  echo "deploying {name}"
}

let value = show("web")
```

Expected:

- `ds check` fails;
- `ds emit bash` fails if checking is not automatically run first;
- diagnostic mentions that the function does not produce a value or writes
  stdout/effects only.

### 4.3 Function with both output and return is rejected for value use

Input:

```ds
fn bad(name = "api") {
  echo "debug"
  return name
}

let value = bad("web")
echo "{value}"
```

Expected:

- check/emission fail;
- diagnostic mentions ordinary stdout in a value-returning function or an unsafe
  mixed output/value function;
- no emitted Bash script is treated as valid output for the test.

### 4.4 Redirected output inside value-returning function

If the implementation supports proving stdout redirection away from stdout, test
that this is accepted:

```ds
fn ok(name = "api") {
  echo "debug" !> "debug.log"
  return name
}

let value = ok("web")
echo "{value}"
```

Expected stdout:

```txt
web
```

Expected side effect: `debug.log` contains `debug` according to existing
redirection semantics.

If the implementation conservatively rejects all command statements inside
value-returning functions, this case should be a diagnostic test instead, and
the completion review must say that redirected stdout proof was deferred.

### 4.5 stderr/log output does not corrupt payload if supported

If the language has a supported way to write to stderr from inside a function,
verify it is allowed in value-returning functions and does not corrupt the
returned value.

If there is no supported stderr-only form today, record this as not applicable.

## 5. Failure and status behavior

### 5.1 Failure before return does not decode a value

Use an existing supported failure mechanism inside a value-returning function.

Example, if `fail` is supported in production code:

```ds
fn bad() {
  fail "no value"
  return "unreachable"
}

let value = bad()
echo "{value}"
```

Expected:

- VM and Bash exit non-zero;
- no `unreachable` output is printed;
- emitted Bash does not attempt to decode a payload after failure.

If `fail` is test-only or unavailable in this context, use the existing command
failure semantics that the current function surface supports.

### 5.2 Command failure in value-returning function

For the current command failure rules, test a function that runs a failing
command before returning. The expected behavior should match existing strictness
semantics.

Assertions:

- VM and Bash agree on status;
- no partial return value is consumed;
- user stdout/stderr behavior matches.

### 5.3 Malformed internal payload guard in generated Bash

If generated helpers expose a reasonable internal guard path, add a direct
generated-Bash development test that corrupts a captured payload only inside the
test harness and verifies a clear generated-script diagnostic.

If this would require brittle generated-code mutation, skip it and rely on unit
tests for the helper parser.

## 6. Unsupported/deferred return values

These tests ensure `v0.26.0` work is not accidentally pulled into `v0.25.0`.

### 6.1 Array return is still unsupported

Input:

```ds
fn names() {
  return ["api", "web"]
}

let value = names()
```

Expected:

- rejected in `v0.25.0`;
- diagnostic mentions collection/array function returns are deferred or
  unsupported.

### 6.2 Map return is still unsupported

Input:

```ds
fn user() {
  return { name: "Ana" }
}

let value = user()
```

Expected: rejected with a clear map/object return diagnostic.

### 6.3 Command-result return is still unsupported

Input:

```ds
fn search() {
  return run grep "x" "file.txt"
}

let result = search()
```

Expected: rejected with a diagnostic pointing to `v0.26.0`/future support for
command-result returns.

### 6.4 Mixed scalar and collection returns

Input:

```ds
fn bad(flag = true) {
  if flag {
    return "api"
  }
  return ["api"]
}

let value = bad(false)
```

Expected: rejected as incompatible/deferred return kinds.

## 7. Existing scalar diagnostics stay correct

### 7.1 Mixed scalar return kinds

Input:

```ds
fn bad(flag = true) {
  if flag {
    return "api"
  }
  return 1
}

let value = bad(false)
```

Expected: same-kind/all-path diagnostic remains clear.

### 7.2 Missing return path

Input:

```ds
fn maybe(flag = true) {
  if flag {
    return "api"
  }
}

let value = maybe(false)
```

Expected: all-path return diagnostic remains clear.

### 7.3 Forward function-value calls remain conservative

Use the currently documented forward-call limitation:

```ds
fn a() {
  return b()
}

fn b() {
  return 1
}

let value = a()
```

Expected: either accepted if this milestone deliberately fixes the limitation,
or rejected with the existing conservative diagnostic. The implementation must
not accidentally accept it only in one backend.

## 8. Bash emission helper tests

### 8.1 Standalone Bash

For every valid emitted script in the suite:

- `bash -n out.sh` succeeds;
- running `out.sh` does not require `ds` in `PATH`;
- generated Bash contains no command invocation of `ds`.

If the test harness can safely run with a restricted `PATH`, include at least one
case where `ds` is unavailable and the emitted Bash still runs.

### 8.2 Helper emission only when needed

Test a script with no value-returning functions:

```ds
echo "hello"
```

Expected: emitted Bash should not include value-return helpers unless the
project's helper policy intentionally emits all helpers unconditionally. If
helpers are unconditional, document that in the completion review.

Test a script with multiple value-returning functions:

```ds
fn a() { return "a" }
fn b() { return "b" }

let x = a()
let y = b()
echo "{x}{y}"
```

Expected: helpers are emitted once, names use the reserved `__ds_` namespace,
and output is:

```txt
ab
```

### 8.3 Strict-mode compatibility

Run emitted Bash for valid cases under the generated strict-mode header. Tests
should catch unbound variables, failed helper commands, and accidental word
splitting introduced by the new protocol.

### 8.4 No payload leak to user stdout

For a script such as:

```ds
fn value() {
  return "api"
}

let v = value()
echo "user:{v}"
```

Expected stdout:

```txt
user:api
```

There must be no encoded payload marker, length prefix, helper debug text, or
sidecar value visible in stdout.

## 9. Parser, HIR, bytecode, and debug-view tests

Because this milestone should not add new syntax, parser/token golden changes
should be minimal.

Required checks:

- existing valid scalar-returning function syntax still parses;
- invalid collection/command-result returns fail in semantic checking or
  lowering with targeted messages rather than parser confusion;
- `ds hir` output for value-returning functions remains deterministic and, if
  the HIR representation changes, includes enough structure to show the value
  function classification;
- `ds bytecode` output remains deterministic for scalar-returning functions;
- debug views do not expose unstable internal Bash payload details as user
  syntax.

If HIR/bytecode golden files are not part of the existing test style, use smoke
tests that run the commands and assert success/non-empty deterministic output.

## 10. Formatter and checker tests

### 10.1 Formatter preservation

Run `ds fmt --check` and normal `ds fmt` on representative scalar-returning
function files. Expected formatting should not change because this milestone
adds no new surface syntax.

### 10.2 Checker warning behavior

Verify that value-return ABI changes do not suppress existing warnings such as:

- unused parameters in value-returning functions;
- unreachable statements after `return`;
- shadowing warnings where already implemented.

Run with:

```sh
./ds check input.ds
./ds check --warnings-as-errors input.ds
./ds check --no-warnings input.ds
```

where appropriate.

## 11. Cross-feature parity cases

### 11.1 Args plus scalar function returns

Input:

```ds
script {
  arg app: string
  flag prod: bool = false
}

fn target_name() {
  if prod {
    return "production"
  }
  return "staging"
}

let target = target_name()
echo "{app}:{target}"
```

Run VM and emitted Bash with:

```sh
api --prod
```

Expected stdout:

```txt
api:production
```

### 11.2 Regex/range/membership plus scalar returns

Input:

```ds
fn app() {
  return "api"
}

fn count() {
  return 3
}

let name = app()

if name in ["api", "web"] && name matches /^a/ {
  for n in 1..count() {
    echo "{name}:{n}"
  }
}
```

Expected stdout:

```txt
api:1
api:2
api:3
```

This proves returned scalar values carry enough kind information into `in`,
`matches`, and range-bound expression contexts.

### 11.3 Cleanup handlers and returned values

If cleanup handlers can call functions or observe values, add a case that
ensures returned scalar values and cleanup output do not corrupt each other.

Example shape:

```ds
fn label() {
  return "api"
}

defer {
  echo "cleanup"
}

let value = label()
echo "{value}"
```

Expected stdout ordering should follow existing cleanup semantics.

## 12. Sanitizer and regression expectations

At minimum, after implementing this test plan, run:

```sh
make test
```

Before closing the milestone, also run sanitizer targets if available:

```sh
make test-asan
make test-ubsan
```

The value-return protocol is likely to touch string ownership, temporary
buffers, emitted Bash helper generation, and function call state. Sanitizer
failures should be treated as milestone blockers unless clearly unrelated and
documented.

## 13. Edge cases checklist

The dedicated suite should cover as many of these as the current language
surface allows:

- empty returned string;
- returned string with leading/trailing spaces;
- returned string with quotes and backslashes;
- returned string with shell metacharacters;
- returned string with newlines;
- returned integer zero;
- returned negative integer;
- returned large integer within the existing supported integer range;
- returned boolean true and false;
- returned null if legal, or diagnostic if illegal;
- nested scalar function calls;
- scalar return from imported function;
- scalar return used in `if`;
- scalar return used in arithmetic;
- scalar return used in `case` if supported;
- scalar return used in `in` membership;
- scalar return used as a range bound;
- scalar return used as regex left operand;
- function with stdout and no value used as statement;
- function with stdout used as value rejected;
- function with stdout plus `return` rejected for value use;
- redirected stdout inside value function accepted or explicitly rejected by
  documented conservative rule;
- array return rejected;
- map return rejected;
- command-result return rejected;
- mixed scalar return kinds rejected;
- missing return path rejected;
- emitted Bash helper emitted once;
- emitted Bash helper absent when not needed, unless helper policy says
  otherwise;
- emitted Bash does not leak payload text;
- emitted Bash remains standalone.

## 14. Manual smoke tests

After automated tests pass, manually inspect at least one emitted Bash file that
contains scalar value-returning functions.

Check that:

- the generated helper names are reserved and deterministic;
- the payload format is not documented as user syntax;
- string quoting is understandable and not obviously vulnerable to word
  splitting or command substitution;
- user-visible stdout is only produced by the original DS script behavior;
- comments or source markers, if emitted, do not appear inside payload-producing
  command substitutions in a way that changes behavior.

Also manually run an emitted Bash script from a directory that does not contain
the original `.ds` file to verify that standalone behavior does not depend on
source-file paths for value-return helpers.

## 15. Completion evidence

When closing `v0.25.0`, record in the spec completion review:

- which payload representation was chosen at a high level;
- whether redirected stdout inside value-returning functions is accepted or
  conservatively rejected;
- whether `return null` is supported or rejected;
- whether helper emission is dependency-based or unconditional;
- any remaining conservative inference limitations;
- full `make test` result;
- sanitizer result or reason it was not run;
- docs/examples changed;
- known technical debt carried into `v0.26.0`.
