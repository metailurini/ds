# v0.26.0 Test Plan — Flat Collection and Command-Result Function Returns

## Purpose

This test plan verifies that `v0.26.0` adds the first structured function
returns on top of the `v0.25.0` value-return ABI without weakening VM/Bash parity
or standalone Bash emission.

The milestone is successful only if functions can return:

- flat arrays of scalar values;
- flat maps/objects with string keys and scalar values;
- command-result objects with stdout, stderr, and status behavior matching the
  existing command-result surface.

The plan intentionally does not treat nested collections, map iteration, index
assignment, direct function-call interpolation in command words, streaming
command results, or binary command capture as supported behavior.

## Test suite location

Add a dedicated suite:

```sh
tests/v0_26/run.sh
```

Wire it into the aggregate test runner used by `make test` if the project has a
central version-suite list. Add matching `make test-v0-26` support if the
Makefile uses per-version targets.

The suite should create private deterministic temp directories, write `.ds`
fixtures, emit Bash scripts, run VM and emitted Bash modes, compare results, and
clean temporary files on success and failure.

## Commands every parity case should exercise

For valid production scripts, each relevant case should run:

```sh
./ds check input.ds
./ds run input.ds [args...]
./ds emit bash input.ds -o out.sh
bash -n out.sh
bash out.sh [args...]
```

Then compare VM and emitted Bash:

- stdout;
- stderr;
- exit status;
- deterministic filesystem side effects, when applicable.

For diagnostics-only cases, run at least:

```sh
./ds check input.ds
./ds emit bash input.ds -o out.sh
```

The test should assert non-zero status and a stable diagnostic substring. Avoid
brittle full multi-line diagnostics unless existing suite style requires golden
output.

For every emitted Bash script, assert:

- `bash -n out.sh` succeeds;
- the generated script does not call the `ds` binary;
- DS helper names use the reserved `__ds_` prefix;
- value-return helpers are emitted only when needed and are not duplicated where
  textual helper scanning is already tested elsewhere.

## 1. Flat array function returns

### 1.1 String array return

Input:

```ds
fn apps() {
  return ["api", "web", "worker"]
}

let names = apps()
echo names[0]
echo names[1]
echo names[2]
```

Expected stdout:

```txt
api
web
worker
```

Assertions:

- array order is preserved;
- VM and Bash output/status match;
- emitted Bash passes `bash -n` and is standalone.

### 1.2 Empty string and whitespace array elements

Input:

```ds
fn values() {
  return ["", "  api  ", "a b c"]
}

let xs = values()
echo "[{xs[0]}]"
echo "[{xs[1]}]"
echo "[{xs[2]}]"
```

Expected stdout:

```txt
[]
[  api  ]
[a b c]
```

Edge assertion: empty element payloads must not be lost or confused with missing
elements.

### 1.3 Shell metacharacter array elements

Input:

```ds
fn values() {
  return ["a b", "semi;colon", "$(echo bad)", "*?[x]"]
}

let xs = values()
echo xs[0]
echo xs[1]
echo xs[2]
echo xs[3]
```

Expected stdout must print the literal strings. The emitted Bash must not execute
`echo bad`, expand globs, or interpret semicolons as commands.

### 1.4 Newline-containing array element

Use the current supported multi-line string syntax.

Example, if triple-quoted strings are supported:

```ds
fn values() {
  return ["head", """one
two""", "tail"]
}

let xs = values()
echo xs[0]
echo xs[1]
echo xs[2]
```

Expected stdout must preserve the newline exactly according to existing string
rules. This prevents naive newline-separated array payloads.

### 1.5 Integer array return

Input:

```ds
fn nums() {
  return [1, 2, 3]
}

let xs = nums()
let total = xs[0] + xs[1] + xs[2]
echo total
```

Expected stdout:

```txt
6
```

Assertion: returned elements keep integer kind in Bash expression sidecars.

### 1.6 Boolean array return

Input:

```ds
fn flags() {
  return [true, false, true]
}

let xs = flags()
if xs[0] {
  echo "first"
}
if !xs[1] {
  echo "second-false"
}
if xs[2] {
  echo "third"
}
```

Expected stdout:

```txt
first
second-false
third
```

### 1.7 Returned array in existing array loop

Input:

```ds
fn apps() {
  return ["api", "web", "worker"]
}

let names = apps()
for name in names {
  echo "app={name}"
}
```

Expected stdout:

```txt
app=api
app=web
app=worker
```

Assertion: this uses only already-supported array loops, not new map iteration.

### 1.8 Returned array in membership check

Input:

```ds
fn allowed() {
  return ["api", "web"]
}

let names = allowed()
if "api" in names {
  echo "api-ok"
}
if !("db" in names) {
  echo "db-missing"
}
```

Expected stdout:

```txt
api-ok
db-missing
```

### 1.9 Return array variable

Input:

```ds
fn apps() {
  let local = ["api", "web"]
  return local
}

let names = apps()
echo names[1]
```

Expected stdout:

```txt
web
```

Assertion: returned array ownership/lifetime is independent of the callee's local
variable lifetime.

### 1.10 Forward returned array through another function

Input:

```ds
fn base() {
  return ["api", "web"]
}

fn wrapper() {
  return base()
}

let names = wrapper()
echo names[0]
echo names[1]
```

Expected stdout:

```txt
api
web
```

## 2. Flat map/object function returns

### 2.1 String/int/bool map return

Input:

```ds
fn service() {
  return { name: "api", port: 8080, enabled: true }
}

let app = service()
echo app.name
echo app.port
if app.enabled {
  echo "enabled"
}
```

Expected stdout:

```txt
api
8080
enabled
```

Assertions:

- field lookup matches equivalent non-returned map/object behavior;
- scalar kinds survive Bash decode.

### 2.2 Map values with empty/whitespace/metacharacter strings

Input:

```ds
fn labels() {
  return { empty: "", padded: "  api  ", shell: "$(echo bad); *" }
}

let data = labels()
echo "[{data.empty}]"
echo "[{data.padded}]"
echo "{data.shell}"
```

Expected stdout:

```txt
[]
[  api  ]
$(echo bad); *
```

The emitted Bash must not execute `echo bad` or expand `*`.

### 2.3 Newline-containing map value

Use supported multi-line string syntax:

```ds
fn data() {
  return { text: """one
two""" }
}

let value = data()
echo value.text
```

Expected stdout preserves the newline exactly according to existing string rules.

### 2.4 Return map variable

Input:

```ds
fn service() {
  let app = { name: "api", tier: "frontend" }
  return app
}

let value = service()
echo "{value.name}:{value.tier}"
```

Expected stdout:

```txt
api:frontend
```

Assertion: returned map ownership/lifetime is independent of callee local scope.

### 2.5 Forward returned map through another function

Input:

```ds
fn base() {
  return { name: "api", port: 8080 }
}

fn wrapper() {
  return base()
}

let value = wrapper()
echo "{value.name}:{value.port}"
```

Expected stdout:

```txt
api:8080
```

### 2.6 Duplicate-key behavior matches existing map literal rules

Use the current language's documented duplicate-key behavior. For example, if the
last key wins:

```ds
fn data() {
  return { name: "old", name: "new" }
}

let value = data()
echo value.name
```

Expected stdout should match the existing non-returned map behavior.

If duplicate keys are rejected, assert that the diagnostic remains the same for
returned map literals.

### 2.7 Missing field behavior matches existing map lookup rules

Input should use an existing supported missing-field scenario. If missing fields
are diagnostics, assert `ds check` rejects. If they produce `null` or a runtime
failure, assert VM/Bash parity.

The key requirement is that returning the map from a function must not change the
missing-field semantics.

## 3. Command-result function returns

### 3.1 Successful command result return

Input:

```ds
fn probe() {
  return run printf "hello"
}

let result = probe()
echo "stdout={result.stdout}"
echo "status={result.status}"
```

Expected stdout:

```txt
stdout=hello
status=0
```

If the current command-result API uses `code` instead of or in addition to
`status`, assert the existing field names documented in the current language
surface.

### 3.2 Command result preserves stderr

Input:

```ds
fn probe() {
  return run sh -c "printf err >&2"
}

let result = probe()
echo "stdout=[{result.stdout}]"
echo "stderr=[{result.stderr}]"
echo "status={result.status}"
```

Expected stdout:

```txt
stdout=[]
stderr=[err]
status=0
```

VM stderr and emitted Bash stderr should remain empty unless the existing command
capture surface intentionally mirrors captured stderr to script stderr.

### 3.3 Non-zero captured command result is data

Input:

```ds
fn missing() {
  return run sh -c "printf nope >&2; exit 7"
}

let result = missing()
echo "status={result.status}"
if result.failed {
  echo "failed"
}
echo "stderr={result.stderr}"
```

Expected stdout:

```txt
status=7
failed
stderr=nope
```

Expected script status: `0`, unless the existing command-result contract differs.
The test must match the current documented `run` capture rule.

### 3.4 Command result preserves multiline stdout/stderr

Input:

```ds
fn probe() {
  return run sh -c "printf 'one\ntwo\n'; printf 'err1\nerr2\n' >&2"
}

let result = probe()
echo result.stdout
echo result.stderr
```

Expected stdout should contain the captured stdout followed by captured stderr
exactly according to current command-result string trimming/trailing-newline
rules. This verifies the value payload is not newline-delimited naively.

### 3.5 Return command-result variable

Input:

```ds
fn probe() {
  let result = run printf "api"
  return result
}

let value = probe()
echo value.stdout
```

Expected stdout:

```txt
api
```

### 3.6 Forward command result through another function

Input:

```ds
fn base() {
  return run printf "api"
}

fn wrapper() {
  return base()
}

let value = wrapper()
echo value.stdout
echo value.status
```

Expected stdout:

```txt
api
0
```

### 3.7 Command result from imported function

Create two files.

`lib.ds`:

```ds
fn probe(name = "api") {
  return run printf "service=%s" name
}
```

`main.ds`:

```ds
import "./lib.ds"

let result = probe("web")
echo result.stdout
echo result.status
```

Expected stdout:

```txt
service=web
0
```

Assertions:

- import-aware `check`, `run`, `emit bash`, and emitted Bash all work;
- helper emission remains deterministic with structured-returning functions in
  imports.

## 4. Return-kind validation

### 4.1 Mixed array and scalar return is rejected

Input:

```ds
fn bad(flag = true) {
  if flag {
    return ["api"]
  }
  return "api"
}

let value = bad(false)
```

Expected:

- `ds check` fails;
- `ds emit bash` fails;
- diagnostic mentions incompatible return kinds or same-kind return requirement.

### 4.2 Mixed array and map return is rejected

Input:

```ds
fn bad(flag = true) {
  if flag {
    return ["api"]
  }
  return { name: "api" }
}

let value = bad(false)
```

Expected diagnostic: incompatible return kinds.

### 4.3 Mixed map and command-result return is rejected

Input:

```ds
fn bad(flag = true) {
  if flag {
    return { stdout: "manual", stderr: "", status: 0 }
  }
  return run printf "api"
}

let value = bad(false)
```

Expected diagnostic: incompatible return kinds, even if the map fields look
similar. A command result remains a distinct DS value kind unless the language
explicitly documents otherwise.

### 4.4 Incompatible array element kinds follow existing collection rules

Use the current rule for arrays such as `[1, "two"]`:

- if mixed scalar arrays are supported, assert returned mixed arrays preserve
  each element kind;
- if mixed scalar arrays are rejected, assert the returned array literal is
  rejected with the same diagnostic as a non-returned mixed array.

### 4.5 Incompatible map value kinds follow existing collection rules

Use the current rule for maps such as `{ a: 1, b: "two" }`:

- if mixed scalar map values are supported, assert returned values preserve each
  field kind;
- if mixed scalar map values are rejected, assert the returned map literal is
  rejected with the same diagnostic as a non-returned mixed map.

### 4.6 Missing return path for structured values is rejected

Input:

```ds
fn bad(flag = true) {
  if flag {
    return ["api"]
  }
}

let value = bad(false)
```

Expected diagnostic: not all paths return a value or equivalent existing message.

## 5. Deferred unsupported forms

### 5.1 Nested array return is rejected

Input:

```ds
fn nested() {
  return [["api"], ["web"]]
}

let value = nested()
```

Expected diagnostic mentions nested arrays/collections are unsupported or
currently deferred.

### 5.2 Nested map return is rejected

Input:

```ds
fn nested() {
  return { app: { name: "api" } }
}

let value = nested()
```

Expected diagnostic mentions nested maps/collections are unsupported or deferred.

### 5.3 Array of maps is rejected

Input:

```ds
fn services() {
  return [{ name: "api" }, { name: "web" }]
}

let value = services()
```

Expected diagnostic mentions arrays of maps or nested collections are unsupported
or deferred.

### 5.4 Map containing array is rejected

Input:

```ds
fn data() {
  return { names: ["api", "web"] }
}

let value = data()
```

Expected diagnostic mentions maps containing arrays or nested collections are
unsupported or deferred.

### 5.5 Direct structured function interpolation remains rejected

Input:

```ds
fn apps() {
  return ["api", "web"]
}

echo "{apps()}"
```

Expected diagnostic:

- direct function-call interpolation in command words is still deferred; or
- structured values cannot be interpolated directly.

This test guards against accidentally implementing `v0.27.0` behavior too early.

### 5.6 Map iteration remains rejected

Input:

```ds
fn service() {
  return { name: "api", port: 8080 }
}

let data = service()
for key, value in data {
  echo key
}
```

Expected diagnostic: map iteration is unsupported/deferred.

### 5.7 Index assignment remains rejected

Input:

```ds
fn apps() {
  return ["api", "web"]
}

let names = apps()
names[0] = "worker"
```

Expected diagnostic: index assignment is unsupported/deferred.

## 6. Stdout safety and value-return ABI regression

### 6.1 Structured value-returning function cannot write ordinary stdout

Input:

```ds
fn bad() {
  echo "debug"
  return ["api"]
}

let value = bad()
echo value[0]
```

Expected:

- `ds check` fails or `ds emit bash` fails before generating runnable Bash;
- diagnostic mentions stdout in a value-returning function, following the
  `v0.25.0` rule.

### 6.2 Redirected output inside structured value function

If `v0.25.0` accepts stdout-producing statements redirected away from stdout,
add:

```ds
fn ok(path = "debug.log") {
  echo "debug" !> path
  return ["api"]
}

let value = ok("debug.log")
echo value[0]
```

Expected stdout:

```txt
api
```

Also assert the file contains `debug` and VM/Bash side effects match.

If redirected output is conservatively rejected in `v0.25.0`, add a diagnostic
test proving the same rule applies to structured value-returning functions.

### 6.3 Effect/output function returning no value remains valid

Input:

```ds
fn show() {
  echo "api"
}

show()
```

Expected stdout:

```txt
api
```

Assertion: adding structured return support must not encode payloads for
statement-only output functions.

### 6.4 Effect/output function cannot be used as structured value

Input:

```ds
fn show() {
  echo "api"
}

let value = show()
echo value[0]
```

Expected diagnostic: function does not produce a value or is output/effect-only.

## 7. Imports and multi-file parity

### 7.1 Imported array, map, and command-result functions together

`lib.ds`:

```ds
fn apps() {
  return ["api", "web"]
}

fn service() {
  return { name: "api", port: 8080 }
}

fn probe() {
  return run printf "ok"
}
```

`main.ds`:

```ds
import "./lib.ds"

let names = apps()
let svc = service()
let result = probe()

echo names[1]
echo "{svc.name}:{svc.port}"
echo "{result.stdout}:{result.status}"
```

Expected stdout:

```txt
web
api:8080
ok:0
```

Assertions:

- import resolution remains relative to the importing file;
- generated Bash contains all needed helpers exactly once where textual helper
  assertions are practical;
- VM and emitted Bash match.

## Acceptance checklist

`v0.26.0` test implementation is complete when:

- flat array return parity tests pass;
- flat map/object return parity tests pass;
- command-result return parity tests pass;
- returned structured values preserve scalar kinds and tricky string contents;
- imported structured-returning functions work in VM and emitted Bash;
- non-zero command-result statuses remain data under the existing capture rule;
- stdout-safety diagnostics still protect value-returning functions;
- mixed/incomplete return kinds are rejected clearly;
- deferred nested collection, map iteration, index assignment, and direct
  structured interpolation forms are rejected clearly;
- generated Bash is standalone, helper emission is deterministic, and every
  emitted fixture passes `bash -n`;
- docs/examples are updated and checked where they become stale;
- aggregate and sanitizer-capable test targets are run or honestly documented in
  the completion review.
