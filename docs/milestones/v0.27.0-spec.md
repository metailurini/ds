# v0.27.0 Spec — Environment Variables and Direct Function Interpolation

## Status

Implementation complete for the implementation pass. This milestone follows `v0.26.0 — Flat
Collection and Command-Result Function Returns` and relies on the portable
scalar value-return rules from `v0.25.0`.

Current implementation note: direct `env.NAME` reads, `env.NAME = scalar`
assignments, expression-backed scalar function-call interpolation, and quoted
command-word scalar function-call interpolation are implemented for VM execution
and emitted Bash. Command-word calls are lowered into private pre-command string
bindings so the outer command only launches after all interpolated calls
succeed.

`v0.27.0` is an ergonomics milestone, not a new data-model milestone. It adds
direct environment-variable access/assignment and allows scalar-returning
functions to be called directly from command-word/string interpolation. It must
not expand collection interpolation, command substitution, scoped environment
blocks, map iteration, index assignment, regex behavior, glob behavior, or
signal/job-control behavior.

## Goal

Make common shell-oriented scripts easier to write while preserving the DS
product contract:

```txt
every supported production feature runs in the VM
every supported production feature emits standalone Bash
generated Bash is standalone and must not call ds
VM and emitted Bash behavior match for stdout, stderr, exit status, and side effects
unsupported or deferred forms fail clearly before partial execution/emission
```

By the end of this milestone:

- scripts can read environment variables through `env.NAME`;
- scripts can assign environment variables through `env.NAME = value`;
- assigned environment variables are visible to child commands in VM mode and
  emitted Bash mode;
- environment values have a documented missing-variable behavior;
- unset support exists if it fits the existing grammar without broad redesign;
- scalar-returning functions can be used directly inside interpolation;
- interpolated function calls run before the outer command is launched;
- failures from interpolated function calls stop the outer command consistently;
- collection-returning, command-result-returning, or stdout-producing functions
  are rejected in command-word interpolation with clear diagnostics;
- all behavior remains deterministic and Bash-emittable without calling `ds`.

## Motivation

DS is a shell-native language. Reading and setting environment variables is a
core scripting need, and forcing users through low-level command workarounds
makes DS feel less direct than Bash.

Users should be able to write:

```ds
env.APP_ENV = "test"
run "./server"
```

and know the child command sees `APP_ENV=test` in both VM and emitted Bash.

The value-return ABI from `v0.25.0` also makes this common pattern safe:

```ds
fn artifact_name() {
  return "app.tar.gz"
}

run "tar" "-tf" "{artifact_name()}"
```

Without a direct interpolation form, users must introduce throwaway variables
for simple scalar helper calls. This milestone removes that friction while
keeping the rule strict: only scalar, stdout-clean value functions may be used
inside interpolation.

## Non-goals

This version does not include:

- scoped environment blocks such as `with env.NAME = value { ... }`;
- environment append/prepend shorthand such as `env.PATH += ":bin"`;
- declaration-time environment defaults for `script { ... }` args/options;
- automatic `.env` file loading;
- environment-variable iteration;
- non-scalar environment values;
- collection interpolation in command words;
- command-result interpolation in command words;
- direct interpolation of arrays, maps, jobs, regex values, or cleanup handler
  values;
- arbitrary command substitution inside command words;
- function calls inside command names if the current command model cannot make
  that portable safely;
- nested function-call interpolation beyond what is needed for scalar calls;
- new map iteration, index assignment, regex, glob, signal, or job-control
  behavior.

Small supporting changes are allowed only when they are required for the scoped
environment and scalar interpolation behavior to be correct, diagnosable, and
portable.

## Required feature work

### 1. Environment reads through `env.NAME`

Add direct read access for environment variables through the reserved `env`
namespace.

Supported form:

```ds
echo env.PATH
let home = env.HOME
```

Required behavior:

- `env` is a reserved environment namespace, not an ordinary user variable;
- `env.NAME` reads the process environment variable named `NAME`;
- the allowed `NAME` shape must be documented and diagnosed consistently;
- valid names should match the conventional shell environment shape unless the
  language already has a stricter identifier rule:
  `[A-Za-z_][A-Za-z0-9_]*`;
- reads work in expressions, interpolation, conditionals, assignments, function
  bodies, and imported modules where equivalent scalar values are legal;
- emitted Bash reads the environment at runtime, not at DS compile time;
- VM mode reads the environment from the process environment visible to `ds`;
- VM and emitted Bash agree for present variables, empty variables, and missing
  variables.

Missing-variable behavior must be chosen deliberately. Preferred rule:

```txt
env.NAME reads as an empty string when NAME is absent.
```

This matches common shell behavior and makes emitted Bash straightforward. If
the current language already distinguishes null/missing scalar values in a way
that is clearly documented, the implementation may choose that model instead,
but the chosen behavior must be reflected in `docs/status.md` and
`docs/language.ds`.

Examples:

```ds
echo "home={env.HOME}"
```

```ds
let mode = env.APP_MODE
if mode == "prod" {
  echo "production"
}
```

### 2. Environment assignment through `env.NAME = value`

Add assignment to environment variables.

Supported form:

```ds
env.APP_ENV = "test"
env.RETRIES = 3
env.DEBUG = true
```

Required behavior:

- assignment updates the current script process environment;
- assigned values are exported to child commands launched after the assignment;
- assigning a scalar value converts it to the documented environment string
  representation;
- string assignment preserves bytes according to existing string rules, except
  NUL bytes remain unsupported if the language/runtime already cannot represent
  them safely;
- integer assignment uses the canonical decimal string representation;
- boolean assignment uses the canonical DS boolean string representation chosen
  for environment export, preferably `true` and `false`;
- assignment order is observable by later environment reads and child commands;
- assignments inside function calls affect the same environment scope as other
  top-level assignments unless the current language already has stronger local
  scope rules;
- emitted Bash must use safe quoting and must not accidentally execute assigned
  values;
- generated Bash must not rely on `ds` to export variables.

Examples:

```ds
env.APP_ENV = "test"
run "sh" "-c" "printf '%s\n' \"$APP_ENV\""
```

```ds
fn configure() {
  env.DEBUG = true
}

configure()
echo env.DEBUG
```

### 3. Environment unset support, if grammar-compatible

Add a way to remove environment variables if the existing grammar already has a
natural unset/delete form or can accept one without a broad redesign.

Preferred user-facing form, if aligned with existing syntax:

```ds
unset env.DEBUG
```

Required behavior if included:

- unsetting removes the variable from the current script environment;
- child commands launched after unset do not receive the variable from DS;
- reading the variable after unset uses the chosen missing-variable behavior;
- emitted Bash uses `unset NAME` safely;
- invalid unset targets are diagnosed.

If unset support would require an awkward special case or conflict with existing
syntax, defer it explicitly and document that `v0.27.0` supports reads and
assignments only.

### 4. Scalar function calls inside interpolation

Allow a direct function call as an interpolation expression when the function is
known to return a scalar value.

Supported forms:

```ds
echo "artifact={artifact_name()}"
run "tar" "-tf" "{artifact_name()}"
```

Scalar return kinds for this milestone:

- string;
- int;
- bool;
- null/status-like scalar kinds only if they already have a documented command
  interpolation representation.

Required behavior:

- the interpolated function call is evaluated before the outer command launches;
- if the function fails, the outer command must not launch;
- failure propagation must match ordinary value-returning function-call
  behavior in VM and emitted Bash;
- the function must obey the `v0.25.0` stdout-clean value-returning rule;
- emitted Bash captures the function return payload through the private ABI,
  decodes it, renders it as a command word/string fragment, then launches the
  outer command;
- decoded values must be quoted safely so shell metacharacters in returned
  strings are literal data, not shell syntax;
- repeated calls in one command are evaluated exactly once per interpolation
  occurrence and in left-to-right order unless the language has already
  documented a different expression evaluation order;
- imported scalar-returning functions work the same as local functions;
- diagnostics are clear when the checker cannot prove the interpolated function
  returns a scalar kind.

Examples:

```ds
fn name() {
  return "api"
}

echo "deploying {name()}"
```

```ds
fn suffix() {
  return 42
}

run "printf" "%s\n" "build-{suffix()}"
```

### 5. Rejections and diagnostics

Reject unsupported interpolation and environment forms before partial execution
or partial emission.

Must reject:

- `env` used as an ordinary assignment target, if that would shadow the reserved
  namespace;
- invalid environment variable names;
- assignment of arrays, maps, command-result objects, jobs, regex objects, or
  other non-scalar values to `env.NAME`;
- direct interpolation of collection-returning functions;
- direct interpolation of command-result-returning functions;
- direct interpolation of functions that may write ordinary stdout;
- direct interpolation of functions with mixed or unknown return kinds;
- command-word interpolation that would require unsupported nested command
  substitution or collection expansion;
- malformed function-call interpolation syntax.

Diagnostics should include the source location of the unsupported form and a
short explanation, for example:

```txt
function call in command interpolation must return a scalar value
```

or:

```txt
environment variable assignment requires a scalar value
```

## VM requirements

- Represent environment reads and writes in the lowered form explicitly enough
  that VM and Bash emitter do not re-infer behavior differently.
- VM environment assignment must affect later DS environment reads and child
  command launches.
- VM unset, if included, must affect later reads and child command launches.
- Function interpolation must evaluate through the ordinary value-return path so
  failures and diagnostics match non-interpolated calls.
- VM command launching must receive fully rendered command words after function
  interpolation succeeds.
- Side effects of interpolated functions must occur exactly once per call.

## Bash emission requirements

- Generated Bash must be standalone and must not invoke `ds`.
- Environment reads should be emitted as runtime Bash environment lookups with
  safe missing-variable handling compatible with strict mode.
- Environment assignment should emit safe assignments/exports that preserve
  literal values and do not perform shell evaluation.
- If unset is included, generated Bash must emit `unset` safely.
- Function interpolation must capture private return payloads from
  scalar-returning functions, decode them, render the scalar value, and only then
  launch the outer command.
- Interpolated command words must remain safely quoted after decoded values are
  inserted.
- A failing interpolated function must prevent the outer command from running
  and must propagate the correct status.
- Helper functions for value-return decoding must be emitted only when required
  and must use the reserved internal helper namespace.
- Generated Bash must pass `bash -n` for every valid fixture.

## Documentation requirements

Update docs only if implementation makes them outdated:

- `docs/language.ds`: document `env.NAME`, environment assignment, unset if
  included, and scalar function-call interpolation examples; mark unsupported
  collection/command-result interpolation as deferred.
- `docs/runtime.md`: describe environment mutation/export behavior and the
  interaction between interpolation and the value-return ABI at a high level.
- `docs/status.md`: update supported/deferred matrix for environment variables
  and direct function-call interpolation.
- `README.md` and examples: update only if they currently contradict the
  implemented behavior or need one small stable example.

Do not expose the private Bash value-return encoding as user-facing syntax.

## Acceptance criteria

`v0.27.0` is complete when:

- `env.NAME` reads are implemented and documented;
- `env.NAME = value` assignments are implemented and exported to child commands;
- unset is either implemented and tested or explicitly deferred in docs;
- scalar function-call interpolation works in both quoted strings and command
  words where current interpolation syntax allows it;
- interpolated function failures prevent the outer command from running;
- unsupported environment values and unsupported interpolation targets produce
  clear diagnostics;
- VM and emitted Bash match for stdout, stderr, exit status, and side effects;
- generated Bash is standalone and passes `bash -n`;
- existing v0.1.0 through v0.26.0 behavior remains unchanged except for
  intentional diagnostics where previously unsupported syntax was ambiguous;
- docs accurately describe supported and deferred behavior.

## Deferred after v0.27.0

- Scoped environment blocks.
- Environment append/prepend shorthand.
- Environment iteration.
- Collection or command-result interpolation.
- Map iteration.
- Index assignment.
- Recursive `**` glob patterns.
- Regex captures/replacement/runtime regex strings.
- Richer signal/job-control APIs.
- Nested collection returns and interpolation.
