# v0.27.0 Test Plan — Environment Variables and Direct Function Interpolation

## Purpose

This test plan verifies that `v0.27.0` adds direct environment-variable access
and scalar function-call interpolation without weakening VM/Bash parity,
standalone Bash emission, or the value-return restrictions established in
`v0.25.0` and `v0.26.0`.

The milestone is successful only if:

- environment reads use runtime environment state;
- environment assignments affect later reads and child commands;
- unset behavior is either implemented/tested or explicitly deferred;
- scalar-returning functions can be called from interpolation safely;
- unsupported collection/command-result/stdout-producing interpolation is
  rejected clearly;
- VM and emitted Bash agree for stdout, stderr, status, and side effects.

## Test suite location

Add a dedicated suite:

```sh
tests/v0_27/run.sh
```

Wire it into the aggregate test runner used by `make test` if the project has a
central version-suite list. Add matching `make test-v0-27` support if the
Makefile uses per-version targets.

The suite should create private deterministic temp directories, write `.ds`
fixtures, emit Bash scripts, run VM and emitted Bash modes with controlled
environment variables, compare results, and clean temporary files on success and
failure.

## Commands every parity case should exercise

For valid production scripts, each relevant case should run:

```sh
./ds check input.ds
./ds run input.ds [args...]
./ds emit bash input.ds -o out.sh
bash -n out.sh
bash out.sh [args...]
```

Then compare VM and emitted Bash:

- stdout;
- stderr;
- exit status;
- deterministic filesystem side effects, when applicable;
- child-process environment observations, when applicable.

For environment-sensitive cases, launch both VM and emitted Bash with the same
controlled environment. Prefer `env -i` plus explicit required variables where
the test host allows it, so host-specific environment values do not leak into
expected output.

For diagnostics-only cases, run at least:

```sh
./ds check input.ds
./ds emit bash input.ds -o out.sh
```

Assert non-zero status and a stable diagnostic substring. Avoid brittle full
multi-line diagnostics unless the existing suite style requires golden output.

For every emitted Bash script, assert:

- `bash -n out.sh` succeeds;
- the generated script does not call the `ds` binary;
- helper names use the reserved internal prefix;
- value-return/interpolation helpers are emitted only when needed and are not
  duplicated where textual helper scanning is already tested elsewhere.

## 1. Environment reads

### 1.1 Present environment variable read

Run with `DS_TEST_ENV=present`.

Input:

```ds
echo env.DS_TEST_ENV
```

Expected stdout:

```txt
present
```

Assertions:

- VM reads the environment visible to `ds run`;
- emitted Bash reads the environment visible to `bash out.sh`;
- value is read at runtime, not during `ds emit bash`.

### 1.2 Runtime read after emit

Emit the Bash script once, then run it twice:

1. `DS_TEST_ENV=first bash out.sh`
2. `DS_TEST_ENV=second bash out.sh`

Input:

```ds
echo env.DS_TEST_ENV
```

Expected outputs:

```txt
first
```

and:

```txt
second
```

Assertion: emitted Bash must not bake in the environment value present during
emission.

### 1.3 Empty environment variable read

Run with `DS_TEST_ENV=` explicitly present but empty.

Input:

```ds
echo "[{env.DS_TEST_ENV}]"
```

Expected stdout:

```txt
[]
```

Assertion: present-empty and missing behavior are handled deliberately and match
between VM and Bash.

### 1.4 Missing environment variable read

Run with `DS_TEST_MISSING` absent.

Input:

```ds
echo "[{env.DS_TEST_MISSING}]"
```

Expected stdout should match the documented missing-variable behavior. If the
preferred empty-string rule is chosen:

```txt
[]
```

Assertion: strict-mode Bash must not fail with an unbound-variable error.

### 1.5 Environment read in expression and conditional

Run with `DS_MODE=prod`.

Input:

```ds
let mode = env.DS_MODE
if mode == "prod" {
  echo "production"
} else {
  echo "other"
}
```

Expected stdout:

```txt
production
```

### 1.6 Environment read inside function

Run with `DS_REGION=apac`.

Input:

```ds
fn region() {
  return env.DS_REGION
}

let r = region()
echo r
```

Expected stdout:

```txt
apac
```

Assertion: environment reads inside value-returning functions remain
stdout-clean.

### 2.1 String assignment then read

Input:

```ds
env.DS_APP = "api"

```

Expected stdout:

```txt
api
```

### 2.2 Assignment overrides inherited value

Run with `DS_APP=old`.

Input:

```ds
echo "before={env.DS_APP}"
env.DS_APP = "new"
echo "after={env.DS_APP}"
```

Expected stdout:

```txt
before=old
after=new
```

### 2.3 Assignment exports to child command

Input:

```ds
env.DS_CHILD_VALUE = "child-ok"
run "sh" "-c" "printf '%s\n' \"$DS_CHILD_VALUE\""
```

Expected stdout:

```txt
child-ok
```

Assertion: VM process-spawn and emitted Bash both export the variable to child
commands.

### 2.4 Integer assignment stringifies canonically

Input:

```ds
env.DS_RETRIES = 3

run "sh" "-c" "printf '%s\n' \"$DS_RETRIES\""
```

Expected stdout:

```txt
3
3
```

### 2.5 Boolean assignment stringifies canonically

Input:

```ds
env.DS_DEBUG = true
echo env.DS_DEBUG
run "sh" "-c" "printf '%s\n' \"$DS_DEBUG\""
```

Expected stdout should match the documented boolean environment string. If the
preferred `true`/`false` rule is chosen:

```txt
true
true
```

### 2.6 Shell metacharacters in assigned values

Input:

```ds
env.DS_LITERAL = "semi; $(echo bad) *?[x]"

```

Expected stdout:

```txt

semi; $(echo bad) *?[x]
```

Assertions:

- emitted Bash must not execute `echo bad`;
- emitted Bash must not expand glob metacharacters.

### 2.7 Empty string assignment

Input:

```ds

run "sh" "-c" "printf '[%s]\n' \"$DS_EMPTY\""
```

Expected stdout:

```txt

```

### 2.8 Assignment inside function affects later child command

### 2.9 Assignment ordering

Input:


## 3. Environment unset, if included

If unset support is implemented in `v0.27.0`, include this section. If unset is
explicitly deferred, replace these tests with one diagnostics/deferred-syntax
test that proves the unsupported form fails clearly.

### 3.1 Unset removes variable from DS reads

Input:

```ds
env.DS_TEMP = "set"
echo "before={env.DS_TEMP}"
unset env.DS_TEMP
echo "after={env.DS_TEMP}"
```

Expected stdout should match the documented missing-variable behavior. With the
preferred empty-string rule:

```txt
before=set
after=
```

### 3.2 Unset removes variable from child environment

Input:

```ds
env.DS_TEMP = "set"
unset env.DS_TEMP
run "sh" "-c" "if [ -z \"${DS_TEMP+x}\" ]; then echo absent; else echo present; fi"
```

Expected stdout:

```txt
absent
```

### 3.3 Invalid unset target diagnostic

Input:

```ds
unset DS_TEMP
```

Expected: `ds check` fails with a diagnostic saying unset requires an
environment target, unless the language already supports unsetting ordinary
variables with different semantics.

## 4. Scalar function calls inside interpolation

### 4.1 String-returning function in quoted interpolation

Input:

```ds
fn app() {
  return "api"
}

echo "deploying {app()}"
```

Expected stdout:

```txt
deploying api
```

### 4.2 String-returning function as command argument

Input:

```ds
fn word() {
  return "hello"
}

run "printf" "%s\n" "{word()}"
```

Expected stdout:

```txt
hello
```

### 4.3 Integer-returning function in interpolation

Input:

```ds
fn build_number() {
  return 42
}

echo "build-{build_number()}"
```

Expected stdout:

```txt
build-42
```

### 4.4 Boolean-returning function in interpolation

Input:

```ds
fn enabled() {
  return true
}

echo "enabled={enabled()}"
```

Expected stdout should match the documented scalar rendering. If booleans render
as `true`/`false`:

```txt
enabled=true
```

### 4.5 Returned shell metacharacters are literal

Input:

```ds
fn literal() {
  return "semi; $(echo bad) *?[x]"
}

run "printf" "%s\n" "{literal()}"
```

Expected stdout:

```txt
semi; $(echo bad) *?[x]
```

Assertions:

- emitted Bash must not execute `echo bad`;
- emitted Bash must not expand globs;
- the outer command receives one argument for the interpolated value.

### 4.6 Empty string return in interpolation

Input:

```ds
fn empty() {
  return ""
}

echo "before{empty()}after"
run "printf" "[%s]\n" "{empty()}"
```

Expected stdout:

```txt
beforeafter
[]
```

### 4.7 Multiple function calls in one command word

Input:

```ds
fn left() {
  return "L"
}

fn right() {
  return "R"
}

echo "{left()}-{right()}"
```

Expected stdout:

```txt
L-R
```

Assertion: calls are evaluated once per interpolation occurrence.

### 4.8 Left-to-right side effects

Use whatever existing file-write or env assignment syntax is supported. Example
with environment mutation if legal inside value-returning functions:

```ds
fn first() {
  env.DS_ORDER = "first"
  return env.DS_ORDER
}

fn second() {
  env.DS_ORDER = "second"
  return env.DS_ORDER
}

echo "{first()}:{second()}:{env.DS_ORDER}"
```

Expected stdout:

```txt
first:second:second
```

If value-returning functions are not allowed to mutate environment in the final
implementation, replace this with an existing supported side-effect mechanism or
diagnostic test. The chosen behavior must be deterministic and documented.

### 4.9 Imported scalar function interpolation

Create an imported module that exports:

```ds
fn app() {
  return "api"
}
```

Main input:

```ds
import "./mod.ds"

echo "app={app()}"
```

Expected stdout:

```txt
app=api
```

Use the project's actual import/export syntax from earlier milestones.

## 5. Failure propagation from interpolated functions

### 5.1 Failing interpolated function prevents outer command

Input:

```ds
fn fail_name() {
  fail "no name"
  return "never"
}

run "sh" "-c" "echo launched > launched.txt" "{fail_name()}"
```

Expected:

- script exits non-zero according to existing `fail` behavior;
- stdout/stderr match VM and Bash expectations for `fail`;
- `launched.txt` is not created.

If `fail` cannot appear in a value-returning function under current rules, use
the existing supported way to make a scalar value-returning function fail.

### 5.2 Later interpolation not evaluated after earlier failure

Input:

```ds
fn bad() {
  fail "bad"
  return "bad"
}

fn side_effect() {
  env.DS_SHOULD_NOT_SET = "set"
  return "x"
}

echo "{bad()} {side_effect()}"
echo env.DS_SHOULD_NOT_SET
```

Expected:

- script exits non-zero before the outer `echo` command launches;
- `DS_SHOULD_NOT_SET` is not set if left-to-right short-circuit is the chosen
  evaluation model;
- VM and emitted Bash match.

If the implementation deliberately evaluates all interpolation expressions
before failure propagation, document that model and update this test
accordingly. The behavior must be deterministic.

## 6. Diagnostics and rejected forms

### 6.1 Invalid environment variable name

Input examples, adapted to parser capabilities:

```ds
echo env.1BAD
```

or:

```ds
env.BAD-NAME = "x"
```

Expected: `ds check` fails with a diagnostic mentioning an invalid environment
variable name.

### 6.2 Assignment of array to environment variable rejected

Input:

```ds
env.DS_BAD = ["a", "b"]
```

Expected: diagnostic says environment assignment requires a scalar value.

### 6.3 Assignment of map to environment variable rejected

Input:

```ds
env.DS_BAD = { name: "api" }
```

Expected: diagnostic says environment assignment requires a scalar value.

### 6.4 Assignment of command result to environment variable rejected

Input:

```ds
env.DS_BAD = run "printf" "x"
```

Expected: diagnostic says environment assignment requires a scalar value or
that command-result values cannot be assigned to environment variables.

Use the exact command-result expression syntax supported by `v0.26.0`.

### 6.5 `env` namespace cannot be shadowed

Input:

```ds
let env = "not-env"
```

Expected: diagnostic rejects shadowing the reserved environment namespace, if
ordinary variables can otherwise use that name.

If earlier language rules already reject this, assert the existing diagnostic.

### 6.6 Collection-returning function interpolation rejected

Input:

```ds
fn names() {
  return ["api", "web"]
}

echo "{names()}"
```

Expected: diagnostic says function call in command interpolation must return a
scalar value.

### 6.7 Map-returning function interpolation rejected

Input:

```ds
fn service() {
  return { name: "api" }
}

echo "{service()}"
```

Expected: diagnostic says function call in command interpolation must return a
scalar value.

### 6.8 Command-result-returning function interpolation rejected

Input:

```ds
fn result() {
  return run "printf" "ok"
}

echo "{result()}"
```

Expected: diagnostic says command-result values cannot be interpolated into
command words in `v0.27.0`.

Use the exact command-result expression syntax supported by `v0.26.0`.

### 6.9 Stdout-producing function interpolation rejected

Input:

```ds
fn noisy() {
  echo "debug"
  return "value"
}

echo "{noisy()}"
```

Expected: diagnostic points to the stdout-producing statement or interpolation
use and says interpolated value functions must be stdout-clean.

### 6.10 Unknown or mixed return-kind function interpolation rejected

Input:

```ds
fn maybe(flag) {
  if flag {
    return "name"
  }
  return ["name"]
}

echo "{maybe(true)}"
```

Expected: diagnostic from same-kind return validation or interpolation checking
rejects mixed scalar/collection returns before execution/emission.

### 6.11 Malformed function-call interpolation rejected

Input:

```ds
echo "{name(}"
```

Expected: parser/checker diagnostic remains clear and source-located.

## 7. Interactions with command execution and quoting

### 7.1 Interpolated function result is one argument

Input:

```ds
fn spaced() {
  return "a b c"
}

run "sh" "-c" "printf '<%s>\n' \"$1\"" "_" "{spaced()}"
```

Expected stdout:

```txt
<a b c>
```

Assertion: returned spaces do not split into multiple arguments.

### 7.2 Interpolation mixed with literal prefix/suffix

Input:

```ds
fn name() {
  return "api"
}

run "printf" "%s\n" "service-{name()}-v1"
```

Expected stdout:

```txt
service-api-v1
```

### 7.3 Environment read plus function interpolation

Run with `DS_PREFIX=svc`.

Input:

```ds
fn name() {
  return "api"
}

echo "{env.DS_PREFIX}-{name()}"
```

Expected stdout:

```txt
svc-api
```

### 7.4 Environment assignment before interpolation

Input:

```ds
env.DS_PREFIX = "svc"

fn prefix() {
  return env.DS_PREFIX
}

echo "{prefix()}-api"
```

Expected stdout:

```txt
svc-api
```

## 8. Bash emission and helper checks

### 8.1 Env-only script does not emit interpolation helpers unnecessarily

Input:

```ds
env.DS_APP = "api"
echo env.DS_APP
```

Assertions:

- emitted Bash passes `bash -n`;
- emitted Bash is standalone;
- value-return interpolation helper functions are not emitted unless the
  existing emitter architecture already emits shared helpers unconditionally.

### 8.2 Interpolation script emits required helpers once

Input:

```ds
fn a() {
  return "a"
}

fn b() {
  return "b"
}

echo "{a()} {b()} {a()}"
```

Assertions:

- emitted Bash passes `bash -n`;
- emitted Bash is standalone;
- value-return decode/render helpers are present once if helper de-duplication
  is part of the emitter design;
- output is `a b a`.

### 8.3 Generated Bash strict-mode missing env safety

Input:

```ds
echo "[{env.DS_NOT_SET}]"
```

Run emitted Bash with `DS_NOT_SET` absent.

Assertion: script succeeds and prints the documented missing-variable rendering;
it must not fail due to `set -u`/unbound variable behavior.

## 9. Regression coverage

Run the existing regression suites for at least:

- scalar function returns from `v0.25.0`;
- collection and command-result returns from `v0.26.0`;
- existing string interpolation without function calls;
- command execution and command-word quoting;
- CLI argument parsing and generated Bash standalone behavior;
- imports and examples.

No existing valid program should change behavior except where the previous
program used syntax that is now intentionally reserved for `env.NAME` or direct
function-call interpolation.

## 10. Documentation checks

Verify docs are consistent after implementation:

- `docs/language.ds` includes examples for `env.NAME`, `env.NAME = value`, unset
  if included, and scalar function-call interpolation.
- `docs/status.md` marks environment reads/assignments and scalar function-call
  interpolation as supported for the implemented version.
- `docs/runtime.md` describes environment export behavior and failure
  propagation for interpolated functions at a high level.
- Unsupported scoped environment blocks, collection interpolation,
  command-result interpolation, map iteration, index assignment, regex, glob,
  and richer signal/job-control APIs remain marked deferred.

## 11. Completion checklist

- `tests/v0_27/run.sh` exists and is wired into aggregate tests.
- Valid env read/assignment/export cases pass in VM and emitted Bash.
- Unset behavior is implemented/tested or explicitly deferred with a diagnostic
  and docs note.
- Scalar function-call interpolation passes in quoted strings and command
  arguments.
- Failure propagation prevents outer command launch.
- Quoting tests prove returned shell metacharacters remain literal.
- Unsupported environment and interpolation forms fail during check/emission.
- Emitted Bash passes `bash -n` and does not call `ds`.
- Full existing regression suite still passes.
