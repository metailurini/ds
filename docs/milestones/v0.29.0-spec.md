# v0.29.0 Spec — Map Iteration

## Status

Planned. This is the next unwritten roadmap milestone after
`v0.28.0 — Cleanup: Value, Environment, and Interpolation Stabilization`.

`v0.29.0` is a feature-foundation milestone for deterministic traversal of
flat maps. It builds on the existing map/object value model from `v0.10.0`, the
flat structured function-return surface from `v0.26.0`, and the value/helper
hygiene stabilized by `v0.28.0`.

This version adds one production language feature:

```ds
for key, value in map_value {
  echo "{key}={value}"
}
```

It must not add index assignment, nested collection traversal, destructuring,
custom iterators, or map mutation during iteration.

## Goal

Let scripts traverse flat map values with a deterministic, portable VM/Bash
contract.

By the end of this milestone:

- `for key, value in map_expr { ... }` works for supported flat map values;
- iteration order is deterministic and documented as sorted ascending by key;
- key and value loop variables are scoped to the loop body and do not leak;
- loop variables shadow outer names only inside the loop body;
- map values can come from named map variables and supported flat
  map-returning functions;
- empty maps, when a supported source can produce them, execute zero iterations;
- scalar map values preserve their value kind during each iteration;
- `break` and `continue` behave the same as in array loops;
- VM execution and emitted Bash produce identical stdout, stderr, exit status,
  and side effects;
- unsupported map iteration sources fail clearly before partial execution or
  emission.

The core product rules remain unchanged:

```txt
every supported production feature runs in the VM
every supported production feature emits standalone Bash
generated Bash is standalone and must not call ds
VM and emitted Bash behavior match for stdout, stderr, exit status, and side effects
unsupported or deferred forms fail clearly before partial execution/emission
```

## Motivation

Flat maps are already useful for configuration-like data:

```ds
let ports = {
  api: 3000,
  web: 5173,
  worker: 9000
}
```

Direct field and bracket access cover known keys, but scripts often need to
render, validate, or export every entry. Without map iteration, users must keep
parallel arrays, hardcode repeated key reads, or drop to Bash-specific behavior.

Map traversal is also a pressure point for VM/Bash parity. Bash associative
arrays do not expose a portable product ordering guarantee. The DS language
therefore must choose an explicit ordering rule instead of accidentally relying
on backend storage order. This milestone chooses sorted key order for all
observable map iteration.

## Non-goals

This version does not include:

- index assignment such as `map["key"] = value` or `array[0] = value`;
- mutation of the iterated map during iteration;
- map deletion, clear, merge, spread, or update helpers;
- nested map/list traversal semantics;
- nested collection literals or nested collection function returns;
- destructuring beyond the exact two-name `for key, value in map` loop header;
- one-name map iteration such as `for key in map`;
- three-or-more-name map iteration headers;
- custom iterator protocols;
- iteration over command-result objects as if they were maps;
- iteration over environment variables;
- iteration over regex capture objects, job objects, handler context values, or
  other future structured values;
- ordered-map insertion-order guarantees;
- sorting by value;
- reverse or custom sort order;
- empty map literal syntax if `{}` still conflicts with the parser/block model;
- collection-valued function parameters;
- typed required parameters or typed return annotations;
- recursive `**` glob behavior;
- regex captures/replacement/runtime regex strings;
- signal/job-control expansion.

Small support changes are allowed only when they are required to make map
iteration correct, deterministic, diagnosable, and Bash-emittable. Any such
change must be recorded in the completion review and covered by the v0.29 test
suite.

## Required feature work

### 1. Syntax and parser behavior

Add support for this map iteration header:

```ds
for key, value in map_expr {
  statements
}
```

Required behavior:

- the header must contain exactly two identifiers before `in`;
- the comma is required between the key and value names;
- the two names must be different;
- the iterable expression follows the existing expression grammar after `in`;
- the loop body uses the existing block syntax;
- source spans for the key name, value name, iterable expression, and loop body
  are preserved for diagnostics, AST output, HIR output, bytecode output, and
  formatter behavior;
- `for key, value in map { ... }` is parsed as a map loop, not as destructuring
  assignment and not as an array loop;
- existing `for item in array { ... }` syntax must keep its current behavior.

Malformed headers remain parser-owned diagnostics:

```ds
for key, in ports { }
for key value in ports { }
for key, value, extra in ports { }
for key, key in ports { }
for key, value ports { }
```

The duplicate-name case may be parser-owned if the parser already has both
identifier tokens locally, or lowerer-owned if duplicate-name validation fits
better with existing scope validation. The diagnostic must still happen before
execution or emission.

### 2. Accepted iterable sources

Support map iteration over these sources:

```ds
let ports = { api: 3000, web: 5173 }
for name, port in ports { ... }
```

```ds
fn ports() {
  return { api: 3000, web: 5173 }
}

for name, port in ports() { ... }
```

If the existing HIR/value-return model already supports forwarding flat map
returns through another value-returning function, that forwarded call should be
accepted as an iterable source as well:

```ds
fn base() {
  return { api: 3000, web: 5173 }
}

fn forwarded() {
  return base()
}

for name, port in forwarded() { ... }
```

Conservative restrictions:

- a named map variable is the safest required source;
- a supported flat map-returning function call is required if expression-call
  iteration can reuse the existing value-return protocol cleanly;
- map field/bracket access as an iterable source is allowed only if the lowerer
  can prove it is a flat map value, which is not expected until nested
  collections exist;
- command-result values are not maps and must not be accepted;
- environment namespace values are not maps and must not be accepted;
- array values remain array-loop iterables only through the one-name loop form;
- temporary map literals in loop headers are allowed only if the existing map
  literal and Bash-emission path can preserve key/value metadata without
  introducing backend-specific behavior. Otherwise require binding the literal
  first and diagnose the temporary expression clearly.

The implementation should prefer consistency with existing array-loop
portability gates: if non-named temporary iterables are rejected for array loops,
non-named temporary map literals may be rejected for map loops too.

### 3. Iteration order

Map iteration order is part of the public contract.

Required order:

```txt
sorted ascending by map key, using bytewise/ASCII string comparison over the
stored key text
```

Required behavior:

- VM and emitted Bash must use the same key ordering;
- order must not depend on hashmap storage order;
- order must not depend on Bash associative-array expansion order;
- order must not depend on locale-sensitive collation;
- generated Bash must force or emulate bytewise ordering rather than inheriting
  ambient user locale behavior;
- string-like keys preserve their exact stored key text for sorting and binding;
- duplicate keys keep the existing map-literal duplicate-key behavior and must
  not create multiple loop iterations for the same final key;
- numeric-looking keys such as `"10"` and `"2"` sort lexically, so `"10"`
  comes before `"2"`.

If implementation discovers that the project already intentionally normalizes
map keys in another way, update this milestone's completion review and docs to
record the exact key text used for ordering. Do not silently switch to insertion
order.

### 4. Loop variable binding and scope

For each map entry:

- the first loop variable receives the key as a string;
- the second loop variable receives the mapped value with its scalar value kind;
- value kinds must remain visible to expression semantics, truthiness,
  interpolation, membership checks, and `case` matching;
- loop variables are local to the loop body;
- loop variables do not leak after the loop;
- loop variables may shadow outer variables only inside the loop body;
- reassigning loop variables inside the body follows the existing scalar
  reassignment rules and must not mutate the source map;
- nested map loops must allocate independent loop-variable storage and must not
  collide in emitted Bash;
- map loops inside functions, test blocks, imported files, signal/defer blocks,
  and conditional/while blocks must follow the existing scope model.

### 5. Empty maps

Empty map iteration must be defined even if empty map literal syntax remains
unsupported.

Required behavior:

- a map value with zero entries executes the body zero times;
- stdout, stderr, exit status, and side effects match VM/Bash behavior;
- loop variables are not bound after the loop;
- no helper or runtime path treats an empty map as null, false, or an error;
- generated Bash remains valid when the iterated associative array has no keys.

If there is still no public source-level way to construct an empty map without
adding ambiguous `{}` syntax, the implementation may validate this through an
existing supported producer only if one exists. Otherwise, document in the
completion review that runtime empty-map handling is implemented but source
coverage waits for the future empty-map-literal milestone. Do not add ambiguous
empty map syntax in v0.29 unless the parser can do so without changing block
semantics or function-body parsing.

### 6. Control-flow interaction

Inside map loops:

- `break` exits the nearest map loop;
- `continue` skips to the next sorted key;
- nested array/map/while loops preserve nearest-loop behavior;
- `return` inside a function body exits the function using the existing
  value-return rules;
- `fail` and `exit` preserve existing process status behavior;
- defers/traps retain their current process-level behavior and must not gain
  map-iteration-specific semantics.

### 7. Mutation during iteration

Map mutation during iteration is rejected for this milestone.

Because index assignment and map deletion are not yet supported, most mutation
forms should already be impossible. If new map mutation syntax becomes parseable
through v0.30 design work or existing helpers, v0.29 must reject mutation of the
currently iterated map with a clear diagnostic rather than defining partial
iterator invalidation behavior.

`array.push` on an unrelated array inside a map loop remains allowed if it
already works in array loops and can preserve VM/Bash parity.

### 8. Diagnostics ownership

Diagnostic ownership follows the existing rules:

- lexer/parser own malformed loop syntax and impossible token shapes;
- lowerer owns iterable eligibility, value-kind validation, map-vs-array loop
  form validation, unsupported temporary iterables, duplicate loop names if not
  parser-owned, map mutation rejection, and backend portability gates;
- VM owns accepted runtime/data failures only;
- Bash emitter owns artifact/output failures and internal accepted-HIR
  invariant defenses only.

Required diagnostic cases include:

- one-name loop over a map: use `for key, value in map`;
- two-name loop over an array: arrays use `for item in array`;
- two-name loop over a string/int/bool;
- two-name loop over a command-result value;
- two-name loop over `env.NAME` or the `env` namespace;
- malformed comma/header forms;
- duplicate key/value variable names;
- temporary map literal if not accepted by the portability gate;
- nested-map or nested-list map values if the loop would require nested value
  binding;
- computed iterable whose map kind is unknown;
- unsupported map mutation during iteration if such a form becomes parseable.

Diagnostics should be specific enough to identify the wrong loop form and the
supported alternative.

### 9. VM behavior

The VM must:

- evaluate the iterable expression once before the loop starts;
- snapshot the sorted key list before the first iteration;
- iterate keys in deterministic bytewise ascending order;
- bind key/value variables in a loop body scope;
- preserve scalar value kinds for values;
- keep source map contents unchanged when loop variables are reassigned;
- support nested map loops without storage collisions;
- implement `break`, `continue`, and `return` through existing control-flow
  mechanics;
- avoid leaking temporary sorted-key storage.

Snapshotting the key list is preferred even while mutation is unsupported. It
makes future mutation decisions explicit and prevents accidental dependence on
hashmap iteration behavior.

### 10. Bash emission behavior

Generated Bash must:

- remain standalone and never call `ds`;
- emit a Bash 4+ guard when associative arrays are required, following existing
  map behavior;
- build or access a deterministic sorted key list for each map loop;
- force bytewise sorting in a locale-independent way, for example by using
  `LC_ALL=C` around sorting or an equivalent internal helper;
- quote all keys and values safely;
- preserve value-kind sidecars for loop value variables;
- use reserved `__ds_` names for internal temporaries;
- avoid collisions between nested map loops, imported functions, and user names;
- emit helper definitions only when required;
- pass `bash -n`;
- pass shellcheck-like readability expectations where the project already
  follows them, without adding shellcheck as a required tool.

If a helper such as `__ds_map_sorted_keys` is added, it belongs to the generated
Bash helper layer and must be included by dependency scanning only when accepted
HIR needs it.

### 11. Formatter, AST, HIR, and bytecode/debug output

Public debug/tooling commands must stay coherent:

- `ds tokens` recognizes existing tokens without introducing unnecessary new
  ones;
- `ds ast` displays the two loop variable names and map iterable expression;
- `ds hir` displays enough map-loop information to diagnose backend drift;
- `ds bytecode` shows map-loop execution in a stable human-readable way if the
  VM bytecode has distinct instructions;
- `ds fmt` preserves and normalizes `for key, value in map { ... }` without
  converting it to the one-name form;
- formatter output remains idempotent;
- parse/check/fmt behavior on malformed map-loop headers remains clear.

### 12. Documentation updates

Update docs only where they become outdated:

- `docs/status.md` should move map iteration from deferred to supported after
  implementation;
- `docs/language.ds` should mark map iteration as implemented in v0.29 and
  document sorted key order;
- `docs/runtime.md` should describe the map iteration order contract and any
  Bash helper/locale requirement;
- `docs/parity-contracts.md` should mention deterministic map iteration as a
  VM/Bash parity requirement;
- `docs/diagnostics.md` should list map-loop ownership if the wording changes;
- `docs/concept-map.md` and `docs/source-map.md` should move map iteration from
  clear-while-rejected to its implemented concept home;
- examples may be updated to use map iteration only after implementation is
  complete.

Do not update docs to imply index assignment, nested collections, empty map
literal syntax, custom iterators, or insertion-order maps are supported.

## Acceptance criteria

`v0.29.0` is complete when:

- map loops parse, lower, execute in VM mode, and emit standalone Bash;
- VM/Bash parity holds for stdout, stderr, exit status, and side effects;
- sorted key order is deterministic and documented;
- key/value loop variables are scoped and kind-preserving;
- `break`, `continue`, nested loops, imports, functions, and test blocks behave
  consistently;
- malformed and unsupported forms fail before partial execution/emission;
- emitted Bash passes `bash -n`, does not call `ds`, and includes only required
  helpers;
- docs accurately describe supported map iteration and still defer index
  assignment, nested collections, recursive glob, and advanced regex work;
- the dedicated v0.29 test suite passes and is wired into aggregate tests.
