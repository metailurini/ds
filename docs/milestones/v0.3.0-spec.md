# v0.3.0 Spec — Minimal C Runtime and Bytecode VM

## Status

Implementation and tests complete.

## Goal

Add the first direct execution path for `ds` scripts through a minimal register bytecode VM.

This version should execute the same core language subset that `v0.1.0` parses and `v0.2.0` emits to Bash, while adding only the runtime substrate needed to make that execution path reliable and testable.

`v0.3.0` proves the second core project principle after Bash emission: every supported feature should run directly in the VM and emit to standalone Bash.

## Motivation

`ds` is not only a Bash generator. The default user experience should eventually be:

```sh
ds ./script.ds
```

To reach that goal without creating two separate languages, this version introduces the shared middle layer and VM foundation that future features can build on.

The VM should not walk the AST directly as the long-term execution strategy. It should execute bytecode produced from a lowered representation so VM behavior, Bash emission behavior, diagnostics, and debug output can stay aligned.

This milestone also creates the first real runtime substrate for C-side implementation work. Runtime helpers are allowed inside the `ds` tool, but they must not become hidden dependencies of emitted Bash.

## Non-goals

This version does not include:

- advanced optimizer;
- JIT compiler;
- native compiler;
- imports;
- functions;
- loops;
- arrays or maps as user-facing language values;
- CLI argument blocks;
- command result capture;
- command pipelines beyond whatever the existing frontend subset already accepts;
- advanced redirection syntax;
- standard library functions such as `file.exists`;
- formatter;
- interactive REPL;
- Bash helper redesign beyond what parity requires.

The VM should execute only the currently supported `v0.1.0` / `v0.2.0` language subset.

## User-facing commands

Add or complete:

```sh
ds <file.ds>
ds run <file.ds>
ds bytecode <file.ds>
```

Suggested behavior:

- `ds <file.ds>` runs the script through the VM;
- `ds run <file.ds>` is an explicit spelling of the same VM execution path;
- `ds bytecode <file.ds>` prints a stable human-readable bytecode dump;
- all commands parse and validate the source before execution or bytecode output;
- all commands exit `0` on success;
- all commands exit non-zero on parse, lowering, bytecode, VM, or process execution error;
- diagnostics should include file, line, and column when tied to source text.

Existing debug commands should continue to work:

```sh
ds tokens <file.ds>
ds ast <file.ds>
ds check <file.ds>
ds emit bash <file.ds> -o <file.sh>
```

## Supported input subset

The VM should support the same user-facing subset as `v0.2.0`:

- comments, ignored for execution;
- `let` variables;
- string literals;
- integer literals;
- boolean literals;
- basic string interpolation;
- identifier expressions;
- unary `!` expressions;
- comparison expressions supported by the current frontend/emitter;
- `if` statements;
- `if` / `else` statements;
- nested blocks;
- simple command statements.

Unsupported syntax should fail clearly before execution.

## Shared lowering layer

Add the first HIR or equivalent lowered representation so the VM and Bash emitter can share semantic behavior.

Requirements:

- Lower from parsed AST into a representation suitable for both bytecode generation and Bash emission.
- Preserve enough source span information for diagnostics and bytecode dumps.
- Track declared variables and reject unknown variable references.
- Track simple value kinds where needed for condition and interpolation behavior.
- Keep lowering intentionally small; it should not become a full optimizer in this milestone.

The exact internal name may be `HIR`, `IR`, or another project-consistent name, but the architecture should avoid separate semantic implementations for VM and Bash emission.

## Minimal runtime substrate

Add only the runtime pieces needed by the first VM.

### Strings

Implement minimal string support:

- `DsStr` or equivalent borrowed string view;
- `DsString` or equivalent owned dynamic string;
- construction from C strings and source slices;
- append operations needed by interpolation and diagnostics;
- clear ownership rules;
- tests for allocation failure paths where practical.

### Values

Implement `DsValue` or equivalent tagged runtime values for:

```txt
null
bool
int
string
```

Requirements:

- values can be copied or retained according to explicit ownership rules;
- string values do not dangle after source buffers are freed;
- comparisons are deterministic;
- truthiness is documented and tested.

Suggested truthiness for this milestone:

- `true` is truthy;
- `false` is falsey;
- non-zero integers are truthy;
- zero is falsey;
- non-empty strings are truthy only if the milestone implementation intentionally supports string truthiness;
- empty strings are falsey only if string truthiness is intentionally supported;
- otherwise non-boolean conditions should produce a clear diagnostic.

The implementation should choose one conservative rule and test it. If `v0.2.0` already chose a condition model for Bash emission, VM behavior must match it.

### Arrays and maps for internals

Implement minimal internal containers only where needed:

- `DsArray` or vector support for compiler/runtime lists such as instructions, constants, registers, argv entries, and diagnostics;
- `DsMap` as the project-owned map wrapper for scopes, globals, or symbol tables;
- temporary `libs/hashmap` backing is allowed if wrapped behind `DsMap`.

User-facing array and map syntax remains deferred.

`libs/hashmap` is a staging location only. Code added in this milestone should make it clear that future cleanup will absorb or replace the staging implementation behind normal `ds` runtime APIs.

## Bytecode format

Define an initial bytecode format with:

- instruction opcode;
- register operands where needed;
- constants table;
- source location table or instruction-to-source mapping;
- human-readable dump output.

Suggested instruction families:

```txt
LOAD_CONST
LOAD_VAR
STORE_VAR
NOT
COMPARE_EQ
COMPARE_NE
COMPARE_GT
COMPARE_GE
COMPARE_LT
COMPARE_LE
INTERPOLATE
JUMP
JUMP_IF_FALSE
RUN_CMD
RETURN
NOP
```

The exact names may differ, but the bytecode dump should be stable enough for tests.

The bytecode format should be simple and explicit. Do not add an optimizer or complex control-flow representation in this version.

## Register VM behavior

The VM should:

- execute bytecode instructions in order;
- maintain registers;
- maintain variable storage and block scopes;
- evaluate supported expressions;
- execute conditionals;
- run command statements through a process abstraction;
- propagate command exit failures consistently;
- return a process exit code to the CLI;
- release owned runtime memory on normal and error paths.

## Variable behavior

Input:

```ds
let name = "Danh"
let count = 3
let ok = true
```

VM behavior:

- `name` stores a string value;
- `count` stores an integer value;
- `ok` stores a boolean value;
- duplicate declarations in the same scope should either fail clearly or follow the existing documented frontend rule;
- references to unknown variables fail before execution when possible.

## String interpolation behavior

Input:

```ds
let name = "Danh"
echo "Hello {name}"
```

VM command behavior should be equivalent to running:

```sh
echo "Hello Danh"
```

Requirements:

- `{name}` references a known variable;
- interpolated values are converted to strings predictably;
- unknown interpolation names fail clearly;
- expression interpolation remains deferred;
- literal brace behavior should match the `v0.2.0` Bash emitter rule.

## If behavior

Input:

```ds
let target = "production"

if target == "production" {
  echo "yes"
} else {
  echo "no"
}
```

Expected VM stdout:

```txt
yes
```

Supported condition forms should match the frontend and Bash emitter:

- identifier condition if already supported;
- unary `!`;
- `==`;
- `!=`;
- `>`;
- `>=`;
- `<`;
- `<=`.

Numeric and string comparisons must match Bash emission behavior for this subset. If the comparison model is intentionally conservative, document and test the limitation.

## Command execution behavior

Input:

```ds
echo "one"
echo "two"
```

Expected VM stdout:

```txt
one
two
```

Requirements:

- command words execute in source order;
- string arguments remain single arguments;
- interpolated string arguments remain single arguments;
- command exit status is reflected in `ds` exit status;
- a failing command should stop execution unless the language later adds explicit error handling;
- stdout and stderr should pass through naturally unless tests intentionally capture them.

Process execution should be isolated behind a small API so tests can use fake process runners where practical.

## VM and Bash parity

For the supported subset, VM mode and emitted Bash mode should agree on:

- stdout;
- stderr shape where practical;
- exit code;
- variable and interpolation behavior;
- branch selection;
- command ordering;
- failure behavior.

Exact diagnostic wording may differ between VM and Bash runtime failures, but source-time diagnostics should remain project-consistent.

## Generated Bash requirements remain unchanged

This milestone must not weaken Bash emission.

Generated Bash must still:

- be standalone;
- start with the chosen Bash shebang;
- use the strict header chosen in `v0.2.0`;
- avoid depending on the C runtime;
- pass existing Bash emission tests.

Any semantic change required for VM execution must be reflected in Bash emission behavior and tests.

## Bytecode dump output

`ds bytecode <file.ds>` should print readable output for debugging.

Suggested shape:

```txt
constants:
  0: string "Hello"
  1: bool true

instructions:
  0000 LOAD_CONST r0, const 0    # examples/basic.ds:1:12
  0001 RUN_CMD    ["echo", r0]   # examples/basic.ds:2:1
  0002 RETURN     0
```

Requirements:

- stable instruction ordering;
- stable opcode names;
- includes constants where useful;
- includes source location comments or equivalent source mapping;
- does not include raw pointer addresses;
- does not include nondeterministic memory addresses or timestamps.

## Diagnostics

Diagnostics should cover:

- parse errors before lowering;
- unknown variables;
- unknown interpolation names;
- unsupported syntax;
- invalid bytecode generation state;
- runtime type mismatch;
- command execution failure when the process cannot be launched;
- allocation failure where practical.

Diagnostics tied to source code should include file, line, column, and a clear explanation.

Input:

- VM exits non-zero;

## Acceptance criteria

`v0.3.0` is complete when:

- `ds <file.ds>` runs supported scripts through the VM.
- `ds run <file.ds>` runs supported scripts through the same VM path.
- `ds bytecode <file.ds>` prints a deterministic bytecode dump.
- A shared lowering layer exists for VM and Bash emission semantics.
- Minimal runtime string, array, map, and value primitives exist where needed.
- `DsMap` or equivalent wraps the staged hashmap dependency instead of exposing it directly across the codebase.
- The VM supports `let`, expressions, interpolation, `if/else`, nested blocks, and simple command statements for the supported subset.
- Command failures produce correct non-zero exit behavior.
- Existing lexer, parser, checker, and Bash emitter behavior remains intact.
- Runtime unit tests exist for strings, arrays, maps, and values.
- Bytecode tests exist.
- VM integration tests exist.
- VM/Bash parity tests exist for the supported subset.
- Docs are updated if implementation decisions differ from the roadmap, architecture, runtime, or language catalog.

## Deferred items

Deferred to later versions:

- cleanup of frontend/runtime/backend boundaries: `v0.4.0`;
- CLI argument blocks;
- imports and Bash bundling;
- functions;
- loops;
- user-facing arrays and maps;
- command capture;
- advanced redirection;
- standard library helpers;
- tracing flags such as `--trace-cmd` and `--trace-vm`;
- optimizer and bytecode performance tuning.

### Implementation notes

- The first VM and Bash emitter now consume the same lowered program representation. Lowering clones the supported AST subset into backend-facing statements/expressions while performing symbol lookup, interpolation validation, duplicate declaration checks, supported operator checks, and block-local scope boundary validation.
- VM comparison semantics intentionally match the current Bash-emission limitation: values are converted through deterministic string rendering before comparison. Type-aware numeric dispatch remains deferred.
- The current `DsMap` is a project-owned wrapper used by the VM/runtime API. It does not expose staged `libs/hashmap` types across the normal codebase.
- VM execution runs command statements with `fork`/`execvp`, preserves normal stdout/stderr behavior, and stops on the first non-zero command exit.
- The `v0.3.0` test-plan pass now adds runtime unit tests, bytecode golden tests, VM integration tests, diagnostics coverage, command failure tests, sanitizer checks where available, and VM/Bash parity fixtures.
