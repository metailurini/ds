# v0.3.0 Test Plan — Minimal C Runtime and Bytecode VM

## Purpose

This test plan verifies the first direct execution backend for `ds`.

`v0.3.0` should execute the supported `v0.1.0` / `v0.2.0` language subset through a register bytecode VM, introduce the minimal runtime substrate needed by that VM, and prove VM/Bash parity for the same user-facing behavior.

The test plan should be implemented before or alongside development and updated if scope changes.

## Test categories

`v0.3.0` should include tests for:

- minimal runtime primitives;
- lowering / semantic representation;
- bytecode generation;
- bytecode dump output;
- VM execution;
- command process execution;
- CLI behavior;
- diagnostics;
- memory and ownership edge cases;
- VM/Bash parity;
- regression coverage for v0.1.0 and v0.2.0 behavior.

Use focused fixtures for the supported subset. Do not use `docs/language.ds` as an executable fixture because it intentionally contains future syntax.

## Runtime unit tests

### String view tests

Test borrowed string view behavior for:

- empty view;
- full C string view;
- source slice view;
- view with embedded spaces;
- view with quotes;
- view with backslashes;
- view with UTF-8 bytes;
- equality between same-length equal views;
- inequality for same prefix but different length;
- inequality for different content;
- safe behavior when length is zero and pointer is null if that representation is allowed.

### Owned string tests

Test owned dynamic string behavior for:

- initialize empty string;
- initialize from C string;
- initialize from string view;
- append string;
- append character;
- append empty string;
- append many small fragments;
- append content requiring capacity growth;
- preserve NUL terminator for C interop if provided;
- clear without freeing capacity if supported;
- free is idempotent only if the implementation promises it;
- allocation failure paths where practical through test hooks.

Edge cases:

- very long string near chosen test memory limits;
- string containing `$HOME`;
- string containing `$(echo bad)`;
- string containing backticks;
- string containing braces used by interpolation;
- string containing newline if source strings support it.

### Value tests

Test `DsValue` or equivalent for:

- `null` construction;
- boolean construction for `true` and `false`;
- integer construction for zero, positive, and large values;
- string construction from owned runtime string;
- copying or retaining values according to ownership rules;
- freeing values without leaks;
- equality for equal values;
- inequality for different types;
- deterministic string conversion for interpolation;
- deterministic truthiness or clear rejection of non-boolean conditions.

Truthiness cases should match the implemented spec:

- `true` condition;
- `false` condition;
- `!true`;
- `!false`;
- integer condition if supported;
- string condition if supported;
- non-boolean condition diagnostic if unsupported.

### Array/vector tests

Test internal array support for:

- initialize empty array;
- push one item;
- push many items;
- capacity growth;
- indexed read;
- indexed write if supported;
- length tracking;
- clear;
- free;
- out-of-bounds defensive behavior where applicable;
- allocation failure paths where practical.

Use realistic element types used by the implementation, such as instructions, constants, pointers, or string views.

### Map tests

Test `DsMap` or equivalent wrapper for:

- initialize empty map;
- insert one key;
- lookup existing key;
- lookup missing key;
- update existing key;
- insert many keys;
- keys with common prefixes;
- keys with underscores and digits;
- collision-heavy cases if the backing implementation allows test control;
- delete key if supported;
- clear/free releases owned resources;
- no direct exposure of staged `libs/hashmap` types outside the wrapper boundary.

Scope tests should use the map through the same public internal API used by lowering and VM code.

## Lowering tests

Lowering tests should verify that parsed AST becomes the shared semantic form used by bytecode generation and Bash emission.

### Successful lowering

Test lowering for:

- empty file;
- comments-only file;
- single `let` statement;
- multiple `let` statements;
- string variable;
- integer variable;
- boolean variable;
- identifier expression;
- unary `!` expression;
- equality comparison;
- inequality comparison;
- ordering comparison;
- simple command;
- command with string argument;
- command with interpolation;
- `if` without `else`;
- `if` with `else`;
- nested `if`;
- command after block;
- mixed script with variables, conditionals, and commands.

### Lowering diagnostics

Test diagnostics for:

- unknown variable reference;
- unknown interpolation variable;
- duplicate variable in same scope if disallowed;
- invalid assignment target if possible;
- unsupported expression form;
- unsupported statement form;
- condition type mismatch if non-boolean conditions are rejected;
- comparison type mismatch if the implementation rejects mixed comparisons;
- source location preservation for each error.

### Scope tests

Test scope behavior for:

- variable declared before `if` used inside block;
- variable declared inside `if` used inside same block;
- variable declared inside `if` used after the block if disallowed;
- same variable name in nested scope if shadowing is allowed;
- same variable name in nested scope if shadowing is rejected;
- same variable name in sibling branches;
- branch-local declarations do not corrupt outer scope.

The tests should follow the rule chosen by the milestone implementation and document any conservative limitation.

## Bytecode generation tests

Bytecode tests should focus on deterministic instruction shape rather than internal pointer identity.

### Constants table

Test constants emitted for:

- string literal;
- empty string;
- integer zero;
- positive integer;
- boolean `true`;
- boolean `false`;
- repeated constants if deduplication is supported;
- repeated constants if deduplication is intentionally not supported.

The test should assert whichever behavior is chosen, not leave it accidental.

### Instruction generation

Test bytecode generation for:

- empty file emits `RETURN` or equivalent;
- `let name = "Danh"` emits load/store instructions;
- `let ok = true` emits boolean constant and store;
- `!ok` emits load and not instructions;
- `name == "Danh"` emits comparison instruction;
- each supported comparison operator emits the correct comparison instruction;
- `if` emits conditional jump and return/continuation correctly;
- `if/else` emits false jump and end jump correctly;
- nested `if` emits correct jump targets;
- command statement emits command instruction with argv representation;
- interpolated command argument emits interpolation or string-build instructions;
- command after block has the correct instruction order.

### Source map tests

Test bytecode source metadata for:

- instruction generated from first line;
- instruction generated after blank lines;
- instruction generated after comments;
- instruction generated inside nested block;
- instruction generated from string interpolation;
- diagnostic points back to the source expression or statement that caused it.

## Bytecode dump golden tests

Each bytecode fixture should include:

```txt
input.ds
expected.bytecode.txt
```

Recommended fixtures:

- empty file;
- simple variable;
- string interpolation;
- true branch;
- false branch;
- nested `if`;
- simple command;
- mixed script.

Golden dump requirements:

- stable opcode names;
- stable instruction numbering;
- stable constant formatting;
- stable register formatting;
- stable jump target formatting;
- stable source location formatting;
- no pointer addresses;
- no timestamps;
- no absolute temporary paths unless normalized.

## VM execution tests

### Empty and no-op scripts

Test:

```ds
# empty
```

Expected:

- exit `0`;
- stdout empty;
- stderr empty or no unexpected error.

Comments-only script should behave the same.

### Variable execution

Test scripts:

```ds
let name = "Danh"
echo "{name}"
```

Expected stdout:

```txt
Danh
```

Additional cases:

- integer variable interpolated into command argument;
- boolean variable interpolated into command argument;
- multiple variables used in one command;
- variable used before declaration fails before execution;
- many variables do not corrupt each other.

### Expression execution

Test:

- `true` evaluates true;
- `false` evaluates false;
- `!true` evaluates false;
- `!false` evaluates true;
- `1 == 1`;
- `1 != 2`;
- `2 > 1`;
- `2 >= 2`;
- `1 < 2`;
- `2 <= 2`;
- string equality;
- string inequality;
- mixed-type comparisons if supported;
- mixed-type comparisons fail clearly if unsupported.

### Conditional execution

Test true branch:

```ds
let ok = true
if ok {
  echo "yes"
} else {
  echo "no"
}
```

Expected stdout:

```txt
yes
```

Test false branch:

```ds
let ok = false
if ok {
  echo "yes"
} else {
  echo "no"
}
```

Expected stdout:

```txt
no
```

Additional cases:

- `if` without `else` and false condition prints nothing;
- nested true/true branches;
- nested true/false branches;
- nested false outer branch skips inner commands;
- command after `if` still runs when previous command succeeds;
- branch-local variables follow documented scope rules.

### String interpolation execution

Test interpolation in command arguments:

- interpolation at beginning of string;
- interpolation in middle of string;
- interpolation at end of string;
- multiple interpolations;
- adjacent interpolation and text;
- interpolation next to punctuation;
- integer interpolation;
- boolean interpolation;
- unknown interpolation name fails clearly;
- literal braces behavior matches Bash emitter behavior;
- expression interpolation remains rejected clearly.

Example:

```ds
let app = "api"
let target = "staging"
echo "deploy:{app}:{target}"
```

Expected stdout:

```txt
deploy:api:staging
```

### Command execution tests

Test command behavior for:

- simple command;
- command with multiple words;
- command with quoted string argument containing spaces;
- command with interpolated argument containing spaces remains a single argument;
- command inside true branch runs;
- command inside false branch does not run;
- command after successful command runs;
- failing command stops execution;
- missing command exits non-zero and reports useful error;
- command stderr passes through;
- command exit code becomes `ds` exit code where practical.

Use portable shell commands in tests. Prefer `printf`, `echo`, `true`, `false`, and small test helper scripts over platform-specific tools.

### Failure behavior

Input:

```ds
false
echo "after"
```

Expected:

- VM exits non-zero;
- stdout does not contain `after`;
- emitted Bash parity test has the same exit behavior.

Input:

```ds
missing_command_for_ds_test
```

Expected:

- VM exits non-zero;
- diagnostic or process error mentions the missing command;
- no crash.

## VM/Bash parity tests

For each parity fixture:

1. run through VM mode;
2. emit Bash;
3. run `bash -n` on generated Bash;
4. run generated Bash;
5. compare stdout;
6. compare exit code;
7. compare stderr only where stable enough.

Recommended fixtures:

- empty script;
- comments-only script;
- string variable and echo;
- integer variable and echo;
- boolean variable and echo;
- string interpolation;
- multiple interpolations;
- `if` true branch;
- `if` false branch;
- `if` without else false branch;
- nested `if`;
- comparison operators;
- command ordering;
- command failure stops script;
- command with string containing spaces;
- command with safe literal content such as `$HOME` and `$(echo bad)` as data.

Parity expectations:

- success cases stdout should match exactly;
- success cases exit code should match exactly;
- failure cases exit code should match non-zero;
- diagnostic text may differ if documented, but VM should not silently succeed when Bash fails or vice versa.

## CLI tests

### Implicit run

```sh
ds examples/basic.ds
```

Expected:

- exits `0` for valid supported script;
- runs through VM path;
- stdout matches script behavior.

### Explicit run

```sh
ds run examples/basic.ds
```

Expected:

- same behavior as implicit run;
- same exit code and stdout.

### Bytecode dump

```sh
ds bytecode examples/basic.ds
```

Expected:

- exits `0`;
- prints deterministic bytecode;
- does not execute commands from the source script.

### Existing commands still work

Test:

```sh
ds tokens examples/basic.ds
ds ast examples/basic.ds
ds check examples/basic.ds
ds emit bash examples/basic.ds -o /tmp/basic.sh
```

Expected:

- each command keeps its existing behavior;
- Bash emitter tests from `v0.2.0` still pass.

### Error cases

Test:

```sh
ds
ds run
ds bytecode
ds run missing.ds
ds bytecode missing.ds
ds unknown-command examples/basic.ds
```

Expected:

- exits non-zero;
- prints usage or clear error;
- does not crash;
- missing file reports missing file.

## Memory and ownership tests

Use sanitizers where available.

Recommended targets:

```sh
make test

make ubsan
```

If target names differ, use the project-standard equivalents.

Test memory safety for:

- empty script;
- many variables;
- many constants;
- many commands;
- deeply nested conditionals within reasonable parser limits;
- long strings;
- repeated VM runs in one process if the architecture supports it;
- error path after partial lowering;

Expected:

## Edge cases

### Source shape

- Empty file.
- Comments-only file.
- File without trailing newline.
- Blank lines before first statement.
- Many blank lines inside block.
- Deeply nested `if` within a documented safe limit.
- Long single-line command.
- Many short commands.

### Values

- Empty string.
- String with spaces.
- String with double quote.
- String with single quote.
- String with backslash.
- String with dollar sign.
- String with command-looking text `$(echo bad)`.
- String with backticks.
- String with braces.
- Integer zero.
- Large integer within supported range.
- Boolean true and false.

### Control flow

- False `if` without `else` skips body.
- True `if` without `else` runs body.
- `else` branch runs exactly once.
- Nested branches do not fall through incorrectly.
- Commands after blocks execute in correct order.
- Failing command inside branch stops script.

### Bytecode

- Jump target at end of file.
- Jump over empty block if empty blocks are supported.
- Jump over `else` branch.
- Nested jump targets are patched correctly.
- Bytecode dump for invalid source fails before printing partial misleading output.

### Process execution

- Command exits `0`.
- Command exits non-zero.
- Command does not exist.
- Command argument contains spaces.
- Command argument contains shell metacharacters that should remain data when quoted in `ds`.
- Command stdout is large enough to cross normal stdio buffering boundaries if practical.

## Manual smoke tests

Run a simple VM script:

```sh
cat > /tmp/ds-vm-basic.ds <<'DS'
let name = "Danh"
echo "Hello {name}"
DS

ds /tmp/ds-vm-basic.ds
```

Expected stdout:

```txt
Hello Danh
```

Run bytecode dump:

```sh
ds bytecode /tmp/ds-vm-basic.ds
```

Expected:

- deterministic instructions;
- no command output from the script itself;
- no pointer addresses.

Run parity smoke:

```sh
ds /tmp/ds-vm-basic.ds
ds emit bash /tmp/ds-vm-basic.ds -o /tmp/ds-vm-basic.sh
bash -n /tmp/ds-vm-basic.sh
bash /tmp/ds-vm-basic.sh
```

Expected:

- VM stdout and Bash stdout match;
- both exit `0`.

Run failure parity:

```sh
cat > /tmp/ds-vm-fail.ds <<'DS'
false
echo "after"
DS

ds /tmp/ds-vm-fail.ds
ds emit bash /tmp/ds-vm-fail.ds -o /tmp/ds-vm-fail.sh
bash /tmp/ds-vm-fail.sh
```

Expected:

- both VM and Bash runs exit non-zero;
- neither prints `after`.

## Completion notes

Implemented in `tests/run_v0_3.sh`, `tests/test_v0_3_runtime.c`, and the `tests/v0_3/` fixtures/goldens. The top-level `make test` target runs the v0.1, v0.2, and v0.3 suites. `make asan` and `make ubsan` are available for sanitizer-backed test runs where the local compiler supports them.

The v0.3 suite documents and tests the conservative comparison model: values are rendered to deterministic strings before comparison so VM behavior matches the current Bash emitter. Type-aware numeric comparison is intentionally deferred.
