# v0.31.0 Spec — Recursive Glob Patterns

## Status

Planned. This is the next unwritten roadmap milestone after
`v0.30.0 — Index Assignment`.

`v0.31.0` expands the existing `glob` and `glob!` standard-library helpers so
scripts can traverse directory trees portably. It must keep the project rule that
every accepted production feature runs in the VM and emits to standalone Bash
with matching observable behavior.

## Goal

Add deterministic recursive `**` glob support to the existing `glob(pattern)`
and `glob!(pattern)` APIs.

By the end of this milestone:

- `glob("**/*.ds")` and `glob!("src/**/*.c")` are accepted when the pattern uses
  the scoped recursive-segment contract;
- recursive `**` means zero or more directory segments;
- results are deterministic, duplicate-free, and sorted in a VM/Bash-parity-safe
  order;
- dotfile, hidden-directory, symlink, no-match, and invalid-pattern behavior is
  specified and tested;
- literal invalid recursive patterns fail during checking/lowering;
- dynamically constructed invalid recursive patterns fail as runtime data errors
  in both VM mode and emitted Bash;
- emitted Bash remains standalone and does not depend on the caller's ambient
  shell options such as `globstar` or `dotglob`.

The core product rules remain unchanged:

```txt
every supported production feature runs in the VM
every supported production feature emits standalone Bash
generated Bash is standalone and must not call ds
VM and emitted Bash behavior match for stdout, stderr, exit status, and side effects
unsupported or deferred forms fail clearly before partial execution/emission
the lowerer owns language/parity gates; backends consume accepted HIR
```

## Motivation

The existing `glob` and `glob!` helpers make shallow file selection portable, but
real scripts often need to find files throughout a tree:

```ds
for file in glob("src/**/*.ds") {
  echo file
}
```

Raw Bash can do this only when the script deliberately manages shell options such
as `globstar`, sorting, and hidden-file behavior. Those defaults are easy to
forget and differ from the VM's runtime implementation. `v0.31.0` should turn the
common recursive traversal case into a boring portable helper while keeping the
surface smaller than a general filesystem query language.

## Non-goals

This version does not include:

- new glob syntax outside the existing `glob` and `glob!` helper calls;
- custom glob flags or option objects;
- brace expansion;
- extglob syntax;
- shell command substitution or environment expansion inside glob patterns;
- `~` expansion;
- Windows path semantics;
- filesystem watchers;
- streaming/lazy glob iterators;
- following directory symlinks during recursive traversal;
- recursive delete/copy/move helpers;
- changing `lines`, `file`, `dir`, or `path` helper semantics;
- regex captures, regex replacement, or runtime regex strings;
- cleanup/debt work scoped to `v0.33.0` unless it is necessary to implement this
  milestone safely.

Treat `v0.32.0` regex expansion and `v0.33.0` collection/glob/regex cleanup as
future work. Do not pull them into this milestone.

## Required feature work

### 1. Supported public API

No new top-level syntax is introduced. Recursive globbing uses the existing
helpers:

```ds
for file in glob("**/*.ds") {
  echo file
}

for file in glob!("src/**/*.c") {
  echo file
}
```

Required behavior:

- `glob(pattern)` returns an array/iterable of matching path strings;
- unmatched `glob(pattern)` returns an empty array/iterable;
- `glob!(pattern)` returns matches or fails when the pattern has no matches;
- recursive patterns are accepted anywhere existing `glob` and `glob!` calls are
  accepted: loops, value bindings, indexing, interpolation through scalar reads,
  functions, imports, tests, and command words after scalar binding;
- accepted recursive glob results remain string arrays for collection and loop
  portability rules;
- helper names, arity, and string-argument rules remain the existing stdlib
  contract.

### 2. Recursive segment contract

A recursive glob segment is a path segment exactly equal to `**`.

Supported examples:

```txt
**/*.ds
src/**/*.c
src/**/test-*.ds
./**/*.txt
```

The segment means zero or more directory segments at that position:

```txt
src/**/*.ds
```

matches both:

```txt
src/main.ds
src/nested/deep/main.ds
```

Default v0.31 restrictions:

- support exactly one recursive `**` segment per pattern;
- reject multiple recursive segments such as `src/**/tests/**/*.ds` unless the
  implementation deliberately amends this spec before release and tests the
  parity implications;
- reject adjacent recursive forms such as `**/**`;
- reject ambiguous uses where `**` is not a full path segment, such as
  `src/**file.ds`, `src/foo**bar.ds`, or `src/***.ds`;
- reject recursive segments in patterns whose path normalization would be
  ambiguous for the current POSIX-style path model.

Normal non-recursive glob patterns continue to use the existing `*`, `?`, and
bracket-class surface. A single `*` remains the ordinary single-segment wildcard;
recursive behavior belongs only to a full `**` segment.

### 3. Path model and returned strings

Recursive globbing uses the same POSIX-style path model as the existing standard
library helpers.

Required behavior:

- relative patterns are evaluated relative to the process current working
  directory;
- absolute patterns are allowed only if existing `glob` behavior already supports
  absolute patterns portably; otherwise they are rejected with a clear diagnostic
  and recorded as deferred;
- returned relative paths remain relative strings;
- returned absolute paths remain absolute strings when absolute patterns are
  accepted;
- the implementation must not add a leading `./` unless the pattern itself starts
  with `./`;
- zero-directory matches collapse the recursive segment without producing double
  slashes;
- path separators in returned results are `/`;
- the input pattern is data, not shell code. It must not execute commands,
  expand variables, or read shell aliases/functions.

The milestone should not normalize away `..`, resolve symlinks, expand `~`, or
absolutize paths unless an earlier helper already documents that behavior.

### 4. Result ordering and duplicates

Recursive glob results must be deterministic and duplicate-free.

Required behavior:

- sort returned path strings lexicographically by byte value, equivalent to a
  stable `LC_ALL=C` ordering for ASCII-path test fixtures;
- do not depend on filesystem enumeration order;
- do not depend on the user's locale;
- return each matching path at most once;
- preserve exact path spelling from the chosen traversal representation, subject
  to the returned-string rules above;
- keep VM and emitted Bash order identical for every accepted pattern.

If the implementation uses Bash tools such as `find`, `sort`, or shell globs, it
must force or emulate the same ordering contract internally without leaking locale
or shell-option changes to user code.

### 5. Dotfile and hidden-directory behavior

The default recursive-glob behavior should match the existing shell-style rule:
patterns do not match path components beginning with `.` unless the corresponding
pattern segment begins with `.`.

Required behavior:

- `glob("**/*.ds")` does not return `.hidden.ds` in the current directory;
- `glob("**/*.ds")` does not recurse into `.git`, `.cache`, or other hidden
  directories;
- `glob("**/.env")` may match `.env` files in visible directories because the
  final pattern segment begins with `.`;
- `glob(".config/**/*.json")` may traverse `.config` because that hidden
  directory is named explicitly before the recursive segment;
- a hidden directory below a recursive segment is not traversed unless a future
  flag system explicitly enables hidden traversal.

Do not add an `include_hidden` option in this milestone. If implementation
constraints require a narrower hidden-file contract, update this spec and the
syntax catalog before release rather than letting VM and Bash drift.

### 6. Symlink behavior

Recursive traversal must avoid cycles and backend-specific surprises.

Required behavior:

- directory symlinks are not followed by the recursive `**` traversal;
- symlink entries are returned when the final matched path itself satisfies the
  pattern;
- broken symlinks should be returned when the directory entry name matches and
  the platform exposes it through the traversal API without following it;
- a symlink to a regular file may be returned as a matching path;
- a symlink to a directory may be returned only when the pattern matches the
  symlink path itself, but its children are not traversed through that symlink;
- traversal must not loop indefinitely through symlink cycles.

If broken-symlink parity is not portable in the current test environment, keep
that case as a manual/conditional test and document the limitation before closing
the milestone.

### 7. No-match and failure behavior

The existing `glob` vs `glob!` distinction remains unchanged.

Required behavior:

- `glob("src/**/*.missing")` produces zero iterations and a successful script;
- `glob!("src/**/*.missing")` fails the script with a clear runtime diagnostic;
- no-match failure occurs before any loop body executes for the failed `glob!`;
- no-match diagnostics include enough source context to identify the helper call;
- VM and emitted Bash agree on exit status and stderr wording at the same
  granularity the project already requires for runtime diagnostics.

### 8. Static and dynamic validation ownership

Validation follows the existing diagnostics ownership model.

Parser/frontend owns:

- malformed call syntax;
- malformed strings;
- normal tokenization and AST preservation.

Lowerer owns:

- wrong helper arity;
- non-string pattern arguments when statically known;
- literal recursive glob patterns that violate the v0.31 segment contract;
- literal multiple-recursive-segment patterns if the default single-`**` contract
  remains in force;
- unsupported iterable use of helper results;
- any parity gate that can be decided before execution.

VM/runtime and emitted Bash helpers own:

- invalid recursive pattern strings produced dynamically at runtime;
- no-match failures for `glob!`;
- filesystem traversal failures, permission failures, and other OS/data errors;
- internal accepted-HIR invariants that should be unreachable after lowering.

Backend code must not become the language owner for source-level recursive glob
acceptance. Backend diagnostics for unsupported recursive forms are acceptable
only as dynamic runtime data failures or internal invariants.

### 9. HIR and stdlib metadata

Recursive glob support should reuse the existing stdlib/helper model instead of
introducing backend-specific parsing.

Required behavior:

- stdlib metadata still identifies `glob` and `glob!` as string-pattern helpers;
- lowered HIR carries enough information for backends to know a call may require
  recursive matching helpers;
- literal pattern validation should happen once in lowering or shared metadata
  helpers, not separately in VM and Bash;
- dynamic pattern validation should use a shared pattern classifier where
  practical, so VM and Bash helper behavior stays aligned;
- debug HIR output should remain deterministic and reveal helper calls clearly
  enough to diagnose dependency drift.

If the implementation adds a shared recursive-glob pattern parser/classifier, it
belongs with stdlib/glob metadata or runtime support, not in a backend-only file.

### 10. VM behavior

The VM implementation must provide recursive traversal without shell expansion.

Required behavior:

- evaluate the pattern expression exactly once;
- validate dynamic recursive-pattern shape before traversal;
- traverse the filesystem using runtime/process current working directory;
- apply existing non-recursive pattern matching for ordinary path segments;
- implement the `**` segment as zero or more directory segments;
- avoid following directory symlinks;
- collect matching path strings as owned runtime string values;
- sort and deduplicate results before exposing them to loops/indexing;
- return an empty collection for non-required no-match cases;
- fail required no-match, permission, and traversal errors with runtime
  diagnostics that carry source context where available;
- keep memory ownership clear for potentially large result sets.

The VM must not use a shell to expand recursive patterns.

### 11. Bash emission behavior

Emitted Bash must be standalone and parity-safe.

Required behavior:

- emitted scripts must not call `ds` or the C runtime;
- emitted scripts must not rely on the user's ambient `shopt -s globstar`,
  `nullglob`, `failglob`, or `dotglob` settings;
- any shell options changed inside helpers must be local/restored before user
  commands execute;
- helper names must stay in the reserved `__ds_` namespace;
- generated helpers must quote paths safely, including spaces and leading dashes;
- recursive results must be sorted and deduplicated with the same observable
  ordering as VM results;
- `glob!` no-match failure must stop execution consistently;
- helper dependency scanning must emit recursive-glob helpers only when accepted
  HIR needs them;
- non-recursive glob helper emission must keep existing behavior and should not
  grow recursive-only dependencies unnecessarily;
- emitted Bash must pass `bash -n`.

The Bash implementation may use portable Bash plus common POSIX tools only if the
project accepts those tools as part of the standalone Bash contract. If a tool is
not acceptable, implement the helper in Bash directly or narrow the milestone
before release.

### 12. Interactions with existing language features

Recursive glob results must compose with existing accepted behavior:

- `for file in glob("**/*.ds") { ... }` iterates sorted strings;
- `let files = glob("**/*.ds")` stores a string array;
- indexing a known recursive glob result keeps the known string element kind when
  existing collection-kind tracking supports that for `glob`;
- `len(glob("**/*.ds"))` or equivalent length helpers keep existing semantics if
  already supported;
- function calls may return recursive glob arrays where flat array returns are
  supported;
- imports may contain helper functions that use recursive globs;
- test blocks may create controlled directories and assert recursive results;
- command statements may use scalar paths produced by recursive glob loops;
- interpolation of a scalar loop variable or indexed glob result works through
  the existing interpolation rules;
- `break`, `continue`, `return`, `fail`, `exit`, defers, and traps keep existing
  control-flow behavior around recursive glob loops.

Do not add direct collection-to-command splatting or command-word recursive glob
syntax in this milestone. Users should bind or loop over glob results explicitly.

### 13. Formatter, AST, HIR, and bytecode/debug output

Public tooling must remain coherent:

- `ds tokens` should not require new tokens for recursive glob support;
- `ds ast` should show ordinary helper calls with recursive pattern strings;
- `ds hir` should show accepted helper calls in a stable way;
- `ds bytecode` should show any distinct helper/runtime call consistently if the
  VM bytecode has separate operations;
- `ds fmt` should preserve recursive glob pattern strings exactly;
- formatter output must remain idempotent;
- `ds check` should report literal invalid recursive patterns before backend
  selection.

### 14. Documentation updates

Update docs only where they become outdated during implementation:

- `docs/status.md` should move recursive `**` glob patterns from deferred to
  supported after implementation;
- `docs/language.ds` should mark recursive globbing as implemented in v0.31 and
  document the scoped `**` segment contract;
- `docs/runtime.md` should describe recursive traversal, sorting, hidden-file,
  symlink, and dynamic-runtime failure behavior;
- `docs/parity-contracts.md` should mention recursive glob parity requirements;
- `docs/diagnostics.md` should update the static/dynamic recursive-glob
  diagnostic examples;
- `docs/concept-map.md` and `docs/source-map.md` should move recursive globbing
  from clear-while-rejected to its implemented concept home;
- examples may use recursive globbing only after implementation is complete.

Do not update docs to imply glob flags, hidden traversal flags, multiple `**`
segments, regex captures/replacement/runtime regex strings, or cleanup work from
`v0.33.0` are supported unless those features are explicitly implemented and
tested in this milestone.

## Acceptance criteria

`v0.31.0` is complete when:

- recursive `**` patterns parse, lower, execute in VM mode, and emit standalone
  Bash through the existing `glob` and `glob!` helpers;
- VM/Bash parity holds for stdout, stderr, exit status, and filesystem side
  effects in controlled fixtures;
- zero-directory matches, nested matches, no-match behavior, dotfiles,
  hidden directories, symlinks, sorting, spaces, and leading-dash paths are
  covered by tests;
- invalid literal recursive patterns fail during checking/lowering;
- invalid dynamic recursive patterns fail as runtime data errors in both VM and
  emitted Bash;
- generated Bash passes `bash -n`, does not call `ds`, does not leak shell-option
  changes, and includes only required helpers;
- docs accurately describe supported recursive globbing and still defer regex
  expansion, cleanup work, custom glob flags, hidden traversal flags, and
  symlink-following behavior;
- the dedicated v0.31 test suite passes and is wired into aggregate tests.

## Deferred to later milestones

- Regex captures, replacement, and runtime regex strings: `v0.32.0`.
- Cleanup across collection, glob, and regex behavior: `v0.33.0`.
- Richer signal/job-control behavior: `v0.34.0+`.
- Multiple recursive `**` segments per pattern unless this spec is deliberately
  amended during implementation.
- Custom glob flags such as include-hidden, follow-symlinks, directories-only,
  files-only, max-depth, or stable absolute/relative conversion options.
- Brace expansion, extglob, shell-style variable expansion, and `~` expansion.
- Streaming/lazy glob iterators and filesystem watcher APIs.
- Windows path semantics and cross-drive traversal behavior.
- Directory symlink traversal and cycle-detection policy beyond not following
  symlinked directories.
