# v0.32.0 Spec — Regex Captures, Replacement, and Runtime Regex Strings

## Status

Production implementation is complete. The dedicated `v0.32.0` test suite is
intentionally not added in the implementation-only pass and should follow
`docs/milestones/v0.32.0-test-plan.md`.

`v0.32.0` completes the practical regex layer that `v0.23.0` intentionally left
small. It must preserve the core project rule that every accepted production
feature runs through the VM and emits to standalone Bash with matching
observable behavior.

## Goal

Add a conservative, portable regex data API on top of the existing `matches`
operator:

- capture access for successful matches;
- regex-based replacement;
- runtime regex strings with deterministic validation;
- exact VM/Bash parity for accepted POSIX-ERE-compatible behavior;
- clear rejection for regex features that Bash and the VM cannot share.

By the end of this milestone:

- `text matches pattern_string` is accepted when `pattern_string` has string
  kind and is validated as a supported runtime regex;
- `regex.match(text, pattern)` returns a flat match-result map with capture
  values when the match succeeds;
- `regex.replace(text, pattern, replacement)` performs deterministic global
  regex replacement;
- regex literals still work in the existing `matches` position and may also be
  passed to the scoped regex helpers;
- optional unmatched captures, no-match results, replacement backreferences,
  invalid runtime patterns, and case-insensitive matching have specified
  behavior;
- emitted Bash remains standalone and does not call `ds` or depend on ambient
  shell options.

The product rules remain unchanged:

```txt
every supported production feature runs in the VM
every supported production feature emits standalone Bash
generated Bash is standalone and must not call ds
VM and emitted Bash behavior match for stdout, stderr, exit status, and side effects
unsupported or deferred forms fail clearly before partial execution/emission
the lowerer owns language/parity gates; backends consume accepted HIR
```

## Motivation

`v0.23.0` made regex matching useful for boolean filters:

```ds
if branch matches /^release\/[0-9]+$/ {
  echo "release branch"
}
```

Real scripts also need to extract version numbers, normalize text, and accept
patterns from arguments, environment variables, or small helper functions:

```ds
let m = regex.match("v1.2.3", /^v([0-9]+)\.([0-9]+)\.([0-9]+)$/)
if m.matched {
  let major = m["1"]
  echo "major={major}"
}

let pattern = "^release/[0-9]+$"
if branch matches pattern {
  echo "runtime pattern matched"
}

let normalized = regex.replace("api-123 web-456", /([a-z]+)-([0-9]+)/, "$1:$2")
```

This milestone should make those operations portable without turning `ds` into a
PCRE dialect or accepting regex syntax that emitted Bash cannot reproduce.

## Non-goals

This version does not include:

- full PCRE, Perl, Python, JavaScript, or Rust regex compatibility;
- named captures;
- non-capturing groups unless the VM/Bash-compatible regex subset is deliberately
  expanded in this spec before implementation;
- lookaround;
- pattern backreferences such as `(a)\1`;
- lazy quantifiers;
- inline flags such as `(?i)`;
- Unicode property classes such as `\p{L}`;
- word-boundary shortcuts unless an exact VM/Bash contract is proven first;
- multi-line regex literals;
- regex values as first-class compiled objects;
- regex splitting;
- replacement callbacks;
- replacement count limits or replace-first APIs;
- capture arrays with nested/optional value types;
- a custom regex engine dependency that is not also available to emitted Bash;
- broad collection cleanup scoped to `v0.33.0`.

Treat broad regex compatibility and richer text-processing APIs as future work.
Do not pull them into `v0.32.0` unless the roadmap and this spec are amended
deliberately.

## Required feature work

### 1. Regex pattern inputs

`v0.32.0` supports two regex pattern input forms:

1. existing regex literals, such as `/^v([0-9]+)$/` and `/api/i`;
2. string expressions that contain supported POSIX ERE pattern text.

Required accepted examples:

```ds
let literal_ok = "v1" matches /^v[0-9]+$/

let pattern = "^v([0-9]+)$"
let dynamic_ok = "v1" matches pattern

let from_fn = pattern_for_versions()
let m = regex.match("v2", from_fn)

let replaced = regex.replace("api-123", /([a-z]+)-([0-9]+)/, "$1:$2")
```

Validation requirements:

- regex literals keep the `v0.23.0` lexer/parser/lowerer validation path;
- direct string literals used as regex patterns should be statically validated
  when the lowerer can see the literal text;
- dynamically constructed string patterns are validated at runtime by both VM and
  emitted Bash helpers before use;
- invalid dynamic patterns fail as runtime data errors before later side effects;
- non-string dynamic pattern operands are rejected by lowering when their kind is
  known, or by runtime type guards if the kind is only knowable at runtime;
- all accepted runtime string patterns use the same supported regex subset as
  regex literals, except they are not wrapped in `/.../` delimiters.

String pattern examples:

```ds
let ok = "release/12" matches "^release/[0-9]+$"
let m = regex.match("v1.2", "^v([0-9]+)\\.([0-9]+)$")
```

Runtime string patterns do not accept trailing literal flags such as
`"pattern/i"`. Flags are passed through helper arguments where this milestone
explicitly supports them.

### 2. Case-insensitive matching and flags

Regex literals continue to support the existing `/.../i` flag from `v0.23.0`.

For runtime strings, `v0.32.0` adds an optional flags string to the regex helper
APIs:

```ds
let m = regex.match("API", "^api$", "i")
let out = regex.replace("API api", "api", "svc", "i")
```

Required behavior:

- accepted flags are either `""` or `"i"`;
- repeated flags such as `"ii"` are rejected;
- unknown flags are rejected;
- runtime flag strings that are not statically known are validated at runtime;
- `/.../i` and helper flag `"i"` have the same case-insensitive behavior;
- emitted Bash may use `nocasematch` or helper-local normalization, but must
  restore any shell option state it changes;
- scripts that do not use case-insensitive regex must not change shell options.

The `matches` operator with a runtime string operand does not grow a flags slot
in this milestone. Use `regex.match(text, pattern, "i").matched` when dynamic
flags are required.

### 3. Runtime `matches` strings

Extend the existing `matches` expression so the right operand may be either a
regex literal or a string-kind expression:

```ds
let pattern = "^release/[0-9]+$"

if branch matches pattern {
  echo "release"
}
```

Required behavior:

- the left operand must still be a string;
- a regex literal right operand preserves existing `v0.23.0` behavior;
- a string right operand is treated as pattern text, not a literal substring;
- the expression returns bool;
- invalid runtime pattern strings fail at runtime;
- the right operand cannot be an array, map, command-result object, function that
  returns a non-string value, env object, or collection element with known
  non-string kind;
- boolean combinations, interpolation, function returns, tests, and `case`
  expressions may use runtime-string `matches` wherever bool expressions are
  already accepted.

### 4. `regex.match`

Add a standard-library helper for match data:

```ds
let m = regex.match(text, pattern)
let m = regex.match(text, pattern, flags)
```

Where:

- `text` must be string-kind;
- `pattern` may be a regex literal or string-kind expression;
- `flags` is optional and must be `""` or `"i"`;
- the helper returns a flat map/object with scalar values.

Required match-result shape:

```txt
matched   bool    true when the pattern matched
full      string  full matched substring, or "" when no match
"0"      string  same full matched substring, or "" when no match
"1".."9" string  capture values for supported capturing groups when matched
```

Example:

```ds
let m = regex.match("v1.2.3", /^v([0-9]+)\.([0-9]+)\.([0-9]+)$/)

if m.matched {
  let major = m["1"]
  let minor = m["2"]
  let patch = m["3"]
  echo "version {major}.{minor}.{patch}"
}
```

Required behavior:

- no match is not an error;
- no match returns `matched: false`, `full: ""`, and `"0": ""`;
- numbered capture keys are guaranteed only after a successful match;
- optional unmatched captures within a successful match are represented as the
  empty string, matching portable Bash `BASH_REMATCH` observability;
- captures that match an empty string are also represented as the empty string;
- named/direct field access is supported only for identifier-safe keys such as
  `matched` and `full`; numeric captures use bracket access such as `m["1"]`;
- capture groups are numbered by opening parenthesis, matching POSIX/Bash order;
- support at least capture groups `1` through `9`;
- direct literal patterns with more than nine capture groups are rejected during
  checking/lowering;
- dynamic patterns with more than nine capture groups fail at runtime with a
  clear diagnostic;
- the returned map is a normal flat map value for the already supported map
  access, interpolation, function-return, and map-iteration rules;
- nested maps/arrays are not introduced by this helper.

Do not add a throwing `regex.match!` helper in this milestone. Scripts should
check `m.matched` explicitly.

### 5. `regex.replace`

Add a standard-library helper for global regex replacement:

```ds
let out = regex.replace(text, pattern, replacement)
let out = regex.replace(text, pattern, replacement, flags)
```

Where:

- `text` must be string-kind;
- `pattern` may be a regex literal or string-kind expression;
- `replacement` must be string-kind;
- `flags` is optional and must be `""` or `"i"`;
- the helper returns a string.

Required behavior:

- replacement is global and left-to-right over non-overlapping matches;
- no-match replacement returns the original string;
- `$0` expands to the full match;
- `$1` through `$9` expand to supported capture groups;
- `$$` expands to a literal `$`;
- a lone `$` or `$` followed by an unsupported character is rejected;
- a reference to a capture group that cannot exist is rejected statically for
  literal patterns and at runtime for dynamic patterns;
- an optional unmatched capture expands to the empty string;
- replacement text is not a regex and is not shell code;
- replacement may produce empty, shorter, longer, or multi-line strings if the
  existing string model supports those contents;
- patterns that produce zero-length replacement matches fail with a runtime data
  diagnostic in this milestone rather than risking divergent VM/Bash loops.

Example:

```ds
let raw = "api-123 web-456"
let normalized = regex.replace(raw, /([a-z]+)-([0-9]+)/, "$1:$2")
echo normalized
```

Expected output:

```txt
api:123 web:456
```

This milestone intentionally does not add replace-first, replace-count, callback,
or split behavior.

### 6. Supported regex subset

The `v0.23.0` supported subset remains the default:

```txt
literal characters except unescaped `/` and newline in regex literals
escaped literal slash `\/` in regex literals
escaped backslash `\\`
anchors `^` and `$`
any character `.`
character classes such as `[abc]`, `[^abc]`, `[a-z]`
capturing groups `( ... )`
alternation `|`
quantifiers `*`, `+`, `?`, `{m}`, `{m,n}`
optional flag `i`
```

`v0.32.0` makes capturing groups observable through `regex.match` and
`regex.replace`, but does not expand the pattern grammar unless implementation
requires a narrowly documented amendment.

Still unsupported:

```txt
lookaround
named captures
pattern backreferences
inline flags
non-capturing group syntax if not shared with the portable subset
lazy quantifiers
Unicode character classes
word-boundary shortcuts without an exact parity contract
multi-line regex literals
```

Unsupported constructs in regex literals or direct string literals should fail
before execution/emission. Unsupported constructs in dynamically constructed
patterns fail at runtime before later side effects.

### 7. Parser, AST, HIR, and stdlib representation

Parser/frontend responsibilities:

- preserve existing regex literal tokenization and diagnostics;
- continue rejecting unterminated regex literals and regex literal newlines;
- parse `regex.match(...)` and `regex.replace(...)` as ordinary helper calls;
- parse runtime-string `matches` without adding new tokens;
- avoid deciding value-kind, capture-count, replacement, or backend behavior.

Lowerer responsibilities:

- own acceptance of runtime-string `matches`;
- own `regex.match` and `regex.replace` arity/kind checks;
- validate regex literals and direct string literal patterns where possible;
- validate direct literal replacement strings where possible;
- reject known unsupported constructs before backend selection;
- produce backend-neutral HIR/helper metadata for pattern kind, flags, capture
  count when known, replacement usage, and runtime-validation requirements;
- reject unsupported map/array/command-result/env operands before VM/Bash code.

HIR responsibilities:

- represent regex operations without embedding Bash text or VM-specific register
  behavior;
- carry source spans for runtime diagnostics;
- carry enough metadata for Bash helper dependency discovery;
- preserve regex literal text and decoded string pattern text consistently.

Stdlib metadata responsibilities:

- add the `regex` namespace without weakening unknown-helper diagnostics;
- mark return kinds: bool for runtime-string `matches`, map for `regex.match`,
  string for `regex.replace`;
- record which helpers require embedded Bash support.

### 8. VM behavior

The VM owns direct execution of accepted HIR.

Required VM behavior:

- compile/validate runtime regex strings before each regex operation;
- execute matching with the same search semantics as existing `matches`;
- expose capture groups according to the match-result map contract;
- implement global replacement with `$0`..`$9` and `$$` replacement expansion;
- fail invalid runtime patterns, invalid runtime flags, too many capture groups,
  invalid replacement syntax, nonexistent replacement groups, and zero-length
  replacement matches with clear runtime diagnostics;
- avoid memory leaks for failed regex compilation, failed map construction,
  failed replacement, and early returns;
- preserve existing stdout/stderr/status behavior.

### 9. Bash emission behavior

The Bash emitter owns standalone rendering of accepted regex HIR.

Required Bash behavior:

- emitted Bash must not call `ds`;
- scripts using regex helpers emit only the necessary `__ds_` helper functions;
- helper names remain in the reserved `__ds_` namespace;
- helpers must not depend on user aliases, functions, shell options, locale, or
  ambient `BASH_REMATCH` contents;
- helper-local changes to `nocasematch` or other options are restored before
  returning;
- capture extraction uses Bash behavior only behind a helper that implements the
  documented `ds` contract;
- runtime invalid patterns/flags/replacements fail before later side effects;
- generated scripts pass `bash -n`;
- generated scripts that do not use regex helpers do not emit regex helper code.

If implementation discovers a POSIX/Bash capture or replacement edge case that
cannot be made portable, move the rejection to lowering/runtime validation and
record it in this spec before closing the milestone.

### 10. Diagnostics and debugging behavior

Diagnostics should be phase-owned:

- lexer/parser: malformed regex literal syntax, unterminated literals, invalid
  literal delimiters, and illegal literal newlines;
- lowerer: invalid static pattern strings, unsupported constructs, wrong arity,
  wrong known operand kinds, invalid literal flags, invalid literal replacement
  syntax, known nonexistent replacement capture references, too many static
  capture groups, and unsupported direct regex values;
- VM/runtime helpers: invalid dynamic pattern strings, invalid dynamic flags,
  too many dynamic capture groups, invalid dynamic replacement strings,
  nonexistent dynamic replacement capture references, zero-length replacement
  matches, and runtime type errors not knowable earlier;
- Bash emitter: only internal emission failures for already accepted HIR.

Debug outputs should remain deterministic:

- `ds tokens` preserves regex literal text;
- `ds ast` shows regex literals and ordinary regex helper calls;
- `ds hir` or equivalent output shows stable regex operation/helper metadata;
- `ds bytecode` remains pointer-free and stable if regex helper calls compile to
  bytecode instructions.

Diagnostics should include source spans and keep the existing style. They should
not expose private helper payloads unless the failure is an internal invariant
error.

Update docs only when implementation changes the supported user-facing surface.

Expected docs/examples updates during implementation:

- `docs/language.ds`: move capture/replacement/runtime-string examples from
  deferred comments into the supported regex section;
- `docs/status.md`: update support matrix after implementation and tests;
- `docs/runtime.md`: describe runtime pattern validation, match-result maps,
  replacement expansion, optional-capture behavior, and unsupported regex forms;
- `docs/parity-contracts.md`: add or update regex parity notes if HIR/helper

- `docs/diagnostics.md`: update only if new ownership wording is needed;
- `CHANGELOG.md`: add a planned/completed entry;
- examples: add one honest capture/replacement/runtime-pattern example if it can

Do not overclaim PCRE support, named captures, regex split, replace-first, or
Unicode-aware matching.

## Acceptance criteria

`v0.32.0` is complete only when:

- runtime-string `matches` parses, checks, runs in VM mode, and emits to
  standalone Bash;
- `regex.match` returns the specified flat map result in VM and emitted Bash;
- `regex.replace` returns the specified global replacement result in VM and
  emitted Bash;
- literal and runtime string patterns share the supported regex subset;
- direct invalid literals fail before execution/emission;
- dynamic invalid patterns, flags, replacements, and zero-length replacement
  matches fail at runtime before later side effects;
- case-insensitive literal and helper-flag behavior is parity-tested;
- optional unmatched captures are represented as empty strings consistently;
- capture groups above `9` are rejected;
- generated Bash passes `bash -n`, contains no `ds` invocation, and emits helper
  code only when needed;
- VM/Bash stdout, stderr, exit status, and side effects agree for all accepted
  test fixtures;
- docs/examples distinguish supported v0.32 regex APIs from deferred PCRE,
  named-capture, split, and replace-count behavior;
- the dedicated `v0.32.0` test suite and relevant previous suites pass, or any
  unrelated host limitation is documented honestly in the completion review.

## Out-of-scope list for implementers

Do not pull these into implementation while working on `v0.32.0`:

- named captures;
- regex split;
- replace-first or replacement count options;
- callback replacements;
- pattern backreferences;
- lookaround or lazy quantifiers;
- inline flags;
- raw strings unless already implemented by a separate milestone;
- Unicode-aware regex classes or locale-dependent semantics;
- matching over binary data;
- arbitrary capture arrays or nested return values;
- new map/list mutation beyond `v0.30.0`;
- collection/glob/regex cleanup scoped to `v0.33.0`;
- signal/job-control work scoped to later milestones;
- backend expansion beyond standalone Bash.
