# v0.33.0 Spec — Cleanup: Collection, Glob, and Regex Stabilization

## Status

Implementation and dedicated-test pass complete for the scoped production-code,
documentation, and regression coverage requested by the `v0.33.0` cleanup
milestone. The dedicated `tests/v0_33/run.sh` suite is wired into aggregate test
targets and documents the remaining host-dependent skips inside the test output.

`v0.33.0` is a cleanup/stabilization release. It must not add new user-facing
syntax or broaden the language surface. Its job is to make the features added
from `v0.25.0` through `v0.32.0` feel like one coherent, portable contract
before the project moves into the higher-risk signal/job-control work planned
for `v0.34.0+`.

## Goal

Stabilize the collection, glob, and regex feature wave by auditing and fixing
VM/Bash parity gaps, documentation overclaims, examples, helper hygiene, and
technical debt that now sits directly on the hot paths for:

- scalar, collection, and command-result value returns from `v0.25.0` and
  `v0.26.0`;
- direct environment access and command-word interpolation from `v0.27.0`;
- map iteration from `v0.29.0`;
- flat index assignment from `v0.30.0`;
- recursive glob patterns from `v0.31.0`;
- runtime regex strings, capture maps, and replacement from `v0.32.0`.

The outcome should be boring and confidence-building:

```txt
no new syntax
no new data structures
no new regex/glob features
VM and emitted Bash agree for the supported surface
docs/examples do not claim deferred behavior is supported
generated Bash remains standalone and helper-hygienic
source ownership docs match the implementation shape
technical debt is recorded with concrete owners and constraints
```

The companion test plan lives at `docs/milestones/v0.33.0-test-plan.md`.

## Motivation

The previous feature wave added a lot of practical scripting power: structured
returns, environment mutation, deterministic map iteration, flat mutation,
recursive file traversal, and regex capture/replacement. Each feature was scoped
to preserve VM/Bash parity, but the combined surface now crosses many modules:

- lowerer portability gates;
- VM runtime values and stdlib helpers;
- Bash structured-value sidecars;
- generated Bash helper dependency scanning;
- generated Bash helper bodies;
- examples, status docs, language catalog, and milestone docs.

This is exactly the point where a cleanup milestone should pay down integration
debt before adding process/signal features. Bugs found late in `v0.31.0` and
`v0.32.0` were not missing syntax; they were parity/hygiene problems caused by
subtle backend differences such as Bash process substitutions, ambient shell
options, helper emission scope, and anchored regex replacement behavior.

`v0.33.0` should make those classes of mistakes harder to repeat.

## Product principles preserved

The project rules remain unchanged:

```txt
Every accepted production feature runs in the VM.
Every accepted production feature emits standalone Bash.
Generated Bash must not call ds.
Lowering owns semantic/parity gates for statically knowable forms.
VM and Bash helpers own runtime data/OS failures.
Unsupported or deferred forms fail clearly before partial execution/emission.
Cleanup versions are real milestones, not optional chores.
```

## Non-goals

Do not implement any of these in `v0.33.0`:

- nested collections;
- collection references, aliases, or mutation through aliases;
- sparse arrays;
- array/map deletion;
- slice assignment;
- map sorting options or custom comparators;
- environment iteration or `.env` loading;
- custom glob flags;
- multiple recursive `**` segments;
- hidden traversal flags;
- symlink-following recursive traversal;
- brace expansion, extglob, shell variable expansion, or `~` expansion in glob
  helpers;
- named regex captures;
- regex split;
- replace-first/count-limited replacement;
- replacement callbacks;
- first-class compiled regex values;
- richer regex dialect support such as lookaround, pattern backreferences,
  lazy quantifiers, inline flags, Unicode properties, or PCRE compatibility;
- new signal/job-control APIs;
- native or alternate shell backends;
- broad parser or VM rewrites unrelated to the stabilization targets.

If a parity bug is found in the supported surface, fix the bug. If a behavior is
not already supported by the prior milestone specs, keep it rejected/deferred and
document the boundary.

## Required cleanup work

### 1. Collection contract stabilization

Audit the collection behavior introduced and hardened across `v0.25.0` through
`v0.30.0`.

Required outcomes:

- flat array and flat map values keep their documented scalar element/value
  boundary;
- returned arrays/maps preserve element/key/value kind metadata in both VM and
  Bash;
- collection variable copies remain value copies, not aliases;
- map iteration remains deterministic bytewise/ASCII key order in VM and Bash;
- map iteration over supported flat map-returning functions still works without
  leaking return transport data to stdout;
- array loops, map loops, membership, conditions, `case`, interpolation, and
  function returns compose without backend drift;
- `items[index] = scalar` and `map[key] = scalar` still mutate only named flat
  collection bindings;
- array assignment rejects sparse/out-of-bounds writes consistently;
- map assignment rejects empty keys and unsupported key/value kinds consistently;
- mutation of a map currently being iterated remains rejected before execution or
  emission;
- unsupported temporary/function-call/command-result/nested mutation forms stay
  rejected by parser/lowerer diagnostics, not backend fallbacks;
- docs and examples do not imply nested collection values, aliases, deletion,
  sparse arrays, or field-style map assignment are supported.

Allowed fixes:

- parity bug fixes in VM/Bash execution;
- clearer lowerer diagnostics for already-rejected unsupported forms;
- small refactors that keep ownership boundaries intact;
- docs/examples corrections that reflect existing supported behavior.

Disallowed expansion:

- accepting new collection shapes or mutation targets;
- adding nested collection storage;
- adding references/aliases;
- changing deterministic map ordering.

### 2. Recursive glob stabilization

Audit the `glob` / `glob!` behavior after `v0.31.0`.

Required outcomes:

- exactly one complete `**` path segment remains the only accepted recursive
  form;
- `**` remains zero or more directory segments;
- results remain sorted, duplicate-free strings;
- `glob` no-match returns an empty array;
- `glob!` no-match fails before loop bodies or later side effects;
- hidden path components remain skipped unless explicitly named by a non-`**`
  path segment;
- directory symlinks are not traversed;
- file symlinks and broken matching symlinks remain handled according to the
  documented traversal/matching contract;
- runtime traversal failures fail consistently in VM and emitted Bash;
- generated Bash does not rely on ambient shell options such as `globstar`,
  `dotglob`, `nullglob`, `failglob`, or user-modified `IFS`;
- literal invalid recursive patterns are rejected by the lowerer/shared
  classifier;
- dynamic invalid recursive patterns fail as runtime data errors in VM/Bash
  helpers;
- docs do not imply raw Bash globstar behavior or shell expansion semantics.

Allowed fixes:

- parity bug fixes in recursive traversal and sorting;
- helper hygiene fixes that narrow generated Bash helper inclusion;
- clearer docs for hidden paths, symlinks, no-match behavior, and runtime
  filesystem failures.

Disallowed expansion:

- multiple recursive segments;
- partial `**` segments;
- custom traversal flags;
- shell-native brace/extglob expansion;
- symlink-following traversal.

### 3. Regex stabilization

Audit the `v0.23.0` and `v0.32.0` regex surface as one contract.

Required outcomes:

- regex literals and runtime string patterns share the supported regex subset;
- `matches` keeps boolean behavior for literals and runtime strings;
- `regex.match` returns the documented flat map with `matched`, `full`, `0`, and
  numbered capture keys for groups present in the validated pattern, up to `9`;
- unmatched optional captures remain empty strings;
- no-match maps remain populated consistently for all materialized keys;
- `regex.replace` remains global and data-only;
- replacement expansion supports only `$0` through `$9` and `$$`;
- zero-length replacement matches remain rejected to avoid infinite loops and
  VM/Bash drift;
- optional flags remain exactly `""` or `"i"`;
- emitted Bash explicitly controls `nocasematch` for both case-sensitive and
  case-insensitive regex operations;
- emitted Bash helper scanning includes only required regex helper bodies;
- unsupported dialect features fail with clear diagnostics before partial
  execution or emission when statically knowable;
- dynamic invalid patterns, flags, replacements, and capture limits fail before
  later side effects in both VM and emitted Bash;
- docs do not imply PCRE/Python/JS/Rust regex compatibility.

Allowed fixes:

- VM/Bash parity fixes for accepted POSIX-ERE-shaped behavior;
- static/dynamic diagnostic wording cleanup if ownership remains correct;
- refactors that keep shared validation in `ds_regex.*` and backend execution in
  VM/Bash helpers.

Disallowed expansion:

- broadening the regex dialect;
- adding first-class regex values;
- exposing a richer nested match object;
- adding split or replace-count APIs.

### 4. Helper dependency and generated Bash hygiene

Audit generated Bash helper discovery and helper bodies for the combined
collection/glob/regex surface.

Required outcomes:

- emitted Bash includes every helper needed by accepted HIR, including helpers
  used inside nested expressions, statement-style user-function call arguments,
  interpolation, loops, handlers, and returns;
- emitted Bash does not include large unrelated helper bodies when a narrower
  helper is sufficient;
- helper definitions are deduplicated;
- helper names remain under the reserved `__ds_` namespace;
- generated scripts pass `bash -n`;
- generated scripts do not call `ds`;
- generated scripts guard Bash 4+ behavior when associative arrays or other
  Bash-4-only features are required;
- helper bodies do not depend on ambient shell options, caller `IFS`, current
  shell state, or user aliases/functions;
- helper body failures propagate to the generated script instead of being hidden
  inside pipelines, process substitutions, or subshells.

Allowed fixes:

- helper scanner refactors in `src/bash_deps.c` if they reduce duplication and
  keep semantic validation out of the scanner;
- helper body refactors in `src/bash_helpers.c` if they improve propagation,
  isolation, or maintainability;
- source-map/concept-map updates when ownership becomes clearer.

Disallowed expansion:

- turning helper scanning into a semantic validator;
- moving source-language acceptance decisions into Bash-only code;
- adding a generated runtime dependency on `ds`.

### 5. Documentation and examples reconciliation

Reconcile docs and examples for the supported surface.

Required outcomes:

- `docs/status.md`, `docs/language.ds`, `docs/runtime.md`,
  `docs/parity-contracts.md`, `docs/diagnostics.md`, `docs/source-map.md`,
  `docs/concept-map.md`, `docs/technical-debt.md`, and `docs/release-checklist.md`
  agree with the implemented behavior through `v0.32.0`;
- old milestone docs may remain historical, but current docs must not present
  deferred behavior as supported;
- examples use final supported forms and avoid workarounds that are no longer
  necessary;
- examples do not imply unsupported nested collections, raw shell globstar,
  advanced regex dialect features, or mutation semantics beyond the flat named
  collection boundary;
- `examples/bad.ds` remains intentionally invalid;
- new or updated examples should be deterministic and portable.

Docs may be updated in this milestone when they are stale, misleading, or
overclaiming. Do not rewrite project principles or roadmap direction unless the
cleanup exposes a real contradiction.

## Technical debt exploration

The v0.33 implementation pass must include an explicit technical debt audit.
Use the following checklist and record concrete findings in either
`docs/technical-debt.md`, `docs/source-map.md`, `docs/concept-map.md`, or the
completion review section of this spec.

The audit should prefer targeted, behavior-preserving improvements over broad
rewrites. Long cohesive files are acceptable; mixed ownership and duplicated
policy are not.

### Current findings to investigate

#### H1 — `bash_deps.c` is now a broad helper-dependency scanner

**Categories:** file/module organization, function size, duplication, constants,
testing gaps, documentation and intent.

`src/bash_deps.c` now contains many parallel tree walkers named
`expr_uses_*`, `stmt_uses_*`, and `command_uses_*`. The scanner is important and
mostly policy-neutral, but it is becoming easy to miss new HIR expression
positions or over-emit helpers.

Required exploration:

- identify duplicated traversal patterns;
- check whether helper discovery covers all statement/expression payloads added
  through `v0.32.0`;
- check whether literal-vs-dynamic glob/regex helper decisions are documented;
- consider a small internal visitor/fact accumulator only if it reduces
  duplication without creating a generic semantic engine;
- add tests for helper inclusion/exclusion instead of relying on inspection.

Do not move lowerer validation into `bash_deps.c`.

#### H2 — `vm_stdlib.c` mixes many stdlib runtime concerns

**Categories:** file/module organization, separation of concerns, function size,
error handling, performance risks.

`src/vm_stdlib.c` owns file/path/env/cmd/lines/glob/regex helper execution. This
is acceptable as a VM stdlib implementation file, but glob and regex are now
large enough that future work may make the file hard to navigate.

Required exploration:

- verify sectioning and names make helper ownership clear;
- look for duplicated regex/glob validation already owned by `ds_regex.*` or
  `ds_stdlib.*`;
- check whether runtime diagnostics remain data/OS failures instead of semantic
  language gates;
- consider extraction only if there is a cohesive runtime cluster such as
  `vm_regex.c` or `vm_glob.c` with enough weight to justify a real module.

Do not split one tiny helper into a new file.

#### H3 — `bash_helpers.c` is a generated-helper catalog with growing bodies

**Categories:** file/module organization, architecture boundaries, constants,
security/data safety, observability/debugging.

`src/bash_helpers.c` contains generated Bash text for unrelated helper families.
The catalog shape is expected, but helper bodies can hide shell-state,
subprocess, quoting, or failure-propagation problems.

Required exploration:

- audit recursive glob and regex helper bodies for ambient shell-option
  dependencies;
- audit pipeline/process-substitution/subshell shapes that can swallow failures;
- check temporary-file cleanup and quoting in helper bodies;
- check whether helper error messages are consistent with VM diagnostics;
- keep helper snippets readable enough that future shell bugs can be reviewed.

Do not move source-language semantic acceptance into generated Bash helpers.

#### H4 — collection portability gates are centralized but easy to bypass

**Categories:** architecture boundaries, separation of concerns, error handling,
testing gaps.

`src/lower_collection.c` gives collection parity policy a home, while
`src/lower_stmt.c`, `src/lower_expr.c`, and `src/lower_command.c` still decide
many context-specific collection forms.

Required exploration:

- verify unsupported temporary/computed/nested collection forms fail in the
  lowerer or parser, not VM/Bash;
- verify command-word interpolation and normal interpolation enforce the same
  flat-index boundary where they claim to;
- check all mutation forms for named-target and scalar-RHS enforcement;
- update source/concept docs if ownership is broader than currently described.

Do not centralize context-specific rules so aggressively that command-word and
normal interpolation boundaries become unclear.

#### H5 — regex validation exists in both shared C and generated Bash forms

**Categories:** duplication, constants/shared values, dependency hygiene,
security/data safety.

`src/ds_regex.c` owns the C validation contract, but emitted Bash must carry a
standalone validator. This is intentional duplication for standalone Bash, but
the accepted/rejected dialect and error wording can drift.

Required exploration:

- compare shared C validation and emitted Bash validation for escapes, deferred
  groups, lazy quantifiers, capture count, flags, and replacement references;
- verify both paths reject unsupported features before later side effects when
  dynamic values are invalid;
- check whether version-specific diagnostic strings are centralized enough for
  current maintenance;
- add parity tests for edge cases that only one validator might reject.

Do not add a runtime dependency from emitted Bash to the C validator.

#### H6 — examples and release checklist lag behind the latest surface

**Categories:** dead/stale code, documentation and intent, testing gaps.

Some project-level docs and examples were written before the latest collection,
glob, and regex milestones. Historical milestone docs may stay historical, but
current docs and examples must not ask readers to use old workarounds or list
now-supported features as deferred.

Required exploration:

- update current docs that still list regex captures/runtime strings or
  recursive glob as deferred;
- verify `examples/collections.ds`, `examples/regex.ds`, and `examples/stdlib.ds`
  demonstrate final supported forms without overclaiming;
- verify release checklist known limitations match the current status;
- make examples part of the v0.33 test plan.

Do not rewrite docs solely for style.

#### H7 — large dispatcher functions remain risk points

**Categories:** function/component size, observability/debugging, documentation
and intent.

Large dispatchers such as `emit_stmt`, `compile_stmt`, `compile_expr`, VM main
execution, formatter/AST/HIR dumps, and parser/lexer switches are not wrong by
line count alone. The risk is that new cleanup fixes may add unrelated logic to
already broad switches.

Required exploration:

- keep collection/glob/regex fixes near their real owner;
- add section comments or small named helpers when a dispatcher case starts
  doing multiple jobs;
- avoid creating one-file-per-case modules;
- keep debug dumps in sync with HIR only when representation actually changes.

#### H8 — full regression runtime is long and can hide timeout-only gaps

**Categories:** testing gaps, observability/debugging, configuration/environment
handling, performance risks.

Recent manual runs sometimes timed out in long signal suites without showing a
failure. That is not a product bug by itself, but v0.33 should make regression
evidence easier to collect.

Required exploration:

- run and record focused suites from `v0.25` through `v0.32`;
- run aggregate `make test` when feasible;
- if aggregate timeout happens, record which suite was running and which
  focused suites passed;
- avoid making signal tests noisier or less deterministic while collection/glob
  and regex cleanup is underway.

## Checklist mapping for the requested debt audit

Use this checklist during implementation and completion review:

- **File/module organization:** confirm `bash_deps.c`, `vm_stdlib.c`,
  `bash_helpers.c`, and lowerer collection/regex/glob files have honest owners.
- **Naming consistency:** check helper names, diagnostic labels, Bash helper
  names, regex/glob classifier names, and collection value-kind names.
- **Separation of concerns:** keep semantic gates in lowering/shared metadata,
  VM runtime failures in VM code, and generated-shell artifact/runtime behavior
  in Bash code.
- **Architecture boundaries:** do not let Bash-only implementation details
  redefine language behavior; do not let VM-only convenience bypass Bash parity.
- **Function/component size:** improve large functions only when a local helper
  clarifies a real subtask; do not split by line count.
- **Duplication:** review regex validation, glob validation, helper traversal,
  collection kind checks, and diagnostic wording.
- **Constants and shared values:** look for repeated helper names, versioned
  diagnostic fragments, Bash helper names, regex flags, and capture limits.
- **Dead or stale code:** remove obsolete workarounds, stale comments, or docs
  that describe now-supported features as deferred.
- **Error handling and edge cases:** emphasize runtime filesystem errors,
  invalid dynamic data, no-match cases, empty values, zero-length regex matches,
  and side-effect ordering.
- **Testing gaps:** add negative and parity cases where unsupported behavior is
  easy to misuse.
- **Dependency hygiene:** keep emitted Bash standalone and avoid adding external
  tools beyond baseline shell utilities already required by existing helpers.
- **Configuration/environment handling:** test ambient shell options, locale,
  `IFS`, environment reads/mutations, and Bash version guards.
- **Performance risks:** watch repeated traversal/sorting, regex replacement
  loops, helper scanner repeated walks, and very large generated helper bodies.
- **Security and data safety:** audit quoting, replacement text, glob paths,
  temporary files, command arguments, and generated Bash injection boundaries.
- **Observability and debugging:** diagnostics should name the rejected feature
  and preserve source locations where possible without noisy logs.
- **Documentation and intent:** update source/concept maps and milestone
  completion notes to explain non-obvious ownership decisions.

## Diagnostics and ownership expectations

The diagnostic contract does not change in `v0.33.0`.

- Lexer/parser own malformed syntax and tokenization errors.
- Lowerer owns semantic diagnostics, statically knowable unsupported forms,
  portability gates, name/kind validation, and parity gates.
- VM owns runtime data, OS, process, filesystem, regex execution, glob traversal,
  and environment failures.
- Bash emitter owns accepted-HIR rendering failures and generated artifact
  problems.
- Generated Bash helpers own runtime data/OS failures that can only be known
  after the script starts.

If implementation discovers backend-specific source-language rejection, move it
to the lowerer unless it is truly dynamic data or artifact failure.
