# v0.34.0 Spec — Text Literal and Broken-Pipe DX

## Status

Implementation and focused test pass complete. The dedicated `tests/v0_34/run.sh`
suite is wired into the aggregate test targets after `v0_33`, and the focused
v0.34 suite now covers the scoped literal-brace and broken-pipe contracts.

`v0.34.0` is the first milestone in the post-`v0.33.0` DX-priority wave. It
addresses two concrete annoyances found while writing real `ds` scripts:

1. literal `{` and `}` are awkward inside interpolated strings;
2. common closed-pipe usage such as `ds run script.ds | head` can produce noisy
   broken-pipe diagnostics.

This version should be small, practical, and intentionally scoped. It must not
turn into a raw-string redesign, a new formatting language, or a job-control
milestone.

## Goal

Make text-emitting scripts feel less surprising while preserving the language's
existing VM/Bash parity contract:

```txt
literal braces are easy to write in ordinary strings
existing interpolation continues to work
unsupported interpolation still fails clearly
closed stdout pipes from ordinary output do not produce noisy diagnostics
explicit command failures remain observable when users ask for them
VM behavior and emitted standalone Bash behavior match
```

The companion test plan lives at
`docs/milestones/v0.34.0-test-plan.md`.

## Motivation

The `docs/dx-issues.md` audit identified literal braces and broken-pipe noise as
the two highest-priority DX issues because they affect common shell-style
scripts immediately.

Literal braces appear in many scripting tasks:

- generating JSON snippets;
- writing config files;
- templating small source-code fragments;
- printing shell commands or examples;
- composing diagnostic messages that mention interpolation syntax itself.

Today, strings already use `{expr}` for interpolation, so literal braces require
awkward workarounds such as shelling out to `printf` with numeric escapes. That
is too much ceremony for a scripting language.

Broken pipes are equally common in CLI workflows:

```sh
ds run report.ds | head
bash emitted-report.sh | head
```

When the downstream program closes the pipe early, a script that is merely
writing normal output should not look like it failed in an alarming way. At the
same time, `ds` must not hide real command failures or make explicit error
handling impossible.

## Product principles preserved

This milestone keeps the project constitution intact:

```txt
Every accepted production feature runs in the VM.
Every accepted production feature emits standalone Bash.
Generated Bash must not call ds.
Commands remain shell-native.
Diagnostics remain clear for unsupported forms.
Bash emission shapes the design.
Small boring syntax wins over clever syntax.
```

## Supported syntax and behavior

### 1. Literal braces in strings

Define exactly one small, documented brace-literal spelling for ordinary and
triple-quoted strings. The recommended spelling is doubled braces:

```ds
let open = "{{"
let close = "}}"
let json = "{{ \"name\": {name} }}"
```

Required contract if doubled braces are accepted:

- `{{` emits one literal `{`;
- `}}` emits one literal `}`;
- `{expr}` remains interpolation;
- doubled braces are recognized only by the DS string/interpolation parser, not
  by the shell;
- doubled braces work anywhere current string interpolation works:
  - `let` string literals;
  - interpolated command words;
  - function return values;
  - array/map scalar elements where strings are already supported;
  - triple-quoted strings;
  - strings in imported modules;
- existing valid scripts that use interpolation keep the same behavior;
- existing invalid unmatched-brace diagnostics remain clear.

The implementation may choose a different minimal spelling only if the spec is
updated before implementation to explain why doubled braces would conflict with
existing supported syntax. Do not support multiple brace-escape syntaxes in this
milestone.

### 2. Interpolation compatibility and diagnostics

The current interpolation model remains the baseline:

```ds
let name = "api"
echo "deploying {name}"
```

Required diagnostics:

- unmatched `{` still fails at check/parse/lower time with a source span;
- unmatched `}` still fails clearly unless it is part of the chosen literal
  close-brace spelling;
- malformed expressions inside `{...}` still fail as interpolation expression
  errors;
- ambiguous combinations such as `{{name}` or `{name}}` must be specified and
  tested as either valid deterministic output or rejected with a clear message;
- literal-brace parsing must not silently drop text.

Final resolution for ambiguity with doubled braces:

```txt
"{{name}"   -> rejected: lone `}` after literal `{name`; write `{{name}}`
"{name}}"   -> rejected: lone `}` after interpolation; write `}}` for a literal `}`
"{{name}}"  -> literal "{name}"
"{name}}}"  -> interpolation of name followed by literal "}"
```

This strict rule keeps `}}` as the only literal close-brace spelling and avoids
making a single close brace sometimes literal depending on context, including
after a literal open brace created by `{{`.

### 3. Broken-pipe quieting

Standardize behavior for writes to a closed stdout pipe caused by normal script
output.

The primary user story is:

```sh
ds run many-lines.ds | head -n 1
bash many-lines.sh | head -n 1
```

Required contract:

- normal output writing to closed stdout should not print noisy diagnostics such
  as `command \`echo\` failed with exit 141`;
- VM and emitted Bash should agree on observable stdout/stderr shape for the
  common `head` case;
- cleanup handlers that are already supported by current versions should still
  run according to the existing cleanup contract;
- quieting should be limited to broken-pipe/closed-stdout cases, not arbitrary
  command failures;
- explicit command capture should still expose the command status when users
  intentionally capture a command result;
- pipelines whose left side fails for reasons other than closed stdout must still
  report failure according to the current command-failure rules.

The implementation should classify conventional broken-pipe statuses/signals in
a portable way:

- POSIX signal termination by `SIGPIPE` usually appears as status `141` in shell
  contexts;
- direct write errors may surface as `EPIPE` in VM code;
- generated Bash should not rely on `ds` to classify the condition. Standalone
  Bash cannot portably distinguish a child killed by `SIGPIPE` from a child that
  explicitly exits with status `141`, so its accepted fallback is a narrow
  heuristic: only uncaptured, unredirected status `141` with stdout connected to
  a pipe-like destination may be quieted. Explicit status `141` remains visible
  when stdout is a terminal or regular file.

### 4. Exit status policy for closed stdout

The milestone must define and document the final process status for the common
quiet broken-pipe case.

Preferred policy:

- when the script is terminated only because downstream stdout closed, suppress
  the noisy diagnostic and exit successfully after supported cleanup completes;
- if an explicit command-result capture observes a command that exited due to
  broken pipe, preserve its `code`, `ok`, `failed`, `stdout`, and `stderr`
  fields according to the current command-result contract;
- do not convert unrelated command failures into success. The VM enforces this
  with raw wait-status inspection. Emitted Bash preserves this for ordinary
  statuses and for status `141` when stdout is not pipe-like; exact SIGPIPE vs
  explicit `exit 141` separation under an inherited pipe is a documented Bash
  portability limitation rather than a new language feature.

If implementation finds that emitted Bash cannot portably make the top-level
status successful without unsafe side effects, the spec must be amended with the
narrowest portable alternative before closure.

## Non-goals

Do not implement any of these in `v0.34.0`:

- raw strings as a broad new string-literal family;
- heredocs or here-strings;
- format strings with width/precision/alignment semantics;
- interpolation expression expansion beyond the current supported expression
  surface;
- new command substitution syntax;
- JSON literals or JSON standard-library helpers;
- general exception handling;
- background jobs, `wait`, process groups, or job control;
- arbitrary signal handler context;
- broad pipeline semantics changes unrelated to closed stdout;
- changing the meaning of existing valid interpolation;
- adding a second brace-escape spelling for convenience.

## VM behavior

VM execution must:

- parse and evaluate literal-brace strings identically to emitted Bash;
- preserve the existing runtime value kinds for strings;
- avoid special cases that work only for `echo`; any normal command/output path
  that hits closed stdout should use the same classification rule where
  possible;
- suppress noisy diagnostics for the scoped broken-pipe case;
- keep real command failures visible;
- avoid memory leaks when string interpolation fails or when output is interrupted
  by a broken pipe;
- preserve supported cleanup/defer/trap behavior on early output termination.

## Bash emission behavior

Generated Bash must:

- remain standalone and never call `ds`;
- render literal braces safely in quoted strings and command words;
- pass `bash -n` for all new examples and fixtures;
- avoid depending on ambient shell options such as `pipefail`, `errexit`,
  `failglob`, or `globstar` beyond the generated script's own controlled
  settings;
- classify/suppress scoped broken-pipe diagnostics without hiding unrelated
  command failures;
- avoid duplicate helper definitions;
- include broken-pipe helper logic only when needed if practical, or document why
  a tiny always-present trap/helper is acceptable.

## Diagnostics and debugging behavior

Required diagnostics:

- unmatched literal/interpolation braces point to the offending string span;
- malformed interpolation after adding literal braces keeps the old quality or
  improves it;
- unsupported structured interpolation remains rejected as before;
- broken-pipe quieting must not remove diagnostics for command-not-found,
  permission-denied, non-zero ordinary exits, failed `glob!`, invalid regex, or
  unsupported syntax.

Debug commands should remain useful:

- `ds tokens` should make the chosen string spelling visible enough for debugging;
- `ds ast`, `ds hir`, and `ds bytecode` should not crash on literal-brace
  strings;
- emitted Bash should be readable enough to inspect how literal braces and
  broken-pipe handling are represented.

## Examples

Representative supported examples after this milestone:

```ds
let name = "api"
echo "{{ \"service\": \"{name}\" }}"
```

Expected output:

```json
{ "service": "api" }
```

```ds
fn template(name = "") {
  return "function {name}() {{ return 0; }}"
}

echo template("main")
```

Expected output:

```txt
function main() { return 0; }
```

```ds
for n in 1..1000 {
  echo "line {n}"
}
```

When run as:

```sh
ds run lines.ds | head -n 1
```

It should print the first line without a noisy broken-pipe diagnostic.

## Acceptance criteria

`v0.34.0` is complete when:

- the chosen literal-brace spelling is implemented in VM and emitted Bash;
- existing interpolation behavior remains compatible;
- malformed brace/interpolation cases have clear diagnostics;
- common `script | head` broken-pipe cases are quiet in VM and emitted Bash;
- explicit command-result capture still exposes broken-pipe status where
  applicable;
- unrelated command failures remain noisy/visible;
- docs and examples reflect the final contract;
- `tests/v0_34/run.sh` is wired into the aggregate test targets;
- focused historical string/interpolation/pipeline suites still pass;
- generated Bash for new fixtures is standalone and passes `bash -n`.

## Deferred items

These are intentionally deferred beyond `v0.34.0`:

- raw-string syntax, if still desirable after doubled braces;
- JSON helpers;
- richer template/format APIs;
- structured row/record output;
- background jobs and `wait`;
- broad signal/job-control integration;
- full aggregate sanitizer runs if the environment cannot complete them, provided
  focused v0.34 sanitizer checks are run and the limitation is recorded.
