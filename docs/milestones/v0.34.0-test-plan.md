# v0.34.0 Test Plan — Text Literal and Broken-Pipe DX

## Status

Implemented and wired. `tests/v0_34/run.sh` is executable, included in the
aggregate `Makefile` version list after `v0_33`, and passed the focused v0.34
suite in this sandbox. Focused ASAN/UBSAN `v0.34` runs passed, and the required
focused historical suites through `v0.27` also passed. The expanded v0.33 suite
progressed through helper-position checks and into handler-helper emission but
exceeded the sandbox timeout before completion, so that verification limitation
is recorded without weakening the tests.

## Purpose

`v0.34.0` adds the first post-`v0.33.0` DX-priority improvements:

1. a small way to write literal `{` and `}` in strings that already support
   interpolation;
2. quiet handling for the common broken-pipe case where script output is piped
   into a consumer such as `head`.

The tests must prove that the implementation is useful, portable, and tightly
scoped. They must not imply raw strings, JSON support, new interpolation
expressions, background jobs, or general job control.

## Test conventions

The suite should provide helpers for:

- creating isolated temporary workspaces;
- running `ds check`, `ds tokens`, `ds ast`, `ds hir`, `ds bytecode`, and
  `ds fmt` where relevant;
- running VM execution and emitted Bash execution;
- checking `bash -n` for emitted scripts;
- comparing VM/emitted-Bash stdout, stderr shape, exit status, and side effects;
- asserting emitted Bash does not invoke `ds`;
- running a script through `head` with timeouts so broken-pipe tests do not hang;
- asserting diagnostics contain stable words without depending on entire stderr
  formatting;
- skipping only genuinely host-dependent broken-pipe variants with a printed
  reason.

For parity tests, compare deterministic output byte-for-byte. Use `LC_ALL=C`
when sort/order is relevant.

### 2. Literal braces in ordinary strings

Assuming the chosen spelling is doubled braces, test these VM/Bash parity cases.
If the spec is amended to choose a different spelling, update the fixtures before
implementation closes.

#### 2.1 Single literal open brace

```ds
echo "{{"
```

Expected stdout:

```txt
{
```

#### 2.2 Single literal close brace

```ds
echo "}}"
```

Expected stdout:

```txt
}
```

#### 2.3 Literal pair

```ds
echo "{{}}"
```

Expected stdout:

```txt
{}
```

#### 2.4 Literal braces around interpolation

```ds
let name = "api"
echo "{{ \"service\": \"{name}\" }}"
```

Expected stdout:

```txt
{ "service": "api" }
```

#### 2.5 Literal interpolation syntax as text

```ds
echo "{{name}}"
```

Expected stdout:

```txt
{name}
```

#### 2.6 Interpolation followed by literal close brace

```ds
let name = "api"
echo "{name}}}"
```

Expected stdout:

```txt
api}
```

#### 2.7 Literal open brace followed by plain text

```ds
echo "{{name"
```

Expected stdout:

```txt
{name
```

#### 2.8 Multiple literal braces

Test deterministic output for:

```ds
echo "{{{{"
echo "}}}}"
echo "{{{{}}}}"
```

Expected stdout:

```txt
{{
}}
{{}}
```

#### 2.9 Whitespace and shell metacharacters

```ds
let value = "x y"
echo "{{ path: \"{value}\", chars: \"$*?[]\" }}"
```

VM and emitted Bash must match exactly. Emitted Bash must not allow shell
expansion of the metacharacters.

### 3. Literal braces in triple-quoted strings

#### 3.1 Multi-line template

```ds
let name = "api"
let body = """
server {{
  name = "{name}"
}}
"""
echo body
```

Expected output preserves newlines and emits literal braces.

#### 3.2 Empty interpolation-looking template

```ds
let body = """
{{}}
{{name}}
"""
echo body
```

Expected output:

```txt
{}
{name}
```

#### 3.3 Unterminated interpolation in triple string

A string such as:

```ds
let bad = """
hello {name
"""
```

must fail with a clear diagnostic and no partial execution.

### 4. Literal braces in expression positions

#### 4.1 Function return

```ds
fn render(name = "") {
  return "function {name}() {{ return 0; }}"
}

echo render("main")
```

VM and emitted Bash output:

```txt
function main() { return 0; }
```

#### 4.2 Array and map scalar values

```ds
let items = ["{{", "}}", "{{x}}"]
let map = { open: "{{", close: "}}", expr: "{{name}}" }
echo items[0]
echo items[1]
echo items[2]
echo map["open"]
echo map["close"]
echo map["expr"]
```

Expected output is literal brace text in VM and emitted Bash.

#### 4.3 Import boundary

Create `lib.ds`:

```ds
fn make_block(name = "") {
  return "block {name} {{ ok }}"
}
```

Create `main.ds` importing it and printing the result. VM and emitted Bash must
match and emitted Bash must remain standalone.

#### 4.4 Command words

```ds
let name = "api"
printf "%s\n" "{{{name}}}"
```

Expected command argument should be `{api}`. Verify through a command that prints
arguments one per line, not by relying on shell expansion.

### 5. Brace diagnostics and parser/lowerer behavior

Each case should fail at `ds check` or earlier than execution/emission. Assert
non-zero status, stable diagnostic wording, and absence of side-effect markers.

#### 5.1 Lone open brace

```ds
echo "hello {"
touch should-not-exist
```

#### 5.2 Unclosed interpolation expression

```ds
let name = "api"
echo "hello {name"
touch should-not-exist
```

#### 5.3 Lone close brace if not part of escape

```ds
echo "hello }"
touch should-not-exist
```

If the implementation chooses to allow lone `}` as literal text, amend the spec
and replace this with the exact rejected ambiguity cases.

#### 5.4 Malformed interpolation expression

```ds
echo "value {1 + }"
touch should-not-exist
```

The new brace-literal implementation must not degrade the old expression error.

#### 5.5 Structured interpolation remains rejected

Existing unsupported structured command/string interpolation cases must remain
rejected, for example direct array/map values where current language rules only
allow scalar reductions.

### 6. Formatter and debug output

#### 6.1 Formatter preserves literal-brace spelling

Run `ds fmt` on scripts containing doubled braces. Formatting must not turn
literal braces into interpolation or invalid strings.

#### 6.2 Tokens/AST/HIR/bytecode smoke

For a representative brace fixture, run:

```sh
ds tokens fixture.ds
ds ast fixture.ds
ds hir fixture.ds
ds bytecode fixture.ds
```

All should complete without crashes. Where output is stable enough, assert that
literal-brace content remains visible.

### 7. Emitted Bash quoting and standalone behavior

#### 7.1 `bash -n` and no `ds` dependency

Every emitted brace fixture must:

```sh
ds emit bash fixture.ds -o fixture.sh
bash -n fixture.sh
! grep -q 'ds ' fixture.sh
```

Use a safer grep pattern if comments mention `ds`; the intent is no runtime call
to the `ds` executable.

#### 7.2 Ambient shell hostility

Run emitted Bash brace fixtures under hostile parent settings:

```sh
set -f
IFS=':'
```

and, where possible:

```sh
shopt -s failglob nullglob dotglob globstar
```

The literal-brace output must remain unchanged.

#### 7.3 Helper hygiene

If broken-pipe or brace handling adds Bash helpers, assert:

- helpers are emitted only when needed if practical;
- helper definitions are not duplicated;
- helper names remain private/internal;
- helper bodies do not call `ds`.

### 8. Broken-pipe quieting: common top-level output

Use timeouts for every pipeline case to avoid hangs. Run both VM and emitted Bash
forms.

#### 8.1 Many `echo` statements piped to `head`

Fixture:

```ds
for n in 1..1000 {
  echo "line {n}"
}
```

Commands:

```sh
ds run fixture.ds | head -n 1
bash fixture.sh | head -n 1
```

Expected:

- stdout contains exactly `line 1`;
- stderr does not contain noisy command-failure text such as `failed with exit
  141` or `Broken pipe` from DS diagnostics;
- process exits without hanging.

Record the chosen final status policy and assert it.

#### 8.2 Larger output than pipe buffer

Use enough lines/bytes to make closed-pipe behavior likely even on fast hosts.
Expected behavior matches 8.1.

#### 8.3 Function-produced output

```ds
fn write_lines() {
  for n in 1..1000 {
    echo "line {n}"
  }
}

write_lines()
```

Piped to `head`, this should be quiet in VM and emitted Bash.

#### 8.4 Imported function-produced output

Same as 8.3, but `write_lines` lives in an imported module. Emitted Bash must be
standalone and quiet.

#### 8.5 Cleanup still runs

Fixture:

```ds
defer {
  touch cleaned
}

for n in 1..1000 {
  echo "line {n}"
}
```

When piped into `head`, verify `cleaned` exists after VM and emitted Bash runs if
this matches the existing cleanup contract. If the current cleanup contract cannot
guarantee this for closed stdout, document and assert the exact supported rule.

### 9. Broken-pipe quieting: command failures must stay visible

#### 9.1 Ordinary non-zero command still fails

#### 9.2 Command not found still fails

#### 9.3 Permission denied still fails when host supports it

#### 9.4 `glob!` and invalid regex errors remain visible

Existing runtime errors unrelated to closed stdout must keep diagnostics.

### 10. Broken-pipe command-result capture

#### 10.1 Captured command status remains observable

Create a fixture where a captured command can experience a broken pipe or closes
stdout early in a controlled way. Assert that the resulting command object still

Do not require quiet top-level behavior to erase captured status.

#### 10.2 Captured non-zero command still reports fields

Regression for existing command-result semantics:

```ds

```

Must remain unchanged.

### 11. Pipeline and signal boundary cases

These tests protect scope rather than expand behavior.

#### 11.1 Non-broken-pipe pipeline failure

A pipeline that fails for an ordinary reason must still follow the current
pipeline failure contract.

#### 11.2 SIGPIPE classification only

If a child exits with `141` for a reason that is not a closed stdout write and can
be constructed portably, do not blindly suppress the diagnostic. If not portable,
record as a reviewer checklist item.

Required assertions after the implementation pass:

- VM execution must use raw wait-status information and keep an explicit
  `exit 141` visible when the process was not actually terminated by `SIGPIPE`.
- Emitted Bash must keep explicit `exit 141` visible when stdout is a terminal or
  regular file.
- Emitted Bash may document and retain the unavoidable portable-Bash ambiguity
  where inherited pipe stdout plus status `141` cannot distinguish explicit
  `exit 141` from a real `SIGPIPE` without writing probe bytes or using
  non-standalone helpers.

#### 11.3 No background jobs introduced

Search emitted Bash and docs changes to make sure `&`/`wait` behavior is not
newly documented as supported by this milestone.

## Edge-case matrix

Literal brace cases to include:

| Case | Expected |
|---|---|
| `"{{"` | `{` |
| `"}}"` | `}` |
| `"{{}}"` | `{}` |
| `"{{{{"` | `{{` |
| `"}}}}"` | `}}` |
| `"{{name}"` | rejected lone `}`; write `{{name}}` |
| `"{{name}}"` | `{name}` |
| `"{name}}}"` | interpolation then `}` |
| `"{{{name}}}"` | `{` + interpolation + `}` |
| triple-quoted doubled braces | same semantics as ordinary strings |
| imported function returning braces | VM/Bash parity |
| array/map elements with braces | VM/Bash parity |
| command arguments with braces | no shell expansion |
| malformed single `{` | clear diagnostic |
| malformed expression inside `{}` | clear diagnostic |

Broken-pipe cases to include:

| Case | Expected |
|---|---|
| top-level loop piped to `head` | quiet, no hang |
| emitted Bash piped to `head` | quiet, no `ds` dependency |
| large output piped to `head` | quiet, no hang |
| function output piped to `head` | quiet |
| imported function output piped to `head` | quiet |
| cleanup after closed stdout | follows documented cleanup rule |
| ordinary `false` command | still visible failure |
| command not found | still visible failure |
| invalid regex/glob | still visible failure |
| captured command result | status remains observable |
