# v0.36.0 Spec — Function Parameter Kind Inference

## Status

Implementation and dedicated `v0.36.0` regression coverage are complete. The
focused suite lives in `tests/v0_36/run.sh` and is wired into `Makefile` as
`make test-v0-36`. It is a DX-focused language pass that removes the need to
write dummy defaults only to make helper functions type-check.

The implementation work must preserve the project-wide VM/Bash parity rule:
accepted source programs lower to the shared HIR contract and have defined,
matching behavior in direct VM execution and standalone emitted Bash.

## Goal

Allow ordinary required scalar function parameters to be used in places that
already require a known scalar kind, without forcing callers or authors to spell
fake default values.

The motivating example should become valid:

```ds
fn clean_line(line) {
  let t = line.trim()
  return t
}

let cleaned = clean_line("  api  ")
echo "{cleaned}"
```

Before this milestone, authors often had to write:

```ds
fn clean_line(line = "") {
  let t = line.trim()
  return t
}
```

That spelling works because the default gives `line` a static string kind, but
the default is not semantically meaningful. `v0.36.0` should infer the required
parameter kind from compatible local usage instead.

## Motivation

`docs/dx-issues.md` identifies dummy defaults for string-method inference as the
third prioritized DX issue after literal-brace/broken-pipe cleanup and core
string parsing helpers. The issue is most visible when writing small reusable
text helpers:

```ds
fn before_paren(sig) {
  return sig.split("(")[0].trim()
}
```

The author intent is clear: `sig` is string-like because it is the receiver of
string helpers. Requiring `sig = ""` is surprising, makes APIs look optional
when they are not, and can hide accidental omitted arguments behind a dummy
default. The milestone should make required-parameter helpers feel natural while
keeping the language intentionally small.

## Product principles preserved

This milestone preserves these project principles:

- **Shell-native, standalone Bash parity.** Inferred parameter kinds must lower
  to metadata the VM and emitted Bash can both honor. Generated Bash must remain
  standalone and must not call `ds` at runtime.
- **Simple, boring semantics.** The accepted mechanism is scalar usage
  inference, not a broad static type system.
- **One language, two backends.** The parser, semantic/lowering checks, HIR, VM,
  and Bash emitter must agree on accepted and rejected programs.
- **Clear diagnostics over surprising coercion.** Conflicting uses or unprovable
  call arguments are rejected rather than silently converted.
- **Incremental pre-1.0 design.** Typed parameters remain planned syntax, but
  this milestone should solve the immediate DX problem without committing to a
  broad type-system surface.

## Chosen mechanism

`v0.36.0` uses **local usage-based scalar kind inference for required untyped
function parameters**.

It does **not** add public typed-parameter syntax in this milestone.

Examples:

```ds
fn normalize(line) {
  return line.trim().lower()
}

fn first_piece(line, sep) {
  return line.split(sep)[0]
}

fn within(s, start, end) {
  return s.slice(start, end)
}

fn enabled(flag) {
  if flag {
    return "yes"
  }
  return "no"
}
```

The inferred kinds are:

```txt
normalize(line: string)
first_piece(line: string, sep: string)
within(s: string, start: int, end: int)
enabled(flag: bool)
```

The syntax remains exactly the existing untyped required parameter syntax. The
inferred signature is an internal lowering/HIR/backend contract, not a new user
syntax.

## Supported behavior

### 1. Parameter-kind states

Each function parameter has one of these internal kind states after lowering:

- `string`;
- `int`;
- `bool`;
- `unknown`.

Defaulted parameters keep the existing behavior: their literal default gives
them a static scalar kind and call-site validation uses that kind for both
omitted and explicit arguments.

Required parameters start as `unknown`, then local body usage may constrain them
to `string`, `int`, or `bool`. Parameters that are never used in a kind-sensitive
position remain `unknown` and keep existing behavior.

### 2. Usage constraints that infer `string`

A required parameter is inferred as `string` when it is used as:

- the receiver of a supported string method, including the `v0.19.0` and
  `v0.35.0` helpers;
- a string argument to a supported string method or stdlib helper that already
  requires a string;
- a string value passed to `contains`, `starts_with`, `ends_with`, `replace`,
  `split`, `index_of`, `last_index_of`, `count`, `char_at` receiver, `slice`
  receiver, or equivalent accepted string-helper positions;
- a formatted interpolation value using a string-specific transform such as
  `upper`, `lower`, `trim`, or string width/alignment if those formats already
  require a known string kind;
- a comparison or `case` selector/arm position where the existing parity
  contract requires the value to remain string-kind rather than unknown-kind and
  all observed constraints agree that it is string.

Plain interpolation such as `"{name}"` does not, by itself, force `name` to be a
string. Interpolation may render supported scalar values. Only string-specific
formatting or helper usage constrains the kind.

### 3. Usage constraints that infer `int`

A required parameter is inferred as `int` when it is used as:

- an operand to supported integer arithmetic;
- an integer comparison operand where the other side is statically int or the
  operation already requires int parity;
- an index expression for arrays/maps where the accepted source requires an int;
- the index argument to `char_at`;
- a start or end argument to `slice`;
- a numeric width/precision/padding interpolation input only if the existing
  formatting contract already requires a known integer kind;
- an argument to any current stdlib/helper position that already requires an
  integer.

This milestone does not add string-to-int parsing or implicit numeric coercion.

### 4. Usage constraints that infer `bool`

A required parameter is inferred as `bool` when it is used as:

- a direct condition where existing kind-aware truthiness requires a known bool;
- an operand to `&&`, `||`, or `!` where those operators require boolean parity;
- a `case` selector/arm position whose kind-aware matching requires bool;
- an argument to a helper position that already requires a bool.

The implementation must preserve existing ds truthiness. It must not treat any
non-empty shell string as `true` in emitted Bash when the ds value is meant to be
boolean.

### 5. Neutral uses

These uses do not infer a more precise kind on their own:

- passing a parameter to a plain command word;
- plain interpolation without a scalar-specific format requirement;
- assigning the parameter to a local without another kind-sensitive use;
- returning the parameter directly when no other usage constrains it;
- comparing two unknown parameters to each other with an equality operator, if
  neither side has a known/inferred kind;
- passing the parameter to another function parameter whose required kind is
  still unknown.

Neutral uses may preserve or propagate a kind once another constraint has
already inferred one.

### 6. Conflict rules

If a required parameter is used in incompatible scalar-kind positions, lowering
must reject the function before VM execution or Bash emission.

Examples rejected by `v0.36.0`:

```ds
fn bad(value) {
  let cleaned = value.trim()
  let doubled = value * 2
}
```

```ds
fn also_bad(flag) {
  if flag {
    echo "enabled"
  }
  let upper = flag.upper()
  echo "{upper}"
}
```

Diagnostics should name the parameter, the incompatible kinds, and the relevant
uses where practical. A diagnostic that points only to the later conflicting use
is acceptable if it clearly states the earlier inferred kind.

### 7. Call-site validation

When a function parameter has an inferred scalar kind, every call to that
function must pass an argument whose kind is statically known and compatible.

Accepted argument examples:

```ds
clean_line("  api  ")
clean_line(result.stdout)
clean_line(lines("input.txt")[0])
clean_line(other_string_helper())

within("abcdef", 1, 4)
within(text, start_index, end_index)

enabled(true)
enabled(config_ok())
```

Rejected argument examples:

```ds
clean_line(42)
within("abcdef", "1", 4)
enabled("true")
```

If the argument is an unknown required parameter from the caller, the callee's
requirement may infer the caller parameter kind when it does not conflict:

```ds
fn clean_line(line) {
  return line.trim()
}

fn clean_twice(line) {
  return clean_line(clean_line(line))
}
```

Here, `clean_twice(line)` is inferred as `line: string` because the nested call
requires a string. This propagation must remain scalar-only and acyclic. If the
implementation cannot prove a call argument's kind without circular inference,
it should reject the program with a clear diagnostic rather than guessing.

### 8. Import and forward-call behavior

Inferred parameter-kind metadata must be available across the existing composed
import path.

An imported helper like this:

```ds
fn clean_line(line) {
  return line.trim()
}
```

must validate callers in the importing file exactly as a same-file declaration
would.

Calls before declaration remain supported only to the extent already supported
by the function collection/lowering pipeline. `v0.36.0` must not reintroduce
source-order drift between VM execution and emitted Bash.

### 9. Defaulted parameters

Defaulted parameters keep their existing contract:

```ds
fn label(name = "api") {
  return name.upper()
}
```

Rules:

- default literals still define parameter kind;
- omitted defaulted arguments still bind the literal default;
- explicit arguments must still match the default kind;
- a defaulted parameter used in a conflicting kind-sensitive position is
  rejected just like an inferred required parameter;
- required parameters before defaulted parameters may now also be inferred.

This milestone must not make defaulted parameters optional in any new way or
change arity behavior.

### 10. Return-kind interaction

Parameter inference should feed existing return-kind inference.

Examples:

```ds
fn clean(line) {
  return line.trim()
}

fn id_string(line) {
  let t = line.trim()
  return line
}
```

Both functions return `string`. `line` in `id_string` is inferred as string by
the neutral local plus kind-sensitive `trim` usage.

If a function returns an unconstrained unknown required parameter directly and no
other use constrains it, existing conservative behavior should remain: the
function either cannot be used where a scalar return kind is required, or it is
rejected with the current targeted diagnostic. Do not add generic polymorphic
identity functions in this milestone.

### 11. HIR/debug visibility

Debug output should make inferred parameter kinds visible enough for reviewers
and tests to confirm behavior.

At minimum, `ds hir` or another existing debug surface should distinguish:

- defaulted string/int/bool parameter kinds;
- inferred required string/int/bool parameter kinds;
- unknown required parameters.

The exact textual format is implementation-defined, but it must be stable enough
for focused regression tests.

### 12. Bash emission behavior

Generated Bash must bind inferred required parameters with the same private
scalar-kind metadata used for defaulted parameters and returned scalar values.

Requirements:

- generated Bash validates explicit arguments to inferred parameters before the
  function body observes them;
- type tags for inferred string/int/bool parameters are set consistently whether
  the argument is a literal, variable, field access, indexed collection element,
  or function return in a supported call position;
- rejected wrong-kind calls fail before partial body side effects;
- emitted Bash does not depend on `ds`, C runtime helpers, non-standalone helper
  binaries, or non-portable shell plugins;
- helper functions remain in the reserved `__ds_` namespace and are included
  only when needed.

If the implementation already validates compatible scalar kinds before Bash
artifact writing, runtime Bash checks may be smaller, but emitted Bash must still
preserve metadata and fail predictably for dynamic supported values.

### 13. VM behavior

The VM must execute inferred-parameter functions without coercing values.

Requirements:

- arguments passed to inferred parameters carry the expected `DsValue` scalar
  kind at function entry;
- wrong-kind calls fail before body side effects;
- the VM uses existing string/int/bool runtime values and helper implementations;
- inferred kinds compose through recursion diagnostics, imports, forward calls,
  function returns, loops, `case`, and test blocks consistently with lowerer
  acceptance.

### 14. Diagnostics and checker behavior

Diagnostics must be clear and phase-owned:

- parser diagnostics remain responsible for malformed function syntax;
- lowerer diagnostics reject unsupported typed parameters if typed syntax remains
  unimplemented;
- lowerer diagnostics reject incompatible parameter usages and unprovable
  call-site kinds before execution or emission;
- runtime diagnostics handle only value-dependent failures that cannot be known
  statically, not the static parameter-kind contract itself;
- `ds check --warnings-as-errors` should still treat warnings separately from
  kind errors.

Diagnostic messages should prefer wording such as:

```txt
parameter `line` inferred as string from `.trim()` but later used as int
function `clean_line` expects argument 1 `line` to be string, got int
cannot infer required parameter `value`: used as both string and bool
cannot prove argument kind for inferred string parameter `line`
```

Exact wording may differ, but tests should lock the meaningful parts.

## Non-goals

Do not implement any of these in `v0.36.0`:

- public typed required-parameter syntax, unless implementation proves that the
  usage-inference mechanism is impossible and the spec is deliberately amended;
- return annotations;
- generic functions, overloads, union types, type aliases, traits, or interface
  constraints;
- collection-valued parameters;
- row/record parameters or destructuring parameters;
- variadic parameters, named arguments, or keyword-only arguments;
- optional required parameters or changed default-argument arity rules;
- runtime auto-coercion between string, int, and bool;
- string-to-int or bool-to-string parsing helpers;
- polymorphic identity functions;
- recursive function-kind inference beyond a conservative fixed-point that can
  be proven deterministic;
- broader command-word typed interpolation;
- any new public stdlib/string helper beyond what `v0.35.0` already scoped;
- native or alternate shell backends.

If implementation uncovers a useful adjacent feature, record it as deferred
instead of silently widening the milestone.

## Examples

### Cleaning text without dummy defaults

```ds
fn clean_line(line) {
  return line.trim().lower()
}

let cleaned = clean_line("  API  ")
echo "{cleaned}"
```

Expected output:

```txt
api
```

### String delimiter helper

```ds
fn before(marker, line) {
  let idx = line.index_of(marker)
  if idx < 0 {
    return line
  }
  return line.slice(0, idx)
}

let name = before("=", "name=value")
echo "{name}"
```

Inferred signature:

```txt
before(marker: string, line: string) -> string
```

### Integer range helper

```ds
fn take(line, start, end) {
  return line.slice(start, end)
}

let part = take("abcdef", 1, 4)
echo "{part}"
```

Inferred signature:

```txt
take(line: string, start: int, end: int) -> string
```

### Boolean helper

```ds
fn maybe_print(enabled, text) {
  if enabled {
    let cleaned = text.trim()
    echo "{cleaned}"
  }
}

maybe_print(true, "  ok  ")
```

Inferred signature:

```txt
maybe_print(enabled: bool, text: string)
```

### Conflict diagnostic

```ds
fn broken(value) {
  let cleaned = value.trim()
  echo "{cleaned}"
  let doubled = value * 2
}
```

This must be rejected because `value` cannot be both `string` and `int`.

### Imported helper

```ds
# lib.ds
fn clean(line) {
  return line.trim()
}

# main.ds
import "./lib.ds"

let cleaned = clean("  ok  ")
echo "{cleaned}"
```

The imported call must infer and validate the same `string` parameter contract
as a same-file call.

## Acceptance criteria

`v0.36.0` is complete only when all of the following are true:

- Required untyped parameters can be inferred as `string`, `int`, or `bool` from
  accepted local usage constraints.
- The motivating `fn clean_line(line) { return line.trim() }` style no longer
  needs a dummy default.
- Inference composes with the `v0.35.0` string helpers and direct post-method
  indexing forms.
- Inferred parameter kinds are validated at all supported call sites, including
  same-file calls, calls before declaration, imported functions, nested calls,
  function-return arguments, command-result fields, script args/options where
  already kinded, collection element reads with known element kinds, and test
  blocks.
- Conflicting parameter usages fail before partial execution or Bash emission.
- Wrong-kind call arguments fail before partial body side effects.
- Defaulted parameter behavior is preserved.
- Unknown required parameters remain accepted in neutral statement-style helper
  functions where existing behavior allows them, and remain rejected where a
  known kind is required.
- VM execution and emitted Bash have matching stdout, stderr shape, exit status,
  and side effects for accepted and rejected focused cases.
- Generated Bash remains standalone and does not call `ds`.
- Debug output exposes inferred/defaulted/unknown parameter-kind distinctions
  well enough for tests.
- `docs/language.ds`, `docs/status.md`, `docs/runtime.md`, `docs/diagnostics.md`,
  `docs/parity-contracts.md`, and `docs/dx-issues.md` are updated if the
  implementation changes their current claims.
- Dedicated `v0.36.0` tests cover the scoped inference, diagnostics, VM/Bash
  parity, emitted-Bash hygiene, docs, and deferred-syntax guards.

## Deferred items

The following remain deliberately deferred after this milestone:

- public typed required-parameter syntax such as `fn f(name: string)`;
- typed return annotations;
- generic/polymorphic functions;
- recursive inference that requires broad fixed-point type solving;
- collection-valued parameters and destructuring parameters;
- row/record parameters and row-field inference;
- variadic and named arguments;
- implicit scalar coercions;
- string parsing/tokenizer helpers beyond `v0.35.0`;
- broader command-word interpolation of structured/function values;
- richer static type-checking outside the scalar function-parameter boundary.

### Implementation completion notes

1. `string` is inferred from string-method receivers and arguments, string
   stdlib/helper arguments, `matches` operands, and method-call interpolation;
   `int` is inferred from arithmetic, indexes, ranges, unary minus, and
   `char_at`/`slice` index arguments; `bool` is inferred from `if`/`while`/
   `assert` conditions, logical operators, and known bool contexts.
2. Required parameters still remain `unknown` when they are used only in neutral
   positions such as direct echo/command words, direct return forwarding, plain
   interpolation without a kind-sensitive operation, or other unknown-typed
   helper boundaries. That is acceptable because the language has not added a
   broad type system or public annotations.
3. Wrong-kind arguments are rejected by the lowerer before body execution or
   Bash emission for statically known scalar arguments. VM execution and emitted
   Bash also carry defensive inferred/defaulted parameter-kind checks when a
   function is entered.
4. Same-file, calls-before-declaration, imported functions, return-kind
   predeclaration, and nested user-function calls use the same inferred
   signature metadata through the composed lowering pipeline.
5. The implementation does not add public typed-parameter syntax, typed return
   annotations, or implicit scalar coercion.
6. Generated Bash stays standalone. It uses private type sidecars and existing
   helper-dependency scanning rather than calling `ds` at runtime.
7. Updated docs: `README.md`, `CHANGELOG.md`, `docs/language.ds`,
   `docs/status.md`, `docs/runtime.md`, `docs/diagnostics.md`,
   `docs/parity-contracts.md`, `docs/dx-issues.md`, and this spec.
8. No dedicated regression tests were added in this implementation pass per the
   request. Focused smokes covered the original dummy-default DX issue, nested
   propagation, wrong-kind call rejection, command-word interpolation inference,
   and VM/Bash parity; the dedicated test suite remains the follow-up work.
