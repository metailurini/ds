# v0.36.0 Test Plan — Function Parameter Kind Inference

## Status

Planned follow-up. The production implementation is complete, but this suite
has not been added yet because the implementation request explicitly excluded
new tests. This test plan must still be implemented before `v0.36.0` is fully
closed. It is derived from `docs/milestones/v0.36.0-spec.md` and should change
only when the spec is deliberately amended.

## Purpose

The `v0.36.0` suite must prove that required scalar function parameters can be
inferred from local usage, validated at call sites, and executed with VM/Bash
parity without adding a broad type system.

The suite should show that:

1. Required parameters infer `string`, `int`, and `bool` from accepted
   kind-sensitive uses.
2. The original dummy-default DX issue is fixed for ordinary string helpers.
3. Inference composes with `v0.35.0` string parsing helpers and direct indexing
   after method calls.
4. Same-file, forward, imported, nested, returned, command-result, collection,
   script-argument, and test-block call sites validate inferred kinds.
5. Conflicting usages and wrong-kind arguments are rejected before partial body
   side effects.
6. Defaulted-parameter behavior and existing unknown-parameter behavior remain
   unchanged outside the scoped inference contract.
7. Generated Bash remains standalone, helper-hygienic, and kind-aware.

Do not add tests that imply public typed required-parameter syntax, typed return
annotations, generics, overloads, union types, collection-valued parameters,
row/record parameters, variadic/named arguments, implicit scalar coercion, or
polymorphic identity functions.

## Test suite location

Add the dedicated suite at:

```txt
tests/v0_36/run.sh
```

Wire it into aggregate test targets in `Makefile` after `v0_35`.

Favor small fixtures with exact expectations. Reuse the shared helpers from
`tests/lib/testlib.sh`, especially any helper that:

- writes fixtures in isolated workspaces;
- runs VM execution and emitted Bash execution from separate directories;
- validates generated Bash with `bash -n`;
- compares stdout, stderr shape, status, and deterministic side effects;
- checks generated Bash contents for helper inclusion/exclusion and absence of
  `ds` runtime calls.

If a helper does not yet exist for a needed assertion, add the smallest focused
test helper and keep it generic enough for later suites.

## Test conventions

For every VM/Bash parity fixture, compare deterministic behavior:

```txt
stdout
stderr shape where deterministic
exit status
filesystem side effects where deterministic
```

For static rejection cases, assert that all relevant commands reject before
execution or artifact creation:

```sh
ds check fixture.ds
ds hir fixture.ds
ds bytecode fixture.ds
ds run fixture.ds
ds emit bash fixture.ds -o fixture.sh
```

Use exact diagnostic substrings for the meaningful contract:

- parameter name;
- expected kind;
- actual or conflicting kind;
- callee name and argument index when applicable;
- no broad internal stack traces.

Avoid overfitting to incidental punctuation unless existing suites already lock
that style.

For fail-fast tests, place a deterministic side effect after the expression or
call that must fail:

```ds
fn clean(line) {
  echo "entered" > "body-marker.txt"
  return line.trim()
}

clean(42)
echo "after" > "after-marker.txt"
```

The expected result for a wrong-kind call is that neither marker exists if
validation is supposed to happen before entering the body. If the implementation
legitimately validates at a different earlier point, the test may assert the
stronger no-side-effect behavior.

For generated Bash hygiene, inspect the emitted script for:

- no invocation of `ds`;
- no duplicate helper definitions;
- reserved `__ds_` helper namespace only;
- inferred parameter type metadata present when functions need it;
- no helper inclusion for neutral functions that do not require inference.

### 3. String parameter inference

#### 3.1 Receiver string method infers string

Fixture:

```ds
fn clean(line) {
  return line.trim()
}

echo clean("  api  ")
```

Expected VM/Bash stdout:

```txt
api
```

Also assert that the same function without a dummy default passes `ds check`,
`ds hir`, `ds bytecode`, `ds run`, and `ds emit bash`.

#### 3.2 Chained string methods infer string

Fixture:

```ds
fn normalize(line) {
  return line.trim().lower().replace("-", "_")
}

echo normalize("  API-WEB  ")
```

Expected stdout:

```txt
api_web
```

#### 3.3 String method arguments infer string

Fixture:

```ds
fn has_marker(line, marker) {
  return line.contains(marker)
}

if has_marker("abc:def", ":") {
  echo "yes"
}
```

Expected stdout:

```txt
yes
```

`line` and `marker` must both infer string.

#### 3.4 `v0.35.0` string helpers infer string

Fixture:

```ds
fn before(marker, line) {
  let idx = line.index_of(marker)
  if idx < 0 {
    return line
  }
  return line.slice(0, idx)
}

echo before("=", "name=value")
```

Expected stdout:

```txt
name
```

Assert `marker` and `line` are string-inferred and `idx` remains int.

#### 3.5 Direct post-method indexing composes with inference

Fixture:

```ds
fn first_clean(line, sep) {
  return line.split(sep)[0].trim()
}

echo first_clean("  api  : worker", ":")
```

Expected stdout:

```txt
api
```

This proves `v0.35.0` direct indexing keeps string element kind and `v0.36.0`
infers both required parameters correctly.

#### 3.6 String-specific interpolation format infers string

Fixture:

```ds
fn shout(label) {
  echo "{label:upper}"
}

shout("api")
```

Expected stdout:

```txt
API
```

Plain `{label}` remains neutral and should not be used for this test.
