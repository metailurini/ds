# v0.37.0 Spec — Lightweight Rows and In-Memory Data Processing

## Status

Implemented as a scoped code pass after `v0.36.0`. It is the fourth pass in the
current script-writing DX wave: after text literal cleanup, core string parsing
helpers, and function parameter kind inference, `v0.37.0` gives scripts a small
in-memory row model so data-processing scripts no longer need to encode records
as delimiter-separated strings and temporary files.

The implementation work must preserve the project-wide VM/Bash parity rule:
accepted source programs lower to the shared HIR contract and have defined,
matching behavior in direct VM execution and standalone emitted Bash.

## Goal

Add the smallest coherent structured-row story for shell-native scripts:

```ds
let rows = []

for file in glob("src/**/*.c") {
  let loc = 1
  rows.push({ file: file, line: 1, name: path.basename(file), loc: loc })
}

let sorted = rows.sort_by("loc", "desc")

for row in sorted {
  echo "{row.loc}\t{row.file}:{row.line}\t{row.name}"
}
```

The supported model is **a named array/list of flat row values**. A row value is
a flat map-like object with string field names and scalar string/int/bool field
values. A row array is an ordered list whose rows share one schema: the same
field names with the same scalar kinds.

The milestone is intentionally not a general nested-collection or dataframe
system. It should make common analyzer/reporting scripts pleasant while keeping
the implementation small enough to emit to standalone Bash.

## Motivation

`docs/dx-issues.md` records that the pure `ds` C-function analyzer had to write
intermediate rows to a temporary file and sort colon-separated text externally:

```text
.ds-c-functions.out
```

The natural data shape was closer to:

```ds
{ file: file, line: start_line, name: func_name, loc: loc }
```

Without row arrays and sort-by-field support, scripts must choose between
fragile delimiter encoding and dropping back into shell utilities too early.
Shell-native commands should remain available, but the language should be able
to buffer and sort simple records directly when that makes the script clearer.

## Product principles preserved

This milestone preserves these project principles:

- **Shell-native, standalone Bash parity.** Row arrays must run in the VM and
  emit to standalone Bash without calling `ds` or the C runtime at Bash runtime.
- **Simple, boring semantics.** Rows are flat scalar records with deterministic
  copy and sort behavior, not classes, schemas, references, or a dataframe API.
- **One language, two backends.** Parser, lowering, HIR, VM, Bash emission, and
  diagnostics must agree on accepted and rejected row programs.
- **Clear diagnostics over implicit guessing.** Schema mismatches, nested row
  values, unsupported mutation, and unsupported command/interpolation positions
  must fail clearly instead of partially working in one backend.
- **Incremental pre-1.0 design.** The milestone deliberately solves the row-list
  DX problem without admitting arbitrary nested arrays/maps or collection-valued
  function parameters.

## Chosen model

`v0.37.0` uses **lightweight row arrays**:

- a **row** is a flat object/map value with string field names and scalar
  string/int/bool values;
- a **row schema** is the set of field names and their scalar kinds;
- a **row array** is an ordered array whose elements are rows with the same row
  schema;
- row arrays support ordinary iteration, index reads, field reads from row
  values, `push` with schema validation, copy-by-value assignment, and
  `sort_by` returning a sorted copy.

The existing map/object literal syntax is reused for row literals. The existing
array syntax is reused for row-array literals and empty row arrays. No new row
literal syntax, typed schema syntax, class syntax, or dataframe syntax is added.

## Supported syntax

### 1. Row literals

Any map/object literal whose keys are string-like field names and whose values
are supported scalars can be used as a row value:

```ds
let row = { file: "src/main.c", line: 42, name: "parse", loc: 17 }

echo row.file
echo row["name"]
```

Field names follow the current map/object key rules with one additional row
schema requirement: field names must be non-empty strings and must be known at
lowering time for row-array schemas. Identifier-style keys are preferred for
row-like data, but string literal keys are allowed when they are non-empty and
portable:

```ds
let row = { "file": "src/main.c", "line": 42 }
```

Rows may contain only scalar field values:

```ds
let ok = { file: "a.c", line: 1, public: true }
```

Rejected row values include nested arrays, nested maps/rows, command-result
objects, row arrays, and values whose scalar kind cannot be represented in both
backends:

```ds
let bad_nested = { file: "a.c", spans: [1, 2] }
let bad_meta = { file: "a.c", meta: { generated: true } }
let bad_result = { file: "a.c", probe: run printf "ok" }
```

The existing flat map/object behavior remains valid. A row is not a new public
type annotation; it is the subset of flat maps that participates in row-array
schema tracking.

### 2. Row field access

Row fields can be read with existing field or index syntax:

```ds
let file = row.file
let name = row["name"]
```

For row values with a known schema, missing fields are lowering errors:

```ds
let row = { file: "a.c", line: 1 }
echo row.loc
```

For row values loaded through runtime-only map paths where the schema cannot be
fully proven, the existing map missing-key runtime diagnostic remains valid.
The implementation should prefer static diagnostics whenever the row schema is
known.

Field values preserve their scalar kinds. `row.line` may be used in integer
arithmetic, `row.file` may be used with string helpers, and `row.public` may be
used in boolean conditions when the schema records those kinds.

### 3. Row-array literals

An array literal whose elements are rows with the same schema becomes a row
array:

```ds
let rows = [
  { file: "a.c", line: 1, name: "alpha", loc: 10 },
  { file: "b.c", line: 8, name: "beta", loc: 3 }
]
```

Rows in the same row array must have exactly the same field names and the same
scalar kind for each field. Field order in source does not change the schema:

```ds
let rows = [
  { file: "a.c", line: 1 },
  { line: 2, file: "b.c" }
]
```

Rejected row-array literals include:

```ds
let missing = [
  { file: "a.c", line: 1 },
  { file: "b.c" }
]

let wrong_kind = [
  { file: "a.c", loc: 1 },
  { file: "b.c", loc: "unknown" }
]

let nested = [
  { file: "a.c", meta: { generated: false } }
]
```

### 4. Empty row arrays and first-push inference

An empty array literal may become a row array when the first successful `push`
uses a row value:

```ds
let rows = []
rows.push({ file: "a.c", line: 1, name: "alpha", loc: 10 })
rows.push({ file: "b.c", line: 8, name: "beta", loc: 3 })
```

After the first row push, the empty array is specialized to that row schema.
Later pushes must match the same field names and scalar kinds.

This rule must not break existing scalar-array inference. An empty array first
pushed with a scalar remains a scalar array, and a scalar array cannot later
receive a row:

```ds
let names = []
names.push("api")
names.push({ name: "web" }) # rejected
```

Likewise, a row array cannot later receive a scalar:

```ds
let rows = []
rows.push({ name: "api" })
rows.push("web") # rejected
```

Sorting an empty row array is accepted when the receiver is already known as a
row array. Sorting an untyped empty array is rejected because there is no row
schema to validate the requested field against.

### 5. Row-array iteration

`for row in rows { ... }` works for row arrays. The loop variable has the row
schema of the iterable source:

```ds
for row in rows {
  if row.loc > 20 {
    echo "large {row.name} at {row.file}:{row.line}"
  }
}
```

The loop variable is a copy of the row value for the current iteration. Mutating
the loop variable or any field of it does not mutate the source row array. In
this milestone, field assignment on row values is not added, so attempted
field-style row mutation is rejected before backend execution.

Array-loop behavior remains ordered by insertion/index order. Row-array loops do
not sort implicitly.

### 6. Row-array indexing

Indexing a row array returns a row value with the array schema:

```ds
let first = rows[0]
echo first.file
echo rows[0].name
```

The existing array index rules apply:

- indexes are integers;
- negative indexes are errors;
- out-of-range indexes are runtime data failures in both backends;
- index expressions are evaluated once;
- row values produced by indexing are not command-word values by themselves.

Direct field access after indexing is in scope because it is the natural row
use case:

```ds
echo "top={rows[0].name}"
```

If the parser currently cannot represent `rows[0].name`, this milestone must add
the minimal postfix composition needed for index-then-field access without
opening broader arbitrary assignment/mutation syntax.

### 7. Row-array `push`

`array.push(row)` is extended to row arrays:

```ds
rows.push({ file: file, line: start_line, name: func_name, loc: loc })
```

The receiver must be a named array local, following existing mutation rules.
Pushing into temporary arrays, function-call results, indexed elements, command
results, or row fields remains rejected:

```ds
make_rows().push({ name: "api" }) # rejected
rows[0].children.push({ name: "x" }) # rejected
```

The pushed row value is copied into the row array. Later changes to a source map
or local do not mutate the stored row. Generated Bash must preserve empty
strings, whitespace, tabs, newlines, shell metacharacters, braces, and backslash
characters in field values.

### 8. `sort_by` helper

Row arrays support a deterministic sort-by-field helper:

```ds
let by_name = rows.sort_by("name")
let largest = rows.sort_by("loc", "desc")
let smallest = rows.sort_by("loc", "asc")
```

Rules:

- the receiver must be a row array;
- the field argument must be a non-empty string literal naming a schema field;
- the optional direction argument must be the string literal `"asc"` or
  `"desc"`;
- omitted direction means ascending;
- `sort_by` returns a new row array and does not mutate the receiver;
- sorting is stable: rows with equal sort keys remain in their original order;
- string fields sort by bytewise/ASCII order under `LC_ALL=C` semantics;
- integer fields sort numerically;
- boolean fields sort `false` before `true` in ascending order and `true`
  before `false` in descending order;
- empty row arrays sort to empty row arrays;
- unsupported directions, unknown fields, non-row receivers, and non-literal
  field/direction arguments are rejected by lowering.

This milestone deliberately does not add custom comparator functions, multi-key
sorts, locale-aware sorting, case-insensitive sorting, null ordering, or
descending operator syntax. Those can be future helpers if scripts need them.

### 9. Transforming rows

No higher-order `map`, `filter`, or `reduce` API is added. Transformation uses
ordinary loops, conditions, scalar expressions, and `push`:

```ds
let large = []

for row in rows {
  if row.loc >= 25 {
    large.push({
      file: row.file,
      line: row.line,
      name: row.name.upper(),
      loc: row.loc
    })
  }
}
```

The destination row array schema is inferred from the first row pushed. Later
pushes validate against that schema. This keeps the row story readable without
introducing higher-order functions, closures, or collection-valued parameters.

### 10. Function returns

Value-returning functions may return:

- a single row value, following the existing flat map/object return path; and
- a row array with a known schema, extending the existing structured-return ABI
  in the narrow row-array case.

Examples:

```ds
fn make_row(file = "a.c") {
  return { file: file, line: 1, name: "main", loc: 10 }
}

fn make_rows() {
  let rows = []
  rows.push({ file: "a.c", line: 1, name: "main", loc: 10 })
  return rows
}
```

All return paths must agree on row schema and field kinds when returning row
arrays:

```ds
fn bad(flag = true) {
  if flag {
    return [{ file: "a.c", loc: 1 }]
  }
  return [{ file: "b.c", loc: "unknown" }] # rejected
}
```

Collection-valued parameters remain out of scope. Functions may not accept row
values or row arrays as parameters in this milestone. Row-array values returned
from functions may be assigned, iterated, indexed, and sorted in the caller.

### 11. Imports

Imported functions may return row values and row arrays if they satisfy the same
schema and structured-return rules as same-file functions. Import composition
must keep HIR metadata stable so a caller can sort or field-read imported
row-array results:

```ds
import "./rows.ds"

let rows = load_rows()
let sorted = rows.sort_by("loc", "desc")
```

The milestone does not add module-level schema declarations or exported type
names.

## VM behavior

The VM must represent rows and row arrays without lossy string encoding.

Required runtime behavior:

- row values store non-empty field names and scalar `DsValue` field values;
- row arrays store an ordered list of row values plus schema metadata;
- row and row-array assignment copies values deeply enough that later mutation
  of the copy cannot mutate the original;
- `push` copies the pushed row into the target row array;
- row-array indexing returns a row value with schema metadata;
- field access returns scalar values with their original scalar kind;
- `sort_by` returns a new row array and preserves the receiver unchanged;
- string field values preserve exact bytes as already supported by strings;
- integer and boolean field values preserve their scalar kinds through field
  reads, conditions, case selectors, interpolation, returns, and sorting;
- runtime data failures include clear diagnostics for out-of-range indexes,
  schema mismatches that can only be detected dynamically, and internal sort
  helper failures.

Implementation may extend `DsValue` with dedicated row/row-array tags or may use
a private row-array wrapper around existing map/array internals, but HIR and VM
behavior must not expose general arbitrary nested collections.

## Bash emission behavior

Generated Bash must be standalone and must preserve VM behavior.

The exact private encoding is implementation-owned, but it must satisfy these
requirements:

- row arrays cannot be encoded as delimiter-separated records that lose tabs,
  newlines, empty strings, shell metacharacters, braces, or backslashes;
- field values must be stored in quoted Bash variables/arrays with scalar-kind
  sidecars, not reparsed through `eval` or unquoted word splitting;
- Bash 4+ guards may be emitted when row arrays require associative arrays or
  nameref-like behavior, following the existing map guard pattern;
- helper names must stay under the reserved `__ds_` namespace;
- helper definitions must be deduplicated and emitted only when row features are
  used;
- `sort_by` may use standard Unix `sort` under `LC_ALL=C`, consistent with
  existing deterministic map-iteration assumptions, but must quote and encode
  rows so field data cannot be interpreted as shell syntax;
- sorting must be stable and deterministic in the same way as the VM;
- returned row arrays must travel through the private function-return ABI without
  using stdout as a data channel;
- generated Bash must reject or fail clearly for runtime data errors rather than
  producing partial or invalid output.

Emitted Bash should not expose the row-array payload format as public API. Tests
may inspect generated Bash for helper presence, deduplication, namespace hygiene,
standalone execution, and absence of fragile delimiter encodings, but should not
lock internal variable names more tightly than necessary.

## Diagnostics and debugging behavior

Diagnostics should follow existing phase ownership:

- parser diagnostics for invalid syntax;
- lowering diagnostics for unsupported row shapes, schema mismatches that are
  statically visible, unsupported row-array mutation targets, non-literal
  `sort_by` fields/directions, row values in command positions, and row/row-array
  parameters;
- VM runtime diagnostics for dynamic out-of-range indexes and dynamic row-array
  data failures;
- Bash runtime diagnostics for the same dynamic failures in emitted scripts;
- Bash emission diagnostics only for accepted-HIR rendering/artifact failures.

Diagnostics should include:

- the row field name when a field is missing or has an incompatible kind;
- the expected and actual row schema when a row push or array literal mismatches;
- the receiver kind when `sort_by` is called on a non-row array;
- the allowed directions when `sort_by` receives an invalid direction;
- a short next step when obvious, for example "use a scalar field such as
  `row.name`" when a whole row is used in a command word.

Debug views should expose row metadata enough for tests and developers:

- `ds ast` should show normal object/array/postfix syntax without needing public
  row annotations;
- `ds hir` should show row schemas or row-array element metadata for row values,
  row arrays, loop variables, field reads, and `sort_by` calls;
- `ds bytecode` should show row/row-array operations or clearly named helper
  instructions if dedicated bytecode is added;
- `ds fmt` should preserve the supported row literal, row-array literal,
  `push`, field access, and `sort_by` syntax.

## Examples

### Basic row collection and sorting

```ds
let rows = []

rows.push({ file: "src/main.c", line: 10, name: "parse", loc: 42 })
rows.push({ file: "src/runtime.c", line: 5, name: "run", loc: 7 })

for row in rows.sort_by("loc", "desc") {
  echo "{row.loc}\t{row.file}:{row.line}\t{row.name}"
}
```

Expected output:

```text
42	src/main.c:10	parse
7	src/runtime.c:5	run
```

### Transforming into a new row array

```ds
let public = []

for row in rows {
  if row.name.starts_with("ds_") {
    public.push({
      file: row.file,
      line: row.line,
      name: row.name.upper(),
      loc: row.loc
    })
  }
}
```

### Imported row-array result

```ds
import "./analyzer.ds"

let rows = analyze("src")
let sorted = rows.sort_by("file")

for row in sorted {
  echo "{row.file}:{row.line} {row.name}"
}
```

## Non-goals

This milestone does not add:

- public row/schema/type declarations;
- typed row or row-array parameters;
- collection-valued parameters of any kind;
- arbitrary nested arrays or maps;
- arrays inside row fields;
- maps/rows inside row fields;
- command-result objects inside row fields;
- null/missing field values;
- field deletion;
- field-style assignment such as `row.loc = 3`;
- nested mutation such as `rows[0].loc = 3`;
- sparse row arrays or append-by-index assignment;
- higher-order collection APIs such as `map`, `filter`, `reduce`, or custom
  comparator callbacks;
- multi-key sort, locale-aware sort, natural sort, case-insensitive sort,
  reverse iteration, or sort configuration objects;
- serialization formats such as JSON/CSV;
- database, dataframe, or streaming query features;
- public Bash payload compatibility guarantees.

## Acceptance criteria

`v0.37.0` is complete when:

- row literals with scalar fields lower, run in the VM, and emit to standalone
  Bash;
- row-array literals and empty-array first-push row inference work with matching
  schema validation in both backends;
- row field access through loop variables, locals, returned rows, and indexed
  row arrays preserves scalar kind metadata;
- row-array iteration preserves insertion order;
- row-array `push` copies values and rejects schema mismatches;
- row-array `sort_by(field[, direction])` returns a sorted copy with stable,
  deterministic string/int/bool ordering and no receiver mutation;
- row and row-array assignment copy by value;
- row-array function returns and imported row-array results work through the
  private VM/Bash value-return boundary;
- unsupported nested values, unsupported mutation, unsupported row parameters,
  command/interpolation misuse, unknown fields, and invalid sort arguments fail
  with clear diagnostics;
- `ds ast`, `ds hir`, `ds bytecode`, and `ds fmt` remain useful for supported row
  programs;
- generated Bash is standalone, uses reserved helper names, deduplicates helper
  definitions, preserves hostile field data exactly, and does not use fragile
  delimiter-separated record parsing;
- VM/Bash parity tests cover row creation, row arrays, field access, iteration,
  sorting, copy semantics, function returns, imports, diagnostics, and edge
  cases;
- docs/examples are updated if implementation behavior differs from this spec;
- deferred items and any remaining row-related technical debt are recorded in
  the completion review.

## Deferred to later milestones

The following should remain future work unless this spec is deliberately
amended before implementation:

- typed row/schema declarations;
- row/row-array function parameters;
- arbitrary nested collection values;
- row-field mutation and row-array element replacement;
- row-array concatenation, slicing, deletion, and insertion helpers;
- multi-key/custom sort helpers;
- JSON/CSV conversion helpers;
- streaming row processors for very large datasets;
- richer recursive walking helpers, which remain planned for `v0.38.0`.
