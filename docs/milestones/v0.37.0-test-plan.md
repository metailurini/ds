# v0.37.0 Test Plan — Lightweight Rows and In-Memory Data Processing

## Status

Implemented. The focused suite lives at `tests/v0_37/run.sh`, follows the
repository's versioned-suite convention, is wired into `make test` through
`TEST_VERSIONS`, and covers the required VM/Bash parity, diagnostics, generated
Bash hygiene, hostile data, imports, and adjacent-feature integration checks.

## Purpose

Prove that lightweight rows and row arrays are a narrow, deterministic,
VM/Bash-parity feature for in-memory data-processing scripts.

The plan focuses on:

- flat row literals with scalar fields;
- row-array literals and empty-array first-push inference;
- row field access from locals, loop variables, indexed rows, and returned rows;
- row-array iteration, copying, pushing, transformation, and sorting;
- row-array function returns and imports;
- Bash helper hygiene and standalone behavior;
- clear rejection of nested collections, unsupported mutation, unsupported
  row/row-array parameters, invalid schemas, and invalid `sort_by` calls;
- edge cases involving empty strings, whitespace, newlines, shell metacharacters,
  braces, duplicated sort keys, boolean fields, empty row arrays, and dynamic
  index failures.

## Required commands

Run the relevant command set for accepted fixtures:

```sh
./ds check file.ds
./ds ast file.ds
./ds hir file.ds
./ds bytecode file.ds
./ds run file.ds
./ds file.ds
./ds emit bash file.ds -o file.sh
bash -n file.sh
bash file.sh
```

For test-block fixtures:

```sh
./ds test file.ds
```

For invalid fixtures:

```sh
./ds check file.ds
./ds run file.ds
./ds emit bash file.ds -o file.sh
```

Invalid fixtures should fail before user commands run when the error is static.
If an error is intentionally runtime-only, both VM execution and emitted Bash
execution must fail consistently and the diagnostic should identify the same
source-level issue.

For generated Bash hygiene:

```sh
grep -n "__ds_" file.sh
grep -n "ds " file.sh
env -i PATH="$PATH" bash file.sh
```

Generated Bash must not call `ds` at runtime. It may call standard Unix tools
that are already part of the project host assumptions, such as `sort`, when the
spec allows it.

## Test conventions

Each accepted parity fixture should compare VM and Bash stdout/stderr/status.
Use existing helper functions where available. If helpers need to be added,
prefer names that make the parity contract obvious, such as:

```sh
run_vm_bash_parity rows-basic.ds
expect_check_failure rows-schema-mismatch.ds "schema"
expect_run_failure rows-index-oob.ds "out of range"
expect_emit_bash_failure rows-invalid-sort.ds "sort_by"
```

Assertions should verify both behavior and phase:

- static schema errors fail under `check`, `run`, and `emit bash`;
- runtime index errors pass `check` when the index is dynamic, then fail under
  both VM execution and emitted Bash execution;
- Bash emission does not write an output file for lowering errors, or writes
  nothing user-runnable if the repository's current convention is to abort
  before artifact creation;
- accepted emitted scripts pass `bash -n` and run with `env -i PATH="$PATH"`;
- emitted helper definitions are deduplicated.

Avoid tests that depend on private helper variable names unless no other
observable signal is available. Prefer behavioral parity and coarse hygiene
checks over locking the internal Bash payload format.
