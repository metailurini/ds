# v0.4.0 Spec — Cleanup: Frontend, Runtime, and Backend Boundaries

## Status

Planned.

## Goal

Repay the first major wave of technical debt after the frontend, Bash emitter, and initial VM/runtime foundation exist.

This version should make the internal pipeline easier to extend before the project adds larger user-facing language features such as CLI argument blocks, imports, functions, loops, and user-facing arrays/maps.

`v0.4.0` is a cleanup milestone. It should preserve current user-facing behavior while simplifying boundaries, making diagnostics consistent, strengthening regression coverage, and recording any remaining debt clearly.

## Motivation

The project intentionally follows a four-version wave:

```txt
0.x.0     Feature foundation
0.x+1.0   Feature expansion
0.x+2.0   Feature integration / usability
0.x+3.0   Cleanup / debt repayment
```

`v0.1.0` created the frontend, `v0.2.0` proved standalone Bash emission, and `v0.3.0` is planned to add the minimal runtime and bytecode VM. Without cleanup, future language features would likely duplicate semantic behavior across the parser, checker, VM, and Bash emitter.

This milestone should make the project boring in the best way: one clear compiler pipeline, one diagnostics style, one source-location model, explicit runtime ownership rules, and stable test fixture layout.

## Starting point review

This milestone starts after the first complete implementation wave:

- `v0.1.0` introduced source loading, diagnostics, lexing, parsing, AST output,
  and `tokens` / `ast` / `check` debug commands.
- `v0.2.0` introduced `emit bash`, standalone Bash generation, Bash safety
  rules, and Bash-oriented golden/runtime tests.
- `v0.3.0` introduced the first lowered program representation, bytecode dump,
  VM execution, runtime primitives, VM/Bash parity tests, direct lowering tests,
  sanitizer targets, and VM runtime block scopes.

The project now has the right broad shape, but several pieces were intentionally
implemented in the smallest useful form. `v0.4.0` should turn those pieces into
clean reusable boundaries before adding new language features.

Observed cleanup inventory from the first wave:

- `include/ds.h` is a single wide header that exposes frontend, HIR, runtime,
  VM, Bash, and utility declarations together. This was useful early, but it is
  becoming difficult to see ownership boundaries.
- AST and HIR shapes are very similar. That may be acceptable, but the reason
  should be explicit: AST owns parsed syntax, HIR owns checked backend-facing
  semantics. Any duplicated traversal should be reviewed.
- Lowering now exists and is shared, but reusable HIR helpers are still minimal.
  Backends should not repeatedly rediscover variable lookup, command argument
  lowering, comparison normalization, or interpolation rules.
- CLI command dispatch has grown from simple debug commands to multiple modes.
  Usage errors should be centralized enough that `tokens`, `ast`, `check`,
  `emit bash`, `run`, and `bytecode` behave consistently.
- Diagnostics exist, but command-line, source, lowering, backend, and runtime
  errors should be reviewed for a consistent source-tied shape.
- Runtime primitives exist, but ownership rules are mostly implied by tests and
  implementation details. They need API-level documentation and stronger
  destructor/clear conventions before arrays/maps become user-facing.
- `DsMap` currently provides a project-owned boundary. The staged `libs/hashmap`
  directory remains present from the early project history and should either be
  safely absorbed later or clearly documented as unused/staged; unrelated code
  must not depend on staged names.
- Test coverage is strong, but runners contain repeated shell helpers and fixture
  conventions. `v0.4.0` should make the layout and runner behavior reusable for
  `v0.5.0+`.
- Documentation has been updated incrementally across versions. `v0.4.0` should
  ensure the architecture/runtime docs describe the implementation that actually
  exists after `v0.3.0`, not only the original plan.

## Non-goals

This version does not include:

- new major syntax;
- CLI argument blocks;
- imports or import bundling;
- functions;
- loops;
- user-facing arrays or maps;
- command result capture;
- new redirection sugar;
- standard-library helpers such as `file.exists`;
- optimizer work beyond deleting obvious duplicate logic;
- bytecode performance tuning;
- changes that require emitted Bash to depend on the C runtime.

User-facing behavior should remain compatible with `v0.1.0` through `v0.3.0` unless the spec explicitly calls out a diagnostic cleanup or bug fix.

## Cleanup principles

Cleanup in this milestone should follow these rules:

- Prefer moving duplicated logic behind a shared internal API over changing user-facing behavior.
- Prefer small, reviewable refactors over broad rewrites.
- Preserve the Bash-emission requirement for every supported feature.
- Preserve VM/Bash parity for the supported subset.
- Keep generated Bash standalone.
- Keep `libs/hashmap` staged unless the `DsMap` boundary is stable enough to absorb it safely.
- Record deferred cleanup explicitly instead of silently leaving ambiguous debt.
- Run full regression tests after each major boundary change.

## User-facing commands

No new user-facing commands are required.

These commands must continue to work:

```sh
ds tokens <file.ds>
ds ast <file.ds>
ds check <file.ds>
ds emit bash <file.ds> -o <file.sh>
ds <file.ds>
ds run <file.ds>
ds bytecode <file.ds>
```

If `v0.3.0` has not yet implemented a command by the time this milestone is started, do not invent new behavior in `v0.4.0`. Instead, preserve the latest completed scope and record the missing predecessor work as blocked or deferred.

## Compiler pipeline boundaries

Clarify and enforce the intended pipeline:

```txt
source
  -> lexer
  -> parser / AST
  -> lowering / HIR or equivalent semantic form
  -> bytecode generator
  -> VM

source
  -> lexer
  -> parser / AST
  -> lowering / HIR or equivalent semantic form
  -> Bash emitter
```

Requirements:

- AST code should focus on parsed syntax, not runtime semantics.
- Lowering/HIR code should own semantic checks shared by VM and Bash emission where practical.
- Bytecode generation should consume the shared semantic representation, not re-parse AST details.
- Bash emission should use the shared semantic representation for behavior-sensitive logic where practical.
- The VM should execute bytecode and runtime values, not AST nodes.
- Debug output should remain stable and testable.
- Any deliberate exception to this pipeline must be documented in the completion review.

Concrete cleanup targets:

- Introduce narrower internal headers or clearly grouped sections so frontend,
  lowering, runtime, VM, Bash emitter, and utility APIs are not all treated as
  one undifferentiated public surface.
- Make `ds check`, `ds emit bash`, `ds run`, `ds <file>`, and `ds bytecode`
  flow through the same parse-and-lower helper where practical.
- Keep `ds tokens` and `ds ast` frontend-oriented, but ensure their failure
  paths use the same source-loading and diagnostic helpers.
- Give HIR/lowered nodes helper functions for common queries rather than making
  every backend switch over raw enum values for semantic decisions.
- Ensure backend-specific code is only responsible for rendering/executing an
  already-lowered program, not validating user-visible language rules again.

Potential reusable helpers to consider:

- `ds_load_source_for_cli(path, diag)` or equivalent for source loading errors;
- `ds_parse_source(...)` for lex/parse/check command setup;
- `ds_lower_source(...)` or equivalent for parse + HIR creation;
- HIR iterators or small visitors for statement/expression traversal;
- helpers for command argument interpolation segments;
- helpers for comparison operator normalization and kind checks;
- a single CLI usage/error printer per command family;
- a test-runner helper library shared by shell test scripts.

## AST, HIR, and semantic cleanup

Review the AST/HIR boundary created by earlier milestones.

Required cleanup:

- Remove or isolate duplicated semantic checks between `check`, `emit bash`, and `run`.
- Centralize unknown-variable and interpolation-name validation where practical.
- Centralize expression kind/value-kind classification where practical.
- Ensure source spans survive from AST through HIR, bytecode, diagnostics, and bytecode dumps.
- Make block/scope behavior explicit and documented.
- Ensure branch-local declarations follow one documented rule.
- Keep command statement representation shell-native without forcing function-call syntax in user code.

Specific review items from `v0.1.0` through `v0.3.0`:

- Decide whether `ds_lower_validate()` remains useful now that
  `ds_lower_program()` exists. If it only duplicates lowering, remove it or make
  it a tiny wrapper around the real lowering path.
- Review whether `DsLowerExpr` and `DsLowerStmt` should keep mirroring AST nodes
  or whether they need explicit backend-ready fields, such as pre-split
  interpolation segments or normalized comparison operators.
- Ensure duplicate declaration, shadowing, and branch-local scope diagnostics are
  produced in one lowering location, not separately in VM/Bash code.
- Ensure unsupported future syntax is rejected before backend execution/emission
  and reports the same source span across `check`, `run`, `bytecode`, and
  `emit bash` where practical.
- Document the current strict scope rule: branch-local names are local to that
  branch/block and shadowing is rejected until the language intentionally adds a
  fuller scope model.
- Review AST/debug output names against HIR/runtime names so debug commands stay
  syntax-focused and do not expose runtime implementation concepts.

The milestone may rename internal types or files if that improves clarity, but it should avoid churn that does not reduce duplication or improve boundaries.

## Runtime ownership cleanup

Review runtime ownership rules introduced by `v0.3.0`.

Required cleanup:

- Document who owns `DsString` buffers at API boundaries.
- Document whether `DsValue` copy operations retain, clone, borrow, or transfer owned data.
- Make array/vector clear/free behavior consistent across runtime containers.
- Make map key/value ownership explicit.
- Ensure normal and error paths release owned runtime memory.
- Ensure allocation failure handling is consistent where practical.
- Remove or document any unsafe lifetime coupling to source buffers.

Concrete ownership decisions to document or adjust:

- `DsString` should be documented as owning `data`, with `len` and `cap` kept
  coherent after init, append, take, and free operations.
- `ds_value_string_take()` should explicitly transfer ownership from a
  `DsString` into a `DsValue`, leaving the source `DsString` safe to discard or
  reinitialize according to the implementation contract.
- `ds_value_copy()` should clearly deep-copy strings and trivially copy null,
  bool, and int values.
- `ds_value_free()` should be the single destructor path for owned string values.
- `DsArray` currently stores `void *`; document whether it is an owning vector,
  a borrowed pointer vector, or needs typed wrappers before storing owned values.
- `DsMap` should document whether keys are copied and whether values are copied,
  moved, or borrowed on set/update.
- VM register cleanup, scope pop cleanup, bytecode free cleanup, and early error
  cleanup should follow the same destructor rules.

Refactor-for-reuse opportunities:

- Add explicit `clear` functions where containers are reused without freeing the
  container object.
- Add typed vectors for common internal lists if repeated `void **` casts make
  ownership unclear.
- Keep allocation helpers simple, but document whether they abort, return false,
  or report diagnostics. Do not mix those strategies silently in one API family.

`docs/runtime.md` must be updated if the implementation chooses ownership rules that differ from the planned runtime document.

## `DsMap` and staged hashmap cleanup

`libs/hashmap` is a temporary staging location. The rest of the project should not depend directly on its concrete types or naming.

Required cleanup:

- Audit all uses of staged hashmap symbols.
- Ensure compiler/runtime code uses a project-owned `DsMap` or equivalent wrapper.
- Remove direct `libs/hashmap` includes from unrelated frontend, lowering, VM, or emitter code where practical.
- Keep staged library license/original files intact while it remains under `libs/hashmap`.
- Decide whether absorption into `src/core` is safe in this milestone.
- Decide whether the current simple `DsMap` implementation is intentionally
  sufficient for now or whether the staged hashmap should replace it behind the
  wrapper. The decision should be based on API stability and tests, not on the
  mere existence of staged code.

Absorption rule:

- If the `DsMap` API and ownership model are stable, this milestone may begin absorbing the staged map implementation into a project-owned core location.
- If not stable, do not force the move. Record exact blockers and keep the wrapper boundary clean.

Completion review should record one of these outcomes:

- **Absorbed:** staged hashmap behavior is moved behind the project-owned map
  implementation, callers still depend only on `DsMap`, and license/history are
  preserved.
- **Still staged and used:** staged implementation remains under `libs/hashmap`,
  but only the `DsMap` wrapper includes/uses it.
- **Still staged and unused:** current `DsMap` remains independent; staged code is
  retained only for later evaluation, and this is documented to avoid confusion.

## Source location and diagnostics cleanup

Standardize diagnostics across all commands.

Required diagnostic shape:

```txt
file.ds:line:column: error: message
```

Where practical, diagnostics should also include a source line and caret/span marker, following the existing frontend style.

Commands that should use consistent diagnostics:

- `ds check`;
- `ds emit bash`;
- `ds run` / `ds <file.ds>`;
- `ds bytecode`;
- frontend debug commands when they fail before output.

Required cleanup:

- Do not print raw internal enum names in user diagnostics unless they are part of debug output.
- Do not print pointer addresses or nondeterministic data.
- Keep unsupported-feature diagnostics clear about whether the issue is syntax, lowering, bytecode generation, emission, or runtime execution.
- Make missing file, invalid CLI usage, parse error, lowering error, and runtime/process error formatting reasonably consistent.
- Ensure backend diagnostics do not lose the original user source span after
  HIR/bytecode lowering.
- Review whether source-line/caret rendering should be called through one helper
  for all source-tied diagnostics.
- Make process/runtime failures include the command source line where practical,
  without pretending that external process errors are parse errors.

Exact wording may change, but tests should lock down the intended stable shape.

The cleanup should distinguish three categories:

- **CLI usage errors:** command is malformed before a source file is known; these
  may use `ds: error: ...` plus usage text.
- **Source-tied compiler errors:** lexer/parser/lowering/backend errors tied to a
  `.ds` span; these should use `file:line:column: error: ...`.
- **Runtime/process errors:** VM command failures or process launch errors; these
  should include source location when available and preserve the process exit
  behavior documented by `v0.3.0`.

## Golden fixture layout cleanup

Standardize the test fixture layout before more milestones add more tests.

Preferred layout:

```txt
tests/
  v0_1/
    fixtures/
    golden/
  v0_2/
    fixtures/
    golden/
  v0_3/
    fixtures/
    golden/
    parity/
  v0_4/
    fixtures/
    golden/
    regression/
```

Required cleanup:

- Keep existing tests readable while normalizing fixture naming.
- Avoid deleting useful regression coverage during moves.
- Make test runners fail clearly when a fixture or golden file is missing.
- Keep generated temporary files outside source fixtures.
- Document the chosen layout if it differs from the preferred shape.
- Extract repeated shell-test helpers where useful, for example assertion,
  temporary-directory, golden-diff, and emitted-Bash helpers.
- Keep version-specific tests independent enough that a failure identifies the
  versioned behavior that regressed.

Do not move fixtures solely for aesthetics. A fixture move is justified when it
improves discoverability, removes duplication, or lets later milestones reuse the
same runner helpers.

## VM/Bash duplication cleanup

Review places where VM and Bash emission implement the same semantics separately.

Required cleanup:

- Identify semantic decisions shared by both backends.
- Move shared decisions into lowering/HIR helpers where practical.
- Keep backend-specific rendering/execution separate.
- Preserve generated Bash readability and standalone behavior.
- Preserve VM process execution behavior.
- Update parity tests if the cleanup changes where an error is detected.

Examples of shared behavior candidates:

- variable lookup;
- interpolation validation;
- expression value-kind checks;
- branch condition validation;
- comparison operator normalization;
- command argument lowering.

Reusable backend boundary goals:

- Bash emitter should render HIR into shell text and shell quoting only; it should
  not own language-level symbol visibility rules.
- Bytecode generation should translate HIR into instructions and constants only;
  it should not perform source-level name validation already handled by lowering.
- VM should execute instructions and manage runtime scopes/registers only; it
  should not inspect AST or HIR nodes.
- Any shared helper introduced for Bash/VM parity must avoid embedding Bash-only
  assumptions into VM semantics or VM-only assumptions into Bash output.

Recommended review checklist for each duplicated switch/if chain:

- Is this a syntax decision? Keep it in parser/AST code.
- Is this a language semantic decision? Move it to lowering/HIR.
- Is this a bytecode encoding decision? Keep it in bytecode generation.
- Is this a runtime execution decision? Keep it in the VM/runtime.
- Is this a shell text/quoting decision? Keep it in Bash emission.

Update documentation so the implemented architecture is understandable.

Required docs review:

## Acceptance criteria

`v0.4.0` is complete when:

- The first-wave debt inventory from `v0.1.0` through `v0.3.0` has been reviewed
  and the completion review records what was cleaned up versus deferred.
- AST/HIR/backend boundaries are reviewed and cleaned.
- Any retained AST/HIR duplication is justified as syntax-vs-semantics structure,
  not accidental repeated validation.
- Shared parse/lower helpers or equivalent command plumbing reduce repeated CLI
  setup where practical.
- Runtime ownership rules are reviewed, documented, and tested.
- `DsMap` wraps staged hashmap usage without unrelated code leaking staged library types.
- A decision is recorded about whether hashmap absorption starts now or is deferred.
- Source location and diagnostic APIs are standardized enough for `check`, `emit bash`, and `run` to report consistent errors.
- Golden fixture layout is standardized or documented with a clear rationale.
- Reusable test-runner helpers are added or the decision not to add them is
  justified.
- Duplicated VM/Bash semantic logic is reduced where practical.
- Full v0.1.0, v0.2.0, and v0.3.0 regression tests still pass.
- VM/Bash parity tests still pass for the supported subset.
- No major user-facing syntax is added.
- Generated Bash remains standalone and passes existing Bash-emission tests.
- Architecture/runtime docs match the cleaned implementation.
- Deferred debt items are listed for future cleanup versions.

### v0.4.0 implementation notes

- `src/main.c` now owns shared CLI helpers for source loading, lexing, parsing,
  and lowering. Behavior-sensitive commands lower once and pass the lowered
  program to the selected backend.
- `src/bash_emit.c` exposes `ds_emit_bash_program()` for callers that already
  have a lowered program. The legacy AST entrypoint remains as a wrapper.
- `src/vm.c` exposes `ds_bytecode_dump_program()` and `ds_vm_run_program()` for
  lowered-program callers. The legacy AST entrypoints remain as wrappers.
- `src/runtime.c` now has `ds_array_clear()` and `ds_map_clear()` to document and
  support reuse without conflating clear and free behavior.
- `docs/runtime.md` records current `DsString`, `DsValue`, `DsArray`, and `DsMap`
  ownership rules and the staged-hashmap decision.
