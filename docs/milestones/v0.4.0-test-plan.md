# v0.4.0 Test Plan — Cleanup: Frontend, Runtime, and Backend Boundaries

## Purpose

This test plan verifies that `v0.4.0` cleanup preserves behavior while improving project boundaries.

Because this is a cleanup milestone, the tests should be regression-heavy. The goal is not to prove new syntax; the goal is to prove that refactors do not break the frontend, Bash emitter, VM, bytecode dump, runtime primitives, diagnostics, or VM/Bash parity created by earlier milestones.

The implementation should follow this test plan before the version is closed. Add or adjust tests if cleanup reveals hidden behavior that must be locked down.

## Test categories

`v0.4.0` should include tests for:

- full v0.1.0 frontend regression behavior;
- full v0.2.0 Bash emitter regression behavior;
- full v0.3.0 runtime, bytecode, VM, and parity regression behavior;
- diagnostic consistency across commands;
- source-location preservation through AST, lowering, bytecode, VM, and Bash emission;
- runtime ownership and cleanup behavior;
- `DsMap` wrapper boundary behavior;
- fixture layout and test runner robustness;
- no new major syntax accepted accidentally;
- generated Bash remaining standalone.

Do not use `docs/language.ds` as a runnable fixture. It intentionally contains future syntax.

## Baseline regression suite

Before refactoring, capture the current passing behavior.

Required baseline commands:

```sh
make check
make test
```

If `v0.3.0` has added dedicated targets, include them, for example:

```sh
make test-v0-3
make test-vm
make test-parity
```

The exact target names may differ. The test plan should be updated to match the implementation.

Failure rule:

- If a baseline test fails before cleanup starts, fix or record the predecessor-version regression before doing cleanup refactors.
- Do not hide a predecessor regression by deleting or weakening tests.

## v0.1.0 frontend regression tests

Run all existing lexer, parser, AST, and diagnostic tests.

Regression coverage must still include:

- empty file;
- comments-only file;
- `let` statements;
- string, integer, and boolean literals;
- command statements;
- `if` without `else`;
- `if` with `else`;
- nested blocks;
- invalid token diagnostics;
- unterminated string diagnostics;
- parse errors with line/column information;
- AST golden output without pointer addresses or nondeterministic data;
- `ds tokens` stable output;
- `ds ast` stable output;
- `ds check` success and failure paths.

Edge cases:

- file without trailing newline;
- CRLF input if previously supported;
- UTF-8 bytes inside strings and comments;
- adjacent command tokens;
- multiple blank lines;
- deeply nested block up to the project’s practical test limit;
- syntax from future roadmap versions rejected clearly.

## v0.2.0 Bash emitter regression tests

Run all existing Bash emitter tests.

Regression coverage must still include:

- `ds emit bash <file.ds> -o <file.sh>` success;
- invalid CLI usage for `emit bash`;
- no output file written on invalid source;
- standalone shebang and strict-mode header;
- safe internal variable prefixing;
- string, integer, and boolean `let` emission;
- command statement emission order;
- command argument quoting;
- interpolation in command strings;
- interpolation in `let` string values;
- `if` and `if/else` emission;
- nested `if` emission;
- comparison operator emission;
- generated Bash passes `bash -n`;
- generated Bash runtime output matches expected output;
- unsupported assignment/expression diagnostics;
- unknown interpolation variable diagnostics;
- generated Bash does not depend on the `ds` executable.

Edge cases:

- `$HOME` remains literal when inside a `ds` string unless intentionally interpolated;
- `$(...)` remains literal and is not executed by generated Bash;
- backticks remain literal and are not executed by generated Bash;
- quotes, spaces, and backslashes survive emission;
- interpolation next to punctuation;
- many variables;
- long string;
- branch with no runtime output;
- command failure still stops generated Bash under strict mode if that is the documented behavior.

## v0.3.0 VM/runtime regression tests

Run all runtime unit tests, lowering tests, bytecode tests, VM integration tests, and parity tests from `v0.3.0`.

Regression coverage must still include:

- `ds <file.ds>` direct execution;
- `ds run <file.ds>` direct execution;
- `ds bytecode <file.ds>` deterministic output;
- runtime values for `null`, `bool`, `int`, and `string`;
- owned string construction, append, copy/retain rules, and free behavior;
- internal arrays/vectors;
- `DsMap` wrapper behavior;
- command execution through the process abstraction;
- variable declaration and lookup;
- interpolation;
- `if` / `else` execution;
- nested blocks;
- command failure exit behavior;
- parse/lowering/runtime/process diagnostics;
- VM/Bash stdout and exit-code parity for supported fixtures.

Edge cases:

- command not found or process launch failure;
- unknown variable discovered during lowering;
- unknown interpolation name discovered before execution where practical;
- non-boolean condition if the implementation rejects it;
- mixed-type comparison if the implementation rejects it;
- branch-local variable used outside its scope if disallowed;
- allocation failure hooks where practical;
- cleanup after runtime error;
- bytecode dump contains no pointer addresses or timestamps.

## Diagnostic consistency tests

Add tests that compare diagnostic shape across commands.

The exact wording may differ by phase, but each source-tied diagnostic should include:

```txt
file.ds:line:column: error: message
```

Test commands:

```sh
ds check bad.ds
ds emit bash bad.ds -o out.sh
ds run bad.ds
ds bytecode bad.ds
ds tokens bad.ds
ds ast bad.ds
```

Required diagnostic cases:

- missing file;
- invalid CLI usage;
- invalid token;
- unterminated string;
- parse error such as missing `}`;
- unknown variable;
- unknown interpolation variable;
- unsupported expression for Bash emission;
- unsupported expression for VM/lowering if applicable;
- command/process launch failure where practical;
- runtime type mismatch if such a state is possible.

Assertions:

- diagnostics contain filename, line, column, and `error:` when tied to source;
- diagnostics do not contain raw pointer addresses;
- diagnostics do not contain nondeterministic temporary paths except where the test controls the path;
- diagnostics do not expose unrelated internal library type names;
- `emit bash` does not leave a partial output file after source-time failure;
- `check`, `emit bash`, `run`, and `bytecode` agree on source location for the same parse/lowering failure.

Edge cases:

- error on first line, first column;
- error at end of file without trailing newline;
- error after several blank lines;
- error inside nested block;
- error inside interpolated string.

## Source-location preservation tests

Add tests that prove source spans survive cleanup.

Fixtures should include:

- top-level `let` error;
- command argument interpolation error;
- nested `if` condition error;
- error inside `else` branch;
- bytecode dump for a multi-line script;
- VM runtime/process error associated with the command line if practical;
- Bash source comments for generated command lines.

Assertions:

- AST output still shows stable line/column data if it previously did;
- lowering diagnostics point at the user source span, not the generated HIR object;
- bytecode dump source comments point at the original `.ds` file;
- generated Bash source comments point at the original `.ds` file;
- VM/process diagnostics point at the command statement line where practical.

## Runtime ownership regression tests

Use unit tests and sanitizer-friendly integration tests where available.

String ownership cases:

- string value remains valid after source buffer cleanup;
- copied value does not double-free;
- freed value does not leak owned buffer under normal path;
- interpolation result owns its output or clearly documents borrowing;
- append after growth preserves prior content.

Value ownership cases:

- copying `null`, `bool`, and `int` values is safe;
- copying string values follows documented ownership rules;
- comparing values does not mutate or free them;
- freeing arrays/maps containing values uses the documented value destructor path.

Array/vector cases:

- pushing many items grows capacity safely;
- clearing releases contained owned values if documented;
- clearing does not release contained borrowed values if documented;
- out-of-bounds defensive checks behave consistently.

Map cases:

- map key ownership follows documented rules;
- map value ownership follows documented rules;
- updating an existing key releases or preserves old value according to documented rules;
- clearing/freeing the map releases all owned content;
- collision-heavy inserts remain correct.

Edge cases:

- empty string key;
- key with underscore and digits;
- key with common prefix;
- very long key within practical test limits;
- repeated insert/update/delete cycles if delete is supported;
- allocation failure hooks where practical.

## `DsMap` wrapper boundary tests

Add tests or static checks to ensure staged hashmap details do not leak into unrelated code.

Possible checks:

```sh
grep -R "#include \".*hashmap" src include
grep -R "struct hashmap\|hashmap_" src include
```

The exact allowlist should match the implementation. Direct staged-library references should be allowed only in the wrapper implementation and tests that intentionally target the wrapper.

Required behavior tests:

- wrapper init/free;
- insert/get missing/get existing;
- update existing;
- many inserts;
- collision-style keys if practical;
- clear and reuse if supported;
- no dependency on staged library naming in callers.

If absorption into `src/core` starts during `v0.4.0`, add tests proving behavior is unchanged before and after the move.

## Fixture layout and test runner tests

Standardize or document the fixture layout.

Test runner behavior should cover:

- missing fixture fails clearly;
- missing golden file fails clearly;
- golden mismatch prints useful diff context;
- temporary emitted files are written outside fixture directories;
- test runners are executable or invoked through `sh` consistently;
- running tests from the repository root succeeds;
- running tests after `make clean` succeeds;
- repeated `make test` runs do not depend on stale generated files.

Edge cases:

- fixture filename with spaces if supported by test runner conventions;
- fixture with no trailing newline;
- empty expected output file;
- stderr-only failure fixture;
- generated Bash fixture that exits non-zero intentionally.

## VM/Bash parity regression tests

Parity tests should compare VM mode and emitted Bash mode for the supported subset.

Required parity fixtures:

- simple command output;
- multiple command output order;
- string interpolation;
- integer interpolation;
- boolean interpolation;
- `let` string interpolation;
- `if` true branch;
- `if` false branch with `else`;
- nested `if`;
- comparison operators supported by the project;
- command failure exit code;
- unknown variable source-time failure where both paths should reject before execution.

Assertions:

- stdout matches exactly for success cases;
- exit code matches for success and supported failure cases;
- stderr is either matched exactly or normalized according to documented rules;
- generated Bash passes `bash -n` before execution;
- generated Bash remains standalone and does not call `ds`.

Edge cases:

- long output;
- output with spaces and punctuation;
- branch that intentionally produces no output;
- command arguments that look like Bash syntax but should be literal strings.

## No accidental syntax expansion tests

Because `v0.4.0` is cleanup-only, future syntax must not become accepted by accident.

Add negative tests for representative future syntax from `docs/language.ds`, such as:

- `script { ... }` CLI args block;
- imports;
- functions;
- loops;
- arrays as user-facing values;
- maps as user-facing values;
- command capture;
- redirection sugar not yet implemented;
- standard-library helpers not yet implemented.

Each test should assert a clear parse or unsupported-feature diagnostic. Do not lock down misleading wording if the phase may change; lock down the stable diagnostic shape and non-zero exit behavior.

## Generated Bash standalone tests

After cleanup, prove Bash emission still has no runtime dependency.

Tests should verify:

- generated `.sh` has the expected shebang;
- generated `.sh` has strict mode;
- generated `.sh` does not invoke `ds`;
- generated `.sh` does not source a project runtime file;
- generated `.sh` runs from a temporary directory outside the repository;
- generated `.sh` runs after temporarily hiding or renaming the local `ds` binary if practical;
- generated `.sh` passes `bash -n`.

Edge cases:

- script with only variables;
- script with commands and interpolation;
- script with nested conditionals;
- script with failed command when failure behavior is documented.

## Documentation verification

Add manual or scripted checks where practical:

- README command list matches implemented commands;
- README project status does not claim future syntax is implemented;
- `docs/architecture.md` pipeline matches source layout after cleanup;
- `docs/runtime.md` ownership rules match runtime APIs;
- `docs/language.ds` still marks future syntax as planned/candidate where appropriate;
- milestone completion review is updated before close;
- changelog mentions the cleanup.

Do not require documentation tests to parse prose perfectly. The goal is to catch obvious stale claims.

## Suggested implementation sequence

1. Run the baseline regression suite.
2. Add diagnostic consistency tests that fail against current inconsistencies.
3. Add source-location preservation tests.
4. Add or strengthen runtime ownership and `DsMap` boundary tests.
5. Normalize fixture layout and update test runners.
6. Refactor AST/HIR/backend boundaries in small steps.
7. Refactor diagnostics/source locations in small steps.
8. Refactor runtime ownership and map boundaries in small steps.
9. Run full regression and parity tests.
10. Update docs and completion review.

## Known acceptable limitations

The following are acceptable only if documented in the completion review:

- Exact diagnostic wording may differ by phase while sharing the same stable shape.
- Some allocation failure paths may be difficult to force without adding test hooks.
- Staged hashmap absorption may be deferred if the wrapper API is not stable.
- Some stderr parity cases may require normalization because VM and Bash fail in different processes.
- If `v0.3.0` is incomplete when this milestone is attempted, tests tied to VM/runtime behavior must be marked blocked rather than silently removed.
