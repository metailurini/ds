# v0.5.0 Spec — First-Class CLI Args

## Status

Planned.

## Goal

Add first-class script argument declarations through a `script { ... }` block and make the declared arguments available to normal `ds` code in both direct VM execution and emitted standalone Bash.

This milestone should make a simple deployment-style script pleasant to write without hand-rolled Bash argument parsing.

The feature is complete only when the same declared CLI contract works through:

```sh
ds ./script.ds [args...]
ds run ./script.ds [args...]
ds emit bash ./script.ds -o ./script.sh
bash ./script.sh [args...]
```

## Motivation

CLI argument parsing is one of the project’s core reasons to exist. Bash can parse positional arguments, options, and flags, but doing so correctly is repetitive and fragile. `ds` should let authors declare a small contract once and rely on the tool to validate input, bind typed values, and generate useful help.

This version starts that system with the smallest useful shape:

```ds
script {
  arg app: string
  option target: string = "staging"
  option retries: int = 3
  flag force: bool = false
}

echo "Deploying {app} to {target}"

if force {
  echo "force enabled"
}
```

The implementation must preserve the existing architecture rule: parse once, lower once, then feed both the VM and Bash emitter from the shared lowered representation.

## Non-goals

This version does not include:

- subcommands;
- short aliases such as `-f`;
- grouped short flags;
- shell completion;
- config-file defaults;
- environment-variable defaults;
- variadic positional arguments;
- optional positional arguments unless explicitly needed by the implementation;
- custom validation expressions;
- complex validation DSL;
- arrays or maps as argument types;
- user-facing functions;
- imports;
- command result capture;
- redirection sugar;
- changes that make emitted Bash depend on `ds` or the C runtime.

## Supported syntax

Add the `script` declaration block at top level:

```ds
script {
  arg app: string
  option target: string = "staging"
  option retries: int = 3
  flag force: bool = false
}
```

Supported declaration kinds:

```ds
arg name: type
option name: type = default
flag name: bool = false
```

Supported types:

```txt
string
int
bool
```

Type rules:

- `arg` supports `string`, `int`, and `bool` only if bool positional parsing is explicitly implemented and documented. If bool positionals are deferred, reject `arg x: bool` with a clear diagnostic.
- `option` supports `string`, `int`, and `bool` where Bash parity remains simple.
- `flag` is boolean-only.
- `flag` defaults should be `false` in this milestone. A `true` default is deferred unless the implementation intentionally supports `--no-name` or equivalent behavior, which is out of scope for v0.5.0.
- `option` defaults are required in this milestone.
- `arg` defaults are not supported.

Placement rules:

- At most one `script` block is allowed per program.
- The `script` block must appear before executable statements.
- The `script` block is not a runtime block and does not execute commands.
- Declarations inside `script` introduce top-level variables available to later script code.
- Declaration names share the normal variable namespace and must not duplicate each other or later `let` declarations in the same scope.

Naming rules:

- Declaration names use normal identifier syntax.
- Option and flag CLI names are generated as `--kebab-case` only if the implementation already has or adds a documented conversion. Otherwise use the identifier literally as `--name` and reject names that cannot map cleanly.
- For v0.5.0, prefer a conservative one-to-one mapping: `target` -> `--target`, `retries` -> `--retries`, `force` -> `--force`.

## CLI behavior

### Direct VM execution

The direct execution forms should accept script arguments after the script path:

```sh
ds examples/args.ds api --target production --retries 5 --force
ds run examples/args.ds api --target production --retries 5 --force
```

Requirements:

- Parse CLI args according to the `script` block before executing normal statements.
- Bind positional args in declaration order.
- Bind named options by `--name value`.
- Bind boolean flags by presence of `--name`.
- Apply defaults for omitted options and flags.
- Reject missing required positional args.
- Reject unknown options.
- Reject duplicate named options or flags unless the implementation explicitly chooses last-one-wins and documents it. Prefer rejecting duplicates in v0.5.0.
- Reject named options missing their value.
- Reject invalid `int` option or arg values.
- Reject unexpected extra positional args.
- Support `--` to end option parsing, so later tokens are positional values.
- Support `--help` and `-h` for generated help if `-h` does not conflict with the no-short-alias rule. If short aliases are not supported, `-h` may still be accepted as a universal help convenience, but that decision must be documented.
- When help is requested, print help and exit `0` without executing the script body.

### Bash emission

The emitted Bash must be standalone and parse the same declared arguments:

```sh
ds emit bash examples/args.ds -o /tmp/args.sh
bash /tmp/args.sh api --target production --retries 5 --force
bash /tmp/args.sh --help
```

Requirements:

- Generated Bash must not require `ds` at runtime.
- Generated Bash must implement the same missing-arg, unknown-option, missing-value, duplicate-option, invalid-int, and extra-positional behavior as the VM path.
- Generated Bash must define internal variables using the existing safe internal prefix strategy.
- Generated Bash must expose script-declared names to emitted statements using the same variable mapping as normal `let` declarations.
- Generated Bash help text should match VM help text as closely as practical. Exact whitespace may be golden-tested and should be deterministic.
- Generated Bash should keep `set -euo pipefail` unless the argument parser needs a carefully documented local exception.

### Existing command compatibility

Existing commands must continue to work:

```sh
ds tokens <file.ds>
ds ast <file.ds>
ds check <file.ds>
ds bytecode <file.ds>
ds emit bash <file.ds> -o <file.sh>
ds run <file.ds>
ds <file.ds>
```

Command-specific notes:

- `ds check file.ds` validates the `script` block syntax and declaration semantics, but it does not require runtime CLI args.
- `ds tokens file.ds` should show the new keywords/tokens.
- `ds ast file.ds` should show the script block in a stable debug representation.
- `ds bytecode file.ds` should include argument-binding setup or a deterministic representation showing where script args are handled. It should not need actual runtime args unless the implementation explicitly supports `ds bytecode file.ds -- ...` for testing; prefer no runtime args for bytecode dumps.

## Parser and AST behavior

Parser requirements:

- Add tokens/keywords for `script`, `arg`, `option`, `flag`, and type names if they are tokenized as keywords.
- Parse `script { ... }` at top level.
- Parse declaration names, type annotations, and defaults.
- Preserve source spans for the block and each declaration.
- Produce clear diagnostics for malformed declarations.
- Keep command-mode parsing intact so existing command statements still parse the same way.

AST requirements:

- Represent the script block distinctly from normal executable blocks.
- Preserve declaration order.
- Preserve default expression source spans.
- Debug output must be stable and pointer-free.

Malformed examples that should fail clearly:

```ds
script
script {
script { arg }
script { arg app }
script { arg app string }
script { option target: string }
script { option retries: int = "three" }
script { flag force: string = false }
script { flag force: bool = true }
```

## Lowering / HIR behavior

Lowering owns shared semantics for both backends.

Requirements:

- Lower the script block into a backend-facing argument contract.
- Reject more than one script block.
- Reject script blocks after executable statements.
- Reject duplicate declaration names.
- Reject conflicts between script declaration names and later top-level `let` declarations.
- Reject unsupported types.
- Reject defaults whose value kind does not match the declared type.
- Convert defaults into runtime/Bash-ready values.
- Introduce declared names into the normal top-level symbol table for later expressions and command arguments.
- Preserve source locations for diagnostics and bytecode/help output.

The VM and Bash emitter must not implement independent semantic validation for the script block. They may render backend-specific code from the lowered contract.

## VM behavior

The VM should parse runtime argv according to the lowered contract before executing normal bytecode statements.

Runtime binding requirements:

- Required positional args are consumed in declaration order.
- Named options may appear before or after positional args unless `--` has ended option parsing.
- `--` ends option parsing.
- Boolean flags become `true` when present and use their default when absent.
- Options use defaults when absent.
- Integer values are parsed as base-10 signed integers within the project’s supported integer range.
- Invalid integer values produce a clear diagnostic and exit non-zero.
- Missing required args produce a clear diagnostic and exit non-zero.
- Unknown options produce a clear diagnostic and exit non-zero.
- Extra positionals produce a clear diagnostic and exit non-zero.
- Help requests exit `0` and do not execute normal script statements.

The VM should then store declared values in the top-level runtime scope so existing expressions and command interpolation can use them.

## Bash emission behavior

Bash emission should generate a small standalone parser before emitted script body statements.

Generated parser requirements:

- Use only Bash builtins and portable POSIX-ish shell utilities where practical; avoid requiring external tools for parsing.
- Keep generated helper names under the existing internal prefix.
- Preserve `set -euo pipefail` behavior.
- Print deterministic help text.
- Print deterministic error messages to stderr.
- Exit `0` for help.
- Exit non-zero for invalid args.
- Bind parsed values into the same internal variables used by later emitted statements.
- Avoid Bash word-splitting and command-substitution hazards when assigning or echoing argument values.

Security/safety requirements:

- A string argument containing spaces remains one argument.
- A string argument containing `$HOME`, `$(...)`, backticks, quotes, backslashes, or braces is treated as data and must not execute or expand unexpectedly.
- Integer parsing must reject values like `abc`, `1abc`, empty string, and lone sign unless intentionally supported.

## Help output

The exact help format may be simple, but it must be deterministic and useful.

Suggested format:

```txt
Usage: args.ds <app> [options]

Arguments:
  app string

Options:
  --target string    default: staging
  --retries int      default: 3
  --force            boolean flag
  --help             show this help
```

Requirements:

- Include script filename or basename.
- Include required positional args in declaration order.
- Include options and flags in declaration order.
- Include defaults for options and flags where useful.
- Match VM and emitted Bash help text as closely as practical.
- Do not execute script body when help is requested.

## Diagnostics

Source-tied diagnostics must keep the standardized shape:

```txt
file.ds:line:column: error: message
```

Runtime CLI-argument diagnostics may not have a source column, but they should still identify the script and the problematic argument where useful.

Required diagnostic themes:

- malformed script block syntax;
- duplicate script block;
- script block after executable statement;
- duplicate declaration name;
- script declaration conflicts with `let` declaration;
- unsupported type;
- invalid default type;
- missing required positional arg;
- missing option value;
- unknown option;
- duplicate option or flag;
- invalid integer value;
- unexpected extra positional arg;
- unsupported use of future syntax from `docs/language.ds`.

## Examples

Add at least one example script, such as:

```ds
script {
  arg app: string
  option target: string = "staging"
  option retries: int = 3
  flag force: bool = false
}

echo "Deploying {app} to {target}"

echo "retries={retries}"

if force {
  echo "force enabled"
} else {
  echo "force disabled"
}
```

Suggested smoke commands:

```sh

ds examples/args.ds --help
ds run examples/args.ds api --target staging

```

- [ ] `script { ... }` parses at top level.

- [ ] `string`, `int`, and `bool` types are supported according to this spec.
- [ ] Declaration defaults are validated.
- [ ] Duplicate and conflicting names are rejected in lowering.
- [ ] Script declarations become available as variables in later code.
- [ ] `ds check` validates script argument declarations without requiring runtime args.
- [ ] `ds <file.ds> [args...]` parses/binds args and runs through VM.
- [ ] `ds run <file.ds> [args...]` parses/binds args and runs through VM.
- [ ] `ds bytecode <file.ds>` remains deterministic and handles script declarations.

## Deferred Items

The following are intentionally deferred unless the implementation explicitly amends this spec:

- subcommands;
- short option aliases beyond optional universal `-h`;
- optional positional args;
- variadic args;
- environment default values;
- config-file defaults;
- arrays/maps as argument types;
- richer help formatting;
- shell completion;
- custom validation DSL;
- `--no-name` negated boolean flags;
- using script metadata such as description/version in help output.
