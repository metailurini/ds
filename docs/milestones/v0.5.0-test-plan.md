# v0.5.0 Test Plan — First-Class CLI Args

## Purpose

This test plan verifies the first user-facing CLI argument declaration feature for `ds`.

`v0.5.0` should let a script declare required positionals, named options with defaults, and boolean flags, then run with equivalent behavior in direct VM mode and emitted standalone Bash.

The test plan is intentionally comprehensive because this feature touches the lexer, parser, AST printer, lowering, bytecode/VM execution, Bash emission, diagnostics, help output, shell safety, and VM/Bash parity.

## Test categories

The version should include tests for:

- lexer tokens for new keywords and type names;
- parser acceptance/rejection for `script` blocks;
- AST debug output for declarations;
- lowering/HIR argument contract behavior;
- semantic diagnostics for invalid declarations;
- VM argv parsing and binding;
- Bash parser emission and standalone runtime behavior;
- bytecode dump stability;
- generated help output;
- VM/Bash parity for successes and errors;
- CLI usage interactions with existing `ds` commands;
- shell-sensitive argument safety;
- regression coverage for v0.1.0 through v0.4.0 behavior.

Do not use `docs/language.ds` as an executable fixture. It intentionally contains future syntax.

## Lexer tests

Add token tests for:

- `script`;
- `arg`;
- `option`;
- `flag`;
- `string`;
- `int`;
- `bool`;
- colon `:` if not already tokenized;
- equals `=` for defaults;
- braces and newlines inside `script` blocks.

Required cases:

```ds
script {
  arg app: string
  option target: string = "staging"
  option retries: int = 3
  flag force: bool = false
}
```

Edge cases:

- comments inside the script block;
- blank lines inside the script block;
- UTF-8 declaration comments near the block;
- file without trailing newline;
- CRLF input if supported by earlier tests.

Assertions:

- token output is stable;
- source locations are correct;
- new keywords do not break command words outside declaration contexts unless the parser intentionally reserves them.

## Parser tests

### Valid syntax

Parse and AST-print:

- empty `script {}` only if explicitly allowed; otherwise reject it consistently;
- one required positional arg;
- multiple positional args;
- string option with default;
- int option with default;
- bool option with default if supported;
- boolean flag with `false` default;
- comments and blank lines inside the block;
- script block followed by normal statements;
- script declarations used by later interpolation and command `$name` arguments.

Example:

```ds
script {
  arg app: string
  option target: string = "staging"
  option retries: int = 3
  flag force: bool = false
}

echo "Deploying {app} to {target}"
./deploy.sh $app $target
```

### Invalid syntax

Parser diagnostics should cover:

- missing `{` after `script`;
- missing `}` at end of block;
- unknown declaration keyword inside block;
- `arg` without name;
- `arg` without `:`;
- `arg` without type;
- `option` without default;
- `option` with missing `=`;
- `option` with missing default expression;
- `flag` without type;
- `flag` without default if the grammar requires it;
- declaration after the script block body accidentally parsed as command where a declaration was intended;
- nested `script` block inside `if` or normal block.

Assertions:

- each source-tied diagnostic uses `file:line:column: error: message`;
- diagnostics point at the malformed token or nearest helpful source location;
- parser recovery does not produce misleading backend output.

## AST debug tests

Add AST golden output for:

- script block with one arg;
- script block with arg/option/flag;
- script block followed by normal statements;
- script block with comments/blank lines around declarations;
- declarations with string/int/bool defaults.

Assertions:

- AST output preserves declaration order;
- AST output includes source locations or line/column data consistently with existing style;
- output contains no pointer addresses or nondeterministic data;
- existing AST golden tests remain stable unless deliberately updated.

## Lowering / HIR tests

Add direct or integration-style lowering tests for the script argument contract.

Required success cases:

- lower one `arg` declaration;
- lower multiple args in order;
- lower `option` declarations with string/int/bool defaults;
- lower `flag` declarations;
- script declaration names become known variables;
- declared names are usable in interpolation;
- declared names are usable as command `$name` arguments;
- no script block still lowers as before for old fixtures.

Required semantic errors:

- duplicate script block;
- script block after executable statement;
- duplicate `arg` names;
- duplicate `option` names;
- duplicate `flag` names;
- duplicate across declaration kinds;
- declaration conflicts with later top-level `let`;
- unsupported type;
- default type mismatch;
- bool flag with non-bool type;
- bool flag default `true` if not supported;
- unknown declaration form inside script block;
- script declaration shadows an existing top-level name if such a shape can parse.

Assertions:

- lowering owns these errors, not VM/Bash-specific code;
- `check`, `bytecode`, `run`, direct execution, and `emit bash` report equivalent source locations for lowering errors;
- no output artifact is written for invalid source.

## VM argv parsing tests

Add VM integration tests for:

### Success cases

- one required positional arg;
- multiple required positional args;
- omitted options use defaults;
- provided string option overrides default;
- provided int option overrides default;
- provided boolean flag sets value to true;
- omitted boolean flag remains false;
- options before positionals;
- options after positionals;
- mixed options/positionals;
- `--` ends option parsing;
- positional value beginning with `--` after `--` is accepted as data;
- help request exits `0` and does not execute body.

Example runtime checks:

```sh
ds examples/args.ds api
# Deploying api to staging

ds examples/args.ds api --target production --retries 5 --force
# Deploying api to production
# retries=5
# force enabled
```

### Error cases

- missing required positional arg;
- too many positional args;
- unknown option;
- option missing value at end of argv;
- option missing value before another option;
- duplicate option;
- duplicate flag;
- invalid int: `abc`;
- invalid int: `1abc`;
- invalid int: empty string;
- invalid int: lone `-` or `+`;
- int overflow if range checking is implemented;
- `--help` combined with invalid args should follow a documented rule, preferably help wins if present before validation of remaining args.

Assertions:

- success exits `0`;
- invalid args exit non-zero;
- error output is deterministic enough for tests;
- script body does not run after argument errors;
- help output does not run script body.

## Bash emission tests

Add golden tests for generated Bash.

Required generation checks:

- shebang and strict-mode header still exist;
- generated arg parser appears before body commands;
- internal helper names use the existing safe prefix;
- script-declared variables map to safe internal Bash variables;
- defaults are assigned safely;
- `--help` branch prints deterministic help and exits before body;
- invalid argument branches print deterministic errors and exit non-zero;
- normal body emission remains equivalent to v0.2/v0.3 behavior.

Required runtime checks for emitted Bash:

```sh

bash "$tmp/args.sh" api
bash "$tmp/args.sh" api --target production --retries 5 --force
bash "$tmp/args.sh" --help
```

Error cases should mirror VM tests:

- missing required positional arg;
- too many positional args;
- unknown option;
- missing option value;
- duplicate option/flag;
- invalid int;
- `--` behavior;
- shell-sensitive values treated as data.

Assertions:

- generated Bash is standalone and does not call `ds`;
- `bash -n` passes;
- stdout/stderr/exit status matches VM where practical;
- generated Bash contains no pointer addresses, timestamps, or temp paths in golden output.

## Bytecode dump tests

Add bytecode golden tests for scripts with argument declarations.

Required cases:

- script block only if allowed;
- script block plus echo body;
- script declarations used in interpolation;
- script declarations used as command `$name` args;
- script declarations used in `if force`;
- defaults visible in the dump in a deterministic way, or an explicit arg-contract section exists.

Assertions:

- bytecode output is deterministic;
- source comments/source locations point to declaration and body lines correctly;
- output contains no pointer addresses, timestamps, or absolute temp paths;
- bytecode dump should not require runtime argv to print.

## Help output tests

Test generated help for both VM and emitted Bash.

Required checks:

- usage line includes script basename;
- required args are listed in declaration order;
- options are listed in declaration order;
- flags are listed in declaration order;
- defaults are shown for options;
- boolean flags are described clearly;
- `--help` is listed;
- help exits `0`;
- body output is absent;
- VM and Bash help match exactly if practical, or match a documented normalized form.

Edge cases:

- long script filename;
- no options, only args;
- options only, no required args if allowed;
- declaration names with underscores if supported;
- defaults containing spaces or shell-sensitive characters.

## Diagnostics tests

Source-tied diagnostics should use:

```txt
file.ds:line:column: error: message
```

Runtime argument diagnostics may use a CLI-oriented format, but must be deterministic.

Required diagnostics:

### Source diagnostics

- malformed `script` block;
- missing declaration type;
- missing option default;
- unsupported type;
- duplicate declaration name;
- script block after body statement;
- second script block;
- default type mismatch;
- flag with unsupported type;
- declaration conflicts with `let`;
- script declaration used before declared only if the grammar allows such ordering.

### Runtime argv diagnostics

- missing required arg;
- extra positional arg;
- unknown option;
- missing option value;
- duplicate option;
- duplicate flag;
- invalid int;
- invalid use of `--` if any;
- help request with no body execution.

Assertions:

- invalid source prevents VM execution;
- invalid source prevents Bash output creation;
- invalid runtime args do not execute body commands;
- stderr contains the problematic arg name or declaration name where helpful;
- source diagnostics point to the declaration, not to a later backend use.

## Shell safety tests

Run the same safety matrix through VM and emitted Bash.

String arg/option values should be treated as data:

- `hello world`;
- `$HOME`;
- `$(echo hacked)`;
- `` `echo hacked` ``;
- `"quoted"`;
- `back\\slash`;
- `{braces}`;
- `semi;colon`;
- `star*glob`;
- empty string as option value if supported by CLI invocation.

Assertions:

- no command substitution executes;
- no glob expansion changes the value unexpectedly;
- output matches expected literal data;
- Bash and VM output match.

## CLI integration tests

Existing command usage must remain consistent.

Test:

```sh
ds --help
ds tokens args.ds
ds ast args.ds
ds check args.ds
ds bytecode args.ds
ds run args.ds api
ds args.ds api
ds emit bash args.ds -o out.sh
```

Usage/error cases:

- `ds run` with no file still reports usage;
- `ds bytecode` with no file still reports usage;
- `ds emit bash` with no `-o` still reports usage/error;
- direct script invocation passes args instead of rejecting extra argv;
- unknown top-level command still reports usage/error;
- `ds check args.ds extra` rejects extra CLI args rather than treating them as script args;
- `ds tokens args.ds extra` rejects extra CLI args;
- `ds ast args.ds extra` rejects extra CLI args;
- `ds bytecode args.ds extra` should follow the documented rule, preferably reject extra args.

## Edge cases

Implement or explicitly defer tests for:

- no script block: old scripts still run normally;
- empty script block if allowed or rejected;
- script block with only flags;
- script block with only options;
- script block with only required args;
- many declarations;
- long arg value;
- long option value;
- many CLI args;
- option value exactly `--`;
- positional value exactly `--` after separator;
- option-like positional after separator;
- repeated separator `-- --value`;
- negative integer option value such as `--retries -1`;
- plus-signed integer value such as `+5` if accepted;
- zero integer value;
- leading-zero integer value;
- integer overflow;
- defaults with spaces;
- defaults with shell-sensitive characters;
- declaration source locations after blank lines and comments;
- bytecode/help/golden output after no trailing newline;
- failure cleanup after partial argv parsing.

## Sanitizer and memory checks

