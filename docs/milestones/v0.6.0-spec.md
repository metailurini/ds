# v0.6.0 Spec — Imports / Includes

## Status

Planned.

## Goal

Add simple file imports so `ds` scripts can share small reusable definitions without introducing packages, public/private module systems, or named imports too early.

This milestone should support the smallest useful import shape:

```ds
import "./lib.ds"

echo "Deploying {app}"
```

A script with imports is complete only when the same resolved program behaves equivalently through:

```sh
ds check ./main.ds
ds bytecode ./main.ds
ds run ./main.ds
ds ./main.ds
ds emit bash ./main.ds -o ./main.sh
bash ./main.sh
```

Bash output must remain standalone: generated `.sh` files must contain all imported `ds` code needed at runtime and must not invoke `ds`.

## Motivation

After `v0.5.0` adds first-class script arguments, scripts will start to grow beyond single-file examples. Users need a way to share deployment helpers, constants, command snippets, and small reusable setup blocks across scripts.

Imports also force the compiler pipeline to become more realistic:

- source loading must know the importing file path;
- diagnostics must preserve the original file where an error occurred;
- lowering must merge multiple source files into one program while preserving scope rules;
- bytecode and VM execution must stay deterministic;
- Bash emission must bundle imported files into one standalone script.

This version should stay intentionally boring. It is not a package manager. It is local-file inclusion with cycle detection and deterministic ordering.

## Non-goals

This version does not include:

- package manager support;
- remote imports;
- versioned dependencies;
- named imports such as `from "./lib.ds" import deploy`;
- public/private visibility rules;
- namespaces or module objects;
- conditional imports;
- glob imports;
- directory imports;
- imports from environment variables or search paths;
- import-time side-effect controls;
- separate compilation or import caches across CLI invocations;
- standard library modules;
- user-facing functions unless an earlier milestone has already implemented them;
- command result capture or redirection sugar;
- emitted Bash that depends on `ds`.

If any of these are needed while implementing `v0.6.0`, record them as deferred items rather than expanding scope silently.

## Supported syntax

Add a top-level import statement:

```ds
import "./file.ds"
```

Requirements:

- import paths must be string literals;
- paths are resolved relative to the importing file's directory;
- imports are only valid at top level;
- imports should appear before executable statements;
- imports may appear after a `script { ... }` block only if the final design deliberately allows it and documents how script blocks merge;
- imports inside `if`, normal blocks, command statements, expressions, or string interpolation are invalid;
- imported files may themselves contain imports.

Recommended first-version restriction:

- one root program should have at most one effective `script { ... }` argument contract;
- imported helper files should usually not define their own `script { ... }` block;
- if an imported file contains a `script { ... }` block, lowering should reject it unless the milestone implementation explicitly defines merge rules.

The syntax catalog already lists simple imports as the `v0.6.0` target. Update `docs/language.ds` only if the accepted syntax differs from this spec.

## Import resolution rules

Resolution should be deterministic and local:

1. Parse the root file path from the CLI.
2. Resolve each import path relative to the physical directory of the file containing the import.
3. Normalize enough path spelling to detect duplicates and cycles reliably.
4. Load each normalized file once per root program.
5. Preserve first-import order for deterministic diagnostics, bytecode dumps, VM execution, and Bash bundling.

Minimum path behavior:

- `./lib.ds` relative to `scripts/main.ds` resolves to `scripts/lib.ds`.
- `../shared/lib.ds` is allowed if it resolves to a readable local file.
- bare `lib.ds` may be allowed as a relative path, but docs/examples should prefer `./lib.ds` for clarity.
- absolute paths may be accepted if source loading already supports them, but emitted source comments should remain readable.

Invalid paths should produce source-tied diagnostics at the import string location when possible.

## Import graph and cycle detection

The loader should maintain an import stack.

Required diagnostics:

- missing imported file;
- import path is not a string literal;
- malformed import syntax;
- import used outside top level;
- import appears after executable statements if this version requires imports-first ordering;
- import cycle, with a readable stack.

Example cycle diagnostic shape:

```txt
main.ds:1:8: error: import cycle detected: main.ds -> lib.ds -> main.ds
```

Exact wording may differ, but it must include enough path information to debug the cycle.

Duplicate imports should not execute or lower the same file twice. If two files import the same helper, the helper should be loaded once and its top-level definitions/statements should appear once in the effective program.

## Program composition model

`v0.6.0` should define imports as deterministic inclusion, not modules with namespaces.

Recommended model:

- imported files are processed before the importing file's executable statements;
- top-level `let` declarations from imported files are available to later imported files and to the importing file according to the resolved order;
- duplicate declarations across the combined program are rejected by lowering using the original source locations;
- block-local variables remain block-local after composition;
- imported top-level command statements execute as part of the composed program unless the implementation explicitly restricts helper files to declarations-only.

Because user-facing functions are not implemented yet, `v0.6.0` may mostly share constants and simple top-level setup statements. This is acceptable. The important architectural work is multi-file loading, source tracking, and backend bundling.

## Parser and AST behavior

Parser requirements:

- add `import` token/keyword support if the lexer uses keyword tokens;
- parse top-level `import "path"` statements;
- preserve source span for the `import` keyword and path literal;
- include import statements in stable AST debug output;
- keep command-mode parsing intact so command lines starting with ordinary words still parse as commands;
- reject or clearly diagnose malformed import syntax.

AST requirements:

- represent import statements distinctly from command statements;
- preserve import order;
- preserve path literal exactly enough for diagnostics and debug output;
- output must remain pointer-free and deterministic.

Malformed examples that should fail clearly:

```ds
import
import ./lib.ds
import name
if true {
  import "./lib.ds"
}
echo before
import "./later.ds"
```

The final case should fail if imports-first ordering is adopted.

## Source loading / compiler pipeline behavior

The CLI currently centralizes source loading, lexing, parsing, and lowering. `v0.6.0` should extend that shared path rather than adding backend-specific import loading.

Requirements:

- add a source/import loader that returns a composed frontend result or import graph;
- `check`, `bytecode`, `run`, direct execution, and `emit bash` must share the same import resolution and lowering behavior;
- `tokens` and `ast` may remain root-file debug commands, but their import behavior must be documented:
  - either they show only the root file;
  - or they have a deliberate import-aware mode.
- diagnostics from imported files must use the imported file's path, line, and column;
- no invalid import graph should write a partial Bash output file;
- import resolution must not depend on the current working directory except for resolving the root input path.

## Lowering / HIR behavior

Lowering owns shared multi-file semantics for both the VM and Bash emitter.

Requirements:

- lower a composed program into one backend-facing lowered program;
- preserve source file identity on lowered statements and expressions;
- reject duplicate top-level declarations across imported files and root file;
- reject unknown variables after imports are resolved;
- allow root code to reference imported top-level declarations;
- allow imported files to reference earlier imports according to deterministic order;
- reject cycles before lowering or during import graph construction;
- keep existing block-scope rules unchanged;
- do not make VM and Bash emitter perform separate import validation.

## VM behavior

The VM should execute the lowered composed program exactly once in deterministic order.

Requirements:

- imported files are executed once even if imported through multiple paths that normalize to the same file;
- source locations in runtime diagnostics point to the original file;
- command failure propagation remains unchanged;
- script argument parsing from `v0.5.0`, if present, happens once for the root program contract;
- imported variables are stored in the same top-level runtime scope as other top-level declarations after lowering approves them;
- runtime block scopes continue to work across imported statements.

## Bytecode behavior

`ds bytecode <file.ds>` should dump a deterministic composed bytecode program.

Requirements:

- bytecode output should include source comments or source-location data that distinguish files;
- import ordering should be stable;
- duplicate imports should not duplicate bytecode for the imported file;
- imported statements should appear before dependent root statements if that is the composition model;
- bytecode dumps should not include host-specific absolute paths unless the project intentionally uses them.

## Bash emission behavior

Bash emission should bundle imports into one standalone script.

Requirements:

- generated Bash must not call `ds`;
- imported file statements should be emitted once;
- source comments should identify the original file and line for bundled statements;
- strict mode remains enabled;
- generated helper names remain `__ds_` prefixed;
- root script argument parser from `v0.5.0`, if present, should be emitted once;
- invalid import graphs should not create or should remove partial output files;
- emitted Bash behavior should match VM behavior for success and failure cases.

Recommended generated comment shape:

```bash
# ds: lib.ds:1
__ds_name="api"
# ds: main.ds:3
echo "Deploying ${__ds_name}"
```

Exact formatting may differ, but the original source file should be visible.

## CLI behavior

Existing commands should continue to work:

```sh
ds tokens <file.ds>
ds ast <file.ds>
ds check <file.ds>
ds bytecode <file.ds>
ds run <file.ds> [args...]
ds <file.ds> [args...]
ds emit bash <file.ds> -o <file.sh>
```

`v0.6.0` may optionally add an import graph/debug command if it is helpful and explicitly documented, for example:

```sh
ds imports <file.ds>
```

If added, it should be debug-only and deterministic. It must not become a package-management feature.

## Documentation and examples

Add at least one import example, for example:

```txt
examples/import-main.ds
examples/import-lib.ds
```

Docs should explain:

- relative import resolution;
- load-once behavior;
- cycle diagnostics;
- duplicate declaration behavior;
- Bash bundling and standalone output;
- interaction with `script { ... }` from `v0.5.0`, especially whether imported files may declare script arguments.

Update `README.md`, `docs/architecture.md`, `docs/runtime.md`, `docs/language.ds`, and roadmap/status text only where they become outdated.

## Acceptance criteria

- [ ] `import "./file.ds"` parses at top level.
- [ ] imports resolve relative to the importing file.
- [ ] nested imports work.
- [ ] duplicate imports are loaded/emitted/executed once.
- [ ] import cycles fail with a readable import stack.
- [ ] missing imports fail with a source-tied diagnostic.
- [ ] imported top-level declarations are visible to the root file through shared lowering.
- [ ] duplicate declarations across files are rejected with useful locations.
- [ ] VM execution works for imported programs.
- [ ] Bash emission bundles imported programs into one standalone script.
- [ ] VM and Bash behavior match for supported import programs.
- [ ] bytecode dump is deterministic and source-mapped across files.
- [ ] invalid import graphs do not leave successful-looking Bash output artifacts.
- [ ] docs/examples describe import resolution and Bash bundling.
- [ ] deferred import/module features are recorded.

## Deferred items

- Named imports.
- Module namespaces.
- Public/private exports.
- Package manager and dependency versions.
- Remote imports.
- Import graph caching across CLI invocations.
- Standard library imports.
- Formatter support for imports.
- Import-aware editor tooling beyond existing `clangd` project support.
