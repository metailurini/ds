# v0.6.0 Test Plan — Imports / Includes

## Purpose

This test plan verifies the first local-file import feature for `ds`.

`v0.6.0` should allow a root script to import other `.ds` files, compose them deterministically, preserve source diagnostics across files, execute the result in the VM, and emit one standalone Bash script with all imported code bundled.

The plan is intentionally comprehensive because imports touch source loading, parser/AST output, lowering, bytecode, VM execution, Bash emission, diagnostics, CLI behavior, examples, and test-fixture organization.

## Test categories

The version should include tests for:

- lexer/parser support for import syntax;
- AST debug output for import statements;
- import path resolution relative to the importing file;
- nested imports;
- duplicate import load-once behavior;
- import cycle diagnostics;
- missing import diagnostics;
- top-level-only import restrictions;
- imports-first ordering if adopted by the implementation;
- lowering of composed multi-file programs;
- duplicate declaration errors across files;
- source-location preservation across imported files;
- bytecode dump determinism and source mapping;
- VM execution behavior;
- Bash bundling and standalone execution;
- VM/Bash parity for successful and failing programs;
- interaction with `v0.5.0` script arguments if implemented;
- regression coverage for `v0.1.0` through `v0.5.0` behavior.

Do not use `docs/language.ds` as an executable fixture. It intentionally contains future syntax.

## Baseline regression tests

Before implementing v0.6.0 tests, run:

```sh
make check
make test
make test-v0-5
```

If `v0.5.0` does not yet have a dedicated target at implementation time, use the latest existing target and update this plan during the version review.

After implementation, `make test` must run the new v0.6.0 suite in addition to prior suites.

Regression coverage must prove that older commands still work for non-import fixtures:

```sh
ds tokens examples/basic.ds
ds ast examples/basic.ds
ds check examples/basic.ds
ds bytecode examples/basic.ds
ds run examples/basic.ds
ds examples/basic.ds
ds emit bash examples/basic.ds -o /tmp/basic.sh

bash /tmp/basic.sh
```

If `v0.5.0` script args are implemented, include at least one prior args fixture in the regression run.

## Lexer and parser tests

### Valid syntax

Tokenize, parse, and AST-print:

```ds
import "./lib.ds"
```

Additional valid cases:

- multiple imports;
- imports with comments before and after;
- imports separated by blank lines;
- nested path strings such as `"./shared/lib.ds"`;
- parent path strings such as `"../shared/lib.ds"` if allowed;
- imports before a `script { ... }` block if the implementation allows it;
- imports after a `script { ... }` block if the implementation allows it and documents the ordering;
- imports followed by normal statements.

Assertions:

- token output is stable;
- AST output is stable and pointer-free;
- import statements are not printed as command statements;
- source locations point at the `import` keyword and string literal consistently with existing AST style.

### Invalid syntax

Parser diagnostics should cover:

```ds
import
import ./lib.ds
import name
import 123
import "./lib.ds" extra
if true {
  import "./lib.ds"
}
echo before
import "./later.ds"
```

The `import after statement` case should fail if imports-first ordering is required.

Assertions:

- diagnostics use `file:line:column: error: message`;
- malformed imports do not reach VM or Bash emission;
- invalid import syntax does not write a partial Bash output file.

## Import resolution tests

### Relative to importing file

Create fixtures where the root file and imported file are in different directories:

```txt
fixtures/imports_nested/main.ds
fixtures/imports_nested/shared/a.ds
fixtures/imports_nested/shared/b.ds
```

Cases:

- root imports `"./shared/a.ds"`;
- `a.ds` imports `"./b.ds"`;
- `b.ds` imports `"./common.ds"`;
- root can reference values defined through the nested chain if the composition model allows it.

Assertions:

- resolution is based on the importer directory, not the shell current working directory;
- running the same root file from another working directory succeeds;
- diagnostics for nested import failures point to the file containing the failing import.

### Missing file

Cases:

- missing direct import;
- missing nested import;
- unreadable file if portable to test;
- directory path instead of file if portable to test.

Assertions:

- command exits non-zero;
- diagnostic identifies the import location and missing/read-failed path;
- `check`, `run`, `bytecode`, direct execution, and `emit bash` fail consistently;
- directory imports do not produce successful-looking Bash output artifacts;
- `emit bash` leaves no successful-looking output artifact.

### Duplicate imports

Cases:

- root imports the same file twice;
- two imported files import the same shared helper;
- duplicate through path spellings that normalize to the same file, such as `"./shared.ds"` and `"./dir/../shared.ds"` if normalization supports it.

Assertions:

- imported top-level command statements execute once;
- imported `let` declarations appear once in bytecode and Bash output;
- bytecode dump is deterministic;
- generated Bash does not duplicate bundled statements.

## Import cycle tests

Create cycles:

- direct self-cycle: `a.ds` imports `a.ds`;
- two-file cycle: `a.ds` imports `b.ds`, `b.ds` imports `a.ds`;
- three-file cycle: `a -> b -> c -> a`;
- cycle reached from root through a nested import.

Assertions:

- command exits non-zero;
- diagnostic includes a readable import stack;
- source location points at the import that closes or reveals the cycle;
- all behavior-sensitive commands fail consistently;
- no Bash output artifact is left behind for failed emission.

## Lowering / HIR tests

Add direct or integration-style lowering tests for composed programs.

Success cases:

- root references a variable declared in imported file;
- imported file references a variable declared in an earlier imported file if allowed by ordering;
- imported variables work in interpolation;
- imported variables work as command `$name` arguments;
- nested import declarations are available to root after composition;
- no-import program lowers exactly as before.

Failure cases:

- duplicate top-level `let` in root and import;
- duplicate top-level `let` across two imports;
- root references an import that failed to load;
- imported file references a variable that is not visible by ordering;
- imported file contains a script block if the milestone forbids imported script blocks;
- multiple script blocks across root/imports if `v0.5.0` is implemented;
- unsupported future syntax inside imported file.

Assertions:

- lowering owns shared semantic errors;
- VM and Bash do not implement separate import-specific semantic checks;
- diagnostics preserve the original file path for imported-source errors;
- source spans survive through the lowered program.

## Bytecode tests

Add bytecode golden tests for:

- one import with one declaration;
- import with command statement;
- nested imports;
- duplicate import load-once;
- root plus imported statements mixed in deterministic order;
- source locations from multiple files;
- no host-specific unstable absolute paths unless that is intentionally documented.

Assertions:

- bytecode output is deterministic across runs;
- imported statements are present exactly once;
- source comments/locations identify the original source file;
- jump targets remain valid when imported `if`/`else` blocks are present.

## VM execution tests

Success cases:

- root echoes imported string;
- root compares imported int/string/bool values using existing conservative semantics;
- imported file executes a command statement once;
- nested imports execute in deterministic order;
- imported variables are available to root command `$name` arguments;
- runtime block scopes still isolate variables inside imported blocks;
- running from a different working directory still resolves relative imports from the importing file.

Failure cases:

- imported command exits non-zero and propagates the exit status;
- runtime diagnostic in imported file reports imported file location;
- duplicate import does not execute failing command twice;
- missing import fails before runtime execution begins.

If `v0.5.0` script args are implemented, include cases where:

- root script args are available to imported code only if the spec allows it;
- imported helper file cannot define a conflicting `script { ... }` block unless merge rules exist;
- `--help` does not execute imported top-level command statements.

## Bash emission tests

Golden and runtime tests should cover:

- generated Bash bundles one imported file;
- generated Bash bundles nested imports;
- duplicate imports are emitted once;
- source comments include original file names/lines;
- generated Bash is valid under `bash -n`;
- generated Bash runs without `ds` installed or available on `PATH`;
- generated Bash output matches VM output for supported fixtures;
- generated Bash preserves command failure behavior;
- generated Bash parser from `v0.5.0`, if present, is emitted once for the root script.

Safety cases:

- imported string containing spaces;
- imported string containing quotes;
- imported string containing dollar signs;
- imported string containing command-substitution-looking text;
- imported path names containing spaces, if portable for fixtures.

Invalid emission cases:

- missing import;
- cycle;
- duplicate declaration;
- unsupported future syntax in imported file;
- unwritable output path combined with valid imports.

Assertions:

- no invalid import graph produces successful-looking Bash output;
- generated Bash has no dependency on `ds`;
- generated Bash retains strict mode and `__ds_` prefixing.

## VM/Bash parity tests

For each success fixture, compare:

```sh
ds run main.ds [args...]
ds main.ds [args...]
ds emit bash main.ds -o main.sh
bash main.sh [args...]
```

Required parity fixtures:

- simple import;
- nested import;
- duplicate import;
- import with interpolation;
- import with command `$name` argument;
- import with `if`/`else`;
- import plus script args if `v0.5.0` is implemented.

For error fixtures, compare exit behavior and diagnostic shape where practical:

- missing import;
- import cycle;
- duplicate declaration;
- unsupported future syntax in imported file;
- imported command failure.

## CLI behavior tests

Commands to test:

```sh
ds check fixtures/imports_basic/main.ds
ds bytecode fixtures/imports_basic/main.ds
ds run fixtures/imports_basic/main.ds
ds fixtures/imports_basic/main.ds
ds emit bash fixtures/imports_basic/main.ds -o "$tmp/main.sh"
```

If `ds imports <file.ds>` or a similar debug command is added, test:

- usage errors;
- stable graph output;
- missing import diagnostics;
- cycle diagnostics;
- no execution of imported commands.

Also verify:

- `tokens` and `ast` documented behavior for imports;
- `--help` remains stable enough for previous tests;
- direct script execution still distinguishes script path from subcommand names.

## Diagnostics and source-location tests

Required diagnostics:

- parser error in root file;
- parser error in imported file;
- lowering error in imported file;
- runtime command failure location in imported file if surfaced;
- missing import path;
- cycle stack;
- duplicate declaration across files.

Assertions:

- all source-tied diagnostics use `file:line:column: error: message`;
- imported file paths are understandable and stable enough for tests;
- line/column data remains correct after comments and blank lines;
- errors from nested imports do not incorrectly point at the root file.

## Edge cases

Cover:

- empty imported file;
- comments-only imported file;
- imported file without trailing newline;
- deeply nested imports within a reasonable limit;
- duplicate imports through multiple parents;
- import path with `..`;
- import path with spaces if portable;
- very long import path if practical;
- many imported files;
- large imported string;
- imported file with CRLF line endings if existing source loader supports CRLF;
- imported file with future syntax rejected by current milestone;
- root file with no imports still behaves unchanged.

## Static boundary tests

Add checks that protect the architecture:

- VM and Bash backends consume lowered/composed programs, not raw unresolved AST import nodes;
- import resolution is centralized in the shared compiler pipeline, not duplicated in VM and Bash code;
- production code still does not depend on staged `libs/hashmap` names outside the documented boundary;
- generated Bash does not reference project source paths as executable dependencies;
- no new global mutable import cache leaks between CLI invocations.

These may be implemented as grep/static checks if the codebase size remains small.

## Documentation tests / review

Verify docs mention:

- import syntax;
- relative resolution from the importing file;
- load-once behavior;
- cycle diagnostics;
- Bash bundling;
- interaction with `script { ... }` from `v0.5.0`;
- non-goals such as package manager, named imports, remote imports, and module visibility.

Recommended scripted checks:

- README lists the import example command once added;
- `docs/language.ds` marks imports as `v0.6.0`;
- roadmap and milestone files agree on the version title;
- examples referenced by README exist.
