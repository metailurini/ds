# v0.7.0 Spec — Command Results and Redirection

## Status

Planned.

## Goal

Add the first safe command-result model and readable redirection syntax while
preserving the existing shell-native command statement behavior.

This milestone should let scripts inspect command output and exit status without
dropping into Bash-specific `$?`, command substitution, `2>&1`, temporary files,
or fragile quoting patterns.

The feature is complete only when the same behavior works through both direct VM
execution and emitted standalone Bash:

```sh
ds ./script.ds
ds run ./script.ds
ds emit bash ./script.ds -o ./script.sh
bash ./script.sh
```

## Motivation

Plain command statements are intentionally shell-like and fail-fast today:

```ds
npm test
```

That is still useful, but real automation frequently needs to run a command,
capture its output, inspect its exit code, and decide what to do next:

```ds
let result = run npm test

if result.failed {
  echo result.stderr
  exit result.code
}

echo result.stdout
```

Bash can do this, but the readable shape is easy to lose once stdout, stderr,
exit codes, and redirections are mixed together. `ds` should expose these as
boring language/runtime concepts while still emitting normal standalone Bash.

This version also introduces readable redirection sugar for plain command
statements:

```ds
npm run build &> "build.log"
```

instead of requiring users to remember Bash-specific forms such as
`> build.log 2>&1`.

## Non-goals

This version does not include:

- async/background jobs;
- pipelines as first-class result objects;
- command mocking framework;
- streaming callbacks;
- stdin redirection;
- here-docs;
- process substitution;
- terminal control;
- glob expansion changes;
- shell completion;
- user-facing functions;
- arrays/maps beyond whatever already exists;
- config files or environment-default behavior;
- a full standard-library command module;
- changing plain command statements away from fail-fast behavior;
- making emitted Bash depend on `ds` or the C runtime.

## Supported syntax

### Captured command execution

Add `run` as an expression form that captures a command result:

```ds
let result = run npm test
let branch = run git branch --show-current
```

The right-hand side after `run` uses the existing command-mode shape for simple
commands and command arguments:

```ds
let app = "api"
let result = run ./deploy.sh $app
```

Supported in v0.7.0:

- simple command words;
- quoted command arguments;
- `$name` command arguments using existing variable lookup rules;
- captured stdout, stderr, and exit code;
- non-fatal captured command failures.

Unsupported in v0.7.0 unless the implementation deliberately amends this spec:

- captured pipelines;
- captured commands with redirection syntax;
- nested `run` expressions inside another command argument;
- command result destructuring;
- command result arrays or structured streaming output.

### Command result fields

Command result values expose these fields:

```ds
result.stdout
result.stderr
result.code
result.ok
result.failed
```

Field behavior:

- `stdout` is the captured stdout as a string.
- `stderr` is the captured stderr as a string.
- `code` is the process exit code as an integer.
- `ok` is `true` when `code == 0`.
- `failed` is `true` when `code != 0`.

Field access is read-only in this milestone.

### Plain command redirections

Add readable redirection suffixes to plain command statements:

```ds
cmd |> "out.txt"
cmd |>> "out.txt"
cmd !> "err.txt"
cmd !>> "err.txt"
cmd &> "all.txt"
cmd &>> "all.txt"
```

Meaning:

| `ds` syntax | Bash equivalent | Meaning |
| --- | --- | --- |
| `|>` | `>` | redirect stdout, truncate |
| `|>>` | `>>` | redirect stdout, append |
| `!>` | `2>` | redirect stderr, truncate |
| `!>>` | `2>>` | redirect stderr, append |
| `&>` | `> file 2>&1` | redirect stdout and stderr, truncate |
| `&>>` | `>> file 2>&1` | redirect stdout and stderr, append |

Redirection targets in v0.7.0 should be string literals or string-valued simple
expressions if the existing expression model can support them cleanly. Prefer a
conservative implementation that starts with quoted string targets and clear
diagnostics for unsupported expressions.

Plain redirected commands remain fail-fast. A redirected command that exits
non-zero should still make VM execution fail and should still make emitted Bash
fail under the project’s strict-mode behavior.

### Examples

```ds
let test = run npm test

if test.failed {
  echo "tests failed"
  echo test.stderr
  exit test.code
}

echo test.stdout
```

```ds
npm run build &> "build.log"
echo "build output written to build.log"
```

```ds
let branch = run git branch --show-current

if branch.ok {
  echo "branch={branch.stdout}"
}
```

## CLI behavior

Existing CLI commands continue to work:

```sh
ds tokens <file.ds>
ds ast <file.ds>
ds check <file.ds>
ds bytecode <file.ds>
ds run <file.ds> [script args...]
ds <file.ds> [script args...]
ds emit bash <file.ds> -o <file.sh>
```

Requirements:

- `ds check` validates `run`, command-result field access, and redirection
  syntax without executing commands.
- `ds tokens` shows stable tokens for the new syntax.
- `ds ast` shows `run` expressions, result-field expressions, and redirections
  in a stable pointer-free form.
- `ds bytecode` shows deterministic bytecode for captured command execution,
  field access, and redirected commands.
- `ds run` and direct script execution execute captured commands and redirected
  commands with the same semantics.
- `ds emit bash` writes standalone Bash that behaves like the VM for supported
  success and failure cases.

No new CLI subcommand is required for this milestone.

## Lexer and parser behavior

Lexer requirements:

- recognize `run` as a keyword or context-sensitive expression starter;
- recognize `.` for field access if it is not already tokenized;
- recognize redirection operators: `|>`, `|>>`, `!>`, `!>>`, `&>`, `&>>`;
- preserve source locations for each new token/operator.

Parser requirements:

- parse `let name = run command ...` as a captured command expression;
- parse field access expressions such as `result.stdout`;
- parse result fields in conditions and interpolation where expression support
  allows it;
- parse redirection suffixes on plain command statements;
- preserve source spans for the `run` keyword, command words, field names,
  redirection operator, and redirection target;
- reject malformed `run` expressions clearly;
- reject malformed redirections clearly;
- keep existing command-mode parsing intact for non-redirection commands.

Malformed examples should fail clearly:

```ds
let r = run
let r = run |> "out.txt"
let r = run npm test &> "out.txt"
let r = run npm test |> "out.txt"
let r = run npm test | "grep"
echo result.missing
npm test &>
npm test &> 123
npm test &> "a" &> "b"
```

## AST behavior

AST debug output must be stable, deterministic, and pointer-free.

Required representation updates:

- captured command expression node;
- command result field access expression node;
- command statement redirection metadata;
- source locations for new nodes and operators.

AST output should make it obvious whether a command is:

- a plain fail-fast command statement;
- a captured `run` expression;
- a redirected plain command statement.

## Lowering / HIR behavior

Lowering owns shared semantics for both VM and Bash emission.

Requirements:

- lower captured commands into backend-facing HIR nodes;
- lower result-field access into backend-facing HIR nodes;
- lower command redirections into backend-facing command metadata;
- type or shape-check command-result fields;
- reject unknown result fields;
- reject field access on non-result values when known;
- reject unsupported captured command forms;
- reject unsupported redirection targets;
- preserve source locations for diagnostics and bytecode output;
- avoid duplicating command-result semantic checks independently in VM and Bash
  emission.

The VM and Bash emitter may contain backend-specific rendering/execution code,
but they should consume the same lowered command/result/redirection model.

## Runtime and VM behavior

### Process result representation

Add an internal command result value or equivalent runtime representation with:

- owned stdout string;
- owned stderr string;
- integer exit code;
- derived boolean `ok`;
- derived boolean `failed`.

Ownership requirements:

- captured stdout/stderr buffers must be freed exactly once;
- copying/moving command-result values must be explicit;
- runtime cleanup must work under existing ASAN/UBSAN targets;
- large-but-reasonable output should not corrupt memory or truncate silently.

### Captured commands

VM captured command behavior:

- run the command without treating non-zero exit as fatal;
- capture stdout and stderr separately;
- preserve exit code;
- bind the result to the target variable through normal `let` semantics;
- expose fields through the normal expression evaluator;
- support command `$name` arguments using existing variable-to-string behavior;
- avoid shell injection by executing commands through the project’s process
  boundary rather than by concatenating an untrusted shell string, if practical.

If the implementation still uses a shell boundary for portability reasons, the
decision must be documented and shell-safety tests must be added.

### Plain redirected commands

VM redirected command behavior:

- redirect stdout/stderr according to the operator;
- create or truncate/append target files as specified;
- propagate non-zero command exit as the command statement exit;
- keep existing plain command fail-fast behavior;
- produce clear diagnostics for file-open failures.

### Truthiness and conditions

`result.ok` and `result.failed` should be booleans and should work in `if`
conditions:

```ds
if result.failed {
  echo "failed"
}
```

`result.code` should participate in existing comparison semantics. Because the
current comparison model is still conservative/string-style, any numeric caveat
must be documented if it affects command-result examples.

## Bytecode behavior

`ds bytecode <file.ds>` must remain deterministic.

Recommended bytecode shapes may include instructions such as:

```txt
RUN_CAPTURE
GET_FIELD stdout
GET_FIELD stderr
GET_FIELD code
GET_FIELD ok
GET_FIELD failed
RUN_CMD_REDIRECT
```

Exact names are not required, but bytecode output should clearly distinguish:

- plain commands;
- captured commands;
- redirected commands;
- field access.

Source comments/location annotations should continue to identify the original
file and line. Imported files from `v0.6.0`, if already implemented, must retain
their source identity.

## Bash emission behavior

Emitted Bash must be standalone and behaviorally equivalent for supported forms.

Requirements:

- generated Bash must not call `ds`;
- generated Bash may define `__ds_` helper functions for capturing stdout,
  stderr, and exit code;
- helpers must use `__ds_`-prefixed names;
- helper temporary files/directories must be safely created and cleaned up;
- captured non-zero command exits must not terminate the generated script before
  the result is inspected;
- plain command statements, including redirected commands, should remain
  fail-fast under strict behavior;
- redirection emission must match the documented Bash equivalents;
- string/argument quoting must avoid command injection from `ds` variables;
- generated Bash must pass `bash -n`;
- failed `ds emit bash` should not leave a successful-looking partial output
  artifact.

Recommended generated helper shape is implementation-defined, but the emitted
script should remain readable enough for debugging and include source comments
for user statements.

## Diagnostics

Diagnostics must use the standardized shape:

```txt
file.ds:line:column: error: message
```

Required diagnostics include:

- `run` without a command;
- unsupported captured command form;
- unknown result field;
- field access on a non-result value when known;
- redirection operator without a target;
- unsupported redirection target type;
- duplicate redirection suffix;
- file-open failure for redirected output in VM mode;
- unsupported backend lowering state, if encountered;
- any Bash emission failure with no stale output artifact.

Diagnostics should point to the most helpful token: the `run` keyword, the
unknown field name, the redirection operator, or the redirection target.

## Completion review

- Implementation summary: `run` expressions lower to a shared command-result representation consumed by bytecode/VM execution and standalone Bash emission. Plain command redirection metadata lowers with the command statement and supports `|>`, `|>>`, `!>`, `!>>`, `&>`, and `&>>`.
- VM/Bash parity notes: v0.7.0 fixtures compare captured success/failure, captured stderr, command `$name` arguments, `{result.field}` interpolation, import interaction, script-arg interaction, and redirected output files between VM and emitted Bash.
- Diagnostics notes: malformed `run`, unsupported captured redirection/pipeline forms, legacy shell redirection operators, duplicate/missing/bad redirection targets, redirection-open failures, unknown `$name` arguments, missing field names, unknown command-result fields, and known non-result field receivers fail before execution or Bash emission with source-tied diagnostics.
- Runtime ownership notes: command-result values own separate stdout/stderr buffers and copy/free through the normal `DsValue` path; the v0.7.0 C unit covers take/copy/free, string rendering, truthiness, and large buffer copies.
- Tests added: `tests/v0_7/run.sh`, capture/redirection/diagnostic/parity/helper fixtures, golden token/AST/bytecode/Bash outputs, and C units for command-result ownership plus lowered command-result/redirection shape. Edge coverage includes command-not-found capture, executable paths with spaces, result block scope, stale Bash emit cleanup, and source-located redirection-open failures.
- Known limitations: captured pipelines, captured redirection, stdin redirection, command timeouts, here-docs, process substitution, streaming callbacks, and richer command-result/string helpers remain deferred. Redirection targets are still conservative string literals with interpolation validation.
- Deferred follow-up: add a richer command pipeline model, command-result string helpers such as trimming, and broader process/runtime APIs in later milestones.
