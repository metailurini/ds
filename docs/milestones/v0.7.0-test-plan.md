# v0.7.0 Test Plan — Command Results and Redirection

## Purpose

This test plan verifies the first command-result and redirection feature set.

`v0.7.0` should let scripts capture command stdout/stderr/exit code through
`run`, inspect command-result fields, keep plain commands fail-fast, and use
readable redirection syntax. Every supported behavior must work in both direct
VM execution and emitted standalone Bash.

The plan is intentionally broad because command execution touches the lexer,
parser, AST output, lowering, bytecode, VM process handling, Bash helper
generation, diagnostics, runtime ownership, generated-script portability, and
VM/Bash parity.

## Test categories

The version should include tests for:

- lexer support for `run`, `.`, and redirection operators;
- parser and AST support for captured commands, field access, and redirected
  commands;
- lowering/HIR semantics for command-result values and redirection metadata;
- bytecode output for captured commands, field access, and redirected commands;
- VM execution of successful and failing captured commands;
- separate stdout/stderr capture;
- command-result field access: `stdout`, `stderr`, `code`, `ok`, `failed`;
- plain command fail-fast behavior remains unchanged;
- redirected plain command file behavior;
- Bash emission and `bash -n` validity;
- VM/Bash parity for success and failure fixtures;
- diagnostics for malformed syntax and unsupported forms;
- runtime ownership under ASAN/UBSAN where available;
- regression coverage for `v0.1.0` through `v0.6.0` behavior.

Do not use `docs/language.ds` as an executable fixture. It intentionally
contains future syntax.

## Lexer tests

Tokenize valid syntax:

```ds
let result = run npm test
echo result.stdout
npm run build |> "out.txt"
npm run build |>> "out.txt"
npm run build !> "err.txt"
npm run build !>> "err.txt"
npm run build &> "all.txt"
npm run build &>> "all.txt"
```

Assertions:

- `run` is tokenized deterministically according to the implementation’s keyword
  or contextual-token strategy;
- `.` appears as field access punctuation, not as part of an identifier;
- all six redirection operators are distinct and preserve source locations;
- existing command words containing punctuation still tokenize as before where
  they do not conflict with redirection operators;
- comments and blank lines do not affect token locations.

Edge cases:

- operators next to whitespace and no whitespace: `cmd&>"x"` if allowed or a
  clear diagnostic if spacing is required;
- similar but invalid operators: `>`, `>>`, `2>`, `|`, `||`, `&&` if not yet
  supported by the language;
- field access after string/int literals should tokenize consistently even if
  later rejected semantically.

## Parser and AST tests

### Captured command expressions

Parse and AST-print:

```ds
let result = run printf "hello"
let branch = run git branch --show-current
let deployed = run ./deploy.sh $app
```

Assertions:

- captured commands are not parsed as plain command statements;
- command words and `$name` arguments preserve order;
- source locations point to `run` and command words;
- AST output is stable and pointer-free.

### Field access

Parse and AST-print:

```ds
echo result.stdout
echo result.stderr
echo result.code
if result.ok {
  echo "ok"
}
if result.failed {
  echo "failed"
}
```

Assertions:

- field access is represented distinctly from normal identifiers;
- field source locations identify the field name;
- field access works in conditions, command arguments, and interpolation if
  interpolation supports the expression shape by implementation time.

### Redirection syntax

Parse and AST-print all supported redirection operators:

```ds
printf "hello" |> "out.txt"
printf "hello" |>> "out.txt"
sh -c "echo err >&2" !> "err.txt"
sh -c "echo err >&2" !>> "err.txt"
sh -c "echo all; echo err >&2" &> "all.txt"
sh -c "echo all; echo err >&2" &>> "all.txt"
```

Assertions:

- redirection metadata is attached to the command statement;
- targets preserve source locations;
- AST output clearly identifies truncate vs append and stdout/stderr/combined;
- non-redirected command AST output is unchanged.

### Invalid parser forms

Parser diagnostics should cover:

```ds
let r = run
let r = run |> "out.txt"
let r = run npm test &> "out.txt"
let r = run npm test |> "out.txt"
npm test &>
npm test |>
npm test !>
npm test &> "a" &> "b"
```

Assertions:

- commands exit non-zero;
- diagnostics use `file:line:column: error: message`;
- diagnostics point to `run`, the operator, or the missing target location;
- invalid input does not reach VM execution or Bash emission;
- failed Bash emission leaves no successful-looking output file.

## Lowering / HIR tests

Add direct unit tests if practical, or integration tests through `ds check`,
`ds bytecode`, `ds run`, and `ds emit bash` if the lowered representation is not
exposed enough for unit assertions.

Success cases:

- `let r = run printf "hello"` lowers to a command-result value;
- `r.stdout`, `r.stderr`, `r.code`, `r.ok`, and `r.failed` lower to field access;
- field access works after variable lookup;
- redirected command metadata lowers with correct kind and append/truncate flag;
- command `$name` arguments inside `run` reuse the existing command argument
  lowering path;
- source locations are preserved for bytecode and diagnostics.

Failure cases:

- unknown result field: `r.missing`;
- field access on known string/int/bool values if the checker can know this;
- captured command with unsupported redirection;
- captured command with unsupported pipeline;
- redirection target with unsupported expression kind;
- duplicate redirection suffix;
- unknown command variable inside captured command.

Assertions:

- VM and Bash emitter consume the same lowered shape;
- semantic validation is not independently duplicated in both backends;
- diagnostics point to the field/operator/target instead of a generic statement
  location.

## Bytecode tests

Golden-test deterministic bytecode for:

- captured stdout command;
- captured failing command;
- field access for every field;
- branch on `result.ok`;
- branch on `result.failed`;
- redirected stdout truncate/append;
- redirected stderr truncate/append;
- redirected combined truncate/append;
- command result declared in imported file if v0.6.0 is implemented.

Assertions:

- bytecode distinguishes plain commands from captured commands;
- bytecode distinguishes all field names;
- bytecode distinguishes redirection kind and append/truncate mode;
- source locations remain stable after blank lines/comments;
- bytecode output does not include host-specific temporary paths;
- bytecode is deterministic across repeated runs.

## VM execution tests

### Captured successful command

Fixture:

```ds
let r = run printf "hello"
echo r.stdout
echo r.stderr
echo r.code
if r.ok {
  echo "ok"
}
```

Assertions:

- stdout field equals `hello`;
- stderr field is empty;
- code field is `0`;
- `ok` is true;
- `failed` is false.

### Captured stderr

Use a portable helper command such as:

```ds
let r = run sh -c "printf err >&2"
```

Assertions:

- stdout field is empty;
- stderr field equals `err`;
- code field is `0`;
- command itself does not print captured stderr to the script stderr unless the
  script explicitly echoes it.

### Captured non-zero exit

Fixture:

```ds
let r = run sh -c "printf out; printf err >&2; exit 7"
echo r.stdout
echo r.stderr
echo r.code
if r.failed {
  echo "failed"
}
```

Assertions:

- script exits `0` if it does not explicitly exit non-zero;
- stdout/stderr fields are captured;
- code field is `7`;
- `failed` is true;
- `ok` is false.

### Plain command fail-fast still holds

Fixture:

```ds
sh -c "exit 7"
echo "unreachable"
```

Assertions:

- VM exits non-zero;
- `unreachable` is not printed;
- behavior matches pre-v0.7 command-statement semantics.

### Command arguments

Fixture:

```ds
let word = "hello world"
let r = run printf $word
echo r.stdout
```

Assertions:

- `$word` is passed as one argument;
- spaces are preserved;
- quotes, dollar signs, backticks, and command-substitution-looking strings are
  not reinterpreted unsafely.

### Large output

Capture output larger than one typical pipe buffer or stdio buffer when portable,
or at least larger than the project’s small-string starting capacity.

Assertions:

- output is not truncated;
- output does not corrupt memory;
- ASAN/UBSAN pass where available.

## Redirection VM tests

Use temporary directories created by the test runner.

### Stdout truncate and append

Fixtures:

```ds
printf "one" |> "out.txt"
printf "two" |> "out.txt"
```

```ds
printf "one" |> "out.txt"
printf "two" |>> "out.txt"
```

Assertions:

- truncate overwrites;
- append appends;
- stdout is not printed to script stdout;
- command exit code still controls script success.

### Stderr truncate and append

Fixtures use `sh -c "printf err >&2"`.

Assertions:

- stderr output goes to target file;
- script stderr remains empty for successful command;
- append/truncate behavior is correct.

### Combined output

Fixtures use a command that writes both stdout and stderr.

Assertions:

- both streams are redirected to the same file;
- relative ordering is as deterministic as practical for the chosen helper
  command;
- append/truncate behavior is correct;
- generated Bash uses the intended `2>&1` shape or equivalent.

### Redirection failure

Cases:

- target directory does not exist;
- target path is a directory;
- permission failure if portable in the test environment.

Assertions:

- VM exits non-zero;
- diagnostic is clear;
- plain command failure semantics remain fail-fast.

## Bash emission tests

For every supported success fixture:

```sh
ds emit bash fixture.ds -o /tmp/fixture.sh
bash -n /tmp/fixture.sh
bash /tmp/fixture.sh
```

Assertions:

- generated Bash is standalone and does not invoke `ds`;
- helper names use the `__ds_` prefix;
- helper temp files/directories are cleaned up;
- captured command failures do not terminate the generated script before field
  inspection;
- plain redirected command failures remain fail-fast;
- redirection operators emit the correct Bash equivalents;
- source comments are preserved around user statements;
- generated Bash behavior matches VM behavior.

Golden-test generated Bash for at least:

- one captured command fixture;
- one captured failure fixture;
- one combined redirection fixture;
- one fixture that uses command `$name` arguments safely.

## VM/Bash parity tests

Run the same fixture in VM mode and emitted Bash mode, compare:

- stdout;
- stderr where deterministic;
- exit status;
- files created by redirection;
- no unexpected temporary files left behind.

Parity fixtures should cover:

- captured success;
- captured stderr;
- captured exit code `7`;
- branch on `result.ok`;
- branch on `result.failed`;
- stdout redirect truncate;
- stdout redirect append;
- stderr redirect;
- combined redirect;
- command argument with spaces/quotes/dollar signs;
- script args interaction if `v0.5.0` is implemented;
- import interaction if `v0.6.0` is implemented.

## Diagnostics tests

Diagnostics must use:

```txt
file.ds:line:column: error: message
```

Required diagnostic fixtures:

- `run` without command;
- `run` with unsupported redirection;
- `run` with unsupported pipeline;
- unknown result field;
- field access on non-result value when known;
- field access missing field name: `result.`;
- redirection missing target;
- redirection target wrong type;
- duplicate redirection suffix;
- redirection file-open failure in VM mode;
- unknown `$name` inside captured command;
- Bash emission failure leaves no successful-looking output artifact.

Assertions:

- command exits non-zero;
- diagnostic points to the most helpful token;
- parser/lowering failures do not execute commands;
- behavior-sensitive commands fail consistently: `check`, `run`, direct script,
  `bytecode`, and `emit bash` where applicable.

## Runtime ownership and sanitizer tests

Add C unit tests for command-result/runtime process helpers if they exist as
separate APIs.

Suggested unit tests:

- initialize/free empty command result;
- set/copy/take stdout and stderr buffers;
- copy command result with owned strings;
- free command result twice only if API explicitly supports clear/reuse, not
  double-free live values;
- clear/reuse command result;
- large stdout/stderr buffer growth;
- failure path cleanup when one allocation fails, where practical.

Run:

```sh
make asan
make ubsan
```

If allocation-failure hooks do not exist, record the gap in the completion
review instead of inventing a large test-only allocator framework.

## Shell-safety tests

Use values that look dangerous but should be treated as data:

```txt
hello world
"quoted"
'single quoted'
$HOME
$(echo hacked)
`echo hacked`
semi;colon
star*
back\slash
newline-containing values if supported
```

Assertions:

- VM passes values as one command argument where `$name` is used;
- emitted Bash preserves the same argument boundaries;
- command substitution-looking content is not executed;
- redirection targets are quoted safely;
- generated Bash does not introduce unprefixed helper variables.

## Edge cases

Cover at least:

- empty stdout and stderr;
- stdout without trailing newline;
- stderr without trailing newline;
- output with multiple lines;
- output with NUL bytes if the runtime explicitly supports or rejects them;
- command exits `0`, `1`, `2`, and `7`;
- command not found;
- executable path with spaces if portable to create in a temp directory;
- result variable used after nested block;
- result variable declared inside block does not leak outside;
- sibling blocks can use result variables according to existing scope rules;
- redirection target file already exists;
- redirection target parent directory missing;
- append to empty file;
- combined redirection with stdout-only, stderr-only, and mixed output;
- repeated captured commands do not reuse stale stdout/stderr/code;
- many captured commands in one script;
- captured command after imported definitions if imports are implemented;
- captured command after script-arg binding if CLI args are implemented.
