# v0.8.0 Spec — Cleanup: Command Model and Bash Parity

## Status

Planned.

## Goal

Repay command-model technical debt after `v0.5.0` script arguments,
`v0.6.0` imports, and `v0.7.0` command-result/redirection support.

This is a cleanup milestone. It should preserve the supported user-facing
language while making command parsing, lowering, bytecode generation, VM process
execution, Bash helper generation, diagnostics, and parity tests easier to
reuse before `v0.9.0` functions and later data/control-flow features.

The most important outcome is boring consistency:

```txt
one command shape
one command-word validation path
one command-result field model
one process execution abstraction
one VM/Bash parity fixture style
one failure/diagnostic contract
```

## Motivation

The roadmap reserves every fourth version for cleanup. `v0.8.0` closes the
second wave:

```txt
v0.5.0  feature foundation: script arguments
v0.6.0  feature expansion: local imports
v0.7.0  feature integration: command results and redirection
v0.8.0  cleanup: command model and Bash parity
```

The implementation now has useful behavior, but the command path is spread over
several places:

- `include/ds.h` exposes AST, lowered forms, runtime values, backend entrypoints,
  and utility declarations in one wide header.
- `src/parser.c` owns command-mode parsing and redirection suffix parsing.
- `src/lower.c` owns command-word validation, field type checks, interpolation
  validation, script-arg symbols, import composition semantics, and backend-facing
  command metadata.
- `src/vm.c` owns bytecode construction, bytecode printing, runtime scopes,
  command execution, command capture, redirection handling, result-field reads,
  string interpolation, script-arg parsing, and process diagnostics.
- `src/bash_emit.c` owns Bash quoting, command-word emission, redirection emission,
  command capture helpers, result-field rendering, helper dependency detection,
  and generated artifact behavior.
- `tests/v0_7/run.sh` contains useful parity helpers that should become shared
  instead of being copied by later command-heavy versions.

That shape was acceptable while features were small, but functions, arrays/maps,
loops, and future pipelines would amplify every duplicated command rule. This
milestone should clean the current behavior without inventing new syntax.

## Non-goals

This version does not include:

- functions;
- loops;
- arrays or maps as user-facing values;
- pipelines;
- background jobs;
- stdin redirection;
- here-docs;
- command substitution syntax beyond existing `run` capture;
- command mocking;
- a public standard-library command module;
- changing plain commands away from fail-fast behavior;
- adding new command-result fields;
- allowing redirection on captured `run` commands;
- changing generated Bash to depend on `ds` or the C runtime.

Bug fixes and diagnostic improvements are allowed when they preserve the
documented v0.1.0–v0.7.0 behavior or make rejected forms fail earlier and more
consistently.

## Starting point review

This milestone starts after `v0.7.0` has implemented and tested:

- `run` command capture;
- `stdout`, `stderr`, `code`, `ok`, and `failed` result fields;
- command-result field interpolation such as `{result.stdout}`;
- plain command redirection operators `|>`, `|>>`, `!>`, `!>>`, `&>`, `&>>`;
- VM/Bash parity for representative capture and redirection fixtures;
- source-located redirection-open diagnostics;
- stale emitted-Bash artifact cleanup on failed emission.

Observed cleanup inventory from the current codebase:

- `DsWordVec` and `DsRedirect` are copied through AST, lowered statements,
  bytecode instructions, the VM, and Bash emission. A shared command data model
  would make ownership and spans clearer.
- Command-result field knowledge appears in lowering, VM field execution,
  VM interpolation, runtime value conversion, and Bash emission. A tiny shared
  field descriptor/helper would reduce drift.
- Command-word validation lives in lowering, but command-word rendering and
  command-result field expansion are duplicated in VM and Bash backends.
- `src/vm.c` contains both bytecode compilation and VM execution, plus process
  launch/capture/redirection code. The file is large enough that small internal
  extraction would improve readability.
- Process execution does not yet match the `docs/runtime.md` direction of a
  clear `DsProcessResult`-style wrapper. Captured and plain commands share much
  behavior but still use separate low-level paths.
- Bash command-capture helper emission is mostly standalone and correct, but
  helper dependency tracking should be simple and explicit before more helpers
  are added.
- The test infrastructure has shared shell assertions, but VM/Bash parity helpers
  are still version-local in `tests/v0_7/run.sh`.
- CLI load/parse/lower sharing is improved, but artifact cleanup and diagnostic
  consistency should stay locked down with tests across `check`, `bytecode`,
  `run`, direct execution, and `emit bash`.

## Cleanup principles

Cleanup must follow these rules:

- Prefer shared internal helpers over new user-facing behavior.
- Keep refactors small and behavior-preserving.
- Preserve VM/Bash parity for every supported feature.
- Preserve standalone generated Bash.
- Preserve existing source locations or improve them deliberately.
- Keep unsupported roadmap syntax rejected clearly.
- Update docs only to match real behavior or to record cleanup architecture.
- Record deferred debt instead of silently leaving ambiguous TODOs.
- Run the full regression suite after every meaningful boundary change.

## User-facing behavior contract

The following commands must continue to work exactly as documented:

```sh
ds tokens <file.ds>
ds ast <file.ds>
ds check <file.ds>
ds bytecode <file.ds>
ds run <file.ds> [script args...]
ds <file.ds> [script args...]
ds emit bash <file.ds> -o <file.sh>
```

The supported language remains the v0.1.0–v0.7.0 subset:

- comments, variables, strings, integers, booleans, and simple expressions;
- string interpolation for `{name}` and supported command-result fields;
- `if`/`else` and block scopes;
- shell-like command statements with `$name` arguments;
- script argument declarations;
- local imports;
- `run` command-result capture;
- command-result field access;
- plain command redirection suffixes.

No new syntax is required for `v0.8.0`.

## Required cleanup work

### 1. Central command representation

Introduce or formalize a reusable internal command representation for simple
commands.

The representation should make these pieces explicit:

- ordered command words;
- per-word source spans;
- whether the command is plain or captured;
- optional redirection metadata for plain commands;
- redirection operator span and target span;
- ownership and destruction rules.

The exact C API is left to implementation, but code should move toward a shape
similar to:

```c
typedef struct {
    DsWordVec words;
    DsRedirect redirect;
    DsSpan span;
} DsCommand;
```

Requirements:

- AST/debug output may keep syntax-oriented structures if that is clearer, but
  lowered/backed-facing code should not duplicate command ownership logic.
- Lowering, bytecode generation, VM execution, and Bash emission should consume
  the same lowered command shape where practical.
- Command cloning/freeing should be centralized.
- Source spans for command words, redirections, and targets must survive the
  refactor.

### 2. Shared command-word validation and rendering contract

Command words currently have shared validation but backend-specific expansion.
Refactor toward one documented contract:

- literal command words are passed as literal argv words;
- quoted command words decode to one argv word;
- `$name` expands to one argv word using the ds runtime value string;
- `result.stdout`, `result.stderr`, `result.code`, `result.ok`, and
  `result.failed` expand to one argv word where command-mode field usage is
  supported;
- unsupported field access, missing field names, unknown variables, unsupported
  operators, and future pipeline syntax fail before backend execution/emission.

VM and Bash emission may still implement their own rendering mechanics, but the
accepted/rejected inputs and diagnostics should be driven by the same lowered
semantics.

### 3. Shared command-result field descriptors

Create one small internal helper for supported command-result fields.

It should answer:

- is this field known?;
- what kind does it produce: string, int, or bool?;
- what diagnostic should be used for an unknown field?;
- how should bytecode/Bash debug output print the field name?

Requirements:

- Lowering must use this helper for type/kind checks.
- VM field execution and VM string interpolation should not drift from lowering.
- Bash emission should use the same supported field list.
- Tests should catch adding a field in one backend but not the other.

### 4. Process execution wrapper cleanup

Clean the C process path behind plain and captured command execution.

The implementation may introduce a small internal process API, for example:

```c
typedef struct {
    DsWordVec words;
    DsRedirect redirect;
    bool capture;
    DsSpan span;
} DsProcessSpec;

typedef struct {
    DsString stdout_text;
    DsString stderr_text;
    int64_t code;
} DsProcessResult;
```

The exact names are not required, but the cleaned design must make these rules
obvious:

- plain commands stream output and remain fail-fast;
- captured commands do not stream stdout/stderr and never make non-zero exit
  status fatal by themselves;
- command launch failures are represented consistently;
- redirection file-open failures are source-located diagnostics;
- resources are closed/freed on every error path;
- the wrapper is VM-internal or runtime-internal only; emitted Bash stays
  standalone and does not call the C runtime.

### 5. Bash helper generation cleanup

Clean Bash emission helper management for command capture and future helpers.

Requirements:

- Helper names remain under the `__ds_` prefix.
- Helpers are emitted only when used.
- Generated Bash remains standalone.
- Capture helpers preserve separate stdout/stderr and exit code behavior.
- Plain command failure reporting remains consistent with strict-mode behavior.
- Failed `emit bash` continues to remove stale output artifacts.
- Helper dependency detection should be simple enough to extend for functions or
  future runtime helpers.

### 6. Diagnostic consistency pass

Audit command-related diagnostics across `check`, `bytecode`, `run`, direct
execution, and `emit bash`.

Required consistency targets:

- malformed `run`;
- `run` with unsupported redirection;
- unsupported pipeline/legacy redirection operators;
- duplicate redirection suffixes;
- missing or invalid redirection targets;
- unknown command variables;
- field access on non-command-result values;
- unknown command-result fields;
- command-result field interpolation errors;
- redirection file-open failures;
- process launch failures.

Diagnostics should keep the existing project style:

```txt
path/to/file.ds:line:column: error: message
```

Runtime process failures that cannot be known before execution may use runtime
source spans, but they should still identify the relevant command or target.

### 7. Shared parity test infrastructure

Move reusable VM/Bash parity helpers from version-local tests into
`tests/lib/testlib.sh` or another shared test helper file.

The helper should support:

- running a fixture in VM mode from an isolated working directory;
- emitting Bash to a temporary path;
- `bash -n` validation;
- running emitted Bash from another isolated working directory;
- comparing stdout, stderr, exit status, and selected output files;
- passing script arguments;
- preserving enough debug output to investigate failures.

Existing v0.7.0 parity tests should use the shared helper after the cleanup.

### 8. Header and module boundary review

Review whether `include/ds.h` should remain a single public internal header for
now or be split into smaller internal headers. A split is optional, not required.

If a split is attempted, it must be low-risk and behavior-preserving. Good
candidate boundaries are:

- source/diagnostics;
- frontend AST/tokens/parser;
- lowered command/program representation;
- runtime values/containers;
- VM/bytecode;
- Bash emitter.

If the project keeps one header in `v0.8.0`, record why and add a deferred item
with the trigger for splitting later.

## Documentation requirements

Update docs only where the cleanup changes implementation architecture or makes
existing behavior clearer:

- `docs/architecture.md` should describe the cleaned command pipeline.
- `docs/runtime.md` should describe the actual process/result ownership model if
  a process wrapper is introduced.
- `docs/language.ds` should not gain new syntax for this cleanup version, but it
  may clarify that `v0.8.0` is an implementation cleanup for the `v0.7.0` command
  model.
- `README.md` should keep the current status accurate once the cleanup is
  complete.

No new user-facing examples are required unless an existing example becomes
outdated. Prefer keeping `examples/command-result.ds` and
`examples/redirection.ds` as the main command examples.

## Acceptance criteria

`v0.8.0` is complete when:

- no new user-facing syntax was added;
- the supported v0.1.0–v0.7.0 behavior remains intact;
- command representation ownership/cloning/freeing is centralized or explicitly
  documented as deferred;
- command-result field knowledge is centralized enough that VM/Bash/lowering
  cannot drift silently;
- command process execution has a clearer reusable wrapper or a documented
  reason for a smaller cleanup;
- Bash helper generation remains standalone and uses `__ds_` names;
- command-related diagnostics are source-located and consistent across command
  families where practical;
- parity helpers are reusable by future suites;
- all prior tests pass;
- new cleanup/regression tests pass;
- ASAN/UBSAN builds pass where available;
- docs reflect the cleaned architecture;
- remaining deferred debt is listed in this file’s completion review.
