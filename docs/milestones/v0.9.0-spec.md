# v0.9.0 Spec — Functions

## Status

Implemented and tested.

## Goal

Add reusable user-defined functions while preserving the project rule that every
supported feature must work in direct VM execution and emitted standalone Bash.

This milestone should let script authors group repeated deployment, validation,
cleanup, and command-result handling logic without introducing advanced language
features that would be difficult to emit to Bash.

The feature is complete only when the same function behavior works through:

```sh
ds ./script.ds [script args...]
ds run ./script.ds [script args...]
ds emit bash ./script.ds -o ./script.sh
bash ./script.sh [script args...]
```

## Motivation

The language now has enough shell-native behavior to make real scripts useful:

- variables, simple expressions, `if`/`else`, and interpolation;
- first-class script argument declarations;
- local imports;
- command results and redirection;
- cleaned command-model and VM/Bash parity helpers.

Without functions, repeated logic still has to be copied or split into imported
files as top-level executable statements. Functions give `ds` its first reusable
script abstraction while keeping the surface close to Bash users' expectations:

```ds
fn deploy(target) {
  echo "Deploying {target}"
  ./deploy.sh $target
}

deploy("production")
```

The design must stay boring. Functions are named procedures with positional
parameters, local variables, access to outer/imported top-level definitions, and
the existing command/result behavior. This version should not become a general
functional-programming milestone.

## Non-goals

This version does not include:

- closures;
- anonymous functions;
- higher-order functions;
- function values;
- lambdas;
- methods;
- classes or objects;
- named arguments;
- variadic parameters;
- destructuring parameters;
- recursion guarantee beyond rejecting or documenting implementation limits;
- `return` values;
- early `return` statements;
- arrays, maps, loops, ranges, or collection helpers;
- standard-library modules;
- async/background functions;
- pipelines;
- changing plain commands away from fail-fast behavior;
- making emitted Bash depend on `ds` or the C runtime.

If implementation discovers that recursion works naturally in both VM and Bash
without extra machinery, it may be documented as supported only after adding
tests. Otherwise recursion should be rejected with a clear diagnostic or recorded
as deferred.

## Supported syntax

### Function declarations

Add top-level function declarations:

```ds
fn deploy(target) {
  echo "Deploying {target}"
  ./deploy.sh $target
}
```

Function declarations are definitions, not executable statements. Declaring a
function must not run its body.

Supported in `v0.9.0`:

- top-level `fn name(...) { ... }` declarations;
- zero or more positional parameters;
- function bodies using the already-supported statement subset;
- calls to functions declared in the same file;
- calls to functions declared by imported files;
- calls before declaration only if the implementation deliberately builds a
  declaration collection pass. Prefer allowing calls before declaration if this
  keeps Bash and VM behavior consistent; otherwise reject them consistently.

Function names use normal identifier syntax. Function names share the global
definition namespace with script arguments and top-level `let` bindings for the
purposes of duplicate detection.

### Parameters

The required parameter shape is:

```ds
fn deploy(target) {
  echo "{target}"
}
```

Optional type annotations are supported only for `string`, `int`, and `bool` if
they can be validated consistently in both VM execution and emitted Bash:

```ds
fn restart(service: string) {
  docker compose restart $service
}
```

If type annotations are implemented, they must be checked at call boundaries.
If call-boundary checking is not implemented in this milestone, typed parameters
must be rejected with a clear diagnostic and recorded as deferred despite their
presence in the long-term syntax catalog.

Default parameter values are included in this spec because they emit cleanly to
Bash when limited to trailing literal defaults:

```ds
fn deploy_default(target = "staging") {
  echo "Deploying {target}"
}
```

Supported defaults in `v0.9.0`:

- string literals;
- integer literals;
- boolean literals;
- defaults only after all required parameters;
- defaults used only when the argument is omitted.

Rejected defaults:

- defaults before required parameters;
- command-result expressions as defaults;
- function calls as defaults;
- references to earlier parameters as defaults;
- arrays, maps, loops, or future collection syntax.

### Function calls

Add function call statements:

```ds
deploy("production")
deploy_default()
```

Supported argument forms:

- string, integer, and boolean literals;
- identifiers;
- command-result field access;
- simple expressions already supported by the frontend/lowering pipeline;
- string interpolation when already supported in expressions.

The initial user-defined function call surface is statement-oriented. A function
call does not produce a user-visible return value in this milestone. If the
parser internally represents a call as an expression statement, the resulting
value should be `null` or otherwise unavailable to user code. Assigning a
function call to `let` must be rejected unless the implementation deliberately
adds and documents a return-value model, which is out of scope.

### Function bodies

Function bodies may contain the already-supported statement subset:

- `let` declarations;
- expression statements needed for function calls;
- `if`/`else`;
- nested blocks;
- plain command statements;
- captured `run` commands;
- command-result field access;
- plain command redirections.

Function bodies may read:

- their parameters;
- local `let` bindings declared in the body;
- top-level script arguments;
- top-level variables declared before execution reaches the call;
- imported function declarations and top-level definitions according to the
  existing import composition rules.

Function body local variables must not leak into the caller's scope.

## Semantics

### Definition and execution order

Function declarations are collected during parsing/lowering and skipped during
normal top-level execution.

Top-level executable statements still run in composed import order. Imported
function declarations are available according to the existing import rules, but
imported executable statements still execute once before dependent root
statements as documented by `v0.6.0`.

Function calls execute the function body synchronously and return control to the
caller after the body completes.

### Scope and shadowing

Requirements:

- Parameters are local to the function call.
- `let` bindings inside a function are local to that invocation.
- A parameter name must not be duplicated in the same parameter list.
- A function-local `let` must not duplicate another local in the same lexical
  scope according to the existing duplicate-binding rules.
- Local bindings may shadow top-level bindings only if current block-scope rules
  already allow equivalent shadowing; otherwise reject shadowing consistently.
- Function declarations must not be nested inside another function in `v0.9.0`.

### Arity and defaults

For a function with no defaults, the number of supplied arguments must exactly
match the parameter count.

For a function with trailing defaults:

- too few arguments are allowed only down to the number of required parameters;
- missing optional arguments are bound to their defaults;
- too many arguments are rejected;
- defaults are evaluated as literals at call time or lowered as constants.

Diagnostics must name the function and show expected vs actual argument counts.

### Command behavior inside functions

Existing command rules apply unchanged inside functions:

- plain commands are fail-fast;
- captured `run` commands are non-fatal and inspectable;
- command-result fields are `stdout`, `stderr`, `code`, `ok`, and `failed`;
- redirection suffixes apply only to plain command statements;
- unsupported pipelines remain rejected.

If a plain command fails inside a function, direct VM execution and emitted Bash
must fail consistently and must not continue executing caller statements.

## CLI behavior

Existing public commands continue to work:

```sh
ds tokens <file.ds>
ds ast <file.ds>
ds check <file.ds>
ds bytecode <file.ds>
ds run <file.ds> [script args...]
ds <file.ds> [script args...]
ds emit bash <file.ds> -o <file.sh>
```

Requirements:

- `ds check` validates function declarations, function calls, arity, duplicate
  names, default placement, and unsupported forms without executing functions.
- `ds tokens` includes stable tokens for `fn`, parameter lists, commas, defaults,
  and call syntax.
- `ds ast` prints function declarations and call statements in a stable,
  pointer-free form.
- `ds bytecode` prints deterministic function metadata/call instructions where
  bytecode output is implemented.
- `ds emit bash` must fail without leaving stale output when a function feature
  is parsed but unsupported by Bash emission.

## Parser and AST requirements

Parser support must include:

- `fn` keyword;
- function name identifier;
- parameter list with comma separation;
- optional `: type` parameter annotations if implemented;
- optional trailing literal defaults;
- function body block;
- function call statement syntax;
- clear recovery for missing name, missing `(`, missing `)`, missing `{`,
  missing `}`, missing commas, and malformed defaults.

AST/debug output requirements:

- function declarations include name, parameters, defaults, and body;
- call statements include callee name and arguments;
- output is deterministic and pointer-free;
- source locations are preserved for diagnostics and later lowering.

## Lowering and semantic requirements

Lowering should produce one shared backend-facing function representation used by
the VM and Bash emitter where practical.

Required validations:

- duplicate function names;
- duplicate parameter names;
- duplicate or conflicting top-level names;
- nested function declarations;
- unknown function calls;
- wrong argument counts;
- defaults before required parameters;
- unsupported parameter type annotations, if not implemented;
- unsupported default expression kinds;
- assigning a function call result to a variable;
- calling non-function values;
- recursion if unsupported;
- unsupported syntax inside function bodies.

Diagnostics should be source-located at the most helpful span: function name,
parameter name, call callee, offending argument, or default expression.

## VM behavior

Direct VM execution must:

- skip function bodies during top-level execution;
- bind arguments to parameters on each call;
- allocate an invocation-local scope;
- execute supported statements inside the function body;
- restore caller scope after the call;
- propagate plain-command failures out of the function;
- preserve captured-command result behavior inside the function;
- support imported functions according to composed program order;
- detect or reject unsupported recursion consistently.

Bytecode design may use function tables, labels, call frames, or another simple
representation. The chosen representation must not require a separate language
model from Bash emission.

## Bash emission behavior

Emitted Bash must remain standalone and must not require `ds` or the C runtime.

Requirements:

- emit each `ds` function as a Bash function using reserved `__ds_`-style names
  or another collision-safe mangling strategy;
- preserve source markers where useful;
- bind positional Bash function arguments to safe local variable names;
- apply default parameter values consistently with VM mode;
- keep function locals local to the Bash function where Bash supports it;
- emit function calls in original execution order;
- preserve existing generated Bash strict-mode behavior;
- include command-capture helpers only when needed;
- keep imported functions bundled into the single generated script;
- reject unsupported function syntax before writing or keep stale output cleanup
  behavior from earlier milestones.

Generated Bash should avoid user-name collisions by reserving internal prefixes
and by reusing the existing safe variable-name machinery.

## Diagnostics

Required diagnostics include:

- missing function name;
- duplicate function declaration;
- duplicate parameter name;
- unknown function call;
- wrong argument count;
- default parameter before required parameter;
- unsupported parameter type;
- unsupported default expression;
- nested function declaration;
- assigning a no-return function call to a value;
- unsupported recursion, if recursion is not implemented;
- unsupported pipelines or future syntax inside functions;
- Bash emission unsupported-feature diagnostics, if any part is VM-only during
  development.

Diagnostics must include filename, line, column, message, and useful source
highlighting in the existing style.

## Examples

### Basic reusable command wrapper

```ds
fn announce(message) {
  echo "== {message} =="
}

announce("starting")
```

### Script args plus functions

```ds
script {
  arg app: string
  option target: string = "staging"
  flag force: bool = false
}

fn deploy(app, target) {
  echo "Deploying {app} to {target}"
  ./deploy.sh $app $target
}

if force {
  echo "force enabled"
}

deploy(app, target)
```

### Captured command inside function

```ds
fn current_branch() {
  let branch = run git branch --show-current

  if branch.failed {
    echo branch.stderr
    exit branch.code
  }

  echo "branch={branch.stdout}"
}

current_branch()
```

### Default parameter

```ds
fn deploy_default(target = "staging") {
  echo "Deploying {target}"
}

deploy_default()
deploy_default("production")
```

## Acceptance criteria

`v0.9.0` is complete when:

- function declarations parse and appear in AST debug output;
- function call statements parse and appear in AST debug output;
- `ds check` validates supported function programs without executing bodies;
- semantic diagnostics reject duplicate names, bad arity, unsupported defaults,
  unknown functions, nested functions, and no-return value use;
- VM execution supports zero-argument and positional-argument function calls;
- VM execution supports local variables and command/result behavior inside
  functions;
- emitted Bash supports the same function programs as VM execution;
- VM/Bash parity tests cover successful calls, failures, defaults, imports,
  script args, command capture, and redirection inside functions;
- generated Bash remains standalone and passes `bash -n`;
- no supported function feature is VM-only or Bash-only;
- docs/examples are updated only where existing behavior becomes outdated;
- deferred function work is recorded below and in the completion review.

## Deferred items

- Return values and `return` statements.
- Named arguments.
- Variadic parameters.
- Closures and function values.
- Nested functions.
- Methods or module-qualified function names.
- Recursion, unless implemented and tested in this milestone.
- Rich parameter type checking beyond `string`, `int`, and `bool`.
- Expression-valued defaults beyond literals.
- Arrays/maps/loops integration, planned for `v0.10.0`.

## Completion review

Implementation and tests are complete for the scoped `v0.9.0` function changes.

### Implemented

- Top-level `fn name(...) { ... }` declarations.
- Statement-style function calls.
- Zero-argument and positional-argument calls.
- Calls before declaration through a function-signature collection pass.
- Imported function declarations through the existing import composition path.
- Untyped parameters.
- Trailing literal defaults for string, integer, and boolean parameters.
- Per-invocation local scopes for function parameters and local `let` bindings.
- Function bodies using existing statements, blocks, `if`/`else`, plain commands,
  captured `run` commands, command-result fields, and redirections.
- VM function execution with call/return handling and fail-fast plain command
  propagation.
- Standalone Bash function emission with local parameter/default binding and
  local function-scope `let` declarations.
- Semantic rejection for duplicate functions, duplicate parameters, bad arity,
  required parameters after defaults, unsupported typed parameters, unsupported
  default expression kinds, nested function declarations, expression-valued
  function calls, unknown function calls, and recursive function cycles.
- Duplicate top-level function/variable conflicts now emit a single duplicate
  diagnostic instead of repeated duplicate messages for the same conflict.

### Tests added

- Added `tests/v0_9/run.sh` and wired it into `make test-v0-9` and `make test`.
- The suite covers token/AST/bytecode smoke checks, VM/Bash parity for valid
  functions, script arguments, imports, defaults, call-before-declaration,
  command capture, handled captured failures, fail-fast plain commands,
  redirections, metacharacter arguments, direct execution, script help, emitted
  Bash standalone behavior, stale emit cleanup, and source-located diagnostics.

### Behavior differences from spec

- Typed function parameters are parsed but rejected with a clear diagnostic
  because call-boundary type checking is deferred.
- Recursive function cycles are rejected with a clear diagnostic instead of being
  supported.
- Function calls are statement-only and do not produce values.

### Deferred follow-up work

- Return values and `return` statements.
- Typed parameter call-boundary validation.
- Recursion support, if it is deliberately designed and tested for both VM and
  standalone Bash emission.
- Named arguments, variadic parameters, closures/function values, nested
  functions, methods/module-qualified functions, and non-literal defaults.

### Docs updated

- `README.md` documents the scoped function support and deferred recursion.
- `docs/language.ds` and `examples/functions.ds` were updated during the initial
  implementation pass to show the supported function surface.
