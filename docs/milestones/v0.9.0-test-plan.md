# v0.9.0 Test Plan — Functions

## Purpose

This test plan verifies the `v0.9.0` functions milestone without expanding into
`v0.10.0` arrays, maps, or loops.

The central requirement is VM/Bash parity. Every supported function program must
behave the same when run directly by `ds` and when emitted to standalone Bash.

The plan is intentionally comprehensive because functions touch parsing,
lowering, scopes, bytecode/VM execution, Bash emission, imports, script args,
commands, and diagnostics.

## Scope under test

Covered:

- top-level function declarations;
- zero-argument functions;
- positional parameters;
- trailing literal default parameters;
- optional `string`/`int`/`bool` parameter annotations only if implemented;
- function call statements;
- local function scopes;
- access to script arguments and top-level bindings;
- imports containing functions;
- plain commands inside functions;
- captured `run` commands inside functions;
- command-result fields inside functions;
- redirection inside functions;
- deterministic debug output;
- standalone Bash emission;
- source-located diagnostics.

Not covered as supported behavior:

- return values;
- early `return`;
- assigning a function call result;
- closures;
- function values;
- nested functions;
- named arguments;
- variadic parameters;
- arrays, maps, and loops;
- pipelines;
- standard-library functions.

Unsupported items still need negative tests so they fail clearly.

## Required test targets

Add a dedicated suite:

```txt

```

Update the top-level test runner so:


Use existing shared helpers from `tests/lib/testlib.sh`, especially the reusable

version-local copy.

## Lexer tests

Validate tokenization for function syntax.

Cases:

- `fn deploy() {}`;
- `fn deploy(target) {}`;
- `fn deploy(app, target) {}`;
- `fn deploy(target = "staging") {}`;
- `fn restart(service: string) {}` if typed parameters are supported;
- call syntax `deploy("production")`;
- commas between parameters and arguments;
- defaults with string, integer, and boolean literals;
- function syntax adjacent to existing script blocks, imports, commands, and
  `if` blocks.

Assertions:

- `fn` is tokenized as a keyword if the lexer has keyword-specific output;
- parentheses, commas, colons, equals signs, and braces are stable;
- debug token output is deterministic and pointer-free;
- comments and newlines around function declarations do not change token order
  unexpectedly.

## Parser and AST tests

### Valid parse cases

Run `ds ast` and `ds check` for:

```ds
fn hello() {
  echo "hello"
}

hello()
```

```ds
fn deploy(target) {
  echo "Deploying {target}"
}

deploy("production")
```

```ds
fn pair(a, b) {
  echo "{a}:{b}"
}

pair("x", "y")
```

```ds
fn deploy_default(target = "staging") {
  echo "{target}"
}

deploy_default()
deploy_default("prod")
```

```ds
fn defaults(a, b = 2, c = true) {
  echo "{a}:{b}:{c}"
}

defaults("x")
```

If parameter type annotations are supported:

```ds
fn restart(service: string, retries: int, force: bool = false) {
  echo "{service}:{retries}:{force}"
}
```

Assertions:

- AST includes function name, parameters, defaults, and body;
- AST includes call statements with callee and argument list;
- AST output is pointer-free and stable;
- function declarations do not appear as command statements;
- function calls are not confused with shell-like command statements.

### Parser recovery and syntax diagnostics

Each invalid fixture should fail `ds check` with a source-located diagnostic:

```txt
fn { }
fn () { }
fn deploy( { }
fn deploy(target { }
fn deploy(target,) { }
fn deploy(target,, other) { }
fn deploy(target = ) { }
fn deploy(target = run echo hi) { }
fn deploy(target = "x", other) { }
fn deploy(target) echo "missing block"
fn deploy(target) {
  echo "missing close"
```

Assertions:

- diagnostics include filename, line, and column;
- parser recovery does not crash or loop;
- no invalid fixture emits Bash output;
- no invalid fixture executes commands during `check` or failed emission.

## Semantic/lowering tests

### Name validation

Reject:

```ds
fn deploy() {}
fn deploy() {}
```

```ds
script {
  arg deploy: string
}

fn deploy() {}
```

```ds
let deploy = "x"
fn deploy() {}
```

```ds
fn deploy(target, target) {}
```

```ds
fn deploy(target) {
  let target = "x"
}
```

depending on the existing duplicate/shadowing rule.

Assertions:

- duplicate diagnostics point at the duplicate name;
- diagnostics mention the original name when the project style supports it;
- VM and Bash backends are not reached after semantic failure.

### Call validation

Reject:

```ds
missing()
```

```ds
fn deploy(target) {}
deploy()
```

```ds
fn deploy(target) {}
deploy("a", "b")
```

```ds
fn deploy(target = "staging") {}
let result = deploy()
```

```ds
fn deploy() {}
deploy.named("x")
```

```ds
fn outer() {
  fn inner() {}
}
```

Assertions:

- wrong-arity diagnostics name the callee and expected/actual counts;
- assigning a function call result is rejected until return values exist;
- nested functions are rejected;
- unknown callees are rejected before execution/emission.

### Default parameter validation

Valid:

```ds
fn f(a, b = "x", c = 3, d = false) {
  echo "{a}:{b}:{c}:{d}"
}

f("req")
f("req", "override")
f("req", "override", 4)
f("req", "override", 4, true)
```

Reject:

```ds
fn f(a = "x", b) {}
```

```ds
fn f(a = other) {}
```

```ds
fn f(a = run echo hi) {}
```

```ds
fn f(a = file.exists("x")) {}
```

Assertions:

- missing optional args bind defaults in VM and Bash;
- supplied optional args override defaults;
- defaults are literal-only;
- diagnostics point at the default value or parameter name.

### Parameter type annotations

If implemented, test accepted annotations:

```ds
fn show(name: string, count: int, enabled: bool = true) {
  echo "{name}:{count}:{enabled}"
}

show("api", 2)
```

And rejected calls:

```ds
show(2, "bad")
show("api", true)
show("api", 2, "true")
```

If type annotations are not implemented, test that annotated parameters fail
with a clear unsupported-feature diagnostic and that `docs/milestones/v0.9.0-spec.md`
completion review records the deferral.

## VM execution tests

Run through `ds run` and direct `ds <file>`.

### Basic calls

Cases:

- zero-argument function prints one line;
- one-argument function prints the argument;
- multi-argument function prints arguments in order;
- function declaration before call;
- call before declaration if supported, otherwise clear diagnostic;
- multiple calls to the same function;
- function body is not executed unless called.

Expected assertions:

- stdout exactly matches expected text;
- stderr is empty for successful fixtures;
- exit status is `0`;
- declaration-only file exits successfully with no function body output.

### Scope and locals

Fixtures:

```ds
let target = "outer"

fn show(target) {
  echo "inner={target}"
}

show("local")
echo "outer={target}"
```

```ds
fn count_once() {
  let value = "local"
  echo value
}

count_once()
count_once()
```

```ds
fn leak() {
  let secret = "hidden"
}

leak()
echo secret
```

Assertions:

- parameters shadow or reject according to the spec and existing rules;
- local variables are fresh per invocation;
- locals do not leak to caller;
- using a leaked local fails with a source-located unknown-name diagnostic.

### Script args inside functions

Fixture:

```ds
script {
  arg app: string
  option target: string = "staging"
  flag force: bool = false
}

fn deploy() {
  echo "{app}:{target}:{force}"
}

deploy()
```

Run with:

```sh
ds run fixture.ds api --target prod --force
ds fixture.ds api --target prod --force
```

Assertions:

- functions can read bound script args;
- script help still exits before executing function bodies;
- missing/invalid script args fail before function execution.

### Command capture inside functions

Fixtures:

```ds
fn capture() {
  let result = run sh -c "printf out; printf err >&2; exit 7"
  echo "stdout={result.stdout}"
  echo "stderr={result.stderr}"
  echo "code={result.code}"
  echo "ok={result.ok}"
  echo "failed={result.failed}"
}

capture()
```

```ds
fn nonfatal() {
  let result = run sh -c "exit 9"
  if result.failed {
    echo "handled {result.code}"
  }
}

nonfatal()
echo "after"
```

Assertions:

- captured non-zero commands do not abort the function;
- command-result fields keep their existing values;
- caller continues after handled captured failure.

### Plain command failure inside functions

Fixture:

```ds
fn fail() {
  sh -c "exit 6"
  echo "unreachable"
}

fail()
echo "caller unreachable"
```

Assertions:

- VM exits non-zero;
- output after the failing plain command is absent;
- emitted Bash has the same status/output behavior;
- diagnostics or stderr shape follows existing plain-command failure contract.

### Redirection inside functions

Fixtures:

```ds
fn write_out() {
  printf "hello" |> "out.txt"
}

write_out()
```

```ds
fn write_err() {
  sh -c "printf err >&2" !> "err.txt"
}

write_err()
```

```ds
fn write_all() {
  sh -c "printf out; printf err >&2" &> "all.txt"
}

write_all()
```

Assertions:

- redirected files are created in the process working directory;
- stdout/stderr redirection behavior matches `v0.7.0`;
- VM/Bash parity helper compares output file contents;
- redirection open failures inside functions are source-located.

## Bash emitter tests

For every supported valid fixture above:

```sh
ds emit bash fixture.ds -o fixture.sh
bash -n fixture.sh
bash fixture.sh [args...]
```

Assertions:

- generated Bash is standalone and does not invoke `ds`;
- generated Bash uses collision-safe internal function and variable names;
- generated Bash has no stale output after failed emission;
- function declarations appear before calls in emitted Bash or are otherwise
  ordered correctly;
- default parameters bind the same values as VM mode;
- function locals do not leak into global Bash variables;
- helper functions for command capture are emitted only when needed;
- generated Bash remains compatible with the project's current Bash target.

Additional generated-Bash inspections:

- user function named similarly to an internal helper does not collide;
- parameter named similarly to an internal variable does not collide;
- function name with underscores emits a stable safe name;
- imported function names are mangled consistently.

## VM/Bash parity tests

Use the shared parity helper for each case.

Required parity matrix:

| Case | Expected status | Compare stdout | Compare stderr | Compare files |
| --- | --- | --- | --- | --- |
| zero-arg function | 0 | yes | yes | no |
| one-arg function | 0 | yes | yes | no |
| multi-arg function | 0 | yes | yes | no |
| defaults omitted | 0 | yes | yes | no |
| defaults overridden | 0 | yes | yes | no |
| script args read in function | 0 | yes | yes | no |
| imported function | 0 | yes | yes | no |
| function calls imported function | 0 | yes | yes | no |
| command capture in function | 0 | yes | yes | no |
| captured failure handled | 0 | yes | yes | no |
| plain command failure in function | non-zero | yes | compare where stable | no |
| stdout redirection in function | 0 | yes | yes | yes |
| stderr redirection in function | 0 | yes | yes | yes |
| combined redirection in function | 0 | yes | yes | yes |
| nested block in function | 0 | yes | yes | no |

Edge parity cases:

- function arguments containing spaces;
- function arguments containing `$`, backticks, semicolons, quotes, and braces;
- empty string argument;
- integer `0` argument;
- boolean `false` argument;
- two calls with different argument values to ensure no stale binding;
- local variable name reused across calls;
- function body with string interpolation of parameters and command-result
  fields;
- function declaration in imported file plus top-level executable import body.

## Import integration tests

### Imported function called by root

`lib.ds`:

```ds
fn greet(name) {
  echo "hello {name}"
}
```

`main.ds`:

```ds
import "./lib.ds"
greet("world")
```

Assertions:

- VM and Bash output `hello world`;
- emitted Bash bundles `lib.ds` function into one script;
- no runtime dependency on `lib.ds` remains after emission.

### Imported function calls root function

Choose and document the rule. Prefer rejecting imported function calls to root
functions if the composed declaration model cannot support them clearly.

Test either:

- successful mutual visibility when the implementation supports whole-program
  function collection; or
- clear unknown-function diagnostic when it does not.

### Duplicate imported functions

Reject duplicate function names across imports:

```txt
lib-a.ds: fn helper() {}
lib-b.ds: fn helper() {}
main.ds: import both
```

Assertions:

- duplicate diagnostic identifies the conflicting function;
- load-once behavior still applies to repeated import of the same file;
- import cycles with functions still use the existing import-cycle diagnostic.

## Bytecode/debug output tests

If bytecode output is implemented for functions, add stable golden or substring
tests for:

- function table entry;
- function name;
- parameter count;
- default count or default constants;
- call instruction;
- local scope/frame markers if printed;
- source markers where present.

Assertions:

- bytecode output is deterministic;
- no pointer addresses;
- imported functions appear deterministically;
- unsupported function programs fail before bytecode generation.

If bytecode output intentionally omits function internals, document that in the
completion review and add tests for the documented output shape.

## Diagnostics tests

Each diagnostic test should assert non-zero exit, useful message text, and source
location.

Required diagnostics:

- missing function name;
- malformed parameter list;
- duplicate function name;
- duplicate parameter name;
- nested function declaration;
- unknown function call;
- wrong argument count with too few args;
- wrong argument count with too many args;
- default before required parameter;
- unsupported default expression;
- unsupported parameter type or invalid annotation;
- assigning function call result;
- using a function name as a variable;
- calling a non-function value;
- recursion if unsupported;
- local variable leak;
- function body syntax error;
- unsupported pipeline inside function;
- Bash emission unsupported-feature error if implementation temporarily lacks a
  Bash path for any parsed function form.

Also test that `ds check` does not execute function bodies:

```ds
fn dangerous() {
  sh -c "exit 99"
}
```

`ds check` must succeed or fail only because of static validation, not because
the command ran.

## Edge cases

### Arity and defaults

- zero parameters, zero args;
- one required parameter;
- many parameters, at least five;
- all parameters defaulted;
- mix of required and defaulted parameters;
- omit one, some, and all optional parameters;
- supply too many args;
- call defaulted function repeatedly with different omitted/supplied args;
- default string is empty;
- default string contains spaces and shell metacharacters;
- default integer is `0`;
- default boolean is `false`.

### Names

- function name collides with `script`, `arg`, `option`, `flag`, `run`, `if`, or
  other reserved words and is rejected by normal identifier rules;
- function name collides with a top-level `let`;
- parameter name collides with another parameter;
- parameter named like a top-level binding follows documented shadowing rules;
- names containing underscores;
- names that would collide after Bash-safe mangling;
- imported duplicate names.

### Scope

- local variable does not leak;
- local variable from one call does not leak into the next call;
- nested block inside function has existing block-scope behavior;
- top-level variable visible inside function only according to documented rules;
- function declarations inside skipped `if` blocks are rejected because only
  top-level declarations are supported.

### Commands and shell safety

- argument value with spaces;
- argument value with `$`;
- argument value with backticks;
- argument value with semicolon;
- argument value with braces used in interpolation;
- empty stdout captured inside function;
- stderr-only command captured inside function;
- large but reasonable captured output inside function;
- redirection target open failure inside function;
- plain command failure aborts both function and caller.

### Imports

- imported function only;
- imported executable statement plus imported function;
- repeated import load-once with function declaration;
- import cycle involving function files;
- function call across nested imports;
- emitted Bash from import fixture runs after the original source files are moved
  away or deleted from the temp directory.

## Regression tests from prior versions

Run the full prior test suite after adding functions.

Pay special attention to regressions in:

- command parsing, because `name(...)` must not break shell-like command words;
- string interpolation;
- `script { ... }` block parsing;
- local import composition;
- command-result field descriptors;
- redirection suffix parsing;
- generated Bash helper emission;
- stale Bash output cleanup.

No prior fixture should need behavior changes unless the milestone deliberately
fixes a documented bug. Any changed golden output must be explained in the
completion review.

## Completion checklist

Before marking `v0.9.0` complete:

- `tests/v0_9/run.sh` exists and is executable;
- `make test-v0-9` passes;
- `make test` passes;
- valid function fixtures pass VM/Bash parity;
- invalid function fixtures fail with source-located diagnostics;
- emitted Bash is standalone;
- no supported function feature is VM-only or Bash-only;
- docs/examples are updated if behavior changed;
- `docs/language.ds` is updated if the implemented syntax differs from this
  spec or a planned syntax is deferred;
- `docs/milestones/v0.9.0-spec.md` completion review records implemented
  behavior, tests, differences, and deferred items.
